# iPhoneでのターン数・到達WAVE列の追加 実行順

`public.rankings` へ `turns` と `reached_wave` の2列を追加する作業です。**既存の行・列・RLS・ポリシー・権限には触りません**（DROP・DELETE・UPDATEをしません）。各SQLは新しいクエリにファイル全体を貼り付けて実行します。エラーが出た工程では次へ進まず、結果を保存して共有してください。

> **Supabase の SQL Editor は、ファイル全体を実行すると「最後の1文」の結果しか表示しません。**
> そのため3本とも、**最後の1文が「まとめ」**になっています。確認したい値はすべてそこに縦に並ぶので、
> 1回 Run して出てきた表をスクリーンショットするだけで大丈夫です。

> **「Run and enable RLS」ではなく「Run without RLS」を選んでください。**
> Supabaseは `alter table` を機械的に「destructive」と判定して警告を出しますが、このSQLは
> 列を足すだけで既存データを消しません。RLSは `rankings` に既に有効なので、Supabase側に
> 追加のRLS設定を差し込ませる必要はありません。

## なぜ追加するのか

スコアランキングを見ても、その記録が**どういう終わり方だったのか**が分かりません。10WAVEを走り切った記録も、WAVE3で力尽きた記録も、同じ「スコアだけの1行」に見えます。

- `turns` … **クリアした周回**でかかった累計ターン数。クリアしていない周回はNULL
- `reached_wave` … その周回が**どのWAVEで終わったか**。クリアは10

`turns` をクリア時だけに限るのには理由があります。累計ターン数はWAVEを**倒しきった瞬間にだけ**足される値なので、負け・リタイアの周回では最後に挑んでいたWAVEのぶんが入りません。それをクリアの記録と同じ列に並べると「少ないターンで終えた」ように見えてしまいます。だから途中で終わった周回には入れず、代わりに到達WAVEだけを残します。

## 手順

1. **Safari で Supabase Dashboard を開く**
   プロジェクト `zrzevudkbgtxlbvmuziy` を選び、左のメニューから **SQL Editor** → **New query**。
2. **いまの `rankings` の件数を控える**
   新しいクエリに `select count(*) from public.rankings;` だけを貼って Run し、数字を残します。適用後に比べます。
3. **`RUN_STATS_APPLY_TEST.sql` を実行**（末尾が `rollback;`）
   実適用と同じSQLを一度通す予行演習です。**この実行では何も保存されません**。
4. **まとめの表を確認**
   - `turns 列` が `integer / YES`
   - `reached_wave 列` が `integer / YES`
   - `検査制約` に `rankings_reached_wave_range, rankings_turns_range`
   - `RLS` が `有効`、`ポリシー` と `権限` が今までと同じ
   - `rankings の件数` が手順2と同じ
   赤いエラー表示が無いことも確認します。エラーが出たらそこで停止し、実適用へ進みません。
5. **`RUN_STATS_APPLY.sql` を実行**（末尾が `commit;`）
   同じ安全確認を通ったうえで変更を保存します。最後に `notify pgrst, 'reload schema';` が走り、Data APIが新しい列を認識します。
6. **`RUN_STATS_VERIFY.sql` を実行**（読み取り専用）
   まとめの表で、手順4と同じ内容に加えて次を確認します。
   - `rankings の件数` が手順2と同じ
   - `ターン数が入っている記録` と `到達WAVEが入っている記録` は `0`（この時点では空で正常）
7. **アプリ公開後にもう一度 `RUN_STATS_VERIFY.sql`**
   ゲームを1周してから実行し、`到達WAVEが入っている記録` が増えることを確認します。クリアまで行けば `ターン数が入っている記録` も増え、`最新の5件` に「◯◯ターンでクリア」と出ます。

## 成功判定

- 既存 `rankings` の件数・RLS・ポリシー・権限が適用前後で同じ。
- `turns` / `reached_wave` がどちらも `integer` でNULL許容。
- 既存の記録はすべてNULLのまま（過去の記録が書き換わらない）。
- ゲームを1周すると新しい記録にだけ値が入る。

## エラー時

- 手順3（`rollback;` の予行演習）でエラーが出た場合は、そのまま停止します。**トランザクションは保存されていません。**
- 手順5の実適用でエラーが出た場合も、`begin;` 〜 `commit;` の途中で止まるため保存されません。エラー文をそのまま共有してください。
- 適用後に取り消したい場合は、次の2文で元に戻ります。**既存データには影響しません**（この2列はすべてNULLか、適用後に遊んだぶんの値しか入っていないため）。

```sql
alter table public.rankings drop column turns;
alter table public.rankings drop column reached_wave;
```

Supabase の管理者接続情報はリポジトリに保存しません。SQL Editor を操作できない場合は「未適用」と記録し、適用済みとは報告しません。

## 適用前でもアプリは壊れません

**この作業を後回しにしても、ゲームは今までどおり動きます。** アプリ側は、列がまだ無い環境を自分で見つけて避けるようにしてあります。

- 一覧を開くとき … 列が無いと400が返るので、その2列を外して取り直します
- 記録を送るとき … 同じく400が返るので、その2列を外して**必ず送り直します**（ここで諦めるとスコアが1件も残らなくなるため）

一度気付いたらそのセッションでは最初から外して送るので、無駄な往復は多くても1回です。SQLを適用すればアプリ側は何もしなくても自動的に載りはじめます。

## 事前検証（済み）

PostgreSQL 16 のローカル環境に、Supabaseと同じ前提（`anon` / `authenticated` ロール、RLS付きの `rankings`、`clear_id` のUNIQUE索引、既存データ5件）を用意し、この3本のSQLをそのまま流して確認済みです。

- `RUN_STATS_APPLY_TEST.sql` … 最後に `ROLLBACK` され、2列は**残らない**（0件）
- `RUN_STATS_APPLY.sql` … `COMMIT` → `NOTIFY` まで通り、2列と検査制約2つが作られる
- `RUN_STATS_VERIFY.sql` … 期待どおりの結果。件数・RLS・ポリシー・権限は適用前と同一
- **2回流しても安全**（`if not exists` で守っているため、既存データは消えない）
- アプリと同じ `anon` の立場で、クリアの記録（`turns=87, reached_wave=10`）と途中終了の記録（`reached_wave=4` のみ）を書き込めることを確認
- 既存5件は適用後も両列ともNULLのまま
- ありえない値（`turns=0` / `reached_wave=-3`）は検査制約で**拒否される**

## 検査

- `node tools/ranking/ranking-run-stats-check.js` … Supabaseをスタブした実ブラウザで、列がある場合と無い場合の両方を通す。無い場合に**スコアの保存が落ちない**ことをここで固定している
- `node tools/ranking/bond-levels-schema-match-check.js` … アプリが送る列と、このディレクトリのSQLが食い違っていないかを突き合わせる
