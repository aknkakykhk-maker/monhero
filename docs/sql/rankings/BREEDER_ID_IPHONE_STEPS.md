# iPhoneでのブリーダーID列の追加 実行順

`public.rankings` へ `breeder_id` を1列だけ追加する作業です。**既存の行・列・RLS・ポリシー・権限には触りません**（DROP・DELETE・UPDATEをしません）。各SQLは新しいクエリにファイル全体を貼り付けて実行します。エラーが出た工程では次へ進まず、結果を保存して共有してください。

> **Supabase の SQL Editor は、ファイル全体を実行すると「最後の1文」の結果しか表示しません。**
> そのため3本とも、**最後の1文が「まとめ」**になっています。確認したい値はすべてそこに縦に並ぶので、
> 1回 Run して出てきた表をスクリーンショットするだけで大丈夫です。

> **「Run and enable RLS」ではなく「Run without RLS」を選んでください。**
> Supabaseは `alter table` を機械的に「destructive」と判定して警告を出しますが、このSQLは
> 列を足すだけで既存データを消しません。RLSは `rankings` に既に有効なので、Supabase側に
> 追加のRLS設定を差し込ませる必要はありません。

## なぜ追加するのか

全国ランキングは、いままで**ブリーダー名だけで人を見分けて**いました。曲ごとのランキング（その名前でいちばん高い1件を見せるだけ）なら同名の人がいても大きな害はありません。

ですが、これから作る**全曲合算ランキング**は「その人の全曲を足す」ので、同じ名前の人がいると**別人の点まで足されてしまいます**。順位に応じて報酬を配るなら、ここが曖昧なままでは進められません。

- `breeder_id` … 端末ごとに1回だけ作るID。**名前を変えても変わりません**
- 列を足す前の記録は **NULL のまま**で、あとから埋めることもしません

昔の記録が消えるわけではありません。合算するときに「その名前に結び付くIDが1つだけなら、そのIDの人のもの」として引き継ぎます。同名の人が複数いる名前だけは、どちらのものとも決められないので分けたまま置きます（詳しくは [`../../spec/RHYTHM_RANKING.md`](../../spec/RHYTHM_RANKING.md) §4.4）。

## 順番はどちらが先でもかまいません

アプリ側は「列がまだ無い」と分かると、**IDを外して自動で送り直します**。ですので、

- SQLを先に適用しても
- アプリの公開を先にしても

どちらでも**記録が失われることはありません**。ただし列が無いあいだに遊んだぶんにはIDが付かないので、**SQLを先に適用したほうが、IDの付いた記録が早く貯まります**。

## 手順

1. **Safari で Supabase Dashboard を開く**
   プロジェクト `zrzevudkbgtxlbvmuziy` を選び、左のメニューから **SQL Editor** → **New query**。
2. **いまの `rankings` の件数を控える**
   新しいクエリに `select count(*) from public.rankings;` だけを貼って Run し、数字を残します。適用後に比べます。
3. **`BREEDER_ID_APPLY_TEST.sql` を実行**（末尾が `rollback;`）
   実適用と同じSQLを一度通す予行演習です。**この実行では何も保存されません**。
4. **まとめの表を確認**
   - `breeder_id 列` が `text / YES`
   - `検査制約` に `rankings_breeder_id_shape`
   - `RLS` が `有効`、`ポリシー` と `権限` が今までと同じ
   - `rankings の件数` が手順2と同じ
   - `breeder_id が入っている記録` が `0`
   赤いエラー表示が無いことも確認します。エラーが出たらそこで停止し、実適用へ進みません。
5. **`BREEDER_ID_APPLY.sql` を実行**（末尾が `commit;`）
   同じ安全確認を通ったうえで変更を保存します。最後に `notify pgrst, 'reload schema';` が走り、Data APIが新しい列を認識します。
6. **`BREEDER_ID_VERIFY.sql` を実行**（読み取り専用）
   列と制約が入っていること、件数が変わっていないことを確かめます。適用直後は
   `breeder_id が入っている記録` が `0` で正しいです。
7. **数日後にもう一度 `BREEDER_ID_VERIFY.sql` を実行**
   `直近7日のモンビーの記録` に対して `そのうち breeder_id が入っている記録` が増えていれば、
   アプリからIDが届いています。ここが `0` のままなら、アプリ側が送れていないので知らせてください。

## うまくいかないときは

| 表示 | 意味 | どうするか |
| --- | --- | --- |
| `public.rankings.breeder_id が別の型(...)で既に存在します` | 同じ名前の列が別の型で入っている | 何も変えずに停止しています。列の中身を確認してから相談してください |
| `rankings の件数が変化しました` | 実行中に他から書き込みがあった | 何も保存されずに止まります。少し待って手順3からやり直してください |
| `anon が rankings へINSERTできません` | 権限の設定が想定と違う | 停止しています。権限を確認してから相談してください |

## 元に戻したくなったら

列を消すと、そのあいだに送られたIDも一緒に消えます（記録そのものは残ります）。

```sql
-- 必要になったときだけ。実行前に必ず相談すること
alter table public.rankings drop column if exists breeder_id;
```

アプリは列が無いと分かればIDを外して送るので、消しても新しい記録は残り続けます。
