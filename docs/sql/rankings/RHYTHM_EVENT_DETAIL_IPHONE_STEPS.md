# イベントの「詳細」を出す — iPhoneでの手順

2026-09-11・ユーザー指摘「イベント側の対象曲のほうの詳細がない」。

**1回やれば、以後のイベントでもそのまま効きます。** イベントごとに流し直す必要はありません
（対象曲と期間はアプリから引数で渡しているため）。

## なぜ要るのか

「この曲」タブは `rankings` を**直接**読んでいるので、判定の内訳が入っている `party` 列を
そのまま取れます。イベントタブは**データベース側の関数**を通していて、関数は定義に書いた列しか
返せません。いまの定義に `party` が無いので、アプリが何を頼んでも取れない、という状態です。

## やること

Supabase の SQL Editor で、次の順に貼って実行します。

| 順 | ファイル | 何をするか | 本番に残るか |
| --- | --- | --- | --- |
| 1 | `RHYTHM_EVENT_DETAIL_APPLY_TEST.sql` | 予行演習（末尾が `rollback;`） | **残らない** |
| 2 | `RHYTHM_EVENT_DETAIL_APPLY.sql` | 本適用 | 残る |
| 3 | `RHYTHM_EVENT_DETAIL_VERIFY.sql` | 確認（読み取りだけ） | 残らない |

1 がエラー無く通ってから 2 を実行してください。1 で落ちたら 2 は実行せず、
エラーの文をそのまま伝えてください。

## 見るところ

3 を流したときに、次のようになっていれば成功です。

- ① `rhythm_scores` と `rhythm_identified_scores` の2行が出る
- ② 戻り値の最後が `party jsonb` になっている
- ③ `has_detail` が `true` の行がある（`max_combo` に数字が入る）
- ④ 「内訳なし」は、判定の内訳が保存される前の古い記録です。0でなくても問題ありません
- ⑤⑥ これまでのランキングの件数が前と同じくらいであること

## 変えていないもの

- `public.rankings` の行・列・RLS・ポリシー・権限（`DROP TABLE` / `DELETE` / `UPDATE` / `ALTER TABLE` をしていません）
- 総合の関数 `rhythm_event_totals`
- 週の窓 `rhythm_week_window`

## アプリ側

SQLが未適用のあいだも画面は壊れません。`party` を頼んで断られたら、
**自動でこれまでどおりの取り方へ戻します**（詳細ボタンが出ないだけ）。
なので、SQLの適用とアプリの公開はどちらが先でも大丈夫です。
