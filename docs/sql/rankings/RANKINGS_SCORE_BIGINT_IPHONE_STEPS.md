# iPhoneでの実行順（rankings.score を bigint へ広げる）

大きなスコア（例: 45,054,226,345 ＝ 約450億）がランキングへ載らない件の対処です。
`rankings.score` が `int4`（上限 2,147,483,647 ＝ 約21億）だと、これを超える記録は
Postgres が `22003 numeric value out of range` で丸ごと拒否します。
ゲーム側はスコアを丸めずにそのまま送るため、拒否されると端末に退避するだけで画面には何も出ません。

音ゲー（モンヒロビート）のスコアも同じ `rankings` テーブルへ入るので、直せば両方に効きます。

各SQLは Supabase の SQL Editor で、**新しいクエリにファイル全体を貼り付けて**実行します。
エラーが出た工程では次へ進まず、結果を保存して共有してください。

> ⚠️ **Supabase の SQL Editor は、まとめて実行すると「最後のSQLの結果」しか画面に出しません。**
> `AUDIT` のように select を並べたファイルをそのまま Run すると、いちばん下の結果しか見えません。
> 途中の結果を見たいときは、**その select だけを指でなぞって選んでから Run** してください
> （選んだ範囲だけが実行されます）。

0. **`RANKINGS_SCORE_BIGINT_CHECK_ONE.sql` を実行**（まずこれだけで判断できます）
   全部を1枚の表にまとめてあるので、貼って Run するだけです。7行出ます。
   - **1行目「score の型」** … `integer` なら原因確定
   - **5行目「score にぶら下がるビュー」** … `rhythm_scores` など5枚が並ぶはず
   - **6行目「マテリアライズドビュー」** … `なし` であること
   - **7行目「→ どうするか」** … ここに次にやることが書かれています
   `integer` かつマテリアライズドビューが `なし` なら、2へ進みます。
1. **`RANKINGS_SCORE_BIGINT_AUDIT.sql` を実行**（控えを残すため）
   読み取りだけです。適用前のRLS・ポリシー・権限・索引・ビューの定義を控えます。
   結果は項目ごとに分かれているので、**見たい select を選んでから Run** してください。
   - **A-1** の `score` の `data_type`
     - `integer` … 原因確定。2へ進みます
     - `bigint` … 原因は別です。ここで止めて結果を共有してください
   - **A-3** に並ぶビュー（モンビーの集計 `rhythm_scores` → … → `rhythm_total_rankings` のはず）
     ビューがあると型は変えられないので、`APPLY` がこれを落として、**いまの定義・所有者・
     コメント・権限のまま作り直します**。`dependent_kind` が全部 `VIEW` なら、そのまま進めて大丈夫です。
     `MATERIALIZED VIEW` が混ざっていたら止めて共有してください（中身の作り直しが別に要ります）。
2. **結果を保存**
   A-1〜A-6 の結果表をスクリーンショットで残します。とくに **A-2 の `row_count` と `max_score`** は
   あとで見比べるので必ず残してください（手順0の2行目・3行目と同じ数字です）。
3. **`RANKINGS_SCORE_BIGINT_APPLY_TEST.sql` を実行**
   変更を試して、最後に必ず巻き戻します（本番には何も残りません）。
   成功すると、メッセージ欄に次の流れが順に出ます。
   - 「ビューを落としました」× A-3 に出た枚数（上にあるものから）
   - 「score を integer から bigint へ広げました」
   - 「ビューを戻しました」× 同じ枚数（下にあるものから）
   - 「450億のスコアを保存できることを確認しました」
   最後に `score` が `bigint`、Index が `is_valid=true` / `is_ready=true` で表示されます。
4. **エラーがないことを確認**
   赤いエラーが出ていたら実適用へ進みません。ビューの定義・所有者・コメント・権限が
   元と少しでも違って戻った場合もここで止まります（そのときは何も変わっていません）。
5. **`RANKINGS_SCORE_BIGINT_APPLY.sql` を実行**
   同じ検査を通したうえで確定します。検査に1つでも引っかかればトランザクションごと
   巻き戻るので、途中の状態は残りません。
   既存データは書き換わりません（`int4` → `int8` は値の幅を広げるだけ）。
6. **`RANKINGS_SCORE_BIGINT_VERIFY.sql` を実行**
   `score` が `bigint`（`udt_name` が `int8`）、**件数と最大スコアが手順2の控えと同じ**、
   Index が使える状態、RLS・ポリシー・権限が手順2と同じ、
   V-5 に手順2（A-3）と同じビューが並んでいること、
   V-6 のメッセージで各ビューが「引けます」と出ることを確認します。
7. **ゲームで確認**
   チャレンジのランキング（LEGEND など）と、**モンヒロビートのランキング（曲別・全曲合算）**が
   これまでどおり表示できることを確認します。
   そのあと1回プレイして、新しい記録が載ることを確認します。

## 注意

- 実行中はランキングへの書き込みが一瞬止まります（テーブルロック）。行数がこの規模なら一瞬で終わります。
- 集計ビュー（`rhythm_scores` 〜 `rhythm_total_rankings`）は、この作業のあいだだけ一時的に消えて、
  同じトランザクションの中で元どおり作り直されます。外から見て「無い」瞬間はありません。
- **すでに弾かれてしまった記録は、この作業だけでは戻りません。** 端末には
  `mh_rank_<難易度>` に `nationalSaved:false` として残っているので、
  ゲーム側に「未送信の記録を後から送り直す」仕組みを入れると載せられます（別作業）。
- `level` など他の列は `integer` のままで問題ありません（ブリーダーLvは21億に届きません）。
  A-6 の結果で、ほかに合計や倍率が乗る `integer` 列が見つかった場合だけ、別途相談してください。
