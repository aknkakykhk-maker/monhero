# モンヒロビート: 発熱(重さ)の内訳と、前もって作れるものの一覧

2026-10-11 ドライバー(修理部)。社長「全体的にモンビーは重たい気がする。発熱しやすくて、かくつく。事前読み込みで改善されないの?」への調べ。
ふだんの描き方(既定の 2D canvas)で、bot に曲の最後まで演奏させて測った(`tools/playbot/lib/rhythm-perf-run.js` の `breakdown`)。

## 測り方

- 1回 = ブラウザを新しく開き、曲えらびから入って、bot が最後まで演奏する(横 844x390・CPU 1倍と4倍)
- メインスレッドの CPU 時間(トレースの tdur)を、仕事の種類ごとに分けた。JS は CDP のプロファイラで関数ごと
- **bot がタップの位置を読む分(getBoundingClientRect と、それが起こすレイアウト)は引いてある**(ゲームは毎コマ位置を読まない。#2666 などで済み)
- ほかのスレッド(ラスタ=絵を画素にする・合成)は、この入れ物の Chromium が **合成まで CPU でしている**(SoftwareRenderer)ため、iPhone より大きく出る。
  「何が毎コマ塗り直されているか」の手がかりとして見る

### 読み取れること

1. **ゲームの JS(ノーツを描く・判定)は小さい**(CPU1倍で 0.4〜0.8ms)。ノーツの canvas は JS のうち半分ほど
2. **いちばん大きいのは DOM の「スタイル・レイアウト」**(1倍で 0.8〜2.8ms、4倍で 5〜32ms)。ノーツの多い曲(FREEDOM DiVE↓)ほど増える。
   叩くたびに判定の文字・コンボ・スコアなどの DOM を書き換えている分
3. **塗り直し**: 6秒(349コマ)で数えると、画面全体の土台の層(#document・844x390)が **75回**、判定ラインの層が 69回、上のスコア欄が 40回、コンボの数字が 24回塗り直されていた。
   判定の文字(`data-rhythm-judgment-display`)などが土台と同じ層にあり、変わるたびに大きく塗り直させている。ラスタのスレッドの仕事(1コマ 4.5〜11ms)の元
4. **canvas を画面へ渡す**仕事が 1コマ 0.8〜1.4ms(844x390 の画面いっぱいの canvas を毎コマ渡す)
5. **曲の頭に長いコマ**: どの曲も最初の 0.7〜2秒に 170〜900ms のコマがある(初めて出る演出の準備が演奏中に起きている)。4倍では曲の途中にも 400〜800ms

## 直す候補(前もって作れるもの・軽くなる見込み)

| # | 何を | どう直す | 見込み(この入れ物の数字) | 見た目 |
| --- | --- | --- | --- | --- |
| A | 曲の頭の長いコマ | 演奏前の準備の仕組み(下)。絵の焼き付け・描く部品の温め・初めて出る DOM の演出を、幕開けとカウントダウンの間に済ませる | 曲の頭の 170〜900ms のコマを無くす | 変わらない(幕が最大6秒まで延びることがある) |
| B | 判定の文字・判定ライン・スコア・コンボの塗り直し | それぞれを自分の層に分ける(`will-change`・`contain`)。判定の文字は、焼いてある光(`rhythmBakeJudgmentHalos`)と同じく絵にしておき、切り替えるだけにする | 土台の塗り直し 75回→0回。ラスタ 1コマ 2〜4ms 減・メインの塗り 0.2〜0.5ms 減 | 同じ(画素で突き合わせる) |
| C | スタイル・レイアウト | 叩くたびに書き換える DOM の数を減らす(React の描き直しを判定の文字・コンボだけに絞る/数字は文字だけ差し替える/位置の変化は transform で)。まず何がスタイル計算に入っているかを数える | 1倍で 0.5〜1.5ms 減、4倍で 5〜15ms 減 | 同じ |
| D | ノーツの板(drawHead) | 種類×大きさの段ごとに、板を前もって絵にしておく | 1倍で 0.1〜0.3ms・4倍で 1ms 前後 | 大きさを段にそろえる分の差が出る。画素の突き合わせで許せるかを先に見る |
| E | canvas を画面へ渡す | ノーツの無い所を毎コマ消し直さない・canvas の大きさ(倍率)を見直す | 0.2〜0.5ms | 倍率を下げるなら差が出る(やるなら別に相談) |

効く順の見立て: A(かくつきの体感)→ B(発熱の元のラスタ)→ C(メインの最大)→ D・E。

## 演奏前の準備の仕組み(作り方)

- 入口 `rhythmPrepareRun(chart, settings)`: 決定〜幕が閉じるまでに走らせ、Promise をマクアケくんの `rhythmSongIntroHold(promise)`(幕の側の口)へ渡す。
  幕の決め事: 最短=幕の表示時間・最長6秒・失敗しても済んだ扱い・タップで飛ばしても準備が済むまでは閉じない。幕が閉じても残っていたら、READY の前でもう一度だけ待つ(上限+3秒。延びた時間は stats に残す)。マルチは時間を固定し、待ちで延ばさない
- 中身(どれも演奏中に初めて起きていたもの):
  1. 画像・音の読み込みと音のデコード(今もしているものはそのまま。抜けがないかを確かめる)
  2. 光・ノーツ・判定の文字の絵を焼いておく(`warmSprites`・判定の光。B・D の絵も同じ置き場)
  3. スライドの形・速さの表の前計算(曲ごとに1回)
  4. 演出の DOM(判定・コンボ・モンスターノーツ・叩いた光)を一度だけ見えない所で作り、スタイル計算を済ませておく
  5. 画面に出さずに数コマ描いて、描く部品(canvas・WebGL のシェーダー)を温める
- 出し入れ: まずデバッグの切り替えで入れ、bot の表(曲の最初の5秒と、初めて出る演出の瞬間の1コマ)で良くなったら既定に
- 実機: `stats.frame` に「最初の5秒の 50ms 超のコマの数」(`startOver50`)と「準備で延びた時間」(`prepWaitMs`)を足す(項目を足すだけ)

## 次の人へ

- 内訳を取る: `runOnce({..., breakdown: true, funcs: [...]})`。返す `breakdown` に、関数の自分の時間・指定した関数の含む時間・メインの仕事の種類(2段目まで)・スレッドごと・塗り直した要素・長いコマ(曲の時刻)
- `atStart(page, cdp)`・`atEnd(page, cdp, breakdown, events)` で、測る区間の頭と終わりにページを調べられる(層ごとの塗り直しは CDP の LayerTree.layerPainted で数えた)
