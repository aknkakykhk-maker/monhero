## いまの重さの正体

毎コマ CPU で、見えている帯を数百の区切りに刻み、1つずつ奥行きの投影を計算して canvas に塗っている
(`rhythmSlideSegmentQuads` → `drawSlide`)。帯が長い・多いほど重い。デバッグの WebGL の切り替え(`rhythmCreateGL2D`)も、
毎コマ CPU で作った形を GPU に渡しているだけで根は同じ。

## 作り替えの中身

1. **帯・影の形は一度だけ作って GPU に置く。** 頂点は「譜面の座標」で持つ:
   横=レーン(`rhythmSlideExpectedLane` と幅 `rhythmSlideWidthAt` から左右の端のレーン座標)、
   縦=**速さの表で積み重ねた位置 S(t) = `rhythmScrollPos(t)`**(止まり=倍率0・RUSH を含む)、空中の高さ=`rhythmSlideSkyAt`。
   - S(t) は `rhythmScrollSet(changes, travelMs)` と同じ (changes, travelMs) を鍵に覚え、鍵が変わったら(ノーツ速度が違う・途中で変わる)作り直す
     (RUSH の区間の倍率は travelMs から出るため。テンポくんの指摘 2026-10-11)
2. **毎コマ渡すのは数個の値だけ**(uniform): いまの S(`rhythmScrollPos(visualTime)`)・travelMs・spawnY・travelPx・画面の大きさ・
   空中の持ち上げ(`RHYTHM_SKY_LIFT.ratio`)・道の幅の倍率。奥行きの投影(`rhythmProjectTravelProgress`・`rhythmProjectBoundary`)・
   空中の持ち上げ(`rhythmSkyLiftPx`)・影(持ち上げ0)は頂点シェーダーで計算する(今の式をそのまま移す)
3. **描く回数をまとめる**: 地上の帯1回・空中の帯1回・影1回・芯の線1回。ノーツの板・箱・星は絵を1枚にまとめて1回ずつ
   (見た目の設計 案Z v6 の描き物「半透明の帯1枚+加算の芯の線・箱・暗い影・星1種・細い線」はこの形に乗る)
4. **見えない所は GPU が切る**(画面外の区切りを CPU で探さない)

見込み: HELL 82 → 10〜20ms、既存曲 45 → 10〜15ms 前後。

## S1 でやったこと(2026-10-11・ドライバー)

- `rhythmCreateGpuSlideBand`(rhythm-mode.js・`rhythmCreateGL2D` の手前): 帯の形を譜面の座標で一度だけ GPU に置く部品。
  点1つ = [S(速さの表で積み上げた位置), T(時刻), c(帯の中心), ±hb(ふちまで)] と高さ sky。奥行きの投影・空中の持ち上げは頂点シェーダー(`BAND_VS`)で、
  `rhythmSlideSegmentQuads` の project と同じ式。速さの表(`RHYTHM_SCROLL.points`)が変わったら作り直す。見えなくなって3秒で捨てる
- 押さえている帯は、今の描き方と同じく「いまの位置から次の譜面の点まで」だけ毎コマ刻み直して渡す(刻む点が今の描き方とぴったり同じになる)。その先は GPU に置いた形
- 外周(右のふち→先の角→先の線→先の角→左のふち)は1本の帯につなげて置き、残りの範囲を1回で描く。描く順・色・太さは `drawSlide` と同じ(`drawSlideGpu`)。影は `drawSkyShadowGpu`
- 押さえている光(明るさの範囲・流れる筋)は判定ライン寄りしか使わないので、その範囲だけ CPU で刻む(`travel.window`)
- 出し入れ: デバッグ画面「スライドの帯の描き方(検証用)」→ GPU(`mh_rhythm_gpu_band_v1`)。選ぶとノーツは WebGL で描く。
  WebGL が取れない・文脈が落ちたときは、今までどおり 2D へ戻る(演奏画面の既存の仕組み)。帯の部品が作れなければ CPU で刻む
- 突き合わせで見つけた今の描き方の不具合を1つ直した: ノーツサイズが100%以外だと、空中のスライドが地上の色で描かれていた(`drawSlide` の倍率の写しが高さを落としていた。試作の枠だけ)

## S2 でやったこと(2026-10-11・ドライバー。途中)

- **区切りの線(`rhythmSlideCheckpointLines`)を GPU へ**: 線1本 = 左右の端の丸+その間の線(太さ2)を、帯と一緒に一度だけ置く(`checkpointsOf`。
  頂点の印 aMisc.w=1)。毎コマは「いまより後の線の番目」から「画面の上の外へ出る番目」までを二分探索で決めて1回で描く。
  奥行きは今の描き方と同じく画面の中(0〜1)で決め、画面の高さより上下へ外れた線は頂点シェーダーが消す。CPU の投影は無くなった
- **突き合わせの検査を強くした**: これまでの検査は譜面のノーツをそのまま描いていて、演奏画面が焼き込む「描く点の並び・区切りの線の時刻」が無かった
  (=区切りの線を1本も比べていなかった)。演奏画面の `makeRuntimeNotes` と同じく焼き込むようにし、細い線の抜けは平均の差に埋もれるので
  「差の大きい画素(64以上)が今の WebGL より何画素多いか」(200未満)も見る。線を描かないように壊すと 17 → 1502画素で落ちることを確かめた
- 強くした検査で見つかった S1 のずれを2つ直した
  - ジグザグのスライドの急な角: 2D の線は角を丸くつなぐが、GPU は角を伸ばしていて尖っていた。譜面の点のつなぎ目に「来た側の線・角の丸・出ていく側の線」
    (印 2・4・3)を置き、画面の上で約25度より急なときだけ頂点シェーダーが角を丸める(緩い所は今までと同じ形で、丸は1点に縮めて描かない)
  - 空中のスライドの塗りの色: 2D は区切りごとに両端の平均の高さで1色、GPU は頂点の間で高さをなめらかにつないでいて、空中と地上の色の境目がずれていた。
    空中のあるスライドだけ、区切りごとに頂点を置き直して同じにした(塗りの頂点の数は2倍)
  - 大きく違う画素の上乗せ: S1 のまま 406画素(sheriruth_proto)→ 29画素(全曲の最大)。HELL(テンポくんのブランチの譜面を `--extra`)は 3画素
- 後ろに戻る(マイナスの速さ)への備え: 頂点はそれぞれ投影するので、帯・線の形は位置が時刻の順に並ばなくても崩れない。
  先を打ち切る所(線の範囲)は `rhythmScrollForward()`(速さの表がどれもマイナスでないか)のときだけ切る。いまは `rhythmScrollSet` がマイナスを捨てる
