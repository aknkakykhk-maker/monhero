# 新しい Codex チャットの始め方

チャット履歴がない状態でも、Codex がプロジェクトを誤解せず作業を継続するためのチェックリストです。
Claude や ChatGPT を使う場合も、ツール名に関する箇所以外は同じ流れを利用できます。

## 1. 開始前に準備する情報

- 作業するリポジトリとブランチ
- 今回の目的と、利用者から見た完了条件
- 変更してよい範囲・変更してはいけない範囲
- 関連する GitHub Issue / PR / コミット
- 再現手順、端末・OS・ブラウザ、スクリーンショット、エラーログ
- コミット、プッシュ、PR 作成が必要かどうか

秘密情報、個人情報、実ユーザーのセーブデータはプロンプトへ貼らないでください。

## 2. 最初に貼るプロンプト

次をコピーし、`<...>` を埋めて送信します。詳細な依頼には
[`PROMPT_TEMPLATE.md`](PROMPT_TEMPLATE.md) を併用してください。

```markdown
`<リポジトリのパスまたはURL>` の `<ブランチ名>` で作業してください。

最初に以下を読み、内容の優先関係と現状を確認してください。
1. `CLAUDE.md`
2. `DEVELOPMENT.md`
3. `docs/PROJECT_CONTEXT.md`
4. `docs/KNOWN_ISSUES.md`
5. `tools/README.md`
6. 関連コードと直近の Git 履歴

今回の目的: <目的>
受け入れ条件:
- [ ] <条件1>
- [ ] <条件2>

変更対象: <機能 / ファイル / AI が調査>
変更禁止: <ゲーム仕様、保存形式、バランスなど>
関連情報: <Issue / PR / 再現手順 / ログ>

既存の未コミット変更を保持し、推測で仕様を補わず、スマートフォンの縦画面と
タッチ操作を優先してください。着手前に理解した構成、作業計画、確認が必要な点を
日本語で簡潔に示してください。変更後は関連テストを実行し、変更ファイル、結果、
未確認事項を日本語で報告してください。

Git 作業: <コミットのみ / プッシュとPRまで / 不要>
```

## 3. Codex が着手前に確認すべきこと

依頼者は、Codex の最初の応答または調査結果に次が含まれるか確認します。

- [ ] 現在のブランチと `git status` を確認した
- [ ] 既存の変更を自分の変更と混同していない
- [ ] `monster-hero/src/game-system.jsx` が編集元で、compiled が生成物だと理解した
- [ ] 静的サイト / GitHub Pages / モバイル縦画面という前提を理解した
- [ ] 受け入れ条件と対象外を言い換えられている
- [ ] 変更に対応する検証方法を選んでいる
- [ ] 不明な仕様を勝手に決定していない

## 4. 作業中の引き継ぎ

長い作業を別チャットへ移す前に、現在の AI へ次の形式で引き継ぎメモを作らせます。

```markdown
## 引き継ぎメモ
- 目的:
- ブランチ / HEAD:
- 完了したこと:
- 変更ファイル:
- 未完了のこと:
- 判断と理由:
- 実行済みテストと結果:
- 次に実行するコマンド:
- 注意点 / 既知の課題:
- 関連 Issue / PR:
```

未コミットの差分がある場合は、`git status --short` と `git diff --stat` の結果も添えます。
ただし、長大なソース全文や秘密情報は貼らず、新しいチャット側でリポジトリを読ませます。

## 5. 完了時の確認

- [ ] 受け入れ条件をすべて確認した
- [ ] ゲーム仕様やアセットに意図しない差分がない
- [ ] 必要な生成・検証コマンドが成功した（未実行なら理由がある）
- [ ] 今回の変更に関係するドキュメントを、現在の実装に合わせて更新した
- [ ] コミット・プッシュ・PR の依頼範囲を満たした
- [ ] 最終報告に、更新したコードとドキュメント、更新内容と理由、テスト、未確認事項、今後の改善提案がある

## 6. 情報が食い違う場合

優先順位は、現在のユーザー指示、リポジトリ内の適用範囲が最も狭い指示、
`CLAUDE.md`（Claude 固有）、`DEVELOPMENT.md`（AI 共通）、その他の説明文書の順です。
ただしゲームの現行挙動はコードとデータで確認し、文書との不一致を見つけたら実装を勝手に変えず報告してください。

## 7. ドキュメント・ナレッジ更新ルール

このプロジェクトでは、コードだけでなくドキュメントも常に最新の状態に維持します。

### 基本方針

- コードとドキュメントの内容が一致する状態を維持する
- 推測でドキュメントを書き換えず、現在の実装を正本として更新する
- 今回の変更に関係するドキュメントだけを更新し、関係のないドキュメントは変更しない

### 更新対象

変更内容に応じて、次のうち関連するものを更新します。

- `DEVELOPMENT.md`
- `docs/PROJECT_CONTEXT.md`
- `docs/KNOWN_ISSUES.md`
- `docs/` 以下の関連設計書

### 更新が必要な場合

- ゲーム仕様、バトル仕様、UI 仕様、セーブデータ仕様を変更した
- 新しいシステム、モンスター、アイテムなどを追加した
- 新しい開発ルールが決まった
- 今後も注意が必要な不具合が判明した
- AI が今後も知っておくべき仕様や知識が増えた
- プロジェクト構成が変わった

### 更新しなくてよい場合

- 一時的なデバッグ
- コメント修正のみ
- リファクタリングのみ
- 挙動が変わらない整理
- ドキュメントと無関係な軽微な修正

### プロジェクト改善

作業中に次のようなことを発見した場合は、作業終了時に改善案を提案します。必要であれば、関連ドキュメントも同じブランチ内で更新します。

- 毎回同じ説明や質問をしている
- ドキュメントが不足している、または AI が理解しづらい箇所がある
- 新しい設計書を作成した方がよい
- 既存の設計書を充実させた方がよい
- 今後の開発効率が上がる改善案がある

### 作業完了時の報告

最終報告には、必ず次の項目を含めます。

- 更新したコード
- 更新したドキュメント
- 更新内容
- 更新理由
- 実施したテスト
- 未確認事項
- 今後の改善提案

更新が不要だった場合は、「今回の変更では更新が必要なドキュメントはありません。」と、その理由を報告します。
