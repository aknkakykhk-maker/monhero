# ランキングに出す「いまの見た目」設計書

2026-09-16 にユーザーの依頼で実装した（「アイコンとフレームは更新時じゃなくて常に設定してるやつが
ランキングに出るようにできないの？」）。名前も同じ扱いにした（同日、ユーザーが「2」＝名前も含める を選択）。

## 1. 何が問題だったか

ランキングは **1プレイ＝1行**で、その瞬間の名前・アイコン・フレームを記録へ写している。
そのため、あとから見た目を変えても**過去に出した行は古いまま**だった。

記録そのものを書き換えるのは危ない（CLAUDE.md ⑦）ので、**表示に使う見た目だけ**を
別の小さな表から引くことにした。

## 2. しくみ

```
public.breeder_profiles   … 1人1行。breeder_id が主キー
  breeder_id / user_name / icon / profile_frame / updated_at
```

- **記録（`rankings` / `bond_levels`）は1行も書き換えない。** 順位・スコア・集計にも一切関わらない
- 1人1行なので、遊ぶたびに行が増えることはない
- 消す権限（DELETE）は与えていない

### 2.1 いつ書くか

**送るきっかけを決めるのは60-app.jsxの1か所（`lastPublishedProfileRef` のeffect）だけ。**
ボタンごとには書かない。

- **起動してセーブデータを読み終えたとき**（`dataLoaded`）
- **名前・アイコン・フレームのどれかが変わったとき**（保存した経路を問わない）

同じ内容は送り直さない（最後に送った内容を覚えておく。upsertなので送っても害は無いが、通信を無駄にしない）。

> ⚠️ **起動時に送るのが要（2026-09-16に足した）。**
> 最初は「変えたとき」と「遊んだあと」だけで送っていた。それだと
> **一度も設定を変えていない人の行がいつまでも登録されない**。登録が無い人は引き当てようが無いので、
> ランキングはその人を記録に写した当時の見た目で出し続ける。記録ごとに写っている値が違うため、
> 画面によって枠が出たり出なかったりして見える（ユーザー指摘
> 「フレームが反映されてる画面とされてない画面がある」）。原因は画面ごとの実装差ではなく、
> **引き当ての材料が無いこと**だった。

次のときは何もしない。

- 「見るだけ」のプレビュー中（`onboardingPreview`）… 本物の見た目を書き換えないため
- ブリーダーIDが作れない端末 … 誰の行か決められないため（記録の値で今までどおり出る）

失敗しても進行は止めない（次に変えたときか、次に遊んだときに送り直される）。

### 2.2 いつ読むか

`ensureBreederProfiles()` が、ランキングを取りにいく5つの入口
（`sbFetchRankings` / `sbFetchBondLevels` / `sbFetchRhythmRankings` /
`sbFetchRhythmTotalRankings` / `sbFetchRhythmEventRows`）の先頭で呼ばれる。
**60秒は読み直さない**ので、ランキングを開くたびに増えることはない。
失敗しても投げない（見た目が古いままになるだけで、順位は出る）。

### 2.3 どう引き当てるか（`applyLatestBreederProfile`）

**ここだけが差し替えを決める。画面ごとには書かない。**

| 順 | 引き方 | 当たる場合 |
| --- | --- | --- |
| ① | **ブリーダーID** | 記録に `breeder_id` が入っている（2026-09-11以降）。**改名していても当たる** |
| ② | **名前** | IDの無い古い記録。ただし**その名前の人が1人だけ**のとき限定 |
| ③ | — | 見つからなければ、記録に写した値のまま |

②で同名の別人を弾くのは、他人の見た目を出さないため
（全曲合算の `rhythm_identity_map` と同じ考え方・[`RHYTHM_RANKING.md`](RHYTHM_RANKING.md) §4.4）。

★①のために、記録を取るときに `breeder_id` も受け取る（`rankingSelectWithBreederId`）。
名前だけに頼ると、**名前を変えた人が自分の記録に当たらなくなる**。

### 2.4 どこに効くか

エントリを作る7つの関数すべてが `applyLatestBreederProfile` を通るので、**画面側は1行も変えていない**。

`toEntry`（バトルのスコア・ブリーダーLv）/ `bondLevelRowToEntry`（絆Lv・総合力）/
`rhythmRankingEntryFromRow`（モンビー曲別）/ `rhythmTotalRankingEntryFromRow`（全曲合算）/
`rhythmWeekTotalEntryFromRow`（週間）/ `rhythmEventSongEntryFromRow`・`rhythmEventTotalEntryFromRow`（イベント）

## 2.3 登録がまだ無い人の受け皿（2026-09-16）

`breeder_profiles` に登録があるのは**この版のゲームを開いた人だけ**。まだ開いていない人は
引き当てようが無く、**同じ人の行なのに枠が出たり出なかったりする**
（ユーザー指摘「過去のランキングにフレームが対応されてない」。チャレンジの一覧で
同じ♪みゅあ♪さんの5行のうち1行だけ枠が出た）。

そこで、**記録そのものから「その人の最後に分かっている枠」を拾う**（`rememberLooksFromRows`）。

- `profile_frame` の列は 2026-09-15 に足したもの。**値が入っている行は必ずそれ以降のプレイ**なので、
  その人の新しい姿として使ってよい
- 時刻（`created_at`）が取れる一覧では**新しいほう**を選ぶ。
  ★`created_at` を足すのは**件数の決まっている一覧だけ**（スコア・モンヒロビート）。
  ブリーダーLvは全件をページ送りで読む（最大24,000行）ので足さない。あちらは1人1行なので要らない
- 覚えた内容は**画面をまたいで貯まる**。モンヒロビートの記録で分かった枠を、バトルの一覧でも使える
- **同じ名前の人が2人以上いるときは使わない**（他人の枠を出さないため）

優先順位は次のとおり。

| 順番 | 見るもの | 変わるもの |
| --- | --- | --- |
| ① | `breeder_profiles` の登録（＝いま設定しているもの） | 名前・アイコン・枠 |
| ② | 記録から拾った枠 | **枠だけ**（名前とアイコンは記録のまま） |
| ③ | どちらも無い | 記録に写した値のまま |

②が枠だけなのは、`profile_frame` の列だけが「新しいプレイの印」になるため。
`icon` は昔からある列なので、同じ手がかりにならない。

## 3. 残っている限界

- **IDの無い古い記録で、しかも改名した人**は当たらない。記録の名前と今の名前が違うため。
  その行は記録に写した値のまま出る
- **同じ名前の人が2人以上いる名前**も当てない（②の規則）。誰が当てはまるかは
  `BREEDER_PROFILE_VERIFY.sql` の「同じ名前が2人以上いる名前」で分かる
- **他の人の名前とアイコンは、その人がこの版のゲームを開くまで最新にならない。**
  枠は §2.3 の受け皿があるので記録から拾えるが、名前とアイコンには同じ手がかりが無い
- 枠を**外した**人が、この版を開かないまま（古いキャッシュのまま）遊んだ場合は、
  §2.3 が前の枠を出し続ける。その人がこの版を開けば登録され、①が勝って直る

## 3.1 「誰の行か」を決めるのもIDにした（2026-09-16）

見た目の引き当てだけでなく、**同じ人の行を1つにまとめる**のもIDで行う
（ユーザー指摘「名前管理はさすがにだめだろ」）。名前でまとめると、改名した人が2行に分かれ、
同名の別人が1行に混ざる。

`resolveBreederIdFor(entry, bridge)` が1か所で決める。

| 順番 | 見るもの |
| --- | --- |
| ① | 記録に付いている `breeder_id`（`identityKey` も。`name:` で始まるものは除く） |
| ② | **その一覧のなかで、その名前に1つのIDしかぶら下がっていない**ときのID（`breederIdBridgeFrom`） |
| ③ | プロフィール表で**その名前が1人に定まる**ときのID |

> ⚠️ **②の「橋」が要（2026-09-16に足した）。**
> モンヒロビートの記録にはIDが付いているが、**これまでのバトルの記録には付いていない**。
> IDのある行を `id:` で、無い行を `name:` で束ねると、**同じ人がIDの行と名前の行に割れて
> 2行並ぶ**（ユーザー指摘「ランキングが重複で出てる」。ブリーダーLvで
> ☆きき☆・♪みゅあ♪・あつ が2行ずつ出た）。
> 一覧のなかの記録そのものから橋を架けるので、`breeder_profiles` にまだ登録が無い人にも効く。
> **同じ名前に2つ以上のIDがぶら下がっていたら橋は架けない**（別人を混ぜないため）。

使うのは次の2か所。

- `aggregateBreederLevels`（ブリーダーLv）… 名前ごと → **IDごと**
- `bondRankingKeyOf` → `mergeBondRankingEntries`（絆Lv・総合力）… 名前×個体 → **ID×個体**。
  重なったら**絆Lvの高いほう（＝いまの値）**を残す

どちらも**先に一覧全体を見て橋を作ってから**束ねる（`mergeBondRankingEntries` は正本と旧経路の
両方を合わせて作る）。

②③があるので、IDが付く前の古い記録も、改名していない人ならその人の行として束ねられる。
IDが決められない行だけ、これまでどおり名前で束ねる。

あわせて、**バトルの記録にも `breeder_id` を付ける**ようにした（それまではモンヒロビートだけだった）。

### bond_levels の主キーは変えない

`bond_levels` の主キーは `(user_name, individual_id)` のままにする。変えると既存の行を
壊すことになるため（CLAUDE.md ⑦）。そのため**改名すると行そのものは2つに分かれて残る**。
消すのも危険なので消さない。**画面側でIDを見て1行にまとめて見せる**のが答え。
どの人がそうなっているかは `BOND_LEVELS_BREEDER_ID_VERIFY.sql` の
「改名で2行になっている人」で分かる。

## 4. 適用

`docs/sql/rankings/BREEDER_PROFILE_APPLY.sql`
（予行演習 `_TEST`、確認 `_VERIFY`、手順 `BREEDER_PROFILE_IPHONE_STEPS.md`）。

**ふつうはこちらを使う**: `docs/sql/rankings/PROFILE_LOOK_ALL_APPLY.sql`。
これ1本で `bond_levels.profile_frame`（RHYTHM_RANKING.md §8.10）とこの表の両方を、
**1つのトランザクションで**作る。途中で1つでもおかしければ両方とも元に戻るので、
片方だけ当たった状態にならない。中身は個別の2本とまったく同じ
（`profile-frame-sql-check.js` が、要点の文がすべて入っているかを突き合わせる）。
手順は `PROFILE_LOOK_ALL_IPHONE_STEPS.md`、確認は `PROFILE_LOOK_ALL_VERIFY.sql`。

絆Lv・総合力をIDで見分けるには、さらに
`docs/sql/bond-levels/BOND_LEVELS_BREEDER_ID_APPLY.sql`（`bond_levels` へ `breeder_id` 列）が要る。
これも `PROFILE_LOOK_ALL_APPLY.sql` に含めてあるので、まとめて当てるなら1本で済む。

既存のテーブルには一切触らない。表がまだ無い環境では、アプリは「まだ準備中」として
そのセッションでは以後さわらない（記録に写した値で今までどおり出る）ので、
SQLの適用とアプリの公開はどちらが先でもよい。

## 6. ブリーダーLvの1人1行の表 `breeder_levels`(2026-10-27・社長の決定)

ブリーダーLvのランキングは、これまで `rankings` の `level` を全部読んで並べていた。裏周回やMFバトルカードだけで遊び、
`rankings` に1行も送っていない人は、Lvが高くても載らなかった。そこで1人1行の新しい表を足した。

- **表**: `breeder_levels`(`breeder_id` が主キー・`user_name`・`icon`・`level`)。SQL は
  `docs/sql/rankings/BREEDER_LEVELS_APPLY.sql`(予行は `_APPLY_TEST.sql`・確認は `_VERIFY.sql`)。足すだけで、`rankings` などには触らない。
  削除の権限は与えない。上書きしても Lv は下がらない(trigger が高いほうを残す)
- **送るのは2回だけ**(Supabaseの無料分を気にする社長の指示): ① ゲームを開いてセーブを読み終えた時点 ② ブリーダーLvが上がったとき。
  同じ値・低い値は送り直さない。はじめての設定の前・「見るだけ」のプレビュー中は送らない。失敗しても進行は止めない(次に開いたとき送り直す)
- **読み方**: ランキングを開いたとき、表の全行を読み(1ページ1,000行)、`rankings` の全行読みはそのまま残す。
  表の行を先に並べて `aggregateBreederLevels` に渡すので、同じ人はIDで1行になり、高いほうの Lv が残る。
  まだ表に来ていない人は、今までどおり `rankings` の `level` で載る(消えない)
- **Lv.1 の行は使わない(2026-10-27・社長の決定「消さない」)**: 送る側は Lv.2 から。読む側も Lv.2 以上だけを使う(`level=gte.2` で頼み、返ってきた行も絞る)。
  表に残っている Lv.1 の行(検査の端末が本番へ足した名前「テスト」など)は、消さず・書き換えず、ランキングを作るときだけ外す
- **表がまだ無い環境(SQL未適用)**: 404(PGRST205)を一度見たら、そのセッションでは触らず、今までどおりの表示になる。
  SQL の適用とアプリの公開は、どちらが先でもよい(ただし表が無いうちは送れないので、新しい人は載らない)
- 限界: 公開キーで書けるので、`rankings` と同じく書き換えれば高い Lv を名乗れる(新しい弱みではない)。
  IDは端末ごとなので、機種変すると別の人として1行増える(`rankings` も同じ)

検査: `node tools/ranking/breeder-level-table-check.js`(送る・読む・結線・並べ方・SQL の形)。
