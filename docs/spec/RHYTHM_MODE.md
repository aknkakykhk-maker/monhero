## 1. 初期設計の出典（履歴）

音ゲーの基礎設計は PR #862 `feat: add rhythm mode foundation (音ゲー基盤 STEP 1)` に残っている。

初期設計で確定していた骨格は以下。

- 通常公開はせず、デバッグ画面からのみアクセスする
- 5レーン
- ノーツは `TAP / HOLD / FLICK / SLIDE` の4種類
- 難易度は `EASY / NORMAL / HARD / EXPERT / MASTER` の5段階
- 各難易度に最大スコアを持たせる
- 判定は6段階
- スコアは「判定90% + コンボ10%」を基本構成とする
- 曲データは既存BGM登録を正本とし、音ゲー側は `trackId` で参照する
- 設定保存とBEST保存を独立キーで持つ
- 欠損・不正な保存値は読み込み時に正規化する
- 通常HOMEには入口を追加しない
- デバッグ画面で曲、難易度、最大スコア、設定、BESTを確認できるようにする

## 2. 基本構成（現行仕様）

### レーン

- 表示は5メインレーン
- 細分配置・入力の基準は10サブレーン
- `TAP` / `HOLD` / `FLICK` は `subLane`（始点0〜9）と `subLaneWidth`（幅1〜10）を持てる。
  **幅の上限は全幅（10サブレーン＝5レーン）**。以前は4（2レーンぶん）で頭打ちにしていたが、
  実機で「上限を無くして全幅もありに」と言われて撤廃した（2026-09-04）
- `subLane` を持たない従来ノーツは、メインレーン1本＝サブレーン幅2相当として後方互換を維持する
- 可変幅TAP/HOLD/FLICKは描画範囲 `subLane` 〜 `subLane + subLaneWidth` と同じprojectionを逆変換して開始入力を判定する
- 幅1の入力だけ、表示を太くせずサブレーン幅0.18ぶんを左右へ許容する。隣接時は中心に近い1ノーツだけをclaimedする
- 通常の1入力は1ノーツのみ取得し、別の指はそれぞれ独立して同時取得できる
- TouchではTAPに限り `radiusX` を使って指腹の接触範囲を補助入力へ反映する
- PR #939以降は「1本指最大3サブレーン」という固定上限を正本にしない。実際の接触範囲を70%へ縮小し、隣接サブレーンへ20%以上重なった場合だけTAP候補へ含める（STEP1実機検証で25%は狭すぎ、1本指で3サブレーン押すのが難しいと判明したため20%へ緩和、2026-09-04）
- 現行の接触幅主要定数は `RHYTHM_TOUCH_RADIUS_SCALE=.70`、`RHYTHM_TOUCH_MIN_SUBLANE_COVERAGE=.20`、異常値guardはプレイエリア幅の `.25`
- `radiusX` が0・不正・未対応、または異常に大きい場合は中心入力へfallbackする
- 接触幅で追加する候補はTAP専用。HOLD / SLIDE / FLICKは1本指につき1操作を維持する
- 同一の幅2〜4 TAPを複数の接触サブレーンが覆っても1ノーツとして1回だけ判定する
- touchmoveでは直前の接触集合と比較し、新しく接触したサブレーンだけをTAPの新規入力候補にする。一度外れてから再び入ったサブレーンは再度候補にできる
- PR #941以降、押しっぱなし中の小さな中心揺れを移動扱いしない。中心deadzoneは6〜10pxの範囲を基本とし、プレイエリア幅2%を参照する
- 押しっぱなし中に指腹を明確に広げた場合のみ追加接触を許可する。拡張判定の基準は3px以上かつ10%以上
- 可変幅HOLDは開始ノーツ・HOLD帯・ENDバーを同じサブレーン範囲と幅で投影する
- **HOLDは `holdPoints` で押さえている途中に幅を変えられる**（`[{timeMs, subLane, subLaneWidth}, ...]`）。
  実機で「ホールド・スライドは途中から広がったり小さくなったりもほしい」と言われて足した（2026-09-04）。
  SLIDEは以前から `slidePoints[].subLaneWidth` で出来ていたが、HOLDは始点から終点まで一定だった
- 幅は点と点のあいだを時間で直線補間する。書かなかった項目（`subLane` / `subLaneWidth`）は
  ノーツ本体の値を使う。中心を動かすのはSLIDEの役目なので、HOLDは「その場で太さが変わる」形が基本
- **判定と入力の受け付け幅は始点の帯のまま**。変わるのは見た目と、押さえ続けている最中に
  「外れた」と見なす幅（`rhythmHoldTrackedLane(note, chartTimeMs)`）だけ。
  途中で広がったからといって取りやすくならず、細くなる帯を押さえ続けるのは難しくなる
- HOLD帯の描画は「幅が変わる時刻」がどの高さに当たるかを落下曲線から出し、そこを必ず多角形の頂点にする。
  高さの比だけで刻むと、落下が曲線であるぶん幅の変わり目が実際の時刻からずれる（速いほどずれる）
- `subLane` を持たない旧HOLDは、従来どおりメインレーン1本＝サブレーン幅2相当の見た目と入力を維持する
- 可変幅FLICKは開始ノーツと開始入力を同じサブレーン範囲・幅で扱い、ジェスチャー成立後にruntime上でHOLDへ変換されても元のFLICK幅を維持する
- `subLane` を持たない旧FLICKは、従来どおりメインレーン1本＝サブレーン幅2相当の見た目と開始入力を維持する
- STEP2B-1以降のSLIDEは、始点 `lane` と authored `slidePoints[].lane` / `endLane` を `0, 0.5, 1, 1.5 ... 4` の0.5レーン刻みで指定できる
- SLIDEの途中補間は連続座標のまま描画・追従判定し、0.5刻みに丸め直さない
- SLIDEは `subLaneWidth`（幅1〜10）を持てる
- `slidePoints[].subLaneWidth`（幅1〜10）で途中幅を指定できる
- 実効幅は point → note → 幅2 の順にfallbackし、point間は位置と同じ時間軸で連続補間する
- SLIDEの幅が無い、または不正な場合は従来どおり幅2相当として旧譜面を維持する
- 可変幅SLIDEは開始ノーツと操作中の頭をその時刻の幅へ追従させ、SLIDE帯の各segment両端へ異なる幅を投影する。ENDバーは最終pointの実効幅を使う
- SLIDE開始入力も同じ幅へ合わせる。幅1のみ既存のサブレーン0.18ぶんの入力余白を付ける
- SLIDE途中追従の許容は幅に合わせて変化するが、幅2は従来の `0.82` レーンを維持する
- スマートフォン縦画面・タッチ操作を主対象とする
- レーン、ノーツ、判定ライン、入力座標は同一のprojectionモデルを使う
- 現在は遠近表現を持ち、奥ほど狭く、判定ライン側ほど広く表示する
- 遠近感・収束率・ノーツ幅などの具体値は `monster-hero/data/rhythm-mode.js` を正本とする
- **収束率 `RHYTHM_PROJECTION_TOP_SCALE` は `.18`**（2026-09-03に `.30` から変更）。
  Safe Areaの二重掛けを直した結果プレイエリアの高さが 515px → 743px（iPhone 390×844相当、約1.44倍）になり、
  収束率は「プレイエリアの高さに対する比率」なので、縦だけ伸びると円錐が寝て奥行きが薄く見えるようになった
  （レーン外枠の傾きが以前の約69%まで浅くなった）。`.18` にすると傾きが以前の約96%まで戻り、
  上端が細く収束する設計イメージにも近づく。ユーザー確認のうえ採用した値

### プレイ画面のHUD配置（現行仕様）

- HUDはプレイエリアへ**重ねる絶対配置**（`pointer-events-none` + `absolute inset-x-0 top-0 z-30`）で、レイアウト上の高さを持たない
- ただし**台形の頂点（画面上端・遠近projectionの基準点=yRatio 0）を覆う背景パネルは持たせない**。HUD自身の`<header>`要素には背景色・背景画像を一切付けず、文字には`text-shadow`だけで視認性を確保する
- **この「背景を持たせない」は JSX だけの話ではない。`monster-hero/index.html` のグローバルCSSから
  `[data-rhythm-hud]` へ背景・`backdrop-filter`・`box-shadow` を当てるのも同じく禁止**。
  実際に index.html 側で
  `background:linear-gradient(180deg,rgba(6,9,26,.98),rgba(7,9,24,.90))` +
  `backdrop-filter:blur(10px)` + `box-shadow:0 10px 28px …,0 1px 0 rgba(103,232,249,.12)`
  を当てており、画面上部に不透明な黒い帯ができて台形の頂点と背景を覆っていた。
  JSXしか読まない検査では見えず、実機で「中央上部に黒い帯が残っていてレーンが上まで見えない」と
  指摘されるまで検出できなかった（2026-09-03に撤去）。
  現在は `rhythm-hud-wedge-check.js` / `rhythm-landscape-hud-check.js` が index.html 側の
  `[data-rhythm-hud]` 向け規則も読み込んだうえで、計算済みスタイルの
  背景色・背景画像・影・ぼかしがすべて無いことを実ブラウザで確かめている
- プレイエリアの `box-shadow` も、上端側の `inset` 影は消失点付近を暗く塗り潰すので置かない（下端側のみ）
- HUD本文は、台形が奥へ向かって狭くなる分だけできる**左右の空きウェッジ**（`RHYTHM_PROJECTION_TOP_SCALE=.18`により、画面上端で全体の41%ずつが左右に空く）にだけ置く。中央の台形部分には何も置かない
  - 左ウェッジ（`data-rhythm-hud-left`）: 丸いランクバッジ＋次のランクまでの進捗バー(`rhythmRankProgress`) → スコア → BEST → 難易度バッジ＋TEST表記 → 曲名（2026-09-03、参考にした他アプリの見た目に合わせてランクを文字だけの表示から丸バッジ＋進捗バーへ変更）
  - 右ウェッジ（`data-rhythm-hud-right`）: ハートアイコン＋LIFEバー＋数値 → ポーズボタン（`pointer-events-auto`） → COMBO（同じくLIFEを見出し文字だけの表示からハートアイコン付きのバーへ変更）
- **ウェッジは下へ行くほど狭くなるので、行ごとに使える幅を変える**（1つの固定幅で全行を賄うと、いちばん下の行に合わせるしかなく上が無駄になる）。
  幅は画面幅基準の `vw` で指定する（`%` は親要素基準になり、入れ子だと意図した画面比にならない）。
  現行値: 左列 `max-w-[35vw]` / 難易度の行 `max-w-[34vw]` / 曲名 `max-w-[31vw]` / 右列 `max-w-[33vw]`
- **曲名は `truncate` で切らない。** 実機で「あつ杯テー…」と切れて曲が分からない状態になったため、
  `-webkit-line-clamp:3` で折り返して表示する。`rhythm-hud-wedge-check.js` が `truncate` の再導入を弾く
- 画面のいちばん上の中央（台形の頂点＝ノーツが湧く消失点）には何も置かない。ここを覆うのはPR #983で失敗した形
- 現在のプレイエリアは「画面の高さ − 下の余白8px」。iPhone 390×844相当で 701px → 836px（約19%増）
- **projectionの式は変更していない**。ただしプレイエリアが縦に伸びたぶん `travelPx` が増えるため、
  同じ `noteSpeed` でもノーツの見た目の速度は上がる。`travelMs`（`rhythmTravelMsForSpeed`）は変えていないので、
  判定タイミングと先読み時間は従来どおり
- 検査は `node tools/mode/rhythm-hud-wedge-check.js`（実ブラウザで、台形の頂点がHUDに覆われていないこと・HUD本文がそれが描かれる高さの台形へ一切かぶらないことを実測する）

#### Safe Area は body が1回だけ確保する（重要）

`monster-hero/index.html` の `body` が `height:100dvh; box-sizing:border-box; padding-top:env(safe-area-inset-top); padding-bottom:env(safe-area-inset-bottom)` を持っており、
`#root` 以下はすべて**すでにSafe Areaの内側**にある。したがってプレイ画面側で `env(safe-area-inset-*)` を足し直してはいけない。

以前は `main[data-rhythm-tap-test]` が `paddingTop:env(safe-area-inset-top)` を、HUDがさらに `calc(env(safe-area-inset-top) + 6px)` を持っていたため、
ダイナミックアイランド世代のiPhone（`env(safe-area-inset-top)=59px`）で**上に59px×2＝118pxの空白**ができ、
プレイエリアの高さも上下で計93px（上59＋下34）失われていた。実機で「上のスペースが広いまま」と指摘されて発覚した。

`rhythm-screen-layout-check.js` がこの二重掛けを、`rhythm-hud-wedge-check.js` が実測でのプレイエリア高さ（`画面 − 上Safe − 下Safe − 下余白8px`）を固定している。

#### 経緯（2026-09-02、実機プレイで発覚した失敗と、その原因）

最初にこの配置を試したとき（PR #983）、HUDに**全幅の背景パネル**（`background: linear-gradient(...)`を`inset-x-0`の`<header>`全体へ）を敷いてしまい、台形の頂点そのものを覆っていた。実機で確認したところ、

- 見えている台形の始まりが実際より進んだ位置になり、**遠近感が変わってプレイしづらくなる**
- パネルの不透明な高さぶん、プレイエリアのDOM上の高さが増えても**実際に見える範囲は増えない**（覆っているだけ）

という2つの問題が出たため、いったん元の横帯レイアウト（`header shrink-0`）へ戻した（PR #984）。

その後、**HUDに背景パネルを持たせず、台形の外側の左右ウェッジだけに文字を置く**（中央の台形には何も置かない）形に作り直したところ、台形の頂点は一切覆われず、遠近感を変えずにプレイエリアの高さを実際に拡張できることを確認した（PR #986）。

**この失敗が教えてくれたこと**: `measureTravel`の`spawnY`／`judgmentY`の基準（`playAreaRef`の実際のDOM矩形）を拡張すること自体は問題ではない。問題になるのは、その拡張した範囲を**不透明な要素で覆ってしまう**ことだった。今後この種の配置を変える場合は、「プレイエリアのDOM高さが増えたか」だけでなく「台形の頂点を含む可視範囲が本当に不透明物に覆われていないか」を必ず実機（または`rhythm-hud-wedge-check.js`のような、要素の背景色を実際にサンプルする検査）で確認すること。

### 入力フィードバック

- 5メインレーン表示を保ったまま、projectionに沿う入力発光を使う

### 表示geometryの責務分担（現行仕様）

ノーツまわりの見た目は、次のように責務を分ける。ここを混ぜると、設定を変えた時だけレーンから
はみ出すといった不具合になる。

| 対象 | 基準 |
| --- | --- |
| ノーツの位置（親要素のleft / width / translate3d） | 共通projection |
| ノーツ頭の大きさ | ノーツサイズ設定（頭の`transform: scale`だけ） |
| HOLD帯・SLIDE帯 | レーンgeometry（プレイエリア幅の座標系＋projection） |
| ENDバー | レーンgeometry（終端レーンのprojection） |
| 入力hitbox・判定範囲 | ノーツサイズの影響を受けない |

ノーツサイズはプレイエリアのCSS変数 `--rhythm-note-size-scale` としてノーツ頭にだけ適用する。
親のノーツ要素へscaleを掛けると、子のHOLD帯・SLIDE帯・ENDバーまで一緒に拡大され、
帯が伸びた先の幅がclipPath / polygonの前提とズレる（速度が速いほど帯が長くなるため、
高速ほどズレが目立つ）。この形は採らない。

レーン枠・レーン境界線・サブレーン境界・サブレーン発光も、上端と下端の2点を直線で結ぶ台形にせず、
`rhythmProjectBoundary` を一定間隔（16分割）でサンプルした多点ポリゴンでノーツと同じ曲線へ沿わせる。
projectionは `pow(yRatio, 1.24)` の曲線なので、2点の直線近似では中間の高さで枠だけが
最大10px前後外側へ膨らむ。

**HOLD帯・SLIDE帯も同じ理由で多点にする。** 上端と下端だけを直線で結ぶと、

1. projectionが曲線であるぶん、途中の高さで帯がレーンから外れる
2. 帯が画面上端を越えて長いとき（＝高速時）、clipPathの0%は画面外のyを指すのに、幅は画面内へ
   クランプしたyで計算されるため、**可視範囲の全体が外側へ膨らむ**

という2つのズレが出る。2は速度が上がるほど帯が長くなるので、高速ほど大きくなる。実測では
速度10・HOLD幅1で中心が最大46.8px、幅が最大93.7pxずれていた。

対策として、HOLD帯は「帯の実際の上端（画面外でも可）から下端まで」を16分割し、SLIDEは
authored点の間を実時間で10分割して、それぞれ共通projectionへ沿わせる。HOLD帯は画面上端を
跨ぐときにその位置へも必ずサンプル点を置く（projectionの曲がりが一番きつい場所のため）。
この結果、ズレは中心0.49px・幅0.19px（SLIDEは中心0.61px・幅1.00px）まで下がる。

`node tools/mode/rhythm-note-geometry-audit.js` が、速度1／3／6／10／12 × サイズ80／100／120%の
全組み合わせでこの分担を実ブラウザ実測で検査する。

### ノーツ種別

| 種別 | 基本操作 |
| --- | --- |
| `TAP` | 判定ライン到達時にタップ |
| `HOLD` | 始点で押し、終端まで保持し、終端タイミングで離す |
| `FLICK` | 始点を押した後、一定距離以上を短時間でフリック |
| `SLIDE` | 始点で押し、指定経路を指で追従し、終端タイミングで離す |

1 authored note = 1最終判定を基本とし、HOLDやSLIDEの途中経過で判定数を増やさない。

#### 終点フリック（`endFlick`）

`HOLD` / `SLIDE` には `endFlick: true` を書ける。終端で「離す」代わりに「フリックして終わる」形になる。
**新しいノーツ種別ではなく HOLD / SLIDE への属性**なので、`endFlick` を書いていない既存ノーツの
挙動・判定・見た目はいっさい変わらない（`rhythm-end-flick-check.js` で機械的に固定している）。

- 受付は終端の `RHYTHM_END_FLICK_ARM_MS`（250ms）前から。受付へ入った瞬間の指の位置を基準にする
- 基準から `RHYTHM_FLICK_DISTANCE_PX`（24px。単発FLICKと同じ距離・方向指定なし）動けば成立
- 受付中は追従の外れ判定（`RHYTHM_MID_TRACKING_GRACE_MS` の経路・帯からのズレ）を止める。
  フリックすれば的から外れるのは当たり前のため。受付へ入る前は従来どおり外れたままならMISS
- 成立したら指を離すのを待たず、その時刻で終端判定を出す。判定窓（±`RHYTHM_RELEASE_MAX_MS`＝200ms）と
  `rhythmJudgeRelease`、開始判定との合成（悪いほうを採る）は既存のまま
- フリックしないまま離す／押しっぱなしで終端を過ぎる場合はMISS
- 見た目は終端バーを単発FLICKと同じ緑にし、同じ `⇧` を出す（「ここで弾く」を1つの記号に揃える）。
  `⇧` は終端バーの奥行き `scaleY` を逆数で打ち消して潰れないようにする。
  終端バーの色は `background-image` だけを上書きする（`background` のショートハンドは
  `background-clip` などを巻き添えでリセットするため使わない）
- `TAP` / `FLICK` に `endFlick` を書いても無視する。視覚エディタの不正配置チェックはこれをエラーにする

### END FLICK TEST

デバッグ専用曲「END FLICK TEST」で、終点フリックを実入力確認できる。

- EASY: HOLDの終点フリック（幅1〜4・左右端・最後は左右同時）
- NORMAL: SLIDEの終点フリック（動かしている指をそのまま弾いて終わる）
- HARD: TAP / FLICK と混在。SLIDEとHOLDの終点フリックが同時に来る場面を含む

どの難易度にも**終点フリックではないHOLD / SLIDE**を混ぜてあり、見分けが付くか・
従来どおり離すだけで取れるかを同じ譜面で確かめられる。END FLICK TESTは正式譜面や一般公開導線へ追加しない。

ノーツを取得できない位置へ指を新しく置いたときは、`noteSeEnabled` / `noteSeVolume` に従う短い空押しSEを1回鳴らす。ノーツを現在保持していない指を押したまま横へ動かした場合は、10サブレーンの境界を越えて別サブレーンへ入るたび、その現在座標と既存projection・判定時間・幅1余白で開始判定を1回行う。境界1回につき取得は最大1ノーツで、成功時は既存の成功SEだけ、対象がない時は空押しSEを鳴らす。同じサブレーン内では再判定せず、往復方向でも境界ごとに判定する。TAP取得後は次の境界で別TAPを取得できるが、HOLD / SLIDE / FLICKなどを操作中の指は別ノーツを取得しない。判定文字とFAST / SLOWは同時に表示し、新しい判定のたびに表示期限を更新して約450ms後に同時に消す。

### WIDTH TEST

デバッグ専用曲「WIDTH TEST」で、以下を実入力確認できる。

- EASY: 幅1〜4 TAP、左右端・中央の幅1、隣接幅1同時押し、ワイドTAP、幅1→2→3→4、指腹接触の複数TAP確認
- NORMAL: 幅1〜4 HOLD / FLICK、左右端、隣接同時、HOLD中別TAP、FLICK+別TAP等
- HARD: 0.5レーン刻みSLIDE、折り返し、SLIDE中別TAP
- EXPERT: 幅1〜4 SLIDE、幅4中別TAP、幅1 SLIDE同時操作
- MASTER: S字、ジグザグ、0.5レーン往復、幅1→4→1、多数point、複雑SLIDE中の別TAP/HOLD

WIDTH TESTは正式譜面や一般公開導線へ追加しない。

## 3.5. スコアランク（現行仕様・暫定値）

`RHYTHM_RANKS` / `rhythmRankForScore(score)` で、スコアから **G→F→E→D→C→B→A→S→SS→M**
の10段階ランク（Mが最上位）を算出する。プレイ中はSCOREの横に、リザルト画面には
大きなバッジで表示する。

**難易度ごとの割合(%)ではなく絶対スコアのしきい値で判定する。** %基準だと、EASYで100%を
出してもMASTERで100%を出しても同じ最上位ランクになってしまう。絶対値のしきい値にすることで、
EASYの最大スコア（60万点）はどれだけ極めてもBが上限になり、MASTERの満点(100万点)だけがMへ届く。

2026-09-04、ユーザー指示で各しきい値を1段ずつ上へずらした（＝同じ点数で付くランクは
1段ずつ下がる）。旧しきい値ではEXPERTの満点(90万点)もMに届いてしまい、
「MASTERの満点だけがM」という説明と実際の挙動が食い違っていたため、
EXPERTの満点はSSどまりにして、Mを名実ともにMASTERの満点専用にした。

| ランク | しきい値 | 到達する難易度満点の目安 |
| --- | ---: | --- |
| M | 1,000,000〜 | MASTER満点のみ |
| SS | 900,000〜 | EXPERT満点 |
| S | 800,000〜 | HARD満点 |
| A | 700,000〜 | NORMAL満点 |
| B | 600,000〜 | EASY満点 |
| C | 500,000〜 | — |
| D | 400,000〜 | — |
| E | 300,000〜 | — |
| F | 200,000〜 | — |
| G | 0〜 | — |

ランクはスコアからその場で計算するだけで、BESTの保存形式（`mh_rhythm_best_v1`）へは

## 5. HOLD / SLIDE の終端判定とENDバー（現行仕様）

### 終端判定

- HOLD / SLIDE は終端タイミングで指を離す必要がある
- 終端の離し判定も開始時と同じ ±25 / 50 / 100 / 150 / 200ms を使う
- ±200msを超えた離しはMISS
- 終端から+200msを超えて押しっぱなしでもMISS
- 最終判定は「始点判定」と「終端判定」の悪い方
- SLIDEは途中の経路追従に失敗した場合もMISS
- HOLD / SLIDEを±200msの終端判定幅内で正常に離した場合は、開始入力と同じ仮ノーツSEを1回鳴らす
- 途中追従失敗、±200ms外、touchcancel / pointercancel、FLICKの指離しでは終端SEを鳴らさない

### 失敗したHOLD / SLIDEの見せ方（現行仕様）

MISSになったHOLD / SLIDEは、その場で消さず**譜面上の終端時刻まで薄いグレーで流し続ける**。
いきなり消えると「取り損ねたのか、そもそも無かったのか」が分からないため。

- 対象はHOLD / SLIDEのMISSのみ。TAP / FLICKと、終端を過ぎたノーツは従来どおりその場で消す
- 表示だけの扱いで、判定・コンボ・スコア・BESTには関与しない
- 一度失敗したノーツは復活しない（`done` のまま）
- 判定範囲外へ出ても終端までは表示を続ける

`node tools/mode/rhythm-failed-hold-trail-check.js` で確認する。

### 途中追従判定（現行仕様・暫定値）

HOLD / SLIDEは、始点・終端だけでなく途中の追従も継続的に確認する。1つの入力(pointermove /
touchmove、および毎フレームの再評価)ごとに、その時刻の正しい位置にいるかを見る。

- **SLIDE**: 経路(`slidePoints`)からの横ズレが `rhythmSlideTrackingTolerance`（既存、幅に応じて可変）を
  超えているかを見る
- **HOLD**: 帯の中心からの横ズレが「帯の半分幅 + 0.15レーン（0.3サブレーン、暫定値）」を
  超えているかを見る。従来はHOLDに横ズレ判定が無く、始点さえ取れば指をどれだけ動かしても
  通ってしまっていた
- 外れた瞬間には確定させず、**猶予（暫定120ms）を超えて外れたままの場合だけ**MISSを確定する。
  iPhoneの指ブレで一瞬だけ外れても即失敗にしないための猶予。猶予内に許容範囲へ戻れば
  カウントをリセットする（チェックポイントごとに判定を積み上げるのではなく、常に「今は
  外れているか」を見る）
- 途中で失敗を確定した場合、**指を離すのを待たずその場でMISSにする**。既存の
  「`endTimeMs` 到達で確定判定を呼ぶ」経路(scheduleTick)をそのまま使い、新しい判定経路や
  追加スコアは作らない。1 authored note = 1 最終判定は維持する
- 失敗が確定した直後から、上のグレー表示（薄い半透明）に切り替わる

猶予・HOLDの横ズレ許容は暫定値。実機確認のうえで調整する。
`node tools/mode/rhythm-mid-tracking-check.js` で確認する。

例:

- 始点 MARVELOUS + 終端 GOOD → 最終 GOOD
- 始点 GREAT + 終端 MARVELOUS → 最終 GREAT
- 始点 MARVELOUS + 終端 MISS → 最終 MISS

### ライフ（現行仕様・暫定値）

モンスターノーツ（マスモンの「回復 / バリア / 丈夫さ」）は、ライフの数値が決まっていないと
設計できない。そのためまず**数値の管理と表示だけ**を固定した。

| 項目 | 暫定値 |
| --- | ---: |
| 最大ライフ（`RHYTHM_LIFE_MAX`） | 1,000 |
| 開始時 | 満タン（1,000） |
| MARVELOUS / EXCELLENT | +2 |
| GREAT | +1 |
| GOOD | ±0 |
| BAD | -20 |
| MISS | -50 |

- 0未満・最大超過にはならないよう常にクランプする
- HUDのSCORE / COMBOの下に、残量に応じて色が変わるバーと数値を表示する
- ライフが0になったrunは**不可逆のDOWN**となる。以降は成功判定や将来の回復効果があってもライフを0に固定する
- 0へ到達した判定までは通常どおりスコアへ含め、その判定終了時点のスコアを`lockedScore`として固定する。DOWN後も判定・判定表示・FAST/SLOW・コンボ・判定数は継続するが、スコアは増えない
- ライフ0でも曲を強制終了せず最後までプレイできる
- リザルトscore、スコアランク、BEST更新判定は再計算せず同じ固定スコアを使う。保存形式と保存キー（`mh_rhythm_best_v1`）は変更しない

満タンからMISS 20回で0になる計算。EASYの78ノーツを基準に置いた暫定値であり、
**難易度ごとの調整はまだしていない**（MASTERのような高密度譜面では別の値が要る想定）。

未確定:

- DOWN状態のリザルト上の追加表示
- 難易度別のライフ最大値・減少量
- HOLD / SLIDEの途中失敗を、MISSと同じ減少量にするか

`node tools/mode/rhythm-life-check.js` で確認する。

### ENDバー

- HOLD / SLIDEの終端には、離すタイミングを示す専用ENDバーを表示する
- ENDバーが判定ラインへ到達したタイミングで指を離す
- 表示専用で、入力を遮らない
- runtimeが一時的に変更する `endTimeMs` ではなく、譜面本来の終端時刻を正本として位置を計算する
- HOLDはそのノーツの終端レーン、SLIDEは `slidePoints` の最終位置を優先して終端レーンを決める
- SLIDE終端が0.5レーン位置でも、その連続座標を保ったままENDバーを投影する
- 可変幅SLIDEのENDバーは最終 `slidePoints` の実効幅で投影する
- レーン・ノーツ・帯と同じprojection座標系で描画する

## 5.5 指の持ち替え（現行仕様・2026-09-05）

HOLD / SLIDE を押さえている途中で、別の指へ持ち替えられる。

- 途中で指を離しても、その場では失敗にしない。`note.releasedAtMs` に離した時刻を持たせ、
  「浮いている」状態として取っておく（`activePointerId` は null に戻すので、入力の候補には入る）
- `RHYTHM_HOLD_HANDOVER_GRACE_MS`（120ms）のあいだに同じノーツへ指が置かれたら、そのまま続きへ戻す。
  始点の判定（`holdJudgment` / `holdDeltaMs`）は最初に押さえたときのものを保つので、
  持ち替えで良くも悪くもならない
- 猶予を過ぎても戻ってこなければ、そこで MISS。ずれは「離した時刻」で測る（気づいた時刻ではない）
- 浮いているあいだに終端まで来た場合は、これまでどおり成立させる（終わり際に離すぶんは元から許している）
- 終わり際の猶予 `RHYTHM_HOLD_RELEASE_GRACE_MS`（100ms）とは別の定数にしてある。
  混ぜると「終わりに離す」と「途中で持ち替える」が同じ扱いになってしまう

`node tools/mode/rhythm-hold-handover-check.js` で見張る。

## 7. FLICK / SLIDE（現行仕様）

### FLICK

- 方向指定なし
- 24px以上の明確な移動を検出
- 450ms以内
- `subLane`（0〜9）と `subLaneWidth`（1〜10）で開始位置と幅を指定できる
- 開始ノーツの描画と開始入力はTAP/HOLDと同じ10サブレーンprojectionを使う
- 幅1のみサブレーン0.18ぶんの入力余白を使う
- `subLane` 未指定の旧FLICKは従来のメインレーン幅2相当を維持する

### SLIDE

- `slidePoints` を時間補間して期待レーンを算出する
- authoredの始点・中継点・終点は0.5レーン刻みで指定できる
- authored点間の時間補間値は連続値のまま描画と追従判定へ使う
- `subLaneWidth` で1〜10のデフォルト幅を指定でき、未指定は幅2として旧仕様を維持する
- `slidePoints[].subLaneWidth` で各pointの幅1〜10を指定できる
- 実効幅は `point.subLaneWidth` → `note.subLaneWidth` → `2`
- point間は位置と同じ時間比率で連続補間する
- `lane` / `slidePoints[].lane` はSLIDE中心線。**ただし太いSLIDEが端のレーンを通るときは、
  幅を変えずに中心線を内側へ寄せてレーンへ収める**（`rhythmSlideFittedLane`）。
  中心線のまわりへ幅を広げるだけだと、幅5をレーン0で通したときにプレイエリア幅の15%ぶん
  レーンの外へ帯が出る（実機で「スライドがレーンからはみ出て表示される場面がある」と報告・2026-09-05）。
  TAP/HOLDは `rhythmProjectSubLaneRange` が左端を収まる位置へ寄せていたのに、SLIDEだけ寄せていなかった。
  **寄せは見た目・入力の受け付け・途中追従の的の3つすべてを通る**ので、3つとも同じだけ動きずれない。
  幅2（既存の正式候補v1が使う唯一の幅）はレーン0〜4がそのまま収まるので**何も動かない**
- 始点の入力範囲と開始ノーツは開始時刻、操作中の頭と残り経路SVGは現在時刻、ENDバーは最終pointの実効幅へ合わせる
- 途中追従の中心は `rhythmSlideExpectedLane()` を使い、許容幅は現在時刻の補間幅に合わせる
- 幅2は従来の±0.82レーンを維持する
- 1本の指で経路を追従する
- 途中追従で追加スコア・追加判定を発生させない
- 終端では現在の終端リリース判定を使う

## 8.5 モンスターノーツ（第1弾実装済み・2026-09-03）

設定したマスモンをプレイ内容へ参加させる仕組み。詳細は
[`RHYTHM_FUTURE_IMPLEMENTATION_PLAN.md`](RHYTHM_FUTURE_IMPLEMENTATION_PLAN.md) §3〜§4。

譜面には **通常のTAPノーツへ `monsterSlot:1〜4` を1行足すだけ** で書く。

```js
{ type:'TAP', timeMs:8000, lane:2, subLane:4, subLaneWidth:2, monsterSlot:1 }
```

- `monsterSlot` はマスモン設定の何枠目か。1枠目→1個目、2枠目→2個目…と対応する
- 初期実装は **TAP専用**。HOLD / FLICK / SLIDE には付かない
- 判定・描画・幅の計算は通常ノーツの経路をそのまま通る。**判定窓は専用に甘くしない**
- 能力発動は **GREAT以上**。GOOD / BAD / MISS では不発
- 能力は **主血統** で決まる（元気 / 無敵 / 我慢 / 根性）
- 無敵（6秒）と我慢（15秒）は **別の能力としてそれぞれの残り時間で独立して走る**。
  両方有効なあいだは強いほう（無敵）が勝ち、無敵が切れたらそこから我慢の軽減へ変わる。
  逆に我慢が先に切れた場合は、無敵が残っているあいだダメージ0のまま
- ノーツ上のマスモンは枠・背景なしの染色済み透過画像だけを中央へ表示し、能力発動時はモンスター名を付けず「元気！」等の能力名だけを表示する
- DOWNから復帰できるのは根性だけ。DOWN中に根性をGREAT以上で取ると、その場でライフ50へ復活し、
  **その蘇生ノーツ自身は加算せず、次のノーツからスコア加算を再開する**

確認用に `monster_note_test`（MONSTER NOTE TEST・EASY・約40秒）を用意している。
既存の譜面は触っていない。

## 9. 保存キーとBEST（現行仕様）

保存キー:

- 設定: `mh_rhythm_settings_v1`
- BEST: `mh_rhythm_best_v1`
- モンスターノーツ用のマスモン設定: `mh_rhythm_monsters_v1`

これらを勝手に改名・削除・意味変更しない。

`mh_rhythm_monsters_v1` は **マスモンの個体IDの並び（文字列の配列・最大4件）だけ** を持つ。
名前・染色・能力はマスモン本体（`mh_masu_mons`）から毎回引き直す。音ゲー側へ複製すると
育成や染色の変更に追従できなくなるため、複製しない。

読み込み・保存時に行うのは **形の正規化だけ**（配列でなければ空、重複ID除去、4件で打ち切り）で、
「そのマスモンを今も持っているか」は見ない。マスモン一覧を読む前に存在確認まで行うと、
設定が空として保存し直されてプレイヤーの設定が消えるため。手放したマスモンと
同一ベースモンスターの重複は、**使うときだけ**（`resolveRhythmMonsterSlots`）落とす。

曲×難易度ごとにBESTを保存する。

保持対象:

- `bestScore`
- `maxCombo`
- `clear`
- `fullCombo`
- `allExcellent`
- `allMarvelous`
- 各判定数

欠損値・旧データ・不正値は読み込み時に正規化する。

現行ノーツSE設定は `noteSeEnabled` / `noteSeVolume` を同じ設定キー内で扱う。

## 9.5 全国ランキング「モンビー」（先行実装・2026-09-04）

§18では「正式音ゲー完成まで実装を待ち、Supabase実装を先行しない」としていたが、
ユーザーから「先行公開時にも全国ランキングがほしい」と明示の指示があり、既存の
`rankings`テーブル・列を一切増やさない範囲で先行実装した。詳しい経緯・据え置いた論点は
§18を参照。

### 保存の仕組み（新テーブル・新列なし）

種族チャレンジ(`Species-<血統>-<難易度>`)と同じ考え方で、`rankings`テーブルの
`difficulty`列へ次の専用キーを入れるだけで区別する。

```
Rhythm-<songId>-<難易度id>   例: Rhythm-monster_hero_theme_candidate-HARD
```

(`data/rhythm-mode.js` の `rhythmRankingDifficultyKey` / `parseRhythmRankingDifficultyKey`)

- 書き込みは1プレイ＝1行のまま(既存の`clear_id`による重複防止をそのまま利用)。
- `normalizeRankingDifficulty` / `sbInsertScore` / `sbFetchRankings` は通常バトル・プロ・
  極限・種族チャレンジの固定パターンしか認めておらず、そこへ`Rhythm-...`キーを通すと
  例外になる。**この共通の検証・全モードが経由する経路には一切手を入れず**、
  モンビー専用の`sbInsertRhythmScore` / `sbFetchRhythmRankings`を別に用意した
  (`src/game-system.jsx`)。既存モードのランキング送受信は無関係のまま。

### 難易度合算方式

体験版で遊べる難易度(EASY/NORMAL/HARD、`RHYTHM_DEMO_DIFFICULTY_IDS`)のキーを
`rhythmRankingCombinedMembers(songId)`でまとめて`in.(...)`取得し、1つのランキングとして
表示する。難易度ごとに満点が違う(§3・§3.5)ため、高い難易度で挑むほど上位に近づく
（RHYTHM_MODE.mdの§3で以前から想定していた「将来の難易度混合スコアランキングでも
最大スコア差がそのまま意味を持つ」という設計どおり）。EXPERT/MASTERを体験版へ
追加したときは`RHYTHM_DEMO_DIFFICULTY_IDS`を増やすだけで、合算ランキングにも
自動的に加わる。

### 自分のスコアは1件のみ

書き込みは1プレイ＝1行のまま増え続けるが、**表示のときにユーザー名ごとの最高得点だけへ
畳む**(`rhythmRankingDedupeByUser`、既存の`aggregateBreederLevels`と同じ考え方)。
過去の低いスコアの行を消したり上書きしたりする必要がなく、常に1人1件だけが画面へ出る。

### 詳細ボタン

一覧の各行に「詳細」ボタンを付け、判定内訳(MARVELOUS〜MISSの数)・最大コンボ・
達成した称号(フルコンボ等)を表示する。新しい列は増やさず、既存の`party`列
(種族チャレンジでは育て方の詳細に使っている列)へこの詳細をJSONで持たせている。

### 送信対象

体験版ホームから始めたプレイ(`rhythmPlay.from==='demo'`)だけを送信する。デバッグ画面の
「音ゲーデバッグ」から始めたプレイは送信しない(通常バトルの`debugBattleRef`ガードと
同じ考え方)。送信に失敗しても既存のBEST記録(`mh_rhythm_best_v1`)には影響しない。
失敗した記録だけ、新規キー`mh_rhythm_rank_pending_v1`(直近20件まで)へ退避する
(自動の再送はしない。復旧の手がかりとして残すだけ)。

### 識別・不正対策の水準(既存モードと同じ)

ユーザーの識別はブリーダー名ベースで、アカウントIDのような厳密な本人確認はない。
送信はクライアントから直接Supabaseへ行い、サーバー側でスコアを検証する仕組みは無い。
これは通常バトル・プロ・極限・種族チャレンジのランキングと同じ水準であり、
モンビーだけ特別に緩めたり厳しくしたりはしていない。

### 音ゲーデバッグ画面のタブ構成（現行仕様）

デバッグ画面は、設定ダンプ・曲一覧・譜面エディタ・実機タイミング補正・視覚エディタ・レビューUIを
すべて1本のスクロールへ積んでいたため、入った瞬間に何がどこにあるか分からない状態になっていた。
現在は固定ヘッダーの下に3つのタブを置き、本文スクロールは1つだけにする。

| タブ | 内容 |
| --- | --- |
| ▶ プレイ | 曲・難易度の一覧とテストプレイ（**入場時は必ずここから始まる**） |
| 🎼 譜面制作 | 譜面エディタ一式（実機タイミング補正・視覚エディタ・レビューUIもこの中） |
| ⚙️ 設定・記録 | 座標校正トグルと、保存中の設定の一覧 |

譜面制作UIは**一度もタブを開いていない間は生成しない**（初回入場を軽くし、ごちゃつきを避けるため）。
一度開いた後はDOMを残して表示だけ切り替える。エディタの編集中ドラフトはmount時のクロージャが持つので、

### 譜面候補の作り方（3難易度共通）

`tools/mode/rhythm-monster-hero-chart-build.js` が、実音源のオンセット候補から**決定的に**組み立てる。
乱数を使わないので、同じ入力からは必ず同じ譜面になる。方針を変えるときは譜面を手で書き換えず、
ツールの `PROFILES` を直して作り直す。

候補ファイルは2つある。どちらも同じ音源・同じグリッドで、拾う音の強さのしきい値だけが違う。

| ファイル | しきい値 | 候補数 | 使う難易度 |
| --- | --- | --- | --- |
| `monster-hero-theme-onset-candidates.json` | 0.60 | 372 | EASY |
| `monster-hero-theme-onset-candidates-dense.json` | 0.30 | 604 | NORMAL / HARD |

EASYはすでにレビューへ出しているため、候補ファイルも強さの下限も動かさない。
NORMAL / HARD は刻みやゴーストノートまで拾ったdense側から、それぞれの強さで絞る。

共通の決まり:

- 採用するのは実音源ピークとの差が**±30ms以内**のものだけ（あつ杯テーマ正式候補v1と同じ基準）
- ±30msを超え42ms以内は削除確定ではなく `earReviewGrids` として保留
- 小節（16グリッド）ごとに、その小節の強さに応じた本数だけ選ぶ
- HOLDは曲全体へ等間隔で散らす（先頭から詰めると前半へ固まるため）
- モンスターノーツは4体ぶんを 20 / 40 / 60 / 80% 付近へ、前後を1拍以上空けて置く
- 曲の頭1.8秒と終わり1.2秒は空ける

### 遊んでいるうちに重くなる問題の修正（2026-09-03）

「まだやってるとカクつきが少し気になる」という指摘の原因は、**毎フレームの無駄なDOM書き込み**だった。

- 終わったノーツへ毎フレーム `display:none` を書き直していた（曲が進むほど積み上がる）
- まだ見えないノーツへ毎フレーム `opacity` を書き直していた

どちらも**値が変わるときだけ書く**ようにした（`el._rhythmHidden` / `el._rhythmOpacity` を持たせる）。

それでもカクつきが残るという指摘があり、さらに次の2つを直した。

- **`measureTravel` が毎フレーム `getBoundingClientRect` を3回**呼んでいた。
  直前のフレームで数百個のノーツへ書き込んだスタイルを、毎フレーム強制的に計算し直させていたことになる。
  プレイエリア・判定ライン・ノーツの箱の大きさは**画面が回転・リサイズされない限り変わらない**
  （ノーツは `absolute` の固定高さ `h-5` で、奥行きの拡大は子要素の `transform` なので外側の高さに響かない）ため、
  測った結果を `travelCacheRef` に覚え、`resize` / `orientationchange` と設定変更のときだけ捨てる。
  組み上がる前（高さ0）の値は覚えない
- **能力バッジの文字列を毎フレーム組み立てていた**。曲の大半は何も出ていないので、
  無敵・我慢・根性のどれも動いていないあいだは組み立て自体を行わない

見た目・判定・スコア・落下速度は一切変えていない。

実ブラウザで測った1フレームあたりの走査コスト:

| 条件 | 修正前 | 修正後 | 削減 |
| --- | --- | --- | --- |
| 266ノーツ / 終了30% | 0.142ms | 0.050ms | 65% |
| 266ノーツ / 終了90% | 0.105ms | 0.007ms | **93%** |
| 600ノーツ / 終了90% | 0.244ms | 0.020ms | 92% |

曲の終盤ほど効くため、「遊んでいるうちに重くなる」症状に直接効く。

毎フレームの強制レイアウトをやめた効果（ノーツ数は譜面の実数に合わせた）:

| ノーツ数 | 毎フレーム測る | 覚えておく | 削減 |
| --- | --- | --- | --- |
| 176（EASY） | 0.358ms | 0.091ms | 75% |
| 266（HARD） | 0.347ms | 0.087ms | 75% |
| 400 | 0.395ms | 0.087ms | 78% |

強制レイアウトはiPhone Safariのほうが重いため、実機での効果はこれより大きいと見込まれる。

### タップのたびのカクつき（2026-09-04・実機報告から修正）

上記はいずれも「**毎フレーム**の負荷」を減らすもので、実際に効いていた。しかしそれでも
「**ノーツを押したとき**にカクつく」という報告が残った。この「押したとき」という手がかりから
入力〜判定の経路を読み直したところ、フレーム単位ではなく**タップ1回あたり**の負荷に
はっきりした原因が見つかった。

- `applyJudgment` はノーツを判定するたびに `setView` を呼ぶ（スコア・コンボ・判定表示の更新）
- ところが譜面のノーツは `chart.notes.map(...)` として**描画関数の中に直接書かれていた**
- そのため、ノーツを1つ叩くたびに全ノーツ（最大300要素、子要素込みで1000要素以上）を
  Reactが作り直し、`ref={el=>laneRefs.current[index]=el}` も毎回付け直していた
- つまり「**タップ1回 = 譜面まるごと再構築**」になっていた

修正（判定窓・スコア計算・落下時間・保存形式は一切変更していない）:

| 直したもの | 変更前 | 変更後 |
| --- | --- | --- |
| ノーツのDOM | 判定のたびに全ノーツを再生成 | `useMemo` で固定（譜面・マスモン・軽量モード・演出量が変わったときだけ作り直す） |
| レーン枠・サブレーン境界・サブレーン発光 | 同上 | `useMemo` で固定（発光のON/OFFは元々DOMへ直接書いているのでReactの再生成は不要） |
| 入力時の `getBoundingClientRect()` | touchstart / touchmove のたびに実行（＝指の数ぶん強制レイアウト） | FLICK/SLIDE側が既に使っていた「1フレームに1回だけ測る」キャッシュを共有 |
| サブレーン発光の書き込み | 毎回 `querySelectorAll` で10要素を引き直し、押していない所まで書き込み | 要素を覚えておき、状態が変わったサブレーンだけ書き換え |

回帰防止として `tools/mode/rhythm-perf-check.js` へ4項目を追加した（ノーツDOMを毎回作り直さない／
レーンのDOMも作り直さない／入力のrect取得はキャッシュを共有する／発光は変わった所だけ書く）。

### 指を触れていない降下中のカクつき（2026-09-04・調査と対策）

「タップした瞬間だけでなく、指を触れていない通常のノーツ降下中にもカクつく」という報告を受けて、
入力経路ではなくメインrAF（`scheduleTick`の`tick`）を中心に調べ直した。

**計測で分かったこと**

| 調べたこと | 結果 | 判断 |
| --- | --- | --- |
| 1フレームで走査するノーツ数 | HARDで266、うち実際に描画更新が要るのは**約5** | 53倍の無駄はあるが… |
| その走査コスト（実ブラウザ・266ノーツ） | 中央16.70ms（＝60fps維持）、シナリオ間で有意差なし | **走査自体は主因ではない**（PCでは） |
| `songTimeMs()`の実装 | `AudioContext.currentTime`基準で単調・連続 | **正常。変更しない** |
| ノーツ要素の`will-change` | JSXで**全266ノーツへ出しっぱなし** | 有力候補 |

**`will-change`の出しっぱなしについて**

ノーツのJSXは`willChange:'transform, opacity'`を持っていた。`will-change`は指定された時点で
その要素を合成レイヤーの対象にするため、**まだ出てこないノーツ・画面外のノーツまで含めた
全266要素が常にレイヤー候補**になっていた。GPUメモリが限られるiPhoneでは、
レイヤーの確保・解放や再ラスタライズが単発の引っかかりを生む典型的な原因になる。

実ブラウザで数えた結果:

| | `will-change`が有効な要素 |
| --- | ---: |
| 修正前（全ノーツへ出しっぱなし） | **266 / 266** |
| 修正後（今動いているノーツだけ） | **5 / 266** |

**修正内容**（判定窓・スコア・落下時間・譜面・入力仕様は変更なし）

- `will-change`をJSXから外し、tickの中で「今見えているノーツ」だけへ付け外しする
  （値が変わったときだけ書くので、付け外し自体は1ノーツにつき2回）
- 失敗表示フラグを毎フレーム`el.dataset.rhythmFailed`から読み直していたのをやめ、
  要素へ覚えた値と比べる（書き込む条件は従来と同じ）
- `RHYTHM_PERF`へ「走査ノーツ/frame」「実描画ノーツ/frame」「最悪frameの走査/実描画」を追加
  （既定OFF・計測用rAFは増やさない。長いフレームで何が増えたかを実機で切り分けるため）

**実機の性能計測（iPhone・HARD・8198フレーム、`will-change`修正の適用前）**

| 項目 | 値 | 読み方 |
| --- | ---: | --- |
| 平均fps | 53.7 | 60fpsを維持できていない |
| 平均フレーム | **18.6ms** | 予算16.7msを**常時わずかに超過** |
| 16.7ms超 | **5188 / 8198（63%）** | 大半のフレームが予算超過 |
| 25ms超 / 33ms超 | 616 / 375 | 単発の大きな引っかかりもある |
| 最悪フレーム | 225.0ms | |
| レイアウト測定/frame | 0.16 | 既存対策が効いている（低い） |
| DOM検索/frame | 0.10 | 同上 |
| SLIDE帯更新/frame | 1.57 | |
| ジェスチャーrAF | 839 | 全体の約10%。無入力時の主因ではない |

**「平均18.6ms」＝毎フレームの固定コストが予算を超えている**状態であり、単発の重い処理ではなく
定常的な負荷が主だと分かった。PCの実ブラウザでは走査コストの差が出なかったが、
実機は予算ぎりぎりで動いているため、**1フレームあたりの固定コスト削減がそのまま効く**。

### ノーツ走査を必要な範囲だけに絞る（2026-09-04）

上の計測を受けて、メインrAFの走査範囲を絞った。HARDでは毎フレーム266ノーツを見ていたが、
実際に描画更新が要るのは**約5ノーツ**だった。

絞り込みの規則（どれも取りこぼしが起きない側に倒してある）:

- **先頭**: 「終わっていて、かつ非表示にし終えた」ノーツまで進める。
  失敗して流し続けているノーツはまだ非表示ではないのでここで止まり、取りこぼさない。
  時刻は戻らないので、一度隠したノーツが復活することもない
- **末尾**: `visualTime + travelMs*1.2` を超えるノーツで打ち切る。
  自動MISSもHOLD終端も「すでに来ているノーツ」に対する処理なので影響しない
- **初回フレームだけ**は全ノーツを一巡し、初期の表示状態（非表示）を作ってから絞り込む

曲全体を60fpsで最後まで回して「全走査」と「絞り込み走査」を突き合わせた結果
（`tools/mode/rhythm-note-scan-window-check.js`）:

| | 1フレームの走査ノーツ数 | 判定されたノーツ | 判定時刻のズレ |
| --- | ---: | ---: | ---: |
| 全走査（従来） | 平均 266.0 | 266 / 266 | — |
| 絞り込み（現行） | **平均 4.8（98.2%減）** | 266 / 266 | **0ms** |

判定内容・判定時刻・表示対象は従来と**完全に一致**する。突然消える・出現が遅れる・
MISSが出なくなる、といった副作用が起きていないことを毎回この検査で確かめる。

**まだ確定していないこと**: `will-change`と走査絞り込みの効果は、実機で測り直すまで確定しない。
次は同じ条件で性能計測を取り直し、`平均フレーム` / `16.7ms超` / 追加した`走査ノーツ/frame`を比べる。

この修正を入れたビルド（`BUILD_DATE = 2026-09-04 12:10`）で撮った39秒の実機録画（HARD / 30fps）を
解析したところ、**カクつきは減ったが無くなってはいない**ことが分かった。判定ライン手前の帯だけを
見て「前後は動いているのにそのフレームだけ絵が変わらない」ものを数えると、925フレーム中20件（2.2%）。
**すべて単発（約33ms）で、2フレーム以上続く停止は0件**だった。

ただし30fpsの録画では**16.7ms〜33msのフレーム（60fpsから30〜60fpsへ落ちた状態）は原理的に見えない**。
体感のカクつきの大半はこの範囲にある可能性が高いため、次はアプリ内蔵の性能計測
（音ゲーデバッグ画面の設定タブ、`16.7ms超` / `25ms超` / `33ms超` / `平均fps` / `最悪フレーム`）で確認する。
詳細な経緯は`docs/spec/RHYTHM_ROADMAP.md`「1-K」を参照。

### 100コンボ演出のバグ修正・ランクゲージ・フルコンボ演出（2026-09-04）

実機フィードバック3件を反映した。検査は `rhythm-presentation-check.js`（拡張）、
`rhythm-rank-check.js`（拡張）、新設の `rhythm-fullcombo-celebrate-check.js`（27項目）。

#### 100コンボ演出が最初の100でしか出ないバグ

「100コンボ表示が100でしか出ない」という指摘の原因は、演出の `useEffect` の依存に
`view.combo`（ノーツを取るたび毎回変わる値）を使っていたことだった。

- 100→101のような**節目でない**増加でも毎回effectが再実行される
- 前回の実行が仕掛けた「1.1秒後にコンボ演出を消す」`setTimeout` を、その再実行の
  cleanupが**節目と無関係に毎回解除**してしまう
- 結果、最初の100の表示だけが `opacity:0` のまま固まって二度と動かず、
  200・300では何も起きないように見えていた

修正は、依存を「100の位（tier）が変わったときだけ」動く `comboMilestoneTier`
（`Math.floor(combo/100)`）だけにすること。tierは実際に100の位が変わったときにしか
変化しないため、非節目の増加ではeffectが再実行されず、タイマーは正しく1.1秒後まで生き残る。

あわせて「どんどん派手になる」という要望に応え、`comboMilestoneStage`
（`Math.min(5,tier)`、100〜500以上を1〜5段階に丸めたもの）を追加した。

| 段階 | コンボ | 見た目 |
| --- | --- | --- |
| 1 | 100 | 金色のグラデーション文字 |
| 2 | 200 | よりオレンジに寄せて発光を強める |
| 3 | 300 | 白熱色にして、外周へ広がるリングを1本追加 |
| 4 | 400 | リングをもう1本重ねる |
| 5 | 500以上 | 文字を虹色に流す（頭打ち。以降は同じ見た目） |

#### スコアランクのゲージ表示

丸バッジ横にあった単色の進捗バー（`rhythmRankProgress`）を、目盛り付きの
「ランクゲージ」に見せるよう変更した。

- ランクは難易度によって届く段数が違う（EASYは6段、MASTERは10段）ため、目盛りの数は
  難易度に合わせず一定（4等分）にしている。目盛りは `[data-rhythm-rank-gauge]` への
  `background-image`（純粋な飾り）で、判定・進捗の計算には一切関与しない
- バーの伸び自体は既存の `rhythmRankProgress` のまま変えていない
- 新設の `rhythmNextRankId(score, maxScore)` で「1つ上のランク」を求め、バーの右に
  `→S` のように小さく添える。最上位(M)なら `★MAX`
- マイナスや壊れた値は `rhythmRankForScore` と同じくG扱いにフォールバックする
  （`findIndex` が -1 を返すケースを、既存関数と揃えて明示的に処理する）

バー幅を `w-20` → `w-14` に縮め、ラベル分の増加分を吸収することで、
`rhythm-hud-wedge-check.js`（320×568含む4サイズ）のHUD幅超過を避けている。

##### 難易度の満点を超える次ランクを出さない修正（STEP 0・2026-09-04）

公開直後、Codexレビューで「EASY満点60万点=Aが上限なのに `→S` と表示される」
（NORMAL / HARDでも同様に、その難易度では絶対に届かない次ランクが出る）指摘があった。

`RHYTHM_RANKS` のしきい値（G〜M）は難易度を跨いだ共通の絶対値で、`rhythmNextRankId`は
単純にスコアの1つ上のランクを返すだけだったため、EASYで満点(600,000点)に達しても、
本来EASYでは絶対に届かないはずのS(700,000点)を「次はここまで」として案内してしまっていた。

`rhythmNextRankId(score, maxScore)` に**第2引数**として現在の難易度の満点
（`RHYTHM_DIFFICULTIES`の`maxScore`、呼び出し側は `difficulty.maxScore` を渡す）を追加し、
次ランクのしきい値がその満点を超える場合は「次は無い(`★MAX`)」を返すよう修正した。
`RHYTHM_RANKS`・`rhythmRankForScore`・`rhythmRankProgress`の判定・しきい値そのものは
一切変更していない（表示だけに追加した上限ガード）。`maxScore`を渡さない・0以下・
壊れた値のときは今までどおり上限なし（既存呼び出しとの互換を維持）。

| 難易度 | 満点 | 満点時のランク | 満点到達時の次ランク表示 |
| --- | --- | --- | --- |
| EASY | 600,000 | A | `★MAX`（旧: 誤って`→S`） |
| NORMAL | 700,000 | S | `★MAX`（旧: 誤って`→SS`） |
| HARD | 800,000 | SS | `★MAX`（旧: 誤って`→M`） |
| EXPERT | 900,000 | M | `★MAX` |
| MASTER | 1,000,000 | M | `★MAX` |

※上の「満点時のランク」列は、このSTEP 0修正を行った時点の`RHYTHM_RANKS`（EASY→A / NORMAL→S /
HARD→SS / EXPERT→M）での結果。この直後にユーザー指示でランクのしきい値自体を1段ずつ
ずらしたため、現在の実際の対応は「3.5. スコアランク」の表（EASY→B / NORMAL→A / HARD→S /
EXPERT→SS / MASTER→M）を参照。`★MAX`が出る仕組み（`rhythmNextRankId`の`maxScore`引数）
自体はここに書いたとおりで変わっていない。

#### 曲を終えたあとの「FULL COMBO!」演出

「フルコンボの場合リザルトに行く前に掛け声が出る感じにしたい」という要望に対応した。
**本物の音声ファイルは用意していない**ため、大きな文字のスラムイン演出と、
Web Audioで合成した上昇アルペジオの効果音で代えている。

- `finish()` は既存の `rhythmResultAchievements` の結果（`fullCombo` / `allExcellent`
  / `allMarvelous`、リザルト画面の表示と共通・二重定義しない）を見て、達成があれば
  `view.status` を `'result'` の前に **`'celebrate'`** へ進める
- `celebrate` は独立した全画面（`data-rhythm-celebrate`）。称号を大きく表示し、
  `RHYTHM_NOTE_SE_RUNTIME.playFullCombo()`（E5→G5→B5→E6の上昇アルペジオ、
  既存のタップ音と同じ設定・AudioContextを使い回す）を1回鳴らし、1.3秒後に
  自動で `'result'` へ進む。タップでも即座に進める
- 演出量MINIMAL・軽量モードでは `celebrate` を経由せず、従来どおり直接 `'result'` へ進む
  （リザルト画面自体の称号表示 `data-rhythm-result-celebrate` は設定に関わらず出る）
- `celebrate` 中はプレイ画面のタッチ入力を受け付けない（`'result'` と同じ扱い）
- 保存キーは増やしていない。`onComplete(result,merged)` は演出の有無に関わらず必ず1回呼ぶ

celebrate画面の効果音・タイマーeffectは、100コンボ演出で踏んだのと同じ罠を避けるため、
依存を `view.status` だけにしてある（毎ノーツ変わる値を混ぜない）。

## 14A. 自動譜面制作システム V2（確定・STEP1〜8実装済み）

### 目的

今後の正式譜面制作は、**人が譜面を手直しすることを前提にしない**。

目標は、楽曲ファイルを入力すると、

1. 楽曲解析
2. 楽曲構造マップ作成
3. EASY / NORMAL / HARD / EXPERT / MASTER の5難易度生成
4. 複数候補の自動比較
5. 譜面品質の自動評価
6. 問題区間の自動修正
7. 自動プレイ可能性検査
8. 品質ゲート再評価
9. 合格譜面を正式候補として出力

までを自動で完結させる **AI主体の譜面制作パイプライン** を作ること。

「AIが下書きを作り、人が最後に直す」方式を完成形にはしない。  
人による実プレイ確認は品質改善のために行ってよいが、**正式譜面を作るための必須制作工程にはしない**。

### 現行V1との関係

既存の以下は捨てずに再利用する。

- `rhythm-audio-timing-analyze.js` の実音源解析
- BPM / beatZero / 16分グリッド
- onset候補と `sourceStrength` / `sourcePeakOffsetMs`
- `rhythm-monster-hero-chart-build.js` の難易度別生成ルール
- 10サブレーン
- TAP / HOLD / FLICK / SLIDE
- 幅1〜4
- 視覚譜面エディタ
- 区間ループ
- 不正配置チェック
- 実プレイプレビュー

V2はこれらの前段・生成段・評価段を拡張する。  
既存正式候補JSONや現行譜面を無断で再生成して差し替えない。

### V2の全体パイプライン

```text
音源
 ↓
A. タイミング解析
 ↓
B. 音楽特徴解析
 ↓
C. 楽曲構造マップ
 ↓
D. 難易度別譜面生成
 ↓
E. 複数候補生成
 ↓
F. 譜面批評・品質評価
 ↓
G. 自動プレイ可能性検査
 ↓
H. 問題区間だけ自動修正
 ↓
I. 再評価
 ↓
品質ゲート合格
 ↓
正式候補出力
```

一度の生成結果をそのまま完成扱いにせず、**生成 → 評価 → 修正 → 再評価** を基本ループとする。

### A. タイミング解析

現行のBPM / beatZero / onset解析を維持しつつ、次を扱う。

- BPM
- beatZero
- 拍位置
- 16分グリッド
- 小節頭 / ダウンビート
- テンポ変化候補
- onset位置
- onset強度
- 実音源ピークとグリッドとの差
- 各解析値のconfidence

単に拍へスナップするだけでなく、**小節の1拍目がどこか**を譜面生成へ渡す。

テンポ変化がある楽曲では単一BPMを無理に全尺へ適用せず、テンポマップ方式を選択できる設計にする。

### B. 音楽特徴解析

時間軸上で最低限、以下の特徴量を持つ。

- RMS等によるエネルギー
- onset密度
- 低域 / 中域 / 高域のエネルギー
- 各帯域の瞬間的な立ち上がり
- スペクトルの広がり・明るさ等の変化
- 長く持続する音の候補
- 強いアクセント / キメ候補
- リズムパターン
- フレーズ類似度
- 直前区間からの変化量
- 盛り上がり度 `intensity 0.0〜1.0`
- 各判定のconfidence

低域が強いから必ずキック、というような単純な楽器断定はしない。  
「低域の瞬間アタックが強い」「高域の細かい反復がある」等の**譜面生成に必要な特徴**として扱う。

### C. 楽曲構造マップ

楽曲を固定ラベルだけで無理に分類せず、解析結果から区間ごとに役割を持たせる。

候補ラベル:

- INTRO
- VERSE
- BUILD / PRE_CHORUS
- CHORUS
- BREAK
- BRIDGE
- FINAL_CHORUS
- OUTRO

各区間には最低限、

- startMs / endMs
- intensity
- sectionType候補
- confidence
- 繰り返し元となるsection / phrase
- フレーズ境界
- 主要アクセント

を持たせる。

サビ判定だけへ依存せず、**全時間に盛り上がり度を持たせることを正本方針**とする。

同じ・似たフレーズを検出した場合は、譜面にも共通モチーフを持たせる。  
1番サビ → 2番サビ → ラスサビでは、同じ音楽モチーフを維持しながら難しさ・派手さを段階的に発展させられるようにする。

### D. 難易度別譜面生成

5難易度は単純なノーツ数倍率では作らない。  
**同じ楽曲構造マップを参照しながら、難易度ごとに別の演奏解釈を生成する**。

基本方針:

- EASY: 主拍・主要メロディ・大きなアクセント中心。操作種類と移動量を抑える
- NORMAL: 8分系リズム、伴奏アクセント、HOLD / FLICKを適度に追加
- HARD: 16分候補、可変幅、FLICK / SLIDE、複合操作を導入
- EXPERT: フレーズ表現、同時押し、複合操作、左右移動を増やす
- MASTER: 曲そのものを指で演奏する感覚を狙い、細かなリズム・フレーズ・サビ展開まで最大限反映する

既存の難易度別上限スコア、判定、入力仕様は変更しない。

### セクションによる譜面表現

サビ・盛り上がり区間は単純にノーツ数だけを増やさない。

intensityやsectionTypeに応じて、次を組み合わせる。

- ノーツ密度
- レーン使用範囲
- 可変幅
- 同時押し
- HOLD
- FLICK
- SLIDE
- 複合操作
- 強拍の強調
- 左右移動量
- フレーズモチーフの反復 / 発展

ブレイクや静かな区間では密度を落とし、サビ・ラスサビとの体感差を作る。

### E. 複数候補生成

各難易度について1案だけを生成せず、内部的に複数候補を作れる設計にする。

候補ごとに品質評価を行い、

- 音楽一致
- 音ハメ
- セクション表現
- 難易度適合
- 操作自然さ
- 単調さ
- 過密度
- フレーズ表現
- プレイ可能性

を比較する。

最高評価候補をそのまま採用するだけでなく、必要なら他候補の良い区間を取り込んだ再生成も可能にする。

### F. confidence と譜面品質評価

解析・生成結果にはconfidenceを持たせる。

高confidence:
- 自動採用可能

中confidence:
- 複数候補を比較し再評価

低confidence:
- 人へ丸投げするのではなく、別解析・近傍グリッド・別ノーツ種別を使って自動再検討する

既存の `sourcePeakOffsetMs` による音ズレ監査は維持し、V2ではさらに以下を評価する。

- 音ピークとの一致率
- 拍 / 小節頭との整合
- 無音位置への不自然なノーツ
- セクションごとの密度
- intensityと譜面密度・派手さの相関
- 同じフレーズ間のモチーフ整合
- ノーツ種別比率
- 可変幅比率
- 左右移動量
- 連打速度
- 同時押し量
- HOLD / SLIDE中の複合操作
- 難易度間の段階差
- 同一配置の過剰反復
- 曲全体の密度偏り

### G. 自動プレイ可能性検査

音に合っていても物理的に押しづらい譜面を正式候補にしない。

少なくとも次を検査する。

- 同一指で不可能な短時間移動
- 同時入力数
- 隣接・重複ノーツ
- HOLD中の競合入力
- SLIDE経路と別ノーツの競合
- FLICK直後の不可能な入力
- 可変幅による入力領域衝突
- 10サブレーン上の不正配置
- iPhone縦画面での操作負荷
- 難易度ごとの最大連打・移動量

既存のinvalid placement checkを拡張して使う。

### H. 自動修正ループ

品質評価またはプレイ可能性検査で問題が出た場合、曲全体を毎回作り直さない。

問題のある、

- 小節
- フレーズ
- セクション

を特定し、その範囲だけ再生成する。

修正後は周辺区間との接続も再評価する。  
同じ失敗を無限に繰り返さないよう、修正回数上限と失敗理由を記録する。

### I. 正式候補の品質ゲート

V2で「正式候補」として出力するためには、最低限次を満たす。

- 構造上の不正配置 0
- 自動プレイ可能性の重大違反 0
- 既存の音ズレ監査をPASS
- BPM / beat / downbeatとの整合が許容範囲
- intensityの高低と譜面表現が逆転していない
- 難易度が EASY → NORMAL → HARD → EXPERT → MASTER の順に適切に発展
- 各難易度でノーツ種別・移動・密度が設定した許容範囲
- 同一フレーズの譜面モチーフが不自然に断絶しない
- 解析confidenceが低い重要区間を未解決のまま残さない
- 自動評価で重大警告 0

具体的な数値しきい値は、既存曲を基準にV2実装時に計測して決める。  
しきい値を先に恣意的に固定して「高得点だから良譜面」と扱わない。

### 正式採用と人の確認

V2の目標は **人手修正なしで正式採用可能な譜面**。

人が実プレイして問題を見つけた場合は、その場で手作業修正して終わらせるのではなく、

1. 問題の種類を分類
2. 評価ロジック / 生成ルールへ反映
3. V2で再生成
4. 同じ問題が他曲でも再発しないことをcheck化

することを優先する。

これにより、曲を増やすほど自動生成品質が上がる運用にする。

### V2 STEP1 actual（楽曲特徴・盛り上がり解析）

`tools/mode/rhythm-audio-timing-analyze.js --v2` で実装済み。既存の8kHz mono decode、
onset envelope、BPM推定を再利用し、既存 `monster-hero/data/rhythm-timing.js` のBPM / beatZeroを
譜面制作基準として全尺の特徴マップを作る。ゲームruntime・既存譜面・保存・ランキングには接続しない。

解析単位は500ms窓・250ms hop。V2 JSONには次を保存する。

- 音源SHA-256、解析アルゴリズム版、duration、sample rate、窓幅
- BPM / beatZero / 16分グリッド、4拍子のdownbeat位相候補・時刻・confidence
- onset時刻・強度・近傍グリッド・offset・accent・confidence
- energy（RMS / dBFS / 曲内正規化値）
- low（0〜250Hz）/ mid（250〜2000Hz）/ high（2000〜4000Hz）のRMS・曲内正規化値・attack
- onset density、spectral brightness / spread / change、直前窓からの変化量
- sustain候補、強いaccent候補、簡易rhythm pattern集計
- 各窓の `intensity 0.0〜1.0` とconfidence

intensityは、曲内の外れ値に引っ張られないpercentile正規化後、energy 40%、onset density 20%、
onset strength 12%、spectral change 13%、low 8%、high 7%を合成する。前後1窓で平滑化し、
曲内p05〜p98を0〜1へ写す。したがって絶対音量ではなく、**同じ曲の中での盛り上がり推移**を示す。

confidenceは譜面品質点ではなく解析証拠の信頼度。featuresは信号量・dynamic range・onset数・clipping、
timingは既存制作BPMと独立BPM推定の近さ・自己相関confidence、downbeatは4位相の証拠差を使う。
overallはfeatures 62%、timing 23%、downbeat 15%で合成する。downbeatの位相差が小さい曲は低confidenceのまま保存し、
STEP2が別特徴と合わせて再評価できるようにする。

### V2 STEP2 actual（セクション / フレーズ解析）

`tools/mode/rhythm-chart-v2-step2-analyze.js` で実装済み。STEP1のV2特徴JSONを唯一の入力とし、
ゲームruntimeや既存譜面を読んで答えを曲別に埋め込まない。STEP1のdownbeat候補から小節を作り、
各小節のintensity、energy、low / mid / high、onset density、spectral change、accent等をまとめて扱う。

フレーズ境界は次の組み合わせで決める。

- 隣接小節間の特徴novelty
- intensityの変化量
- 2 / 4 / 8小節周期
- 最小2小節、最大8小節

固定4小節分割にはせず、候補境界の強さに応じて2〜8小節の可変長にする。各フレーズは時間方向を
4点へ再サンプルしたfingerprintを持ち、長さが異なるフレーズ間も同じ特徴空間で比較する。
類似度しきい値以上のものはrepeat groupと過去フレーズ参照を持つ。

セクションは2〜4フレーズを基準に、フレーズ間noveltyとintensity差で可変分割する。各区間には、
INTRO / VERSE / BUILD / CHORUS / BREAK / BRIDGE / FINAL_CHORUS / OUTROの候補score上位4件、
暫定の最上位候補、intensity、confidence、フレーズ一覧、繰り返し元、主要accentを保存する。
ラベルはSTEP2時点の**候補**であり、低confidenceを確定ラベルとして譜面生成へ直結しない。

| --- | --- | ---: | ---: | ---: | ---: | ---: |
| `atsu_cup_theme` | `tools/mode/authoring/atsu-cup-theme-v2-structure.json` | 102 | 19 | 1 | 7 | 0.544 |
| `monster_hero_theme` | `tools/mode/authoring/monster-hero-theme-v2-structure.json` | 110 | 19 | 2 | 8 | 0.552 |

Monster Heroでは、INTRO / BREAK / VERSE / CHORUS / FINAL_CHORUS / OUTRO候補を得た。
あつ杯テーマでは、VERSE / BRIDGE / CHORUS候補、終端にOUTRO候補を得た。両曲とも全尺を隙間・重複なく覆う。

### V2 STEP3 actual（生成ルールへの構造反映）

`tools/mode/rhythm-chart-v2-step3-generate.js` で実装済み（`monster_hero_theme`のみ。
`atsu_cup_theme`は自動生成譜面を持たないため対象外）。V1（`rhythm-monster-hero-chart-build.js`）は
一切変更せず、`require`もしていない完全に独立した実装。STEP1のintensity（timeline）とSTEP2の
sections / phrasesを読んで密度・派手さを決める。採用オンセット候補・音ズレ許容・モンスター配置は
V1と同じ。**採用ループ・小節の上限・レーン決め・HOLD/SLIDEの形・同時押しの置き方は、
仕上がりの点検（2026-09-04、下記「点検で直した欠点」）でV2側だけ作り直した。**

V1は「小節ごとの採用オンセット強さ合計」の三分位だけで密度を決めていたが、これをそのまま
密度上限だけに使っても、実測するとMonster Heroは1小節あたりの実オンセット候補数（4〜5件）が
難易度側の上限を下回っており、上限を変えるだけでは盛り上がりが譜面に出ないことが分かった。
そのためV2 STEP3では、小節の採用条件そのもの（格子の細かさ・採用に必要な強さ）を段で変える。

- 小節ごとのintensityは、STEP1 timeline（500ms窓）のうちその小節に重なる窓の平均
- 全小節のintensityから三分位のしきい値を作り、各小節を段0〜2へ分類する
- セクション種別による調整: `INTRO`/`BREAK`/`OUTRO`は1段下げ、`BUILD`/`PRE_CHORUS`/`CHORUS`/
  `FINAL_CHORUS`は1段上げ、`VERSE`/`BRIDGE`は調整なし（0〜2でclamp）
- 段0（静か）は格子を通常の2倍粗く・採用に必要な強さを+0.15、段2（盛り上がり）は
  格子はそのまま・必要な強さを-0.05し、実際に採用される本数そのものを段で変える
- **小節ごとの上限は「その小節に実際にある音の数」から決める**（2026-09-05に作り直した。下記）。
  盛り上がりの順位（0＝いちばん静か〜1＝いちばん盛り上がる。セクション調整±0.2を含む）は、
  そこへ掛ける倍率としてだけ効く。`perBarByIntensity` は絶対の天井として残す。
  端数は次の小節へ持ち越す（誤差拡散）ので平均は狙いどおりになり、乱数は使わない

  ```
  小節の上限 = min( 天井(perBarByIntensity の折れ線),
                   その小節の音の数 × musicalShare(難易度) × 持ち上げ(0.45〜1.35) )
  ```

  「その小節の音の数」は、難易度によらず同じ物差しで測るため参照源を `dense` に固定する。

  **なぜこうしたか**（実機の指摘: 「現状ハードですら後半むずすぎる。多分終盤にノーツを
  増やしてるから後半が異常にむずくなる。サビは盛り上がってむずくするのはいいとおもうけど、
  あくまでも音楽のテンポを再現してってほしい」）。
  それまでは上限を intensity（音量・厚み）だけで決めていた。ところがこの曲を測ると、
  **リズムの細かさは曲を通してほぼ一定**（1小節あたり4〜8音）で、終盤に増えているのは
  音量のほうだった。つまり「リズムは変わっていないのにノーツだけ倍以上に増える」譜面に
  なっていて、HARDの終盤は音の数の1.75倍までノーツが置かれていた。
  いまは音の数が土台なので、盛り上がっていても音が少ない小節はノーツが増えない。

  | 難易度 | `musicalShare` | 天井 `perBarByIntensity` |
  | --- | ---: | --- |
  | EASY | 0.52 | 2.0 / 4.0 / 5.2 |
  | NORMAL | 0.585 | 2.4 / 4.8 / 6.2 |
  | HARD | 0.75 | 3.0 / 6.0 / 8.0 |
  | EXPERT | 0.93 | 3.6 / 7.0 / 9.2 |
  | MASTER | 1.06 | 4.2 / 8.0 / 10.5 |

  天井はわざと緩めに置いてある。天井が先に効くと、サビの全小節が同じ本数に張り付いて
  曲の濃淡が消える（実際にそうなり、サビ内の「音の数 対 ノーツ数」の相関が0.05まで落ちた）。
  いまはHARDで相関0.67、最後のサビが最初のサビより薄い（3.15 対 3.52 毎秒）
- **候補が上限に届かない小節では、1段細かい候補源から補う**
  （`normal → dense → step1` の順。`supplementedFrom` に出どころを残す）。
  この曲はサビの終盤ほど候補源が薄く（normal: サビ4.3/小節 → 終盤2.4/小節）、
  上限をいくら上げても終盤が薄いままだった。どの段から補うかは `supplementFromTier`
  （EASY〜HARDは段1、EXPERT/MASTERは段0）。**静かな区間（INTRO/BREAK/OUTRO）には足さない**
  ——静けさもその曲の一部で、ここを埋めると「ずっと同じ濃さ」の譜面になるため
- **補う音の下限は、その候補源の中の順位で決める**（`supplementMinStrengthQuantile` = 下位10%を使わない）。
  以前は絶対値0.4で書いていたが、候補源ごとに強さの尺度が違い
  （normalは最小0.60 / denseは最小0.30 / step1は最小0.197）、同じ0.4が
  denseでは「下位9.8%を落とす」、step1では「下位約70%を落とす」という別物の条件になっていた。
  そのため dense が薄いサビの終盤で step1 から補おうとしてもほぼ全部が弾かれ、
  FINAL_CHORUS が CHORUS の9割を割ったままだった（HARD 4.41 / 4.92）。
  順位で切るようにして、較正済みだった dense の挙動（0.4＝下位9.8%）はそのままに、
  step1 側の下限が 0.4 → 0.22 になり終盤が埋まるようになった（HARD 5.23 / 5.29）
- **レーンは「届く範囲のうち、これまで踏んだ回数が少ないレーン」へ**（同数なら向きが続くほう→近いほう）。
  8分未満の間隔では歩幅を最大2レーンに狭める（`laneStepFastMax`）。幅のあるノーツは選んだレーンを中心に置く
- **幅（ノーツの大きさ）は音の強さから決める**。強い音ほど太く（`widths` のいちばん太い幅→3）、
  弱い音のうち下位 `narrowRate` だけが半ノーツ（幅1）になる。ノーツの**種類では決めない**ので、
  TAP・FLICK・SLIDE のどれにも大きさのばらつきが出る（以前はFLICKが無条件に幅1だった）。
  「大きいほど簡単・細いほど難しい」ので、`widths` と `narrowRate` は難易度順:
  EASY/NORMAL は幅2/3/4だけ（`narrowRate` 0）、HARD .10 / EXPERT .22 / MASTER .32
- HOLDの長さは次の音までの間で 4 / 8 / 12 グリッド（1〜3拍）
- 長さ8グリッド（2拍）以上のHOLDへ、押さえている途中の幅変化（`holdPoints`）を
  「広がる → 細くなる → 途中でふくらむ」の順で `holdTaperMaxCount` 本まで付ける。中心は動かさない。
  短いHOLDへは付けない（変わり目が0.35秒ほどしかなく読み取れないため）
- SLIDEは9つの形（`straight` 12g・`long` 16g・`turn` 12g・`short` 8g・`wide` 12g・`taper` 16g・
  `open` 12g・`close` 12g・`swell` 16g）を順番に使い回し、形の持つ幅はその難易度の `widths` の範囲へ収める。
  向きは始点の位置で決める（右寄りなら左へ）。はみ出す・他の長いノーツとぶつかる形は次の形へ譲る
- 同時押しの相方は「反対側へ2レーン」に置く。HOLD/SLIDE中の重ねTAPは同時押しへ割らず、
  長いノーツを押さえている最中の同時押しも置かない（3本目の指が要る配置を生成の段階で作らない）
- 反復フレーズ（`repeatedFromPhraseId`）は、小節数が元フレーズと一致する場合だけ、
  元フレーズと同じフレーズ先頭からの相対グリッドへ音を置く。ただし架空の音は作らない:
  その位置の近傍(±2グリッド)に、反復先の小節が属する段の採用基準を満たす実オンセット候補が
  実在する場合だけ採用し、無ければ置かない（`motif.notesGrounded` / `notesAttempted`で記録）

#### 点検で直した欠点（2026-09-04）

STEP5採用譜面の統計（レーン分布・区間ごとの密度・間隔・形）を、人が耳で確認した正式候補v1と
同じ物差しで比べて見つけたもの。いずれも**V1にも同じ欠点があった**が、V1は耳確認済みなので触らない。

| 欠点 | 原因 | 直し方 |
| --- | --- | --- |
| 上限も供給も効かず、全難易度が2〜3音/小節に張り付く | 採用ループが「最後に取った音」とだけ間隔を比べ、拍頭を先に取ると同じ小節の裏拍が負の差で全部捨てられていた | 同じ小節で取った全部と比べる |
| レーン1に1音も来ない／EXPERT以上は0↔4の往復ばかり | レーン歩きが `lane ± maxLaneStep` の機械的な折り返しで、歩幅2だと 0/2/4、歩幅4だと 0/4 しか踏めない | 踏んだ回数が少ないレーンへ。近い音ほど歩幅を狭める |
| サビの終盤がふつうのサビより薄い | 段が同じ2に潰れる上、候補源そのものが終盤ほど薄い | 上限を盛り上がりの連続値から決め、足りない盛り上がり小節だけ細かい候補源から補う |
| SLIDEが全部同じ形、HOLDが4か8だけ | 形が1つしか無かった | 4つの形を順番に、HOLDに12グリッドを追加 |
| 3本目の指が要る配置ができる | HOLD中の重ねTAPを同時押しへ割っていた | 生成の段階で置かない |
| MASTER が EXPERT より易しい案を採用 | STEP5が難易度どうしを比べていなかった | STEP5で難易度の順を守る（下記） |

#### 曲のタイプ（曲ごとに譜面の性格を変える）

ユーザー指示（2026-09-05）「作成ツールの精度をできるだけ上げた上で、難易度別もそうだけど
**曲によるタイプ**で作ってほしい。この曲は細かいのが多いとか、スライドが多いとか、
うまく曲にあわせて違いが作れるようにしたい」。

それまで譜面の性格は**難易度だけ**で決めていた。どんな曲を入れても同じ配分（同じくらいの
HOLD数・SLIDE数・同じくらいの細かさ）の譜面が出てくる作りだった。
`tools/mode/rhythm-chart-v2-song-type.js` が、**STEP1で既に取ってある特徴量だけ**から
曲の性格を5つの軸（0〜1）で出し、STEP3がその軸で難易度プロファイルを掛け算する。
新しい音源解析は足していない。乱数も使わない。

| 軸 | 何から出すか | 何に効くか |
| --- | --- | --- |
| 細かさ `granularity` | 1秒あたりのオンセット数 / 16分の裏に乗る音の割合 / オンセット間隔の中央値 | 密度・半ノーツ（幅1）の量・格子の粗さ・連打の上限 |
| 伸び `sustain` | `sustainLikelihood` の平均 / 伸びる音の候補が占める時間 | HOLDの本数・長さ・幅変化の数 |
| うねり `motion` | `spectralChange` の平均 / 明るさの揺れ / 低域と高域のバランスの揺れ | SLIDEの本数・曲がりの大きさ・FLICKの本数 |
| 抑揚 `dynamics` | intensity の p90−p10 / `dynamicRangeDb` | 静かな区間と盛り上がりの密度差 |
| 規則性 `regularity` | `regularityConfidence` / 拍頭に乗る音の割合 | 反復モチーフを効かせるかどうか |

**軸はどれも「曲をまたいで比べられる絶対の基準」で正規化する。** 曲の中で正規化すると、
どんな曲でも必ず真ん中の値になり「曲による違い」が出せない。基準の数値は、一般的な
ポップス／ゲーム曲がだいたい 0.3〜0.7 に収まるように置いてある。

**倍率はすべての難易度へ同じだけ掛かる**ので、難易度の順（EASY<…<MASTER）は崩れない。
振れ幅は効く先で分けている。

- **密度に効くもの**（密度・HOLDの長さ・静と動の差）… 難易度どうしの差（1.15〜1.4倍）を
  飲み込まないよう **1.6倍まで**。ここが広すぎると「MASTERよりHARDのほうが忙しい曲」ができる
- **配分に効くもの**（半ノーツ・HOLD・SLIDE・FLICKの量）… 「この曲はスライドが多い」を
  作るのが目的なので広くてよい。**1.5〜3.6倍**（下限も置いて、曲タイプが何も効いていない状態を検出する）

曲が1つしかないと「曲によって本当に変わるのか」を実物では確かめられないので、
`rhythm-chart-v2-song-type-check.js` が**作り物の特徴量**（細かい曲・伸びる曲・よく動く曲…）を
10種類入れて、5つの軸が両端まで振り切れること・**1つの軸を振っても他の軸が動かないこと**・
倍率が狙いどおりの向きへ動くことを確かめる。

Monster Hero の実測: 細かさ0.50 / 伸び0.56 / うねり0.42 / 抑揚0.61 / 規則性0.50 →「素直な曲」。
極端な曲ではないので倍率はどれも 0.92〜1.06 に収まり、この曲の譜面は大きく動かない。

```bash
node tools/mode/rhythm-chart-v2-song-type.js          # 曲のタイプを見る
node tools/mode/rhythm-chart-v2-song-type-check.js
```

#### HOLD / SLIDE の形の作り方（組み合わせで作る）

ユーザー指示（2026-09-05）「ホールド、スライドのバリエーションが少なすぎるからそのへんも
**無限レベルに増やしてと言うか発想力を増やしてほしい。固定概念は極力抜いて**」。

形を並べたリストから選ぶのをやめ、**4つの要素の組み合わせ**で作るようにした。

| 要素 | 種類 | 中身 |
| --- | ---: | --- |
| 経路の型 | 7 | `line` まっすぐ / `arc` 先に大きく動いて落ち着く / `ease` S字 / `turn` 行って戻る / `hook` 行ってから少し戻る / `wave` ひと往復 / `stair` 階段 |
| 長さ | 5 | 8 / 12 / 16 / 24 / 32グリッド（2〜8拍） |
| 振れ幅 | 5 | 0.5 / 1 / 1.5 / 2 / 2.5レーン |
| 幅の変わり方 | 6 | `flat` 一定 / `open` 開く / `close` 閉じる / `swell` ふくらむ / `pinch` くびれる / `pulse` 太い細いを繰り返す |

**7 × 5 × 5 × 6 = 1050通り。** 点の数は長さで決まる（1拍あたり1点、2〜9点）ので、
同じ組み合わせでも長さが違えば形の細かさも変わる。

何本目かから4つの要素を選ぶが、**桁上がり（1本ごとに1つだけ進む）にはしない**。
1曲にSLIDEが10本ほどしかない譜面では、経路しか変わらず長さも振れ幅も幅も全部同じになる
（実際そうなった）。4つとも毎回進め、進む歩幅を各リストの長さと互いに素にしてあるので、
どの軸も全種類を一巡し、組み合わせが戻ってくるのは210本目。乱数は使わない。

**HOLDは中心を動かさず、太さだけが変わる。** 幅の変わり方はSLIDEと同じ語彙を使い回す
（`flat` 以外の5種類）。中心も動かすとSLIDEと区別が付かなくなるため、横の動きはSLIDEの役目にしている。

実測（MASTER・STEP3既定出力）:

```
SLIDE  line-8-0.5-flat / arc-16-2-pulse(幅 1,4,1,4,1) / turn-12-2-swell(1,3,3,1)
       hook-24-1.5-close(4,4,3,3,2,1,1) / stair-16-2-flat / line-32-1-pulse(1,2,4,3,1,2,4,3,1)
       ease-24-1.5-swell(1,2,3,4,3,2,1) / arc-12-2-pinch(4,2,2,4) …12本で10種類
HOLD   open(1,3,4) / close(4,3,1) / swell(1,4,1) / pinch(4,1,4)
```

#### 見た目の参考にするもの（プロセカ / チュウニズム）

ユーザー指示（2026-09-04）「ノーツとか画面とかエフェクトとか色々含めてプロセカやチュウニズムを参考にしてね」。
**取り入れる考え方**と、**この曲・この画面では取らないもの**を先に決めておく。

| 取り入れる | どういうことか | 状態 |
| --- | --- | --- |
| 幅は連続した表現である | ノーツの幅は「種類ごとの固定値」ではなく、音の強さと役割で決まる。全幅から半ノーツまで地続き | 実装済み（幅1〜10） |
| 幅広ノーツは別の形に見せる | 丸い粒を引き伸ばすのではなく、角を落とした棒＋両端の明るい縁。どこからどこまでかが読める | 実装済み（`data-rhythm-note-wide`） |
| 長押しは太さが変わる | プロセカのロングノーツのように、押さえている最中に帯が広がる／細くなる | 実装済み（`holdPoints`） |
| 区切りの一発は大きく | セクションの変わり目を幅広ノーツで示し、曲の構造が目でも分かる | 実装済み（`sectionAccent`） |
| 取れた手ごたえを音と光で返す | 判定ラインでの短い光と、種類ごとに違う音 | 実装済み（前節） |
| 判定文字とFAST/SLOWの位置 | 判定ラインのすぐ上に固定し、ノーツと重ならない | 実装済み |

| 両サイドのマスモン | 空いた三角形へ設定したマスモンを置き、拍に合わせて跳ねさせる。能力中はそのマスモンを光らせる | 実装済み（下記） |

| ノーツを取ったときのヒットエフェクト | 判定ラインで「横へ広がるフラッシュ＋立ち上がる光の柱＋はじける粒5つ」が弾ける。判定ごとに色が違う | 実装済み（下記） |
| 大事な瞬間を大きく祝う | モンスターノーツだけ光を3倍・画面を一瞬染める・マスモンが跳ねる・専用の音 | 実装済み（下記） |

| いまは取らない | 理由 |
| --- | --- |
| 背景の常時アニメーション | 実機（iPhone SE2 / 16e）で毎フレームの塗り直しが増え、発熱時にカクつく |
| レーンが手前へ広がる強い遠近（チュウニズム風） | いまのprojection（1.24乗）で判定位置と入力座標を揃えてあり、変えると入力の当たり判定を全部作り直すことになる |

「取らない」ほうは**やらないと決めた**のではなく、**実機の性能確認（STEP2）で分かったこと**が理由なので、
軽くする方法が見つかったら改めて検討する。

**カクつきは発熱の影響がいちばん大きい**（ユーザー判断・2026-09-05）。この前提で、演出を足すときの
線引きは次のようにしている。

| | 中身 | 発熱時の効き方 |
| --- | --- | --- |
| 足してよい | `transform` と `opacity` **だけ**を動かす。CSSの `@keyframes` で回す | GPUの合成だけで済み、塗り直しが起きない。毎フレームのJSも増えない |
| 足さない | blur・影・filter・広い面積の色を毎フレーム変える。要素が毎フレーム増減する | 塗り直しの重さは画素数に比例する。発熱でGPUが絞られるとそのままカクつきになる |

### ノーツを取ったときのヒットエフェクト

ユーザー指摘（2026-09-05）「画面演出はあまりかわってないけどなにかいじった？
プロセカ、チュウニズムのようなのを参考にしてほしい」
「**モンスターノーツ踏んだときは音も演出も地味すぎる**」。

**以前は「ノーツ1枚ごとの派手なエフェクトは重いので入れない」としていた。これは判断を誤っていた。**
実機でカクついた原因は**画面いっぱいのぼかしを押すたびに描き直していた**ことで、
エフェクトそのものが重かったわけではない。次を守れば発熱時でも負担は増えない。

- 要素は**プレイ開始時に10枚だけ作って使い回す**（押すたびにDOMを増やさない）
- 動かすのは `transform` と `opacity` **だけ**。ぼかし・影・色・幅・高さは動かさない
- 光り方はCSSアニメーションなので、毎フレームのJSは走らない
- 1回の発生で書くのは「位置・幅・色・種類」の数個だけ

#### 光の形（1枚 = `<span><i/><b/><u/>×5</span>`）

初版は「横帯（`<i>`）＋広がる輪（`<b>`）」の2つだったが、実機で
**輪が判定ラインに残り続けて画面が読めなくなった**（下の「残り続けた原因」）。
作り直して、プロセカ／チュウニズムの着弾に寄せた3つの光にした。

| 部品 | 役割 | 動き |
| --- | --- | --- |
| `<i>` 中心のフラッシュ | 判定ラインの上で横へ広がる（プロセカの着弾の光） | `scale(x,y)` と `opacity` |
| `<b>` 立ち上がる光の柱 | 判定ラインから上へ抜ける（チュウニズムの光柱） | `scale(x,y)`（原点は下端）と `opacity` |
| `<u>`×5 はじける粒 | 上・左右へ飛び散る | `translate()`＋`scale()` と `opacity` |

粒の飛ぶ向きは `:nth-of-type()` でCSSに固定で書いてあるので、発生のたびの計算は増えない。
飛距離だけを `--rhythm-spark-scale`（ふつう 1 / モンスター 2.1）で伸ばす。

| | ふつうのノーツ | モンスターノーツ |
| --- | --- | --- |
| 長さ | 340ms | **900ms** |
| 幅 | ノーツの幅 ×1.15 | ノーツの幅 **×1.5** |
| 光の大きさ | 等倍 | フラッシュ・柱とも **約2倍**、粒の飛距離 **×2.1** |
| 色 | 判定ごと（MARVELOUS=桃 / EXCELLENT=水 / GREAT=黄 / GOOD=黄緑 / BAD=赤） | 金色 |
| 画面のフラッシュ | なし | **あり**（あらかじめ置いた1枚の `opacity` だけを動かす） |
| 音 | 既存のタップ音・取得音 | **専用**（C6→E6→G6 の駆け上がり＋C4の低音） |
| サイドのマスモン | ― | **そのマスモンが大きく跳ねる** |
| 能力名 | ― | 大きく弾んで出る |

判定文字（220ms）と**コンボ数**（180ms）も、出た瞬間に一度だけ弾む。
コンボ数はHUD側でプレイエリアの外にあるため、出す・出さないの判定はJS側（演出量）で行う。
演出量MINIMAL・軽量モードでは光・跳ね・弾みを出さない（**音は鳴る**）。
入力は `pointer-events:none` で邪魔しない。

#### 残り続けた原因（2026-09-05・実機で発生）

ユーザー報告「**タップのとこがわけわかんないことになってる**」。判定ラインに輪が
10個ぶん重なって居座っていた。

CSSアニメーションに `fill-mode` を付けていないので、**終わった瞬間に子要素は「既定の見た目」へ戻る**。
初版は輪へ `opacity:.9` を既定で与えていたため、光り終わるたびにその輪が出しっぱなしになり、
使い回している10枚ぶんが全部残った。

→ **子要素の既定は必ず `opacity:0`。** アニメーションのあいだだけキーフレームが上書きする。
`rhythm-hit-effect-check.js` が、CSSの記述と実ブラウザの実測（1.4秒後に全部の子の
`opacity` が 0 か）の両方で見張る。既定を `.9` へ戻すと2件NGになることを確認済み。

実ブラウザで測って確かめている（`rhythm-hit-effect-check.js`）:
**40回発生させてもDOMが10枚のまま**、光が実際に大きさを持って出ている、
光がノーツの位置（中心50.0%）に出る、モンスターノーツの光がふつうより大きい、
1枚あたりの粒が5つある、**光り終わったあと残った不透明度が0**、
CSSアニメーションが実際に動いている、軽量モードでは `display:none` になる。

### 両サイドのマスモン

ユーザー指示（2026-09-05）「画面の空いてる両サイドに設定してるマスモンを出して音にあわせて
ピョンピョンするとか可能？ これも重くなる原因になる？」「モンスターノーツを踏んで効果が
聞いてる間はそのマスモンで画面的にわかるようにするとか」「オプションで表示なしとか薄くするとか
動かないとかそういうのを色々設定できるようにすればいい」。

#### 置き場所

レーンは奥へ向かって狭くなる台形なので、その外側に「上が広く下が狭い三角形」の空きができる
（プレイエリア幅に対して、画面上端で片側41% → 高さ40%で28% → 判定ライン付近で6% → 下端で0%）。
HUDの下・判定ラインの上にあたる **高さ30%と52%** を縦の置き場所にしている。

- 1・3枠目が左、2・4枠目が右（登場順が左右へ交互に並ぶ）
- 大きさは「その高さの空きの72%」と「プレイエリア幅の17%」の小さいほう。最低24px
- **箱の下端でも収まるか確かめて縮める。** 台形は下へ行くほど空きが狭いので、真ん中の高さだけで
  決めると箱の下の角がレーンへ食い込む
- ノーツより後ろ（`z-index:1`。ノーツは2）に置き、`pointer-events:none` なので入力を邪魔しない

#### 発熱に強い作り

- 跳ねるのは **CSSアニメーションで `transform` だけ**。影・ぼかし・色は動かさない
- 速さは曲の1拍（`--rhythm-side-beat`）。**プレイ開始時に一度だけ書く**ので毎フレームのJSは走らない
- 左右で半拍ずらす（`--rhythm-side-delay`）ので、4体が同時に跳ねない
- 能力中の輪は**あらかじめ用意しておいて出し入れするだけ**（押すたびに影を作らない）
- 置き場所と大きさは、プレイエリアの大きさが変わったときだけ測り直す（`rhythmLayoutSideMonsters`）
- 光らせる枠は「変わった瞬間だけ」属性を1つ書き換える。毎フレームは比較用の文字列すら作らない
- 軽量モード・演出量MINIMALでは動きを止める（CSS側で `animation:none`）

#### 絵の出し方（実機で出した不具合）

`DyedMonsterImage` は**染色なしなら `<img>`、染色ありなら `<div>` で返る**。`<div>` の場合は
大きさを渡さないと中身が0pxになり、**能力中の丸い枠だけが出て絵が出ない**（枠は `span` の
`::after` なので、絵が0pxでも正しい場所に出てしまう）。実機でこの状態になった。

- JSX側では入れ物の `<span data-rhythm-side-monster-art>` を挟み、`className="h-full w-full object-contain"` を渡す
- **CSS側でも大きさを与える**（`[data-rhythm-side-monster-art]>*`）。className だけに任せると、
  Tailwindが読めない場面で同じことが起きる
- 収め方（`object-fit`）は**直下の要素にだけ**書く。中の重ね絵は `objectFit:inherit` で
  ここから受け取るので、全 `img` へ書くと染色マスクの仕組みを壊す

### V2 STEP5 actual（複数候補・自動批評）

`tools/mode/rhythm-chart-v2-step5-review.js` で実装済み。検査は
`tools/mode/rhythm-chart-v2-step5-check.js`。

STEP3/4の生成器は「1つの難易度から1つの譜面」しか作らない。実際の譜面作りは
「何案か作って良いものを選ぶ」作業なので、そこを機械化する。

1. 同じ音源・同じ構造解析から、**作り方の数値だけ**を変えた候補を複数作る
2. 出来た譜面を機械的に採点する
3. 順位を付け、いちばん良い案を選ぶ

生成ロジックそのものは触らない。STEP3の生成器へ `--profile-override` を渡して
難易度ごとの制作方針の数値だけを差し替える。**上書きなし（既定）の出力は1バイトも
変わらない**ため、STEP3の決定性チェックはそのまま通る。上書きできるのは作り方の数値だけで、
`level` のような出力の意味づけは拒む。

#### 候補の作り分け

乱数は使わない。したがって何度実行しても同じ順位・同じ採用になる。

| id | 変えるもの |
| --- | --- |
| `base` | 既定 |
| `strong` / `more` | 強い音だけ拾う／弱めの音も拾う（`minStrength` ±0.10） |
| `dense` / `sparse` | 密度（`perBarByIntensity`） |
| `calm` / `wide` | 手の移動幅（`maxLaneStep`） |
| `variety` | HOLD/FLICK/SLIDEの上限を増やす |

作り方を変えても出来上がりが既定と1バイトも変わらない案がありうる（その難易度では
その数値が効いていない）。そういう案を別案として数えると「8案から選んだ」と誤解する
報告になるため、**同じ譜面はまとめて印を付け、「実際に違う譜面になった案: 6/8」のように
正直に出す**。

格子（`latticeGrids`）は案として動かさない。以前の `tight` / `loose` は格子を変えていたため、
HARD / MASTER で「音を粗く拾う」案が構造の点で勝ち、**16分が1つも無い（＝1つ下の難易度と同じ
リズムの）譜面を採用していた**。格子は難易度の設計そのものなので、動かすのは「どの強さの音まで拾うか」だけ。
生成器の既定値は生成器自身に `--print-profiles` で吐かせて読む（写しを持たない）。

#### 採用の条件（点だけで選ばない）

1. **STEP6で「押せない」が0件**であること。候補ごとにSTEP6を `--file` で通し、押せない案は点が高くても採らない
2. **難易度の順を守る**こと。1つ下の難易度で採った案より、ノーツ数が多く、密度が8%以上多く、
   最小の間隔が粗くならず（上の難易度で16分が消えない）、8小節以上ある区間ではどの区間でも
   薄くならない（許容は小節あたり0.35音または20%の大きいほう。静かな区間は音数が少なく、11小節で3音の差が0.27になるため）
3. その中で最高点の案を採る。条件を満たす案が1つも無いときだけ点だけで選び、`orderingKept:false` を残す

外した案は「STEP6で押せない箇所がN件」「1つ下の難易度より易しくなる区間がある」と理由つきで表示する。

#### 採点で見ているもの

どれも譜面のJSONだけから測れる値で、人の好みは入れていない。重みの合計は1.0。

| 項目 | 重み | 見ているもの |
| --- | ---: | --- |
| 音との一致 | .24 | 採用した音からのズレ（`sourcePeakOffsetMs`）の平均。生成器の上限±30msを0点として正規化 |
| 構造への追随 | .22 | 静かな区間（INTRO/BREAK/OUTRO）と盛り上がる区間（CHORUS/FINAL_CHORUS/BUILD/PRE_CHORUS）の小節あたりノーツ数の差。2倍で満点 |
| 狙いの密度 | .18 | 難易度ごとに置いた毎秒ノーツ数の帯に入っているか |
| 単調でないこと | .16 | 同じレーンの連続／同じ間隔の連続／4つ組パターンの使い回し |
| 手の動き | .10 | 8分未満の間隔で3レーン以上跳ぶ組み合わせの割合（25%超で0点） |
| 種類の配分 | .06 | 許可された種別が使われているか（TAPだけの譜面を避ける） |
| 休符 | .04 | いちばん長い空白が長すぎない／空白がまったく無い、を避ける |

「構造への追随」は当初、小節ごとのノーツ数と楽曲の盛り上がり度の相関で測ろうとしたが、

### V2 STEP6 actual（自動プレイ可能性検査の強化）

`tools/mode/rhythm-chart-v2-step6-playability.js` で実装済み。検査は
`tools/mode/rhythm-chart-v2-step6-check.js`。

STEP5の自動批評は「8分未満の間隔で3レーン以上跳ぶ組み合わせの割合」しか見ておらず、
**実際に人間の手で押せるのか**には答えていなかった。HOLDで指が塞がっている最中の別ノーツも、
同時押しの指の届く範囲も、指を戻す時間も見ていない。

ここでは**両手の指を実際に割り当ててシミュレート**し、押せない箇所を場所つきで出す。

#### 手のモデル（`tools/mode/rhythm-hand-model.js`）

スマホを両手で持って親指2本で押す前提。指は2本。
値は**1つのモジュールへ一本化**してあり、STEP3（生成）・STEP6（検査）・STEP7（自動修正）が
同じものを `require` する。道具ごとに書き直すと、直したつもりで別の物差しになるため。

| 定数 | 値 | 意味 |
| --- | ---: | --- |
| `hands` | 2 | 親指2本 |
| `laneSpeedComfort` | 10レーン/秒 | 快適に動かせる速さ（1レーン100ms） |
| `laneSpeedLimit` | 18レーン/秒 | これを超えると押せない（1レーン約56ms） |
| `restrikeComfortMs` | 150ms | 同じ指で叩き直すのに欲しい間隔 |
| `restrikeLimitMs` | 105ms | これより短いと同じ指では押せない（＝毎秒9.5連打が上限） |
| `fingerMinGapLanes` | 1 | **指の太さ。**触る点がこれより近いと指が2本入らない |
| `releaseMarginMs` | 30ms | HOLD/SLIDEを離してから次を押すまでの余裕 |
| `endFlickReleaseMs` | 80ms | 終点フリックは「弾いて戻す」ぶん、指の解放がこれだけ遅れる |

ノーツは時刻順に、届く指のうち無理のないほうへ割り当てる。HOLD / SLIDE はその長さのあいだ
指を占有する（SLIDEは経路のレーンを追う）。届く指が1本も無ければ「押せない」。
限界は満たすが快適を満たさない場合は「忙しい」。

##### 指には太さがあり、ノーツには押せる幅がある（2026-09-05に足した）

実機の指摘「**1枠を隣り合わせで交互に連続押しは物理的に不可能**だからそういう譜面は
作らないようにして。もちろん速度と押すスピードによるから譜面作成ツールの精度をもっと上げて」。

それまでのモデルには指の太さが無く、「1レーン以上離れていること」を**同時押しのときだけ**
見ていた。時間がずれた連続ノーツには何の条件も無かったので、
**16分（87ms）おきに触る点が0.25レーンしかずれない交互押し**が「押せる」と判定され、
HARDに15箇所・EXPERTに39箇所・MASTERに61箇所そのまま出ていた。
`restrikeLimitMs` が55ms（＝毎秒18連打）と非現実的だったことも重なっていた。

いまは連続する2音を次のどちらかでなければ作らない・通さない。

- **指2本で分担する** … 触る点どうしを `fingerMinGapLanes`（1レーン）以上離せる
- **指1本で叩き直す** … 間隔が `restrikeLimitMs`（105ms）以上あり、その時間で移動しきれる

ここで「触る点」は1点ではなく**範囲**で持つ。幅の広いノーツは端から端まで好きな場所を
押せるので、幅8のノーツと幅5のノーツが重なっていても、それぞれの端を押せば指2本が入る。
指自身にも太さがあるので、置ける範囲はノーツの端から指の半径（0.5レーン）を残した内側。
幅1〜2のノーツは指の幅より狭いので、動かす余地が無く中心の1点になる。

| 例 | 触る点を離せる距離 | 87ms（16分） | 173ms（8分） |
| --- | ---: | --- | --- |
| 幅1が隣り合わせ | 0.50 | **押せない** | 押せる（指1本） |
| 幅1が2レーン離れ | 2.00 | 押せる（指2本） | 押せる |
| 幅8と幅5が重なる | 2.50 | 押せる（指2本） | 押せる |
| 同じ幅3が同じ場所 | 0.00 | **押せない** | 押せる（指1本） |

しきい値は実測ではなく設計上の目安。**人が耳で確認して通した既存の正式候補v1が
「押せない0件」で通ること**を検査で固定して較正している（厳しすぎると道具として使えず、
緩すぎると何も見張れないため、「忙しい」が少しは出ることも同時に確認する）。

### V2 STEP7 actual（問題区間の自動修正ループ）

`tools/mode/rhythm-chart-v2-step7-autofix.js` で実装済み。検査は
`tools/mode/rhythm-chart-v2-step7-check.js`。

STEP6が「押せない」「忙しい」を場所つきで出すので、それを入力に譜面を直す。

#### 直すのはレーンだけ

音の時刻・種別・幅・長さ・ノーツ数には一切触らない。時刻を動かしたり音を消したりすると、
STEP1〜5が積み上げたもの（音との一致・構造への追随・motif）が崩れ、
「押せるようになったが曲に合っていない譜面」ができるため。レーンだけなら、
その音を鳴らすタイミングは変わらないまま手の動きだけが楽になる。

手のモデルはSTEP6のものを `require` してそのまま使う（道具ごとにシミュレートを書き直すと、
直したつもりで別の物差しになる）。

#### 悪さを1つの数にまとめる

```
cost = 押せない×10000 + 忙しい×100 + 8分未満で3レーン以上跳ぶ×10 + レーンの偏り×1
```

押せないを最優先で潰し、次に忙しいを減らす。ただし「忙しいを消すために全部を端へ寄せる」
といった直し方をしないよう、跳びとレーンの偏りも同じ数へ入れている。
さらに置き換えを選ぶときだけ、元の場所からの移動をサブレーン1つあたり3として足す
（同じ問題が近い場所でも直せるならそちらを選ぶ）。

1回のパスで問題のあるノーツを順に試し、`cost` が下がる置き換えだけを採る。
同点なら動かさない。乱数は使わないので何度実行しても同じ結果になる。
SLIDEは経路の形を変えず、まるごと0.5レーンずつ平行移動する。
置き換え先は、同じ時刻の他のノーツと重ならないものだけを候補にする。

#### 実測（STEP5採用案を直した結果）

| 難易度 | ノーツ | 直した箇所 | 忙しい | 3レーン以上の跳び | レーンの偏り |
| --- | ---: | ---: | --- | --- | --- |
| EASY | 175 | 0 | 0 | 0 | 2 |
| NORMAL | 197 | 0 | 0 | 0 | 4 |
| HARD | 261 | 2 | 2→0 | 0 | 7 |
| EXPERT | 322 | 7 | 9→0 | 6→5 | 8→12 |
| MASTER | 394 | 16 | 19→0 | 6 | 15→17 |

**全難易度で「押せない」も「忙しい」も0件**になった（`--source step7` でSTEP6にかけて確認）。
音は1つも動いておらず、ノーツ数・種別・幅・長さ・終点フリック・モンスター枠はすべて元のまま。

#### 検査で見張っていること

直す道具でいちばん怖いのは**直しすぎ**なので、次を固定している。

- 音を1つも動かしていない・消していない・種別や幅を変えていない（時刻＋種別＋幅＋長さの多重集合が一致）
- 「押せない」「忙しい」が増えていない（実際にSTEP6へかけて確認）
- 直すために別のところを壊していない（跳びが増えない・5レーンすべてを12%以上使い続ける・同時刻の重なりが無い）
- 直せる問題は実際に直せる（同じ場所で16分連打する譜面を入れて確認）
- 問題が無ければ1箇所も書き換えない
- 何度実行しても同じ結果になる／ランタイム・V1・既存の正式候補v1・STEP5の採用譜面を書き換えない

3か所（音の時刻をずらす・同時刻の重なりを見ない・忙しいだけを見て他を壊す）をわざと壊し、
うち2か所で検査が落ちることを確認した。「同時刻の重なり」は実データでは
「近くへ動かす」重みが効いて重なる位置が選ばれにくく、出力だけでは気づけないため、
実装の形（重ならない候補だけを集めているか）も併せて見張っている。

出力: `tools/mode/authoring/monster-hero-theme-v2-step7-chart-<難易度>.json` と
講評 `-step7-autofix-step5.json`（どちらも `reviewRequired=true` / `runtimeConnected=false`）。

CLI確認:

```bash
node tools/mode/rhythm-chart-v2-step7-autofix.js
node tools/mode/rhythm-chart-v2-step7-autofix.js --write
node tools/mode/rhythm-chart-v2-step7-check.js
node tools/mode/rhythm-chart-v2-step6-playability.js --source step7
```

## 自動譜面制作V3（音の種類・音の高さ・形の語彙から組み立てる）

ユーザー指示（2026-09-05）
「譜面配置やテンポ、そして音ゲーについてはありとあらゆるとこから学習してこのゲームに活かして。
それでいて**最強の譜面作成ツール**を作成して」。

作り方の根拠は [`RHYTHM_CHART_DESIGN.md`](RHYTHM_CHART_DESIGN.md) にまとめてある。
V2（`rhythm-chart-v2-step*`）はそのまま残し、V3は別系統として作った。
デバッグ画面の曲「**Monster Hero 候補v3**」で遊び比べられる。

### V3で変えた4つ

| | V2 | V3 |
| --- | --- | --- |
| 拾う音 | 強さの順位で上からN個 | **音の種類**（大きな一発・重い打点・胴のある音・軽い音）で決める |
| レーン | 使用回数が少ないレーンへ歩く | **形の語彙**（階段・折り返し・交互・トリル・縦連・開き閉じ・ジグザグ）を当てる |

| SLIDEの経路 | 決まった形の組み合わせ | **音の高さの動き**に沿わせる |
| 難易度 | それぞれ独立に作る | **同じ優先順位の上位から何個取るか**だけで分ける（骨格を共有） |

### どんな曲でも作れるようにした（2026-09-05）

ユーザーの問い「全ての曲に対応出来るものになってる？」に、正直に答えると
**作った直後のV3は2曲専用だった**。

| 落とし穴 | 直す前 | 直したあと |
| --- | --- | --- |
| BPM・拍の頭 | `rhythm-timing.js` へ手で記入（登録は2曲だけ） | **音から自動判定**（登録値があればそちらを優先） |
| 拍子・刻み | 4/4・16分の決め打ち | 音から判定（3拍子・3連・跳ねも見る） |
| 曲の区切り | ffmpeg を使う別系統（V2 STEP1/2）の出力 | **音から自動**（自己類似行列＋Foote のノベルティ） |
| 譜面の量 | その曲の打点の何割（1曲に合わせた数字） | **1拍あたり何個**を目標に、毎秒の下限・上限で挟む |
| HOLD等の数 | 1曲に何個（150秒前提） | **1分あたり何個**（30秒の曲でも6分の曲でも合う） |
| 曲の登録 | コードへ直書き | 一覧ファイル＋`--audio` |

#### テンポ判定の作り

自己相関の山だけで選ぶと、半分（173→86.5）・3分の2（169→112.8）・倍を取り違える。
決め手は「**そのテンポの16分格子に、実際の打点がどれだけ乗るか**」。

| | 正しいテンポ | 半分 | 3分の2 |
| --- | ---: | ---: | ---: |
| Monster Hero | **91.2%** | 76.8% | 50.3% |
| あつ杯テーマ | **72.5%** | 39.3% | 45.3% |

そのうえで「拍に音があるか（占有）」と「人が速いと感じる帯」で重みを付け、
最後に**最小二乗で格子を当て直す**。結果、Monster Hero は
BPM 誤差 **0.003%**（150秒で4msのずれ）、拍の頭は登録値と **2ms** 差。

#### 実測（登録の無い6曲を人手なしで通した）

`rhythm-audio-general-check.js` が毎回確かめる。

- 6曲すべてで、テンポ判定 → 区切り検出 → 5難易度の生成 が人手なしで通る
- どの曲でも密度が狙いどおり（曲が変わっても遊んだ感じの忙しさがそろう）
- どの曲でも鳴っていない場所へ置かない／形の語彙を4種以上使う
- EASY〜HARD は「押せない」0件、EXPERT/MASTER も1%以内（自動修正で0件になる）

#### あやしさを申告する（`warnings[]`）

解析のたびに「このまま譜面にしてよいか」を書き出す。重いものが1つでもあれば、

- 重い … `tempo-unstable` / `grid-loose` / `few-onsets` / `timing-undetected`

ずれとして数え、さらに**ずれた窓が全体の3割を超えたとき**にだけ止める。
（「いちばんずれた窓」で決めると、生っぽい演奏の曲を止めてしまう。

### 狙ったノーツと違うノーツが取れていた（2026-09-05）

**どのノーツを叩いたことにするかを、時間の差の絶対値だけで決めていた。**

判定の受付幅は片側240ms（BADの窓）。8分の間隔はBPM170で176msなので、
**次のノーツは常に候補に入っている**。そこで単純に近いほうを選ぶと、
間隔の半分を超えて遅れた瞬間に判定が次へ移る。

| 並び | 間隔 | 何ms遅れると次を取るか |
|---|---|---|
| 16分 | 88ms | 45ms |
| 8分 | 176ms | 89ms |
| 付点8分 | 264ms | 133ms |

しかも取られた次のノーツは本来の時刻には既に消えているので、**1回の遅れで2つ崩れる**。

**判定を広げたから生まれた不具合ではない**（絶対値で選ぶ限り、窓の広さに関係なく
間隔の半分で起きる）。ただし広げたことで「取れて当然」と感じる遅れの範囲が
MARVELOUS 25ms → 55ms、GREAT 100ms → 150ms と広がったぶん、**目立つようになった**。

直し方は「**時刻を過ぎたノーツを先に見る**」。ノーツは前から順に来るので、
前を飛ばして次を取ると必ず破綻する。遅れ側に候補が無いときだけ、
これから来るノーツ（早く押した場合）を見る。どちらの側でも、
そのなかでは時間がいちばん近いもの、同じなら押した位置にいちばん近いものを選ぶ。

```js
const rank = now >= noteTime ? 0 : 1;   // 0=遅れ / 1=まだ来ていない
// rank → 時間の差 → 押した位置との距離 の順に比べる
```

これで「1つめを叩き損ねて2つめのタイミングで叩いた」ときも、
2つめ（差0ms）のほうが1つめ（差176ms）より近いので2つめが取れる＝ずれ込まない。

`tools/mode/rhythm-near-note-match-check.js` が、16分・8分・付点8分のそれぞれで
「遅れても次へ移らない」「取り逃してもずれ込まない」「同時押しは位置で選ぶ」
「タイミング調整を入れても順番が保たれる」ことを、実際に関数を動かして毎回確かめる。

### 曲ごとの歯ごたえ（2026-09-05）

**5曲ともレベルが似たりよったりだった。** 先行公開の5曲は EASY が全部 Lv.8、
HARD 15〜16、EXPERT 22〜23 で並んでいた。曲が違うのに難しさが同じでは、選ぶ楽しみがない。

原因は量の決め方だった。`DENSITY_TARGET` は「1拍あたり何個」しか持っておらず、
曲ごとに違うのは実質テンポだけ。5曲の BPM は 155〜173 しか違わないので、
どの曲も同じ量になっていた。実測でも計算とぴったり一致する。

| 曲 | perBeat × BPM/60 | 実測(EASY) |
|---|---|---|
| MF × ICHIKA MIX | .54 × 169/60 = 1.52 | 1.50 |
| Stay With Me | .54 × 170/60 = 1.53 | 1.53 |
| 綺季一閃 | .54 × 155/60 = 1.40 | 1.41 |

そこで「その曲がどれだけ譜面を詰められるか」を音源から出し、量に掛けるようにした
（`songChallengeFactor`）。

| 見るもの | 効き（指数） | 考え方 |
|---|---|---|
| テンポ | 0.7 | 速い曲ほど16分が詰まって忙しい |
| 毎秒の打点数 | 1.0 | 音が多い曲ほど詰められる |
| 拍のはっきりさ（`beatClarity.ratio`） | 0.55 | 拍が立っている曲は詰めても気持ちよく叩ける。立っていない曲は詰めるほど曲と合わなくなる |

基準は「ふつうの曲」として固定値（BPM 170 / 毎秒7.0打点 / はっきりさ1.30）で持つ。
曲が増えても平均を取り直さずに済み、**昔作った譜面が新しい曲のせいで変わることもない**。
極端にならないよう 0.78〜1.26 で挟む。

**下限（`minPerSecond`）だけは掛けない。** 下限は「これ以下だと間延びして拍が取れない」
ための線であり、薄い曲だからといって下げてよいものではない。上限は掛ける
（掛けないと濃い曲がそこで頭打ちになり、せっかくの差が消える）。

結果（基準の Monster Hero MASTER = Lv.30 は据え置き。`LEVEL_SCALE` を再校正した）:

| 曲 | 歯ごたえ | EASY | NORMAL | HARD | EXPERT | MASTER |
|---|---|---|---|---|---|---|
| Monster Hero | 1.11 | 8 | 11 | 15 | 21 | 30 |
| 綺季一閃 | 0.98 | 7 | 10 | 15 | 20 | 31 |
| ドパガキリミックス | 1.07 | 8 | 9 | 14 | 22 | 28 |
| MF × ICHIKA MIX | 0.86 | 7 | 9 | 12 | 18 | 24 |
| Stay With Me | 0.79 | 6 | 7 | 11 | 17 | 23 |

前は EASY の幅が1（全部8）だったのが3に、HARD が2から4に、EXPERT が2から5に広がった。
MASTER の毎秒ノーツ数も 2.59〜3.84 と、曲の性格どおりに散る。

`tools/mode/rhythm-song-challenge-check.js` が、この差がゲームに出ているかを毎回見張る。
係数を弱めたり密度の決め方を戻したりすると落ちる。

### 同時押しはEASYから（2026-09-05）

同時押しを上位難易度の特権にしていたが、これは間違いだった。**指は2本ある**ので、
離れた2か所を同時に押すのは1か所を押すのとほとんど変わらない。
難しいのは同時押しそのものではなく**置き方**。

だからEASYから出し、下の難易度ほど置き方を易しくする。

| | 間隔（触る場所どうし） | 置く位置 | 前後の空き | 太さ | 1分あたり |
| --- | ---: | --- | ---: | ---: | ---: |
| EASY | 2レーン（左端と右端） | 拍の頭だけ | 3グリッド | 3以上 | 2.4 |
| NORMAL | 2レーン（左端と右端） | 拍の頭だけ | 2グリッド | 3以上 | 3.2 |
| HARD | 1.5レーン | どこでも | 2グリッド | 3以上 | 4.0 |
| EXPERT | 1.25レーン | どこでも | 1グリッド | 2以上 | 4.8 |
| MASTER | 1レーン（指の太さ） | どこでも | 1グリッド | 2以上 | 7.2 |

同時押しは決めの一発なので**元のノーツも動かす**（5レーンしか無いため、
真ん中に置いたままでは離せない）。動かしたあと、前後との跳びがその難易度の上限を
超えないことを確かめる。

「押さえながら別を叩く」は別もの（`tapDuringHold`）。片方の指がふさがった状態で
もう1本を動かすので本当に難しく、こちらはEXPERT以上のまま。

レベルの計算でも、同時押しの重さは**離れているほど軽く**している
（2レーンで+0.15、指の太さぎりぎりで+0.6）。

### 判定ラインの拍と、毎フレームの書き込みを減らす（2026-09-05）

**演出強化**: 判定ラインを曲の1拍で脈打たせる（`@keyframes mhRhythmLinePulse`）。

- 拍の長さ `--rhythm-beat` は `beginRun` で**一度だけ**書く。毎フレームのJSは増えない。
- 動かすのは `opacity` と `scaleY` のみ。`transform-origin:50% 50%` なので**線の位置は動かない**。
  判定・入力・当たり判定には影響しない。
- 軽量モード / 演出量MINIMAL では `animation:none`。

**最適化**（見た目・判定・スコア・譜面は変えない）:

| やったこと | なぜ効くか |
| --- | --- |
| 縦位置 `transform` を、丸めた `yPx` が変わったときだけ書く | 奥にいるノーツは1フレームの移動が1px未満。書けば合成のやり直し対象になるのに、見た目は1pxも変わらない |
| SLIDE の帯の高さ（`--rhythm-slide-height`）を変わったときだけ書く | HOLD の帯では既に行っていた工夫。SLIDE だけ毎フレーム書いていた |

控え（`el._rhythmTransform` / `el._rhythmSlideBody`）は `beginRun` でも捨てる。
**控えだけ古く残ると、値が同じだと判断して書き込みを飛ばし、見た目がズレたまま固まる。**

### 「曲に合っていない譜面」の正体は、ずれではなく**拾う音**だった（2026-09-05）

ユーザー指摘「ステイウィズミーが全然テンポにあった譜面になってない気がする」。

**まず疑ったこと（外れ）**: 全尺は `tempo-unstable` の重い警告を `--force` で押し切っていたので、
格子がドリフトしていると考えた。**測ったら違った。**
曲を8つに割って格子と実打点のずれを見ると、全区間で中央値±7ms以内・±43ms内が96〜99%。
格子は頭から終わりまで合っていた。

**本当の原因**: 拾っている音。打点を拍の位置で分けて強さを比べると:

| 曲 | 拍の頭 | 8分裏 | 16分裏 | 拍の頭÷16分裏 |
| --- | --- | --- | --- | --- |
| Monster Hero | 0.583 | 0.573 | 0.391 | **1.49** |
| ドパガキリ(ショート) | 0.585 | 0.465 | 0.358 | **1.63** |
| 綺季一閃 | 0.569 | 0.479 | 0.483 | 1.18 |
| Stay With Me | 0.405 | 0.403 | 0.393 | **1.03** |
| MF × ICHIKA MIX | 0.480 | 0.470 | 0.489 | **0.98** |

Stay With Me は**強弱で拍が立っていない**。ドラムではなくストリングスや伸びる音の
立ち上がりを16分裏として拾っており、それが打点の半分を占めていた。
結果、譜面の16分裏の割合が HARD 35% / MASTER 42%（Monster Hero は 3〜5%）。
「曲の聞こえるリズムと関係ない場所を叩かされる」状態になっていた。

**直し方**: 解析に `beatClarity`（拍の頭 ÷ 16分裏）を出し、`BEAT_CLARITY_MIN`(1.10) を
下回る曲では、16分裏は**その曲の16分裏のうち強いほうから `OFF_BEAT_KEEP`(35%) だけ**拾う。

- しきい値を「拍の頭の平均」にすると効かない。**拍が立っていない曲ほどその値も低くなる**ため
  （MF × ICHIKA MIX は 0.480 対 0.489 でほとんど落ちなかった）。
  「16分裏の中での上位いくつか」なら曲によらず確実に効く。
- 結果: Stay With Me の16分裏 42%→24%、MF × ICHIKA MIX も同じ理由で作り直し。
  拍がはっきりしている3曲は何も変わらない。

### 同じレーンの長押し中に、別の指で同じレーンを叩けるか（2026-09-05・ユーザーからの質問）

### 叩いたノーツと違うものが取られる（2026-09-05・2回直した）

判定の受付幅(240ms)は、16分(88ms)や8分(176ms)の間隔より広い。
つまり**1回の入力に対して候補が必ず2つ以上ある**。どちらへ渡すかの決め方を2回直した。

| 回 | 決め方 | 起きたこと |
| --- | --- | --- |
| もと | 時間の差の**絶対値**がいちばん小さいもの | 1つめの少しあとに叩くと、まだ来ていない2つめへ移る（ユーザー指摘①） |
| 1回目 | 過ぎている中で**いちばん前** | 2つめの時刻ちょうどで叩いても1つめが取られ、2つめが必ずMISS（ユーザー指摘②） |
| 2回目 | 過ぎている中で**いちばん後ろ** | ①②とも起きない |

いまの決め方。

```
rank 0 = 時刻を過ぎている(遅れて叩いた)  … そのなかで **いちばん後ろ**
rank 1 = まだ来ていない(早く叩いた)      … そのなかで **いちばん前**
同じ時刻なら、押した位置にいちばん近いもの
```

言い換えると **1つのノーツが取られるのは「次のノーツの時刻が来るまで」**。
そこから先は次のノーツのものになる。受付幅が間隔より広くても、受け付ける相手が前後へ滑らない。

- 実装は `rhythmMatchInputBatch` の `const better=rank===0?noteTime>pickedNoteTime:noteTime<pickedNoteTime;`
  **rank 0 と rank 1 で向きが逆**。ここを同じ向きにすると、必ずどちらかの指摘が再発する。
- 検査 `tools/mode/rhythm-near-note-match-check.js` は①②を**セットで**見る。
  片方だけ直すともう片方が落ちるようにしてある。

### 指の持ち替えが一度も成立していなかった（2026-09-05・2回目）

**ユーザーの指摘**「指置き換えも機能してない。してるとしたら時間が短すぎる？」

猶予の長さの問題ではなく、**2か所で塞がっていた**。

1. `rhythmMatchInputBatch` は「いまの時刻の前後 `RHYTHM_INPUT_MATCH_WINDOW_MS`(240ms)以内に
   **始まる**ノーツ」しか候補にしない。3秒のHOLDを2秒押さえてから持ち替えると、
   そのノーツの開始時刻はとっくに窓の外なので、置き直した指がどこにも当たらない。
2. `RHYTHM_GESTURE_RUNTIME.release()` が指を離した瞬間に終端判定を作り、
   `note.endTimeMs` を「いまより前」へ書き換えていた。そのため `inputEnds` は必ず
   「終わり際まで来ている」分岐へ入り、猶予を見る分岐へ一度も行かなかった。

直した形。

- `release()` は、終わりより `RHYTHM_HOLD_RELEASE_GRACE_MS` より手前で離したときは
  **判定を確定させない**。`note.releasedAtMs` を立てて `rhythmFloatingNoteAdd()` するだけ。
  途中で外れて失敗が確定しているとき(`failed`)と、指が取り消されたとき(`cancelled`)は従来どおり確定させる。
- 浮いているノーツは `RHYTHM_FLOATING_NOTES` に控え、`rhythmMatchInputBatch` が
  **開始時刻の窓と関係なく**、ふつうの候補より**先に**拾う
  (押さえ直しを別のノーツへ吸われると持ち替えが必ず失敗するため)。
  見るのは「その時刻に見えている帯へ指が乗ったか」(`rhythmHandoverSpanAt`)だけで、時間の近さは見ない。
- 引き継ぎ時の `bind` へは `picked._rhythmOriginalType||picked.type` を渡す。
  `bind` が `note.type` を `'HOLD'` へ書き換えているので、これが無いと
  持ち替えた瞬間にSLIDEがただのHOLDへ変わって経路の追従が消える。
- 猶予 `RHYTHM_HOLD_HANDOVER_GRACE_MS` は 120ms → **200ms**。
  離す→置き直すは実測で100〜200msかかる。
- 猶予の定数は `data/rhythm-mode.js` へ1つだけ置く。
  持ち替えは「離す側(game-system.jsx)」と「結びつける側(rhythm-mode.js)」の両方が
  同じ数字を見ないと成立しないため。
- 検査 `tools/mode/rhythm-hold-handover-check.js` は、本番の `rhythmMatchInputBatch` を
  偽のブラウザで実際に動かして「1.5秒たってから置き直した指が同じノーツを引き継げる」ことを見る。
  **前の版はここを文面の一致だけで見ていて、しかも「rhythm-mode.js は releasedAtMs を見ない」という
  誤った前提を確かめていたため、壊れていることに気づけなかった。**

### 始めた直後にノーツが出ず MISS だけ増える（2026-09-05）

**ユーザーの指摘**（演奏画面のスクリーンショット）
「初回起動時はよくこの状態になる／リスタートすると直るけど修正してほしい」

ノーツの置き場所は `measureTravel()` がプレイエリアと判定ラインを測って決める。
その結果を `travelCacheRef` へ覚えるのだが、覚える条件が
**`areaRect.height>0` だけ**だった。まだ組み上がっていない最中の値でも
高さは 0 ではないので、そのまま覚え込んで二度と捨てられない。

サンドボックスで実測したところ、スタイルが効く前のプレイエリアは
**844px の画面に対して 3352px** あった。この値で固定されると、ノーツは
画面の外へ置かれたまま戻らない。それでも曲は進むので
`visitNote` の MISS 判定だけが走り、ライフが減っていく。
**リスタートで直っていたのは、そのとき覚えた値を捨てていたからにすぎない。**

四重に塞いだ。

1. **覚える条件を「遊べる形か」にする**(`rhythmTravelLooksReady`)。
   高さ・幅が 0 でないことに加えて、
   ・プレイエリアの高さが画面の1.5倍を超えていない（＝まだ積み上がっている最中ではない）
   ・判定ラインの中心がプレイエリアの中にある
   を満たしたときだけ覚える。満たさない間は毎フレーム測り直すので、
   整った瞬間から正しい位置で流れ始める。
2. **`ResizeObserver` でプレイエリアを見張る。** 大きさが変わったら必ず捨てる。
   絵の読み込み完了・全画面・セーフエリアの確定は `window.resize` を
   起こさないことがあり、それだけでは取りこぼす。監視するだけで DOM は
   書き換えないので、#943 のような自己ループにはならない。
3. **画面が組み上がってから曲を鳴らす。**
   `startRhythmTrack(key, vol, {autoStart:false})` で用意だけして、
   `beginRun` が `waitUntilPlayable()`（rAF で遊べる形になるまで待つ／
   上限 `RHYTHM_LAYOUT_WAIT_MAX_MS`=1.2秒）を通ったあとに `audio.start()` する。
   既定は今までどおり自動再生なので、プレビューなど他の呼び出しは変わらない。
4. **置けないあいだは MISS にしない。** `measureTravel()` の戻りに `ready` を持たせ、
   `ready!==false` を `placeable` として tick が持つ。置けないあいだに過ぎたノーツは
   `applyJudgment` を通さずに取り除く（スコア・コンボ・ライフ・判定数のどれにも入れない）。
   見えていないノーツで減点しないための扱いで、これが最後の砦になる。

検査 `tools/mode/rhythm-first-run-layout-check.js` は、スタイルが効かないまま
演奏を始めさせ、4秒すごしてから途中でスタイルを流し込む。
実機で言えば「画面が組み上がるのが遅れている」状態そのもの。
**修正前は 4秒で ライフが 1000→850 まで減り、修正後は 1000 のまま**。
組み上がったあとにノーツが画面へ出ることまで見る。

### ポーズの「戻る」を押しても戻れない（2026-09-05）

**ユーザーの指摘**（練習のポーズ画面のスクリーンショット）「戻るを押しても戻れない」

`data/rhythm-result-replay-remount.js` は、iPhone Safari で
「プレイエリア側の `touchend` がポーズのボタンの `click` を消してしまう」問題を避けるため、

### 判定をやさしくした・振動・マスモンの待機（2026-09-05）

実機で遊んだユーザーからの5点。

**1. 判定の幅（最優先）**
「やってみて思ったけどめちゃくちゃむずいからタップ判定をもう少しゆるくしたほうがいい」

| | 旧 | 新 |
| --- | ---: | ---: |
| MARVELOUS | ±25ms | **±40ms** |
| EXCELLENT | ±50ms | **±75ms** |
| GREAT | ±100ms | **±130ms** |
| GOOD | ±150ms | **±170ms** |
| BAD | ±200ms | ±200ms（据え置き） |

±25msは、指が触れてから画面が反応するまでの遅れ（端末差で20〜40ms）だけで
最上位判定を外す幅だった。よその音ゲーの最上位判定は±40〜50msがふつう。
**BADだけ動かさない**のは、入力とノーツを結びつける窓が±200msで固定されているため
（`rhythmInputMatchBounds` / `timeDistance<=200`）。ここを超える判定を作ると、
まだ来ていないノーツまで拾ってしまう。

押す場所の余白も広げた。それまで**幅1以外は余白ゼロ**で、見えている帯から
わずかでも外れると取れなかった。指の当たりは点ではなく面なので、狙って押しても外れる。

| | 旧 | 新 |
| --- | ---: | ---: |
| 幅1 | .18サブレーン | **.45サブレーン** |
| 幅2以上 | 0 | **.35サブレーン** |

どちらも「隣のノーツの中心」までは届かない大きさに留める
（幅1が隣り合うとき、隣の中心はサブレーン1.5ぶん先）。

保存してある自己ベストと全国ランキングには手を触れていない。過去の記録はそのまま残り、
これから遊ぶぶんが出やすくなるだけ。

**2. 振動が効かない**
`navigator.vibrate(8)` を呼ぶだけだった。2つ問題があった。

- **iPhone(Safari)には Vibration API そのものが無い**。呼んでも何も起きない
- 8msは短すぎて、対応している端末でも無視されることがある

いまは `RHYTHM_HAPTICS` にまとめ、使える端末では12ms（モンスターノーツは26ms）で呼び、
iOSでは17.4から入った「スイッチ型チェックボックスを切り替えると端末がコツンと鳴る」
仕組みを借りる（画面外の見えないスイッチを押す）。どちらも無い端末では
オプション画面に「この端末は振動に対応していない」と出し、「設定はあるのに効かない」
状態にしない。その場で確かめる「試す」ボタンも置いた。

**3. マスモンが出番のあと止まる**
`[data-rhythm-side-hit="1"]{animation:…Cheer 700ms … 1!important}` の印が
歓声のあとも残り、待機の跳ねを打ち消し続けていた（`!important` かつ1回だけ再生なので、
再生が終わると**何も動かない状態で固定**される）。
歓声が終わったら印を外し、`data-rhythm-side-phase="done"` の待機へ戻す。
出番のあとは最初のぴょんぴょんとは別の動き（1拍の2倍でゆっくり左右へ揺れる）にして、
どの子の出番が済んだかが見て分かるようにした。

**4. 曲えらびで曲を鳴らす**
選んでいる曲を鳴らす。一覧をなぞって選び替えているあいだに読み込み直さないよう、
350ms止まってから鳴らす。画面を離れる・曲を選び替える・設定でOFFにする、のどれでも止まる。
設定は `songPreviewEnabled`（新しいキー・既定ON・既存の保存値には無いので読み込み時に補われる）。

**5. 自己ベストは難易度ごと**
曲えらびの難易度ボタンの中に、その難易度の自己ベストを出す。
全国ランキングは難易度をまたいだ合算のままで、これとは別物。

### 大きく動かす見せ場を足した（2026-09-05）

「まだバリエーションが少ない。スライドで端から端に行く、同時押しで右左くねくねする、
指をクロスしなきゃいけないような配置とか色々必要」という指摘への対応。

**まず測ったこと。** 語彙は14種類あったのに、実際に出ていたのはEASYで6種類・MASTERで10種類。
`ジグザグ` `端振り` `2つ飛ばしの階段` はほぼ1本も出ていなかった。
SLIDEの移動幅は最大2.5レーンで、端から端（4レーン）へ抜ける一本は**一度も無かった**。

**入れたもの（4つ）**

1. **形の語彙を使い切る** — 直前に使った形を後回しにする（上位4件の中でまだ使っていないほうを前へ）。
   跳び1レーンでも作れる形（ゆれ・踊り場つき階段）を足してEASYの選択肢を広げた。
   結果: EASY 6→8種類 / NORMAL 9→11 / HARD 9→13 / EXPERT 8→13 / MASTER 10→15
2. **端から端まで動くSLIDE（スイープ）** — 音の高さから作った経路を引き伸ばす。
   HARDから。難易度の線引きは**追従の速さ**（6 / 8 / 10 レーン毎秒）
3. **同時押しの連なり** — ペアごと右左へ振る・端から端へ流す・間隔を広げる。EXPERT以上
4. **クロス** — 押さえっぱなしより外側を叩かせ、指を交差させる。EXPERTで少し、MASTERで中心に

**同時押しの連なりがEXPERT以上なのは、場所が足りないから。**
5レーン（サブレーン10）しかないので、EASY〜HARDの同時押しの条件
（太いノーツ・大きく離す）を満たすと2つで使い切ってしまう。

| | 幅+幅+間隔 | 動ける幅 |
| --- | ---: | ---: |
| EASY / NORMAL | 3+3+4 = 10 | 0 |
| HARD | 3+3+3 = 9 | 0.5レーン |
| EXPERT / MASTER | 2+2+2 = 6 | 2レーン |

**あわせて直したこと**

- 同時押しの前後には `restrikeLimitMs`（105ms）の空きが要る、という条件を足した。
  同時押しは指を2本とも使うので、直前直後にノーツがあると押せない。
  置き場所を動かしても直らないので、置く前に候補から外す
- 自動修正（STEP7）が同時押しの片方だけを寄せて**離れかたを縮めていた**のを止めた。
  実際にEXPERTの1組が1.00レーンまで縮み、設計の1.25レーンを割った。
  そのぶんMASTERに「忙しい」が数件残るが、押せないは0のまま

**結果（3曲・全難易度で押せない0件）**

| | スイープ HARD/EX/MA | 同時押しの連なり EX/MA | クロス EX/MA |
| --- | --- | --- | --- |
| Monster Hero 候補v3 | 2 / 4 / 3 | 4本 / 6本 | 1 / 4 |
| SIX ÉTERNEL | 0 / 3 / 3 | 6本 / 6本 | 2 / 2 |
| ドパガキリミックス | 0 / 5 / 4 | 6本 / 6本 | 1 / 1 |

SIX ÉTERNEL のHARDでスイープが0本なのは、207BPMでグリッドが短く、
HARDの追従上限（6レーン毎秒）では画面を横断しきれないため。曲の速さで決まる。

### 難易度レベル（Lv.）— 曲をまたいで見比べる物差し（2026-09-05）

難易度の名前（EASY〜MASTER）は「その曲の中での段階」でしかない。曲が増えると
「この曲のHARDと、あの曲のNORMAL、どっちが難しい？」に答えられなくなる。
そこで、譜面そのものから計算する数字 **Lv.** を持たせた。

**基準は「Monster Hero 候補v3 の MASTER = Lv.30」**（ユーザーが決めた基準点）。
ここだけは動かさず、ほかは全部この基準からの相対で決まる。

#### 測り方（`tools/mode/rhythm-chart-level.js`）

音ゲーの難しさは「1曲の合計」ではなく「いちばん忙しいところ」で決まる。
長いだけの曲は難しくない。

1. 1ノーツごとに「指の仕事量」を出す
   - 詰まり具合（直前との間隔が短いほど重い・最大2.2倍）
   - 横の移動（触る点どうしの距離 ÷ 時間・最大2.2倍）
   - 細さ（幅1で+0.35 / 幅2で+0.15）
   - 種類（同時押し+0.5 / FLICK+0.25 / 終点フリック+0.35 / 押さえながら+0.5）
   - SLIDEの折り返し（1回+0.2・最大+0.8）
2. 4秒の窓を1秒ずつずらして「毎秒の仕事量」を出す
3. **上位10%の平均（ピーク）を6割＋全体平均を4割**
4. Lv. = その値 × 係数（基準がぴったり30になる値）

レベルは仕事量に**そのまま比例**させている（曲がりを付けない）。
「Lv.が2倍なら忙しさも2倍」と説明でき、曲が増えても物差しがぶれない。

#### いまのレベル

| 曲 | EASY | NORMAL | HARD | EXPERT | MASTER |
| --- | ---: | ---: | ---: | ---: | ---: |
| Monster Hero 候補v3（**基準**） | 8 | 10 | 15 | 21 | **30** |
| Monster Hero 候補v2 | 9 | 11 | 18 | 27 | 31 |
| Monster Hero 候補v1 | 7 | 9 | 12 | — | — |
| SIX ÉTERNEL | 10 | 11 | 20 | 26 | 38 |
| SIX ÉTERNEL ドパガキリミックス | 7 | 9 | 15 | 18 | 25 |

SIX ÉTERNEL の MASTER が 38 と高いのは、207BPMの曲で毎秒4.15ノーツまで詰まっているため
（Monster Hero は 3.45）。数字が「この曲のMASTERは別格」と正しく言っている。

#### 決まりごと

- レベルは**手で決めない**。`node tools/mode/rhythm-chart-level.js --write` が
  `data/rhythm-mode.js` の `<rhythm-chart-levels>` マーカーの内側だけを書き換える
- 譜面を作り直したら、レベルも必ず作り直す（`rhythm-chart-level-check.js` が食い違いを見つける）
- 8ノーツ未満の確認用の型は測らない（「いちばん忙しい4秒」が意味を持たないため）
- 上限は50まで用意してある（この先もっと難しい曲が来たときのため）

### 音源解析V3

ゲームのBGMは密なミックスで、高域はほぼ鳴りっぱなし。帯域の絶対値で見ると分けられないので、
**その帯域自身の直近の中央値と比べて何倍か**（コントラスト）で見る。

- 帯域は5つ（低40-120 / 中低120-400 / 中400-1600 / 高1600-4000 / 空4000-7800 Hz）
- 打点の性格は4つ … `PUNCH`（低だけ跳ねた）/ `BODY`（中低〜中）/ `LIGHT`（高だけ）/ `FULL`（全部）
- 伸びる長さは、いちばん跳ねた帯域の中で、打点の直前の高さを基準に測る
- 音の高さはメロディの帯（600Hz中心）だけ残してから自己相関で取り、
  オクターブの取り違えを直してならす

実測（Monster Hero）: 打点1085件 / 耳で確認済みの既存候補の82〜87%を含む /
16分格子へ±43msで100% / 大きな一発は拍頭に62% / 軽い音は拍頭16%（裏へ散る） /
重い打点は8分の位置に67% / 音の高さが一気に跳ぶ点0%。

## 16. オプション STEP1（デバッグ導線へ実装済み）

正式公開時にも再利用する音ゲー専用オプションを、現在は音ゲーデバッグ画面の「⚙️ オプション」から開ける。通常HOMEや一般公開導線には接続しない。保存先は既存の `mh_rhythm_settings_v1` を後方互換で拡張し、旧データが `noteSeEnabled` / `noteSeVolume` だけでも欠損項目を現行相当の既定値へ正規化する。

画面は「音量」「プレイ」「表示」「演出・端末」の4カードで、次を設定できる。

- BGM音量 0～100（音ゲー再生だけへ適用）と直接タップによるBGM試聴
- タップ音量 0～100、タップ音 ON/OFF、直接タップによるSE試聴
- ノーツ速度 1.0～12.0（0.1刻み、6.0が従来流速）
- ノーツサイズ 80～120%（5%刻み、入力hitboxは不変）
- 判定タイミング調整 -100～+100ms（5ms刻み）
- FAST/SLOW表示、判定文字表示
- レーン発光（標準／控えめ／なし）
- 演出量（標準／少なめ／最小）、振動、軽量モード

「デフォルトに戻す」は編集中の値だけを戻し、「保存」で初めて確定する。操作ボタンはiPhoneのSafe Areaを避けた画面下固定バーに置き、設定項目だけをスクロールする。未保存変更がある場合は保存ボタンを強調する。振動の既定値はOFFで、Vibration APIがない端末でも失敗しない。

BGM音量・タップ音量・ノーツ速度・ノーツサイズ・判定タイミング調整は、**つまんで動かせるスライダーと、1段階ずつ動かす「−／＋」ボタンの両方**で変更する。現在値は常時表示し、最小値・最大値では対応するボタンを無効化する。範囲・刻み・保存形式・runtime計算は上記の現行仕様を維持する。

当初は「−／＋」だけにしていたが、実機で遊んで**「プラスマイナスでしか変えられないからめんどう」**という指摘があった（2026-09-04）。音量0〜100や速度1.0〜12.0のように幅の広い項目では、端から端まで何十回も押すことになるため。スライダーを足したうえで「−／＋」も残し、ざっくり合わせる／1目盛りずつ詰める、を使い分けられるようにする。スライダーでつまんだ値は必ずその項目の刻みへ丸め、範囲外・数値でない値は範囲の中へ収める。つまみは指で掴めるよう26pxとする。

ノーツ速度は見た目の移動時間（travel）だけを変更する。整数速度を基準点として0.1刻みで線形補間し、6.0は従来相当の2150msを厳密に維持する。基準点は 1.0=7000 / 2.0=6000 / 3.0=5000 / 4.0=4000 / 5.0=3000 / 6.0=2150 / 7.0=1680 / 8.0=1300 / 9.0=1020 / 10.0=800 / 11.0=630 / 12.0=500（ms）で、低速側は等差、高速側は約1.27倍ずつの等比になっている。どの帯域でも0.1動かせば必ずtravelが変わる。authored noteTime・BPM・beatZero・判定窓・入力時刻・スコア・曲時間・HOLD/SLIDEのauthored timingは変更しない。旧保存値（3.0〜10.0 / 0.5刻み）は新しい範囲の内側なのでそのまま読み込める。

ノーツサイズは**ノーツ頭の描画scaleだけ**を変更する。HOLD帯・SLIDE帯・ENDバー・入力hitboxはノーツサイズの影響を受けず、常にレーンgeometry基準のままにする。判定タイミング調整は同一の `judgmentTimingOffsetMs` を表示時計・入力・HOLD終端へ適用し、判定窓幅、BPM、noteTime、スコア計算は変更しない。FAST/SLOW・判定文字・レーン発光は表示だけを変える。演出量は彩度と非必須グロー/影を段階的に抑え、軽量モードは非必須グロー/影とtransitionを停止するが、入力判定、DOM判定ライン、ノーツ、レーンは残す。

正式HOMEへの入口と、正式公開時の最終デザインは未実装。

### 音量の独立性（現行仕様）

音ゲーのBGM／タップ音量は、メインゲーム（HOME）の音量設定とは**完全に独立**している。

- 音ゲーBGM: `Audio_.startRhythmTrack` が作る専用の `rhythmGain` ノードを、メインのBGM音量が
  かかる `bgmGain` を経由せず `ctx.destination` へ直結する。曲ごとの音量差は `safeTrackGain` で
  正規化する。**以前はrhythmGainがbgmGainへ直列に繋がり、両方の音量設定が掛け算になっていた**
  （メイン側のBGM音量を下げると音ゲー側をどれだけ上げても小さいまま・無音になる不具合があった）
- タップ音（SE）: もともとTone.js／`seBus`を使わず専用のAudioContextで鳴らしており、メインの
  SE音量とは無関係
- **全体ミュート（タイトル画面の「音がオフです」）だけは共通**に効く。`Audio_.setEnabled` が
  `window.__mhAudioEnabled` へ反映し、稼働中の音ゲーBGMのgainと、タップ音の`rhythmAudioGloballyEnabled()`
  判定の両方がこれを見る

`node tools/mode/rhythm-audio-independence-check.js` で確認する。

## 19. 週間対象曲と4部門ランキング（確定・未実装）

週間システムは、**正式譜面が完成している曲が3曲以上揃ってから実装する**。

### 対象曲

毎週、本番譜面が完成している曲の中から3曲を週間対象曲として選ぶ。

- 曲A
- 曲B
- 曲C

曲として登録されているだけでは対象にしない。ランキングへ使用できる正式譜面が完成していることを条件とする。

### ランキング部門

週間ランキングは合計4部門。

1. 曲A スコアランキング
2. 曲B スコアランキング
3. 曲C スコアランキング
4. 週間総合スコアランキング

### 難易度の扱い

**各曲ランキングを難易度別ランキングへ分けない。**

EASY / NORMAL / HARD / EXPERT / MASTER の全難易度を、同じ曲の1本のスコアランキングで競う。

ランキングは最終スコアそのものを比較する。

難易度上限スコアが

- EASY 600,000
- NORMAL 700,000
- HARD 800,000
- EXPERT 900,000
- MASTER 1,000,000

なので、MASTERを高精度で攻略できる上級者はより高いスコアを狙える。一方で、MASTERで大きく崩れたスコアより、低難易度を高精度・フルコンボしたスコアの方が上になる可能性がある。

難易度自体への追加順位補正は付けず、**あくまでスコアランキング**とする。

週間総合も1部門として扱い、難易度別ランキングへ分けない。

ただし、週間総合スコアを「3曲BESTの単純合算」にするか等の具体計算式はまだ確定していない。
