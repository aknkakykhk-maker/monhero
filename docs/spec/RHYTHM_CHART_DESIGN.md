# 譜面設計の原則（モンヒロビート）

音ゲーの譜面は「音に合わせてノーツを置く」だけでは成り立たない。
実際に遊ばれている作品（プロジェクトセカイ／CHUNITHM／maimai／太鼓の達人／
beatmania IIDX／Dance Dance Revolution／osu!／Arcaea／Beat Saber など）の譜面には、
共通して守られている作法がある。ここはその作法を、**このゲームの5レーン・10サブレーンの
形に合わせて言い直したもの**。自動生成ツール（`tools/mode/rhythm-chart-v3-*`）は
この文書を実装したものであり、検査（`tools/mode/rhythm-chart-*-check.js`）は
この文書が守られているかを機械で見張るためにある。

---

## 0. いちばん大事な順

譜面の良し悪しは、次の順で決まる。上のものが崩れていると、下をどれだけ凝っても良くならない。

1. **押せるか**（物理的に指が届くか）
2. **音と合っているか**（鳴っていない音を叩かせていないか、鳴っている大事な音を落としていないか）
3. **読めるか**（次に何をすればいいか、見た瞬間に分かるか）
4. **気持ちいいか**（手の流れ、曲の盛り上がりとの一致）
5. **飽きないか**（同じ形の繰り返しになっていないか）

---

## 1. 押せるか — 手の物理

→ 実装と数値は [`RHYTHM_MODE.md` の「手のモデル」](RHYTHM_MODE.md) を参照。

- 指は**2本**（スマホを両手で持って親指で押す）
- 指には**太さ**がある。触る点どうしが1レーン以上離れていないと2本入らない
- 1本の指は**毎秒9.5回**より速くは叩けない（105ms間隔が限界）
- 1本の指は**毎秒18レーン**より速くは動けない
- 押さえている指（HOLD/SLIDE）はその間ふさがっている

**この4つのどれかを破った譜面は、上手い下手に関係なく誰にも押せない。**
「難しい」ではなく「不可能」なので、難易度の話とは別の階層にある。

### 1.1 数ノーツ先まで見て指を割り当てる（2026-09-07）

「押せるか」は、1音ずつ「いま近い指」で取っていくと**誤判定する**。

> いまのノーツだけなら右手が楽 → でも右手を使うと 60ms 後のノーツが取れない。
> いまを左手で取れば、そのあと全部押せる。

`tools/mode/rhythm-hand-simulate.js` の合成テストでこの配置を作り、その場最適（beam=1）が
「押せない」と言い、先読み（beam=8）が押し方を見つけることを毎回確かめている。
手のモデルの値は `rhythm-hand-model.js` の1か所だけで、先読みは**同じ式**で数ノーツ先まで
複数の指の置き方（状態＝2本の指の位置・空く時刻）を持ち越すビームサーチ。
STEP6（プレイ可能性）・STEP7（自動修正）・生成の途中の確認・品質レポートは全部これを使う。

ただし先読みで押し方が見つかるのは「実在する押し方」だけで、**同じ場所を80msで叩き直す**ような
本当に押せない配置は押せないまま残る（合成テストで固定）。

生成の側でも、かたまりを置くたびに直近2拍ぶんを両手でシミュレートして「届くか」を見る。
指の太さ（105ms以内の2音）だけでは、「4レーンを217msで動けない」（207BPMの曲のMASTERで実際に出た）
のような**届かない**配置が通ってしまうため。同時押し・連なり・クロスのように形を決めたあとに
中心を動かす工程では、跳びの上限を「難易度の歩幅」と「その時間で指が動ける距離（18レーン毎秒×0.9）」の
小さいほうにする。MASTERの歩幅4は「1拍あれば4レーン」の意味であって、97msで4レーンではない。

## 2. 音と合っているか — レイヤリング

本物の譜面は「どの音を叩かせるか」を**音の種類ごとに決めている**。
これを**レイヤリング**と呼ぶ。

| 音の種類 | 譜面での扱い | このゲームでの表現 |
| --- | --- | --- |
| キック（低い打点） | 曲の背骨。低難易度でも必ず拾う | 太めのTAP。中央寄り |
| スネア／クラップ | 2拍4拍のアクセント | アクセント幅のTAP。左右で受け合う |
| ハイハット（細かい高音） | 埋め。高難易度でだけ拾う | 細いTAP。16分の裏 |
| 伸びる音（ロングトーン） | 押さえ続ける | HOLD。**音が伸びている長さぶん** |
| 高さが動く音（メロディ・スイープ） | なぞる | SLIDE。**音の高さの動きに沿った経路** |
| 切れる音・しゃくり | 弾く | FLICK・終点フリック |
| 大きな一発（シンバル等） | 区切り | 全幅のアクセント |

### 2.1 やってはいけないこと

- **幽霊ノーツ**（鳴っていない場所にノーツを置く）。密度の目標に届かせるために音の無い場所へ
  置くのは、譜面として最も嫌われる
- **背骨を落とす**（キックやスネアを飛ばして装飾だけ拾う）。曲を叩いている感じが消える
- **同じ音を毎回ちがう扱いにする**。同じフレーズは同じ形で来ないと、覚えられない

### 2.2 密度は「音量」ではなく「音の数」で決まる

盛り上がりの表現に密度を使うのは正しいが、**音楽が実際に持っている音の数を超えて増やしてはいけない**。
音量だけが上がっていく曲で密度を上げ続けると、終盤だけ異常に忙しい譜面になる。
（実際にそうなり、2026-09-05に「後半むずすぎる」と指摘を受けた）

盛り上がりは、密度以外でも表せる。

- ノーツの**幅**を広げる（見た目の圧が上がる）
- **種類**を増やす（HOLD・SLIDE・FLICKが混ざる）
- **同時押し**を入れる
- レーンの**動き**を大きくする

## 3. 読めるか — パターンの語彙

**ここが自動生成でいちばん落とし穴になる。**

レーンを「乱数で」「使用回数が少ない順で」決めると、押せるし音とも合っているのに
**まったく読めない譜面**になる。人が作った譜面が読めるのは、
限られた「形」の組み合わせでできているからで、次に来る形が予測できる。

### 3.1 形の語彙

| 名前 | 形 | 使いどころ |
| --- | --- | --- |
| **階段** | 1→2→3→4 と隣へ順に | 音階が上がる／下がるところ |
| **逆階段** | 4→3→2→1 | 同上（下降） |
| **交互** | 1→4→1→4 | 左右で受け合うリズム |
| **トリル** | 2→3→2→3（速い） | 細かい連打 |
| **縦連** | 3→3→3（同じ場所） | 同じ音の連打。遅いときだけ |
| **折り返し** | 1→2→3→2→1 | フレーズの山 |
| **対称（鏡）** | 中央をはさんで左右対称 | コール＆レスポンス |
| **開き／閉じ** | 中央→外／外→中央 | 盛り上がり／収束 |
| **ジグザグ** | 1→4→2→5→3 | 忙しい区間（高難易度） |
| **小さいジグザグ** | 1→3→2→4→3 | 右へ左へ振りながら上がる（跳び2＝HARDから） |
| **ゆれ** | 3→4→3→2 | 中央を挟んで左右へ1つずつ（跳び1＝EASYから） |
| **踊り場つき階段** | 1→1→2→2→3 | 同じ場所を2つ続けてから上がる（遅いときだけ） |
| **交差ステップ** | 1→4→2→5→3 を大股で | 指を交差させて取る（跳び3＝EXPERTから） |
| **端振り** | 1→5→2→4→3 | 端から端へ大きく振る（跳び4＝MASTERだけ） |
| **同時押し** | 2つ同時（離れているほど易しい） | 決めの一発 |

語彙をそろえても、**選び方が同じなら同じ形しか出てこない**。
実測（2026-09-05）では、14種類の語彙に対してEASYで6種類、MASTERで10種類しか使われておらず、
`ジグザグ` `端振り` は1本も出ていなかった。そこで

- 跳びが1レーンでも作れる形（**ゆれ・踊り場つき階段**）を足してEASYの選択肢を増やす
- **直前に使った形は後回しにする**（上位4件の中で、まだ使っていないほうを前へ出す）

の2つを入れた。結果はEASY 8種類／NORMAL 11／HARD 13／EXPERT 13／MASTER 15。
「同じくらいふさわしい候補の中で新しいほうを選ぶ」だけなので、音との対応は崩さない。

### 3.1.5 2026-09-07 に足した形

「バリエーションがまだ少ない」（同じようなレーン移動が繰り返される）という指摘で足した6つ。
どれも音楽上の根拠がある場所でだけ使う（下の「選ぶ規則」で候補に入る条件が決まっている）。

| 名前 | 形 | 使いどころ | 跳び |
| --- | --- | --- | --- |
| **長い階段** | 0→1→2→3→4→3（6〜8個） | ゆっくり上がり続ける／下がり続けるフレーズ | 1 |
| **呼びかけと返し** | 0,1,0 → 1,2,1 | 同じ音形が2回続くフレーズ（コール＆レスポンス） | 1 |
| **外→内→外** | −2,0,2,0,−2 | 山型の音の動き。サビで前へ出る | 2 |
| **内→外→内** | 0,−2,0,2,0 | 谷型の音の動き | 2 |

### 3.1.8 SLIDEの形の語彙（2026-09-12）

**ユーザー指摘**「バリエーションが少ない。カクカクとか広くなったり短くなったりとか
そういうのもほしい。音ゲーをもっと学習して」。

#### 直す前に何が起きていたか

配信中の譜面のSLIDE 552本が**全本、太さが一定**だった（HARD/EXPERT=幅3 / MASTER=幅2）。
途中で太さが変わるものは**0本**。中継点はどれも7点前後、移動量は上限の2.0/2.5に張り付き。
原因は `slidePathFor` の3か所。

| 場所 | 何をしていたか | 結果 |
| --- | --- | --- |
| `widthFor` の `if(kind==='SLIDE')return at(.4);` | 太さを難易度ごとに1値へ決め打ち | 全SLIDEが同じ太さ |
| `const step=...(endGrid-startGrid)/6` | 長さに関わらず常に約6分割 | **音の細かい揺れを平らに均していた** ＝「カクカク」が出ない正体 |
| `reach=min(2.5,maxLaneStep)` | 音がどれだけ動いても同じ移動量 | 全部が上限へ張り付く |

データ形式（点ごとの `subLaneWidth`）もランタイム（`rhythmSlideWidthAt` の線形補間）も
可変幅に**最初から対応済み**だったので、生成側だけで直せた。

#### 他の音ゲーを調べて分かったこと

- **途中で太さが変わるのは実質2作だけ**。CHUNITHM の「イカす SLIDE」（始点と終点で幅が違う。
  基本的に EXPERT 以上にしか出さない）と、プロジェクトセカイのスライド（中継点ごとに幅を持ち
  イージングで補間）。maimai / Arcaea / Phigros / ガルパ / SDVX は太さ一定。
- プロセカで幅を変える目的は制作者の言葉で2つ ——「**認識難を作る**」と
  「**曲の盛り上がりを表す**（小さければ落ち着き、大きければ盛り上がり）」。
- **SDVX の直角（カクカク）は「形」ではなく「短さ」で決まる**。1/32以下の移動が自動的に
  直角へ昇格する。判定は位置ではなく回した方向だけを見ていて、そのぶん専用の効果音で
  耳から拾わせている。
- **maimai は形が閉じた列挙（11種）**。直線 / 円弧（一周まで）/ p字・q字 / グランドp・q /
  V字 / グランドV字（頂点を自由に置ける）/ 稲妻 / 扇（1→3に分岐、唯一の分岐型）。
- 分岐を持つのは maimai の扇だけ。合流を持つゲームは見つからなかった。

#### いま実装してある語彙

**経路は音の高さに従わせたまま**にする（2.1 の「音と無関係なスライドを置かない」を守るため）。
足したのは「刻みの細かさ」「移動量」「太さの変え方」の3つ。

| 名前 | 太さの変え方 | 当てどころ |
| --- | --- | --- |
| `steady` | 一定 | 伸ばした1音、ロングトーン |
| `widen` | 細→太（0.55→1.0） | クレッシェンド、ライザー、サビへの助走 |
| `taper` | 太→細（1.0→0.55） | ディミヌエンド、リバーブの減衰、フレーズの終わり |
| `swell` | ふくらむ（中央が太い） | ひと山ある伸ばし、深いビブラート |
| `pinch` | しぼむ（中央が細い） | 抜けたあと戻ってくる音 |

選び方（`slideWidthShapeFor`）は乱数を使わない。この生成器は再実行で同じ譜面になることが前提。
**上から順に見て、先に当たったものを使う。**

1. 音の高さが途中で山になる → `swell` ／ 谷になる → `pinch`
2. `onset.character` が FULL / PUNCH（強い頭） → `taper`
3. LIGHT（軽い頭） → `widen`
4. それ以外は、終わりが始まりより高ければ `widen`、でなければ `steady`

実測（67本）では **1 で決まるのが約4割**で、`onset.character` より山谷が優先される。
PUNCH なのに `swell`、FULL なのに `pinch` になる本が3割ほどあるのはそのため
（音の形のほうが太さの表現に直結するので、この順序でよい）。
`steady` は0本だった。伸ばしっぱなしの音は HOLD 側へ行くので、SLIDE に来る条件が
構造的にほぼ存在しない。

基準の太さ（`widthFor` が難易度ごとの上限つきで決めたもの）を**上限**として、細くする方向にだけ出す。

#### 「カクカク」の出し方

中継点の刻みを、**音の高さの曲線がどれだけ細かく揺れているか**で決める（`heightWaviness` ＝
隣り合う差の符号が変わる回数）。揺れている音（ビブラート・トレモロ・うねるベース）ほど
細かく刻んで折れ線として見せ、まっすぐ伸びている音は粗く刻んで素直な直線にする（4〜14分割）。

経路自体は音の高さに従ったままなので、音と無関係な形にはならない。
**形を後から足すのではなく、もともと音の中にあった揺れを均さずに出す**のがこの直しの要点。

#### ジグザグ（＝ユーザーの言う「カクカク」）が出る条件

**等間隔で刻むだけでは出ない。** 音が行って戻る「折り返し点」をまたいでしまい、往復が1本の
直線に均されるため。実測で、刻みを細かくしても経路の折り返しは15%のまま増えなかった
（太さと点の数だけが増えていた）。**音が向きを変えた位置そのものを中継点として置く**と、
はじめてジグザグになる（`turningPoints`。上限 `SLIDE_MAX_POINTS`=20）。

⚠️ **ただし、出せる量の上限は曲そのもの。** SLIDEになる条件（`moves>=0.10` かつ `grids>=6`）を
満たす伸びは4曲で40件、そのうち**実際に音程が行き来しているのは9件（23%）だけ**。
これ以上振らせると 2.1 の「音と無関係なスライドを置かない」に触れる。
ジグザグをもっと増やしたいなら、**SLIDEにする材料そのものを広げる**しかない
（いまは伸びている音だけが対象。往復するアルペジオ・トレモロは単押しになっている）。
これは難易度とノーツ数に直接効くので、やるなら別の判断として扱う。
→ **§3.1.17 で入れた**（2026-09-12・ユーザー指示「スライドにする材料を広げる」）。

⚠️ **しきい値（`HEIGHT_TURN_MIN`）は0.5半音相当（0.028）。** はじめ 1e-6（実質ゼロ）で符号の変化を
数えたら、音の揺れではなく**ピッチ推定のジッタ**を拾っていた。数えた折れ165回のうち
72%が0.5半音未満（中央値0.29半音）で、結果として「中継点の数」と「音の動きの大きさ」が
**逆相関（r=−0.30）** になった（8.2半音動くメロディが5点・折れ0回 ／ 0.5半音の伸ばし音が
17点・折れ7回）。正規化も「長さ」ではなく「実際に動いた回数」で割る
（長さで割ると、まっすぐ長く動く音ほど小さくなって同じ逆転を起こす）。

#### 移動量

音の動きの大きさ（`range`）へ比例させる。上限は難易度の歩幅（`maxLaneStep`、最大2.5）、
**下限は2.0レーン**。下限は3回調整している。

| 下限 | 起きたこと |
| ---: | --- |
| 0.5 | 移動量の中央値が1.5→0.5レーンへ縮み、半分がほぼHOLDになった |
| 1.0 | **「指を止めたままでも通るSLIDE」が 35→44/67本へ増えた** |
| 1.8 | まだ MASTER で 6→11本。`laneAt` の0.5刻みの丸めで 1.8→1.5 になり、振れ幅の半分0.75が MASTER の許容0.82を下回っていた |
| **2.0** | 丸めても2.0が残り、半分の1.0が許容0.82を超える。31/67本＝変更前より少ない |

経路の振れ幅の半分が追従の許容以下だと、指を止めたままでも許容の内側に居続けられる。
カクカクは増えるが操作を要求しない「見た目だけの形」になるので、**そこは必ず測る**。

刻みを粗くすると音の山・谷を飛び越えて、書いたつもりの移動量より実際の振れ幅が
小さく出る。**山と谷の位置は必ず中継点として通す**。

#### 太さの下限は2

下限を1にしたら、幅1の中継点が **MASTER だけ** に出た（MASTER 24本中18本・押さえている
時間の36%が幅1／HARD・EXPERT は0本）。幅1は追従の許容がいちばん狭い（±0.57レーン）ので、
2026-09-11 に直したばかりの「MASTERがいちばん厳しい」状態がそのまま戻る。
基準の太さが1のノーツだけは1のままにする。

#### 効き方（4曲 × HARD/EXPERT/MASTER の SLIDE 67本で実測）

| | 変更前 | 変更後 |
| --- | ---: | ---: |
| 途中で太さが変わる本数 | 0本（0%） | **35本（52%）** |
| 太さの並びの種類 | 11通り | **24通り** |
| 中継点の数 最小/中央/最大 | 3 / 6 / 8 | 3 / 6 / **17** |
| 横の振れ幅 中央/最大 | 2.0 / 4.0 レーン | 2.0 / 4.0 レーン（据え置き） |
| 幅1が出るSLIDE | 0本 | 0本（据え置き） |
| 止めたままでも通る | 35/67本 | **31/67本**（減った） |
| 区間の最大速度 | 2.50 レーン/グリッド | **2.00**（下がった） |
| 折り返しのある本 | 28本（42%） | **30本（45%）** |
| 折り返しの総数 | 41回 | **47回** |
| 折り返す本の平均点数 | 6.7点 | **9.7点** |
| 中継点の間隔に緩急がある本 | 0本 | **50/66本** |

検査は `node tools/mode/rhythm-slide-shape-variety-check.js`。
バリエーションの下限だけでなく、**遊べるかどうか**（太さが2段以上飛ばない／まるごと幅1が無い／
止めたままでも通る割合）も同じ検査で見る。

#### 加速・減速（中継点の間隔）

中継点を等間隔ではなく、だんだん詰める／広げる。合計の長さは変えないのでタイミングはずれない。

| 名前 | 間隔 | 当てどころ |
| --- | --- | --- |
| `accel` | 後半ほど詰まる | せり上がって最後に畳みかける音、ドラムフィル、スネアロール、ライザー |

### 3.1.9 押さえノーツの同時押さえ（2026-09-12・生成器側だけ用意した）

ユーザーの指摘「スライドとかホールドの同時系もなかったっけ？」で分かったこと。

#### 直す前

生成器の1行が、押さえノーツどうしの重なりを**完全に禁止**していた。

```js
if(reserved.some(r=>startGrid<=r.endGrid+1&&endGrid>=r.startGrid-1))continue;
```

そのため配信中の全譜面で HOLD+HOLD / HOLD+SLIDE / SLIDE+SLIDE の同時押さえが**0件**。
一方でランタイムは2本同時を処理できる（デバッグ譜面「幅1 SLIDE同時操作」がある）し、
すぐ下の「2本押さえているときはTAPを置かない」も `covering.length!==1` と
2本を想定して書いてあった。**その分岐は一度も発火していなかった。**

#### 生成器側は用意した

難易度ごとの `heldPair` を足し、**1組だけ**許す形にした（指は親指2本なので3本目は作れない）。

| 難易度 | `heldPair` |
| --- | --- |
| EASY / NORMAL / HARD | `null`（従来どおり作らない） |
| EXPERT | `{perMinute:.8, minOverlapGrids:8, minGapLanes:1.5}` |
| MASTER | `{perMinute:1.6, minOverlapGrids:6, minGapLanes:1.25}` |

「かすっただけ」を同時押さえと呼ばないよう、重なりの長さに下限を置いた。

#### ⚠️ それでも0組。本当の壁は解析側だった

| | 値 |
| --- | --- |
| 解析済みの曲 | 20曲 |
| 伸びる音（`sustains`）の総数 | 2702件 |
| **重なっている組** | **0件** |
| 隣接しているだけの組 | 261件 |

`sustains` は `pitchCurve`（**1グリッドに1つの音高**）の「高さが続いている区間」から
作っている（`rhythm-audio-analyze-v3.js:263-275`）。**単声の旋律線なので、
区間は必ず順番に並び、原理的に重ならない。**

つまり生成器の条件をどう緩めても、入力に重なりが無いので同時押さえは生まれない。
この変更を入れても**配信中の譜面は1音も変わらない**（変更前後で全難易度のノーツ数が一致）。

#### 次にやるなら

- ❌ **2本目を作り出す**のは §2.1 の「幽霊ノーツ」に当たるので**やらない**
  （鳴っていない場所にノーツを置くのは、譜面として最も嫌われる）
- ⭕ **低い帯（ベース）と高い帯（旋律）で別に音高を追う**。どちらも実際に鳴っている音なので
  幽霊ノーツにならず、2つの `sustains` 列は重なりうる。
  ただし `rhythm-audio-features-v3.js` の音高検出を2バンドへ分ける作業が要る（DSPの改修）

#### 解析側だけ先に入れた（2026-09-12）

⭕ のほうを実装した。**旋律とまったく同じ関数**（`biquadBandpass` → `estimatePitch`）を使い、
帯と音域だけ変える。

| | 旋律 | ベース |
| --- | --- | --- |
| 帯（中心Hz / Q） | 600 / .55 | **110 / .7** |
| 音域 | 150〜1200Hz | **40〜250Hz** |

音高の後処理（オクターブの取り違え直し → 中央値でならす → 0〜1の高さへ）と

実測（Monster Hero・BPM 173.153 / 拍の頭 206ms）。

| | 件数 |
| --- | --- |
| 旋律の伸びる区間 | 151件 |
| ベースの伸びる区間 | **142件** |

#### 生成器が実際に置く（2026-09-12）

##### 置き方は1つに決めない

【ユーザー指示】「ノーツの置き方は曲のタイプや難易度でそれに見合った形に置くようにするように
して / 決めごとがあるとつまんなくなる / バリエーションが大事」

「2本目は必ず遠い端へ」のような**1つの決めごとにはしない**。形に名前を付けて語彙にし、
**その場の2本の動き量と難易度**で点数を付けて選ぶ（§3.1.6 と同じ考え方）。

| id | 置き方 | 出る難易度から |
| --- | --- | --- |
| `anchor_out` | 2本目を動かさず、旋律の外側で支える。いちばん読みやすい | すべて |
| `anchor_in` | 内側（中央寄り）で支え、旋律を外で動かす | HARD |
| `parallel` | 2本が同じ向きへ並んで動く（間隔は保つ） | EXPERT |
| `contrary` | 逆向きへ動く（開く・閉じる） | EXPERT |
| `diverge` | 離れていく | EXPERT |
| `converge` | 近づいていく | MASTER |
| `mirror` | 相方の経路を左右反転する。同時スライドでいちばん見栄えのする形 | EXPERT |
| `cross` | 内外が入れ替わる。いちばん忙しい | MASTER |

選び方（`heldPairShapeCandidates`）。

- **動き量の近さ**が主。`wantsBassMove` / `wantsMelodyMove` と実データ（`moves`）の差
- **使った形にはペナルティ**（`usage`×.6）。同じ形が何度も出ない
- **直前と同じ形は +1.5**。続けて同じ形は出ない
- **同点は種（曲ID＋位置）で崩す**。曲がちがえば並びも変わる

##### 置く段は「指の本数の確認」より前

`--- 15.5 同時押さえ ---` として、`--- 16. 指の本数を超える瞬間を作らない ---` の**前**に置く。
2本押さえているあいだのTAPは、16がそこで落としてくれる（実測で EXPERT 5件 / MASTER 6件）。

##### 実測（Monster Hero）

| 難易度 | 置いた組数（狙い） | 使われた形 |
| --- | --- | --- |
| EXPERT | 2組（2組） | `anchor_out` / `parallel` |
| MASTER | 4組（4組） | `converge` / `anchor_out` / `cross` / `parallel` |

**MASTERは4組すべて別の形**になった。

##### 踏んだ落とし穴

`spreadPick(candidates,count,minGap)` は**グリッド位置**を渡す関数（`minGap` もグリッド）。
はじめ配列の添字を渡していたため、添字0と1の差が1しか無いのに `minGap`（8拍ぶん）と
比べられて**2組目以降が全部はじかれ、1組しか置けていなかった**。グリッドを渡して直した。

##### 既存曲は変わらない

既存の解析ファイルには `bassSustains` が無いので、この段は一度も動かない
（`Array.isArray(audio.bassSustains)&&audio.bassSustains.length` で入口を閉じている）。
変更前のワークツリーと突き合わせ、全難易度のノーツ数が一致することを確認済み。

##### 検査

`node tools/mode/rhythm-held-pair-variety-check.js` が見張る。

- 語彙が3種以上・idが重複しない・難易度の段に幅がある
- **動き量の組み合わせで3種類以上の形が1位になる**（1つの決めごとになっていない）
- 使った形は後ろへ回る / 直前と同じ形は続けて出ない / 曲がちがえば並びも変わる
- 実際に生成して、**2組以上置いた難易度では形が2種類以上使われる**

わざと「必ず `anchor_out`」へ戻すと6件落ちることを確認済み（検査が形だけにならないように）。

#### 作り残しを片付けた（2026-09-12・同日）

ユーザーの問い「これってもう同時スライドとか同時ホールドとかでるの？」で、3つの穴が見つかった。

##### ① 形が端で潰れて、名前と中身が食い違っていた

`cross` を選んだのに2本目が動かないHOLDになっていた。レーンを**端ごとに丸めて**いたため、
行き先と出発点が同じ値になっていた。「ずらして収める」(`fitPair`)へ直し、
形に `follows`（`'none'` / `'partner'` / `'own'`）を持たせて、
**`'own'` の形が潰れたらその形は採らず次へ回す**ようにした。

##### ② `converge` / `diverge` の式が相方の動きと打ち消し合っていた

「相方の `from` と `to` にそれぞれ足す」書き方だったため、相方が1レーン動くと
足し引きが相殺して**動かなくなる**。自分の出発点を決めてから
**必ず動く量(`extra`)を足し引き**する形へ直した。

##### ③ 相方しか見ておらず、別のHOLDと指がぶつかっていた

指の間隔を「相方との距離」だけで見ていたので、**同じ時間に重なっている別の押さえノーツ**
との衝突を通していた。重なるすべての押さえノーツと、重なっている区間を刻んで比べる形へ直した。
物差しも本家（`rhythm-runtime-notes.js` の `overlapConflicts`）とそろえ、
「帯の中心どうしの距離」ではなく**2本の指をいちばん離して置いたときの距離**で見る。

> ⚠️ このとき自分の測定でも間違えた。HOLDは `subLane`、SLIDEは `lane` を経路の中心として
> 持っていて**単位がちがう**のに、素の `lane` を突き合わせて「指の間隔0.00レーン」と読み、
> 存在しない不具合を追いかけた。比べる前に必ず同じ物差しへ直すこと。

##### ④ 動き量の目安が実データと桁違いだった

`wantsBassMove` を0〜1の生の `moves` で書いていたが、伸びる音の `moves` は
**中央0.023・p90 0.125・最大0.36**。1.0近くには絶対に来ないので、
`wantsBassMove:.8` のような形は**一度も1位になれなかった**。
目安を「SLIDEになる下限(`slideMinMove`=0.10)を1.0とした倍率」へ直し、
呼ぶ側は `heldPairMoveScale()` を通す。

##### ⑤ 報告の数字が実際と食い違っていた

「4組置いた」と報告したのに譜面には3組しかなかった。後段の
「指の本数を超える瞬間を作らない」で落ちるため。お知らせを**その段のあとへ移し**、
残ったノーツから数え直すようにした（落ちた組数も書く）。

##### 直したあとの実測（Monster Hero）

| 難易度 | 残った組数 | 2本目が動くもの | 形 |
| --- | --- | --- | --- |
| EXPERT | 2組 | 0組 | `anchor_out` / `mirror` |
| MASTER | 2組（1組は指が足りず落ちた） | 1組 | `mirror` / `converge` |

指の間隔はいちばん狭いところで **1.00レーン（下限 1.00）**。
（`mirror` を語彙へ足し、SLIDEの経路を中継点に沿って見るよう直したあとの数字・2026-09-12）

> ⚠️ 同時スライド（§3.1.11）のノーツも `heldPair:true` を持つので、**お知らせは
> `doubleSlide!==true` で絞って数える**。絞らずに数えていたため「狙い2組なのに3組」と
> 報告した（2026-09-12）。

##### 出る組み合わせ・出ない組み合わせ

- ⭕ **同時ホールド**（HOLD＋HOLD）
- ⭕ **ホールド＋スライド** / **スライド＋ホールド**
- ❌ **同時スライド**（両方動く）… **この段では出ない**

最後のは不具合ではない。測ると、ベースの動き量は中央0.023・**0.3以上動く区間は142件中2件**で、
**旋律と重なっていて両方が0.3以上動く組は0組**だった。動いていない音を動くスライドにするのは
§2.1 の「幽霊ノーツ」なのでやらない。ベースが歩く曲（ウォーキングベース）なら出るはず。

> 同時スライドは大事な形なので、**別の段（§3.1.11）で狙って置く**ようにした。
> この段（15.5）はベースの2声が実際に取れたときだけの、いちばん筋の良い形として残す。

##### 検査を幾何で見るようにした

名前だけ数えていると①②を見逃す（実際に見逃した）。`rhythm-held-pair-variety-check.js` へ
次を足した。

- **形が名前どおりに動く**（全8種 × 相方の動き4通りで、`follows` と実際の動きが合う）
- **動き量の目安が実データの届く範囲にある**（倍率3.0以内）
- **同時に押さえるノーツへ指2本が入る**（重なるすべての押さえノーツと総当たり）
- 譜面に残った組数・残った組でも形が2種類以上

### 3.1.11 同時スライド（2026-09-12・狙って置く段を作った）

【ユーザー指示】「同時スライドは結構重要な譜面だから入る仕組みを構築してほしい /
むずかしい側にはなるとおもうけど」

#### なぜ別の段が要るのか

§3.1.9（同時押さえ）は2本目の素を**ベースの伸び**（`bassSustains`）から取る。つまり
「ベースと旋律が同時に、どちらもSLIDEになるだけ動いている場所」が要る。実測でその場所は

| 曲 | 同時スライドになりうる場所 |
| --- | --- |
| Monster Hero | 1箇所 |
| SIX ÉTERNEL | 3箇所 |
| かぜがそよぐ | 0箇所 |

しかなく、**SLIDE＋SLIDEの組は一度も出なかった**。「運よく重なったら出る」では、
大事な形が曲によって丸ごと欠ける。だから狙って置く段を別に持つ。

#### 何を素にするか（幽霊ノーツにしないため）

素は**いま譜面にある、長くてよく動くSLIDE**。その横へ必ず動く2本目を足す。
1つの音に2本置く理由づけは**同時押し（§9の段）と同じ**で、強い一音には2本ぶんの重さがある
（§2.2「盛り上がりは密度以外でも表せる — 同時押しを入れる」）。
そのうえで、置く場所は次のどれかに当たるところだけに限る。

| 素（`doubleSlideSource`） | 意味 |
| --- | --- |
| `bass` | ベースの伸びが重なっている。**本当に2声ある**ので、いちばん良い |
| `strength` | 打点が強い（`sourceStrength` が `minStrength` 以上） |
| `intensity` | 盛り上がりが高い、またはサビに当たる区切り（`climax`） |

#### 相方に選べるSLIDEの条件

| 条件 | なぜ |
| --- | --- |
| 長さが `minGrids` 以上 | 短いと2本目を置く時間が無い |
| 動く幅が `minPartnerSpanLanes`（0.5レーン）以上 | 動いていないSLIDEは同時スライドの相方にならない |
| 動く幅が **`room - gap` 以下** | 端から端まで動くSLIDE（スイープ）はレーンを全部使う。実測で、4→0 の相方には**どの形でも0.00〜0.50レーンしか空かなかった** |

#### 形は語彙から選ぶ（決めごとにしない）

§3.1.9 と同じ `HELD_PAIR_SHAPES` を使い、**動かない形（`follows:'none'`）だけ外す**。
だから2本目は必ずSLIDEになる。左右対称（`mirror`）は同時スライドのために足した形。

- 2本目がどれだけ動くと似合うか（`bassMove`）は、ベースの伸びが重なっていればその実測、
  無ければ**その場の盛り上がり**（`1+intensity*2`）で決める。盛り上がるほど大きく動く形が前へ出る
- 相方からどれだけ離すかも1つに決めない。`gap` を近い順に3通り試す。
  1通りに固定していたとき、**置ける場所が9箇所あって1組も入らなかった**（EXPERT）

#### 密なところでは「2本目を先に離す」

2本押さえているあいだは指が2本ふさがるので、中の打点は16で落ちる。密なところへそのまま置くと
**同時スライド1組のためにTAPが3個消えた**。上限（`maxCoveredNotes`）を超えるぶんは消さずに、
**2本目の終わりを切って先に離す**。同時スライドの見せ場は2本そろって始まるところなので、
終わりがずれても形は保てる。

#### 採る前に、出荷を止めるのと同じ物差しで確かめる

自分で作った物差し（指の間隔）だけで通したところ、品質レポートの「押せない」が
**0→2件へ増えた曲が8つ出た**。出荷を止めるのは両手のシミュレート
（`rhythm-hand-simulate.js`）なので、置く前と置いたあとをそれにかけ、
**押せない箇所が増えないことを確かめてから**採る。

> ⚠️ ここで2回間違えた。
> ① **曲の一部だけを切り出してかけてはいけない。** 指の割り当ては先読み（ビーム）で決まるので、
> 前を切ると**そこまでの割り当てが変わり**、切った側だけ押せなくなることがある。
> ② **件数で比べてはいけない。** 「前も1件・後も1件だから増えていない」で通したが、
> 中身が入れ替わっていた（前の1件が消えて、置いたせいの1件が増えた）。
> **どこが押せないかの集合**で比べる。

#### 出る難易度

EXPERTとMASTERだけ（`PROFILES.doubleSlide`。EASY/NORMAL/HARDは `null`）。

| | EXPERT | MASTER |
| --- | --- | --- |
| 1分あたり | 0.5組 | 1.2組 |
| 長さの下限 | 6グリッド | 5グリッド |
| 2本目が動く幅の下限 | 1レーン | 1レーン |
| 指の間隔の下限 | 1.5レーン | 1.25レーン |
| 落としてよい打点 | 2個 | 2個 |

#### 実測（17曲）

**15曲で同時スライドが出た**。出なかったのは `dullahan`（MASTERのSLIDEが2本だけ）と
`4u_hitasura`（同じく3本だけ）で、どちらも打点中心の曲。
SLIDEがほとんど無い曲に無理へ入れないのは正しい（§3.1 の「曲のタイプに見合った形」）。

使われた形は `mirror` / `parallel` / `contrary` / `diverge` の4種で、1種類に偏っていない。
自動修正（`rhythm-chart-v2-step7-autofix.js`）を通したあとも
**2本とも動くSLIDEのまま**残り、押せない箇所は0件になる。

#### 既存曲は変わらない

`--release` を走らせないので `monster-hero/data/rhythm-mode.js` は触らない。
生成しての突き合わせでは、**EASY/NORMAL/HARDのノーツは1バイトも変わらない**
（変わるのは設定を書き出した `policy.doubleSlide: null` の1行だけ）。
EXPERT/MASTERは同時スライドのぶんだけ増える。

#### 検査

`node tools/mode/rhythm-double-slide-check.js` が見張る。

- `mirror` が名前どおり鏡になっていて、相方が動けば必ず動く
- EASY/NORMAL/HARDには出ない
- **6曲のうち8割以上で1組は出る**（曲ごとに丸ごと欠けない）
- 置いた組は**2本とも動くSLIDE**（片方がHOLDなら同時スライドではない）
- 同時に押さえる2本へ指2本が入る（重なるすべての押さえノーツと総当たり）
- 2本押さえているあいだに3本目を要求するノーツが残っていない
- 形が3種類以上使われる

### 3.1.12 スライドの分岐・合流（2026-09-12・データ形式は変えずに入れた）

【ユーザー指示】「すすめて」（§3.1.8 の「まだやっていないこと」の消し込み）

#### 形式から要る、は思い違いだった

§3.1.8 には「分岐・合流は `slidePoints` が1本道なのでデータ形式から要る」と書いてあった。
これは **1本のノーツの中で経路が割れる**形（maimai の扇）を考えていたため。
遊ぶ形として要るのは

- **分岐** … 1本だったものが、途中から2本になる
- **合流** … 2本だったものが、途中で1本になる

で、これは**2本のSLIDEの端をそろえる**だけで出せる。データ形式も、ランタイムも、
既存の譜面の読み込みも、何も変えていない。

| | 親のSLIDE | 2本目 |
| --- | --- | --- |
| 分岐 | 最初から最後まで1本で続く | 親の**途中の打点**から生えて、親の終わりまで |
| 合流 | 同じ | 親の**途中の打点**から生えて、親の終わりより前に消える |

指は2本なので、分岐点・合流点でも最低 `fingerMinGapLanes`（1レーン）は離す。
帯に幅があるので、1レーン差でも「くっついて割れた」ように読める。

#### 幽霊ノーツ対策は §3.1.11 より強い

2本目の**頭を、親の伸びの中にある実際の打点へ合わせる**（その音が2本目の頭になる）。
そこに既にTAPが置かれていたら、**そのTAPを2本目に置き換える**——
同じ音を叩く代わりになぞるだけなので、増やしてもいないし消してもいない。
検査は「2本目の頭が打点の上にあること」を全件見る。

#### 名前と中身を食い違わせない条件

| 条件 | なぜ |
| --- | --- |
| 分岐は**頭側に1拍**空ける | 親が1本で見えている時間が無いと「割れた」ように見えない |
| 合流は**終わり側に1拍**空ける | 合流したあと親が1本で続く時間が無いと「合わさった」ように見えない |
| 遠い端は、**その時刻の親のレーンから**離す | 分岐点のレーンからの足し算にすると、親が同じ側へ動いていたとき遠い端のほうが親に**近くなる**（実測 −0.21レーン。開きが逆転して「割れて見えない」形になった） |
| 開きは 0.5レーン以上 | 同上。検査でも下限として見る |

#### 採る前の確認は §3.1.11 と同じ

指の間隔を重なるすべての押さえノーツと総当たりで見て、最後に
**出荷を止めるのと同じ両手のシミュレート**（曲全体・押せない箇所の集合で比較）へかける。

#### 実測（17曲）

**14曲で分岐・合流が出た**（EXPERTのみ／MASTERのみを含む）。出なかったのは
`kaze_ga_soyogu` と `crossing_field`。分岐と合流の両方が出ている。
同時スライド（§3.1.11）が出なかった `4u_hitasura` にはこちらが出るので、
**2つ合わせて16/17曲**が「2本のSLIDEが絡む形」を持つ。

払ったコストは、品質レポートの6軸の合計で85譜面ぶんの
**playability +4 / musicality −4 / readability −4 / flow +1 / variety −12 / difficultyFit −4**
（1譜面あたり −0.22点）。自動修正後の「押せない」は85譜面すべて0件で、増えた箇所は無い。

#### 検査

`node tools/mode/rhythm-slide-fan-check.js`。

- EASY/NORMAL/HARDには出ない / ほとんどの曲で出る / 分岐と合流の両方が出る
- 2本目の頭が実際に鳴っている音に乗っている
- 親のSLIDEが2本目の区間をまるごと含んでいる
- 名前どおりの端になっている（分岐は終わりがそろう／合流は親が1拍以上残る）
- 分岐点・合流点で指2本が入り、**反対の端では 0.5レーン以上開いている**
- 2本押さえているあいだに3本目を要求するノーツが残っていない

### 3.1.13 譜面の量の上限（2026-09-12）

【ユーザー指示】「すすめて」（「速い曲のMASTERが過密」の確認）

#### 測ったら、思っていたのと違った

「速い曲のMASTERが過密」を疑って全17曲の密度を測ったが、**品質レポートの帯から出ている曲は
1曲も無かった**（`difficultyFit` は密度の帯に許容0.6を足して見るため、いちばん濃い
SIX ÉTERNEL(BPM207)の MASTER 毎秒4.96・EXPERT 4.56 も減点されていない）。
ピークも4秒窓で最大7.75個／秒で、指の限界（`restrikeLimitMs` / `laneSpeedLimit`）の内側。
**いま薄くすべき曲は無い。**

見つかったのは別のことで、**`maxPerSecond` が上限として働いていなかった**。

```
notesPerSecond = max(minPerSecond, min(maxPerSecond*factor, perBeat*beatsPerSecond*factor))
```

`factor`（曲の歯ごたえ・最大1.9倍）が上限にも掛かるので、EXPERTの上限4.0が7.6まで伸びる。
実際に SIX ÉTERNEL の EXPERT は毎秒4.56 ＝ **MASTERの上限4.6に迫る**ところまで来ていた。

#### 置いた線

`hardMaxPerSecond` を足し、**`factor` を掛けない**上限にした。値は
**品質レポートが減点を始めるところ**（`BANDS.density` の上端 ＋ `inBand` の許容0.6）。

| | EASY | NORMAL | HARD | EXPERT | MASTER |
| --- | ---: | ---: | ---: | ---: | ---: |
| 帯の上端 | 2.1 | 2.5 | 3.3 | 4.1 | 4.8 |
| 上限（＋許容0.6） | 2.7 | 3.1 | 3.9 | 4.7 | 5.4 |

⚠️ **ここを帯の真ん中へ絞ってはいけない。** ユーザー指示「どの曲も難易度が似たりよったり /

上限を下げるとその差をまた潰す。これは「帯から出るほど詰まった譜面が出たときだけ効く安全柵」。

#### いまの曲は1つも変わらない

### 3.1.14 「交互」の測り方を直した（2026-09-12）

`scores.flow` の3割を占める `alternationRate`（16分で並ぶノーツのうち指が交互に使われている割合）は、
**分母が曲によって極端に小さい**。実測で `4u_hitasura` MASTER は291ノーツあって**2組**しか無い。
生の割合で出すと1組入れ替わるだけで 1.00→0.50 になり、`flow` が30点動く。

実際にそれで読み違えた。分岐・合流を入れた前後を比べたとき、
sparse な曲の `flow` が −31／+25 と暴れ、「流れが落ちた」と受け取ってしまった。
数え直すと**1組が入れ替わっただけ**だった。

疑似カウント（`ALTERNATION_PRIOR=8` 組ぶんの「交互だった」を足す）で1.0側へ寄せた。

| 曲 | 分母 | 生の割合 | 直したあと |
| --- | ---: | ---: | ---: |
| `4u_hitasura` MASTER | 2組 | 0.50 | 0.90 |
| `toriko` EXPERT | 4組 | 0.50 | 0.83 |
| `six_eternel_beat` MASTER | 187組 | 0.81 | 0.82 |

濃い曲の測り方は変わらない（0.81→0.82）。返り値へ `alternationTotal`（分母）も出すようにしたので、
次に見るときは分母を確かめられる。

### 3.1.15 1本の指の叩き直しに下限を入れた（2026-09-12・手のモデルの直し）

【ユーザー指示】「すすめて」（§3.1.14 で見つけた「流れ(flow)がいちばん低い」の追跡）

#### 交互率が低い原因は、譜面ではなく物差しだった

`scores.flow` の3割は `alternationRate`（16分で並ぶ2打のうち指が交互に使われている割合）で、
濃い曲では 0.60〜0.82 しか無かった。**同じ指に割り当てられた328組**を調べると、

| 同じ指になった理由 | 件数 |
| --- | ---: |
| 押さえノーツで指が1本ふさがっている | 49組 |
| **レーンが近い（1.5レーン未満）** | **278組** |
| 遠いのに同じ指 | 0組 |

278組の中身は**レーン差0.3〜0.8（＝ほぼ同じレーン）・間隔の中央83ms**。
1本の指で毎秒12打である。にもかかわらず「忙しい(strained)」とも言われていなかった（230/233）。

原因は `rhythm-hand-simulate.js` の `evaluateFinger`。

```
needLimitMs = distance===0 ? restrikeLimitMs : distance/laneSpeedLimit*1000
```

**同じレーンのときだけ**叩き直しの下限（105ms）を見て、少しでも動くなら距離だけで判定していた。
0.5レーンなら `0.5/18*1000 = 28ms` ＝ **1本の指で毎秒36打**が「押せる」扱いになる。

> ⚠️ 同じファイルの `fingerPairFeasible`（近くて速い2打の事前チェック）は、
> 1本で取る場合に**最初から105msを要求していた**。つまり手のモデルの中で
> 2つの物差しが食い違っていた。事前チェックのほうが正しい。

#### 直した式

指を持ち上げて押し直すぶんの時間は、動く距離とは**別に必ず要る**。
動くほうが速いことはないので、下限と移動時間の**大きいほう**を取る。

```
needLimitMs   = max(restrikeLimitMs,   distance/laneSpeedLimit*1000)
needComfortMs = max(restrikeComfortMs, distance/laneSpeedComfort*1000)
```

| 距離 | 直す前 | 直したあと |
| --- | ---: | ---: |
| 同じレーン | 105ms | 105ms（変わらない） |
| 0.5レーン | 28ms | **105ms** |
| 1レーン | 56ms | **105ms** |
| 4レーン | 222ms | 222ms（移動時間が効く。変わらない） |

#### 生成側にも足りない規則があった

物差しだけ直すと、**生成→自動修正のあとでも40譜面のうち13譜面が「押せない」**になった。
押さえノーツで指が1本ふさがっているあいだの打点は**残った1本で全部叩く**ので、
そこは105msより詰められない。この規則が
「指の本数を超える瞬間を作らない」(16)に入っていなかった。

16へ第2段を足した。指が1本しか空いていない瞬間の打点が、直前の打点から
`restrikeLimitMs` 未満なら落とす。

#### それでも取りこぼしが出たので、最後に1段足した

16の2段を入れても、85譜面のうち5譜面に1件ずつ残った。押さえノーツが無いところでも

- 2.50レーンを99msで移動できない
- 同じレーンを83msで叩き直せない

という形が出る。指2本を**交互に**使っても、レーンの離れかたによっては届かない瞬間がある。

形を変えて直すのは自動修正（`rhythm-chart-v2-step7-autofix.js`）の仕事だが、
あちらは**レーンを動かすだけなので時間の詰まりは直せない**。
そこで `--- 16.5 押せない瞬間を残さない ---` を足した。両手のシミュレートにかけて、
押せないと言われた**打点のほう**を取り除く（押さえノーツは譜面の骨格なので残す）。
落ちたぶんは必ずお知らせへ出す。

#### 効き方（17曲・85譜面・自動修正後）

| | 直す前の譜面 | 直したあとの譜面 |
| --- | ---: | ---: |
| 「押せない」が残る譜面 | **25譜面** | **0譜面** |
| EXPERT・MASTERの交互率 | 1.00 | 1.00 |
| EXPERT・MASTERの流れ(flow) | 91 | **92** |
| ノーツ合計 | 29751 | 29779（+0.1%） |

> 「直す前の譜面」の25譜面は、**直した物差しで測り直した結果**。
> 物差しが甘かったあいだは「押せる」と出ていた。

低い難易度への影響はほとんど無い。EASY・NORMAL は**全曲でノーツが1バイトも変わらず**、
HARDは1曲（`six_eternel_beat`）だけ22ノーツのレーンが動いた（数・位置・拾った音は同じ）。
物差しが厳しくなったぶん、生成器がその場で別の（押せる）置き方を選んだもの。

> 交互率が両方1.00なのは、**どちらも直した物差しで測っている**ため。
> 直す前の物差しでは0.72・流れ70に見えていた。物差しを直すと
> 「この譜面は交互で押すしかない」と正しく読めるようになり、
> かわりに**本当に押せない6譜面が表に出た**。それを生成側の規則で消した。

#### 検査

`node tools/mode/rhythm-hand-restrike-check.js`。

- 指が2本空いていれば、16分で1レーン離れた2打は押せて、**左右へ振り分けられる**
- 指が1本しか空いていなければ、同じ2打は**押せない**（ここが直す前は押せる扱いだった）
- 叩き直しの下限が**距離に関係なく**効く
- 大きく動くときは移動時間のほうが効く

`rhythm-hand-simulate.js` の合成テストも時刻を広げた（正解の「右手で3→2を100ms」が
5ms足りなくなったため）。**配置の狙い（先読みなら解けるが、その場最適では解けない）は変えていない。**

> ⚠️ `simulateNotes` がグリッドの長さを `timing.beatMs` から割り出していたのも直した
> （`timing.gridMs` を正本にする）。`gridMs` だけ持つ timing を渡すと NaN になり、
> **押せない判定が丸ごと効かなくなる**。検査を書いたときに実際に踏んだ。

### 3.1.16 「飽きないか」にSLIDEの中身を入れた（2026-09-12）

`scores.variety` は `chart.shapes`（expand/contract などのパターン記録）だけで出来ていて、
**SLIDEの太さ・中継点・移動量が1つも入っていなかった**（§3.1.8 に既知として書いてあったもの）。
SLIDEの形を増やしても点数が1点も動かないので、「飽きないか」を測れていなかった。

打点の形（.85）＋ SLIDEの中身（.15）へ組み替えた。SLIDEの中身は3つ。

| 見るもの | 重み |
| --- | ---: |
| 経路の形の種類（flat / line / sweep / fold / wave） | .40 |
| 太さの並びの種類（同じ並びばかりになっていないか） | .30 |
| 途中で太さが変わるSLIDEの割合 | .30 |

SLIDEを持たない難易度（EASY/NORMAL）は、無いことで減点しない（1.0扱い）。

実測（`authoring` にある譜面。§3.1.8 の太さの作業より前に作ったものが混ざっている）。

| 曲 | SLIDEの中身 | 途中で太さが変わる |
| --- | ---: | --- |
| `six_eternel_beat` MASTER | 0.94 | 11/14本 |
| `monster_hero_theme` MASTER | 0.55 | 0/11本 |
| `dullahan` MASTER | 0.28 | 0/2本 |

太さの作業のあとに作った曲だけ高く出る。**測れていなかったものが測れるようになった。**

> ⚠️ これは測る道具の直しで、譜面は変わらない。ただし
> `rhythm-chart-v3-candidates.js`（複数候補から選ぶ段）は6軸で選ぶので、
> これからはSLIDEの中身が濃い候補が選ばれやすくなる。

### 3.1.17 走る音をなぞるSLIDE（2026-09-12・SLIDEの材料を広げた）

【ユーザー指示】「スライドにする材料を広げる」（§3.1.8 の残り項目）

#### それまでの材料は「伸びている音」だけだった

SLIDEの素は `audio.sustains`（音が伸びている区間）だけで、**音階を駆け上がる／行き来する
アルペジオ・トレモロは1音ずつ短いので sustains にならず、全部単押しになっていた**。
§3.1.8 に「ジグザグをもっと増やしたいなら、SLIDEにする材料そのものを広げるしかない」と
残っていた項目。

素は「速く並んでいて、音の高さが実際に動いている打点の連なり」。1音ずつ鳴っているところを
なぞらせるので**幽霊ノーツ(§2.1)にならない**（経路の中継点はその打点の音の高さそのもの）。
本物の音ゲーでも、グリッサンドや駆け上がりはスライドで書く。

| 条件 | EXPERT | MASTER | HARD |
| --- | ---: | ---: | ---: |
| 1分あたり | 0.4本 | 0.6本 | 0.6本 |
| 打点の数の下限 | 4個 | 4個 | 4個 |
| 打点の間隔 | 8分以下 | 8分以下 | 8分以下 |
| 長さの上限 | 14グリッド | 16グリッド | 12グリッド |
| 音の動きの下限 | 約2半音 | 約2半音 | 約2半音 |

#### 探す場所を間違えた

はじめ `spaced`（打点として採用したぶん）から連なりを探していた。**格子と連なりの上限で
間引かれて連なりが切れており**、4個以上つながる速い連なりがほとんど残っていなかった
（実測: Stay With Me MASTER は速い連なり428本のうち**422本が「短い」で落ちた**）。
「音が走っている」のは曲の性質で、打点として何個採ったかとは別。
`pool`（鳴っている音）から探すよう直した。

長すぎる連なりも、はじめは弾いていた。速い連なりが長い曲でかえって0本になったので
（禁断のレジスタンスが2本→0本）、**捨てずに頭から切って使う**ようにした。

#### ⚠️ 指は2本しかないので、長く押さえる形どうしは必ず取り合いになる

これが今回いちばん大事なところ。走る音のSLIDEを足したら、**同時押さえ(§3.1.9)が
4組→1組へ減った**。長いSLIDEが指を1本占有するので、そのあいだ2本目を置く余地が消える。

対策は2つ。

1. **ベースの2声が取れている場所は避ける。** そこは同時押さえの材料で、「本当に2声鳴っている」
   いちばん筋の良い形だから、こちらが先に取ってはいけない
2. **同時スライド(§3.1.11)の `maxCoveredNotes` を2→4へ**。同時スライドは
   ユーザーが「結構重要な譜面」と言った形なので、1組のためにTAPを4個まで落としてよいとした。
   これで同時スライドは10/17曲→**13/17曲**へ戻った（走る音を止めた場合でも11/17なので、
   走る音のせいで減ったのは実質1曲だけ。減った主因は §3.1.15 で手のモデルを直したこと）

#### 実測（17曲）

**9曲で走る音のSLIDEが出た。** 出ないのは走る音そのものが無い曲
（`kaze_ga_soyogu` / `toriko` / `dullahan` など）で、無い曲へ無理に入れないのは正しい
（§3.1 の「曲のタイプに見合った形」）。経路はいちばん広いもので4.0レーン、折れは最大3回。

#### 検査

`node tools/mode/rhythm-glide-slide-check.js`。

- 半分以上の曲で出る / EASY・NORMALには設定を持たせない
- **頭が実際に鳴っている音に乗っている**
- **音が動いていないのに動く経路を引いていない**
- 走る音（8分以下で打点4つ以上）の上にある / 横に動く経路になっている

> ⚠️ 検査は**印(`glideSlide`)で拾う**。条件で拾おうとしたら、端から端まで動くSLIDE
> （スイープ）まで混ざって「音は0.4半音なのに3レーン動いている」と誤検出した。
> スイープは音の高さではなく見せ場として振る形なので、それで正しい。

### 3.1.18 「音」の伸びしろを直した（2026-09-12・生成器2つ＋物差し1つ）

【ユーザー指示】「音の伸びしろ」（§3.1.10 の追記で「いちばん低い軸は musicality」と分かった）

`scores.musicality` の内訳を測ると、4項目のうち2つは満点だった。

| 項目 | 配点 | 実測（EXPERT・MASTER 18譜面の平均） |
| --- | ---: | --- |
| 拾った音が実際に鳴っている割合 | 40 | **40.0**（満点。伸びしろ無し） |
| 音の無いところに置いていない | 15 | **15.0**（満点。伸びしろ無し） |
| 大事な音を拾えたか | 25 | 18.8 |
| 同じフレーズが同じ形か | 20 | **7.4** ← いちばん低い |

#### ① 形を覚える鍵の式が潰れていた

`phraseConsistency` は2つでできている。**指紋(`motifKey`)のほうは効いていた**
（monster_hero EXPERT で 11/14）が、**区切りの繰り返し(`repeatOf`)のほうが
ほぼ全曲で 0/N だった**（0/8・0/6・0/5・0/3…）。

原因は生成器の鍵の式。

```
`${sourceBar!=null?sourceBar:bar-(bar-section.startBar)}:…`
                            ^^^^^^^^^^^^^^^^^^^^^^^^^^^^ = section.startBar
```

`bar-(bar-section.startBar)` は **`section.startBar` へ潰れる**（意図は
`section.startBar+(bar-section.startBar)` ＝ `bar`）。そのため元の区切りは
**どの小節のかたまりも区切りの先頭の番号で保存**され、繰り返しの区切りは
`repeatOf+(bar-startBar)` で引くので、**区切りの先頭の小節しか一致しない**。

`bar` へ直した。効き方（フレーズ一致 → 音）。

| 曲 | 直す前 | 直したあと |
| --- | ---: | ---: |
| `crossing_field` MASTER | 0.12 → 音82 | **0.77 → 音95** |
| `eiki_boss` EXPERT | 0.00 → 音71 | **0.60 → 音83** |
| `monster_hero_theme` MASTER | 0.52 → 音88 | **0.73 → 音92** |

#### ② 大きい一発が「格子とのずれ」で落ちていた

`maxAbsPeakOffsetMs = 30` で、格子から30msずれた音は `pool` へ入れていなかった。
格子と噛み合わせが悪い曲では、これで**大きい一発の半分が落ちていた**。

| 曲 | 大事な音のずれ 中央 | p90 | 25msを超える数 |
| --- | ---: | ---: | ---: |
| MF × ICHIKA MIX | **25ms** | 39ms | 157 / 320 |
| 綺季一閃 | 19ms | 40ms | 323 / 929 |
| Monster Hero | 9ms | 32ms | 74 / 326 |

落としてしまうと「曲の山なのにノーツが来ない」になる。いちばん良い判定(MARVELOUS)の窓は
**±55ms**なので、43msずれた音を格子へ寄せて置いても**まだ最良の判定の中**に入る。
そこで**大きい一発(FULL)だけ** 43ms（`earReviewMaxOffsetMs` と同じ線）まで許すようにした。

| 曲 | 拾えかた | 音 |
| --- | --- | --- |
| MF × ICHIKA MIX MASTER | 0.37 → **0.47** | 71 → **89** |
| Stay With Me MASTER | 0.48 → **0.58** | 77 → **82** |
| Monster Hero MASTER | 0.76 → **0.83** | 88 → **93** |

ノーツの数はほとんど変わらない（360→360 / 599→596 / 624→622）。
**増やしたのではなく、同じ数の中で「置き場所」が良くなった。**

#### ③ 届かない目標で減点していた（物差しの直し）

`toriko` MASTER は**大事な音250個に対してノーツ151個**なので、どれだけ上手に選んでも
拾えるのは最大0.60。MASTERの目標0.85には**構造的に届かない**。
目標は「拾える上限(`importantReach` = ノーツ数 ÷ 大事な音の数)」で抑えるようにした。
上限が目標より高い曲では何も変わらない。

| 曲 | 拾えかた | 拾える上限 | 比べる目標 | 音 |
| --- | ---: | ---: | ---: | ---: |
| `toriko` MASTER | 0.48 | 0.54 | 0.54 | 89 → **97** |
| `monster_hero_theme` MASTER | 0.83 | 1.00 | 0.85 | 93（変わらない） |

### 3.1.6 譜面文法 — 形を「順位」でなく「点数」で選ぶ（2026-09-07）

`shapeCandidatesFor` は候補を**音との合いかたの順**に並べる。ここまでは以前と同じ。
以前は常に先頭を取っていたので、

- その曲で何度も使った形が、直前でさえなければまた選ばれる
- 前の形の終わりの向きと次の形の始まりの向きが合わず、手の流れが途切れる
- 同じ候補列が出るたびに同じ順で決まる（散らしが「偶数番目か」の1ビットしか無い）

が残っていた。`rankShapes` は**上位4件（＝音との合いかたが同じくらいの候補）の中だけ**で、
次を足して点数化する。音に合わない形が上がってくることは無い。

| 見るもの | 効き |
| --- | --- |
| 音との合いかた（順位） | 1段で2点。最優先 |
| つなぎ | 前の形の最後の動きと次の最初の動きが同じ向きなら流れる。ただし3かたまい以上同じ向きへ流れ続けたら折り返す側を前へ |
| 使用回数 | その曲でその形を使った回数×0.5点（語彙を均す） |
| 場面 | イントロ＝交互・階段を前へ／サビ＝開き・外→内→外・端振りを前へ／アウトロ＝閉じを前へ |
| 散らし | 曲・難易度・かたまり番号の決定的なハッシュで0〜0.9点。乱数は使わない |

先頭の形が「起点をどこに置いても指の条件を満たさない」ときは次の候補を試す（上位6つまで）。
以前は先頭だけを試して、置けなければ1音ずつ逃がす fallback へ落ちていた。fallback は形にならず、
左端から空きを探すので継ぎ目で3レーン跳んでいた（実測: MASTERの8%が fallback）。
起点を決めるときも、かたまいの継ぎ目が1拍未満なら跳びをその難易度の上限までにする。

### 3.1.7 同じフレーズは同じ形（指紋・2026-09-07）

区切りの繰り返し（`repeatOf`）は構造解析が取れたときしか使えず、実測では1曲に3〜7かたまりしか
当たっていなかった。そこで**フレーズの指紋**（ノーツ数｜刻み｜音の高さの上下 ±/=）で覚え、
同じ指紋のフレーズには同じ形を当てる。

- 1回目 そのまま／2回目 左右反転／3回目 少し発展（文法で選び直す＝直前を避けた別の形）／4回目 元へ
- 左右対称の形（トリル・縦連・ゆれ）は反転しても見た目が変わらないので、3回目の「発展」が要る
  （これが無いと、同じフレーズが続く曲で同じ形が7回並んだ）
- HARD以上の3回目以降は、起点も1つずらす

品質レポートの「フレーズ一致」はこの指紋で測る（古い譜面でも譜面そのものから測り直せる）。

### 3.2 形を選ぶ規則

- **音の高さが上がっていれば階段、下がっていれば逆階段**（メロディの動きと画面の動きを合わせる）
- **同じリズムの繰り返しには同じ形**（または左右反転）
- **1つの形は2〜6個のノーツで完結させる**。長すぎると読めない
- **形と形のつなぎ目で無理な跳びを作らない**

### 3.3 手の流れ

- 連続するノーツは**左右交互**が基本。同じ手が続くと「重い」
- 同じ場所の連打（縦連）は、1本の指で叩ける速さ（105ms以上）でだけ
- 階段は手の動く向きと合わせる（右手が右へ抜けていく形が自然）

## 4. 気持ちいいか — 曲の構造との一致

- **セクション**（イントロ／A／B／サビ／間奏／アウトロ）ごとに性格を変える。
  構造解析は名前を付けない（外すと譜面まで外れる）ので、生成器は
  **intro（頭の静かな区切り）／climax（盛り上がりが上位3割）／outro（終わりの静かな区切り）／body**
  の4つだけを出し、形の好み（3.1.6）と同時押しの置き場所（盛り上がっている小節を優先）に使う。
  実際の曲にその構造が無ければ body のままで、固定の型は押し付けない
- **反復するフレーズは同じ譜面**。2回目は左右反転にすると、覚えたうえで新しさが出る
- **コール＆レスポンス**は左右の呼び合いで表す
- **曲の切れ目**では手を止める。ノーツを置き続けると区切りが消える

---

## 5. 飽きないか — 緩急

- 密集のあとには**休符**を置く。休みの無い譜面は、易しくても疲れる。
  生成器は「その難易度でいちばん細かい刻みが上限（maxRun）まで続いたあと、半拍〜1拍は
  装飾の音（拍の頭でない・大きな一発でない）を拾わない」（息継ぎ・2026-09-07）。
  背骨は残すので曲を叩いている感じは消えない
- 難所は**短く**。同じ難所を何度も出さない
- 曲の終わりへ向けて盛り上げるが、**最後のサビが最初のサビより忙しくならない**ようにする
  （曲がそうなっていない限り）

## 6. 難易度は「同じ骨格の濃淡」

低難易度は、高難易度を**間引いたもの**であるべき。

- EASYで覚えた形が、NORMAL・HARDでもそのまま出てくる（学習曲線になる）
- 難易度が上がると「新しい要素が1つだけ増える」
- 難易度ごとに別々に作ると、EASYにあってHARDに無い、といった逆転が起きる

### このゲームの段

| 難易度 | 増えるもの |
| --- | --- |
| EASY | TAPとHOLDだけ。8分の位置。レーン移動は1つずつ。**同時押しは左端と右端で拍の頭だけ** |
| NORMAL | ＋FLICK、2レーンの移動 |
| HARD | ＋16分の位置、SLIDE（16分の連なりは2つまで）。同時押しの間隔が1.5レーンへ |
| EXPERT | ＋3レーンの移動、長押し中の別タップ、細いノーツ |
| MASTER | ＋4レーンの移動、長い16分の連なり、細いノーツ最多。同時押しは指の太さぎりぎりまで |

#### 同時押しは「できること」の段ではない

同時押しを上位難易度の特権にしていた時期があったが、これは**間違い**だった。
指は2本あるので、離れた2か所を同時に押すのは、1か所を押すのとほとんど変わらない。
難しいのは同時押しそのものではなく**置き方**（近さ・拍の外・前後の詰まり・細さ）。

だからEASYから出す。かわりに下の難易度ほど置き方を易しくする。

| | 間隔（触る場所どうし） | 置く位置 | 前後の空き | 太さ | 1分あたり |
| --- | ---: | --- | ---: | ---: | ---: |
| EASY | 2レーン（左端と右端） | 拍の頭だけ | 3グリッド | 3以上 | 2.4 |
| NORMAL | 2レーン（左端と右端） | 拍の頭だけ | 2グリッド | 3以上 | 3.2 |
| HARD | 1.5レーン | どこでも | 2グリッド | 3以上 | 4.0 |
| EXPERT | 1.25レーン | どこでも | 1グリッド | 2以上 | 4.8 |
| MASTER | 1レーン（指の太さ） | どこでも | 1グリッド | 2以上 | 7.2 |

同時押しは「決めの一発」なので、**位置を動かしてよい**。5レーンしか無いため、
真ん中に置いたままでは十分に離せない。動かしたあとも、前後のノーツとの跳びが
その難易度の上限を超えないことを確かめる。

**「押さえながら別を叩く」はこれとは別**。片方の指がふさがった状態でもう1本を動かすので
本当に難しい。こちらはEXPERT以上のまま（`tapDuringHold`）。

**同時押しの前後には、指が空くまでの時間が要る。** 同時押しは指を2本とも使うので、
その直前・直後に別のノーツがあると、どちらかの指を叩き直すしかない。
`restrikeLimitMs`（105ms）より短い間隔では、どこへ置いても押せない。
置き場所をあとから動かしても直らないので、**置く前に候補から外す**。

#### 大きく動かす3つの見せ場

2026-09-05に「まだバリエーションが少ない。スライドで端から端に行く、同時押しで右左くねくねする、
指をクロスしなきゃいけないような配置」という指摘を受けて足した。
どれも**難易度ごとにどこまで許すか**が本体で、許す・許さないは「できること」ではなく
**指がどれだけ速く動くことになるか**で決める。

| | 端から端へ動くSLIDE | 同時押しの連なり | クロス |
| --- | --- | --- | --- |
| EASY | — | — | — |
| NORMAL | — | — | — |
| HARD | 追従6レーン毎秒まで／2.5レーン以上動く | — | — |
| EXPERT | 追従8レーン毎秒まで／3レーン以上 | 3つまで・165ms以上あけて | 少しだけ |
| MASTER | 追従10レーン毎秒まで／3.5レーン以上 | 4つまで・140ms以上あけて | 中心に |

**端から端へ動くSLIDE（スイープ）**
経路を新しく作るのではなく、**音の高さから作った経路をそのまま引き伸ばす**。
引き伸ばしは向きを変えない写像なので「SLIDEの向きが音の高さと合っている」は保たれる。
どこまで大きくするかは「区間ごとの追従の速さが上限を超えない、いちばん大きい倍率」で決める。
中継点を0.5レーン刻みへそろえたあとにもう一度速さを測る（丸めで動きが増えることがあるため）。

なお**細かく刻むほど良いわけではない**。1グリッドおきに取ると、ならす前の段差がそのまま
1区間の動きになってしまう。実測では ならし1/間隔2 で7本、ならし2/間隔3 で24本置けた。

**同時押しの連なり（右左くねくね）**
等間隔に並んだ単押しをまとめて同時押しの列に変え、ペアごと動かす。
形は「左右のはしを行き来する（swing）」「はしからはしへ流れる（parallel）」「間隔を広げる（open）」。

EXPERT以上にしか置かないのは、できないからではなく**場所が足りない**から。
5レーン（サブレーン10）しかないので、EASY〜HARDの同時押しの条件を満たすと2つで使い切る。

| | 幅+幅+間隔 | 動ける幅 |
| --- | ---: | ---: |
| EASY / NORMAL | 3+3+4 = 10 | 0 |
| HARD | 3+3+3 = 9 | 0.5レーン |
| EXPERT / MASTER | 2+2+2 = 6 | 2レーン |

**クロス（指を交差させる置き方）**
押さえっぱなしのHOLDより**さらに外側**を叩かせる。片方の指が固定されているので、
もう1本がその外側まで行くしかなくなる。ただの単押しの並びでは、どちらの指で取るかは
遊ぶ人の自由なので、譜面の側から交差を強いることはできない。

外側は狭いので、入らないときは**その難易度で使える細さまで落としてよい**
（交差は狙って取る一発なので、細いほうが理にかなう）。

#### 自動修正に「設計のほうを壊させない」

忙しい配置を直す工程（STEP7）は、ノーツを左右へ寄せて解決する。
ところが同時押しの片方だけを寄せると、**難易度ごとに決めた「離れかた」が縮む**。
実際にEXPERTの1組が1.00レーンまで縮み、設計の1.25レーンを割った。

そこで「いま離れているぶんより狭くしない」を自動修正の条件に足した。
そのぶんMASTERに「忙しい」が数件残ることがあるが、**押せない**は0のままで、
設計のほうを壊すよりよい。

## 7. 拾う音の選び方（難易度ごと）

同じ曲でも、難易度によって「どの音を拾うか」が変わる。

| 難易度 | 拾う音 |
| --- | --- |
| EASY | 大きな一発と、拍の頭のキック・スネアだけ |
| NORMAL | ＋8分のキック、はっきりした歌の頭 |
| HARD | ＋16分の裏の目立つ音、伸びる音（HOLD）、動く音（SLIDE） |
| EXPERT | ＋ハイハットなどの細かい音 |
| MASTER | ほぼ全部 |

**「強い順にN個」ではなく「この種類の音を拾う」で選ぶ。**
強さの順位だけで選ぶと、同じフレーズの中で拾ったり拾わなかったりが起きて、
リズムが崩れて聞こえる。

## 8. 自動生成でとくに気をつけること

人が作るときは自然にやっていて、機械にやらせると抜けるもの。

1. **同じフレーズを同じ形にする**（機械は毎回ゼロから決めがちで、バラバラになる）
2. **形の語彙を使う**（機械は「条件を満たす置き場所」を探しがちで、形にならない）
3. **休符を残す**（機械は上限まで埋めがち）
4. **音の無い場所へ置かない**（機械は目標密度に届かせようとする）
5. **難易度をまたいで骨格を共有する**（機械は難易度ごとに独立に作りがち）
6. **押せるかを常に確かめる**（機械は「見た目の距離」だけで判断しがち）

## 8.5 どんな曲でも作れること（一般性）

譜面づくりの作法を守っていても、**その曲でしか動かない道具**では意味がない。
自動生成の道具が「1曲専用」になりやすい場所は決まっている。

| 落とし穴 | 症状 | 直し方 |
| --- | --- | --- |
| BPM・拍の頭を手で書く | 書いた曲しか作れない | 音から自動で出す（人が確かめた値があればそちらを優先） |
| 拍子・刻みを決め打ち | 3拍子や3連の曲で崩れる | 音から判定する |
| 別の道具の出力に頼る | その道具が動かない曲では作れない | 必要なものは自分で出す |
| 譜面の量を「その曲の音の何割」で決める | 曲が変わると量が変わる | **1拍あたり何個**を目標にし、毎秒の下限・上限で挟む |
| HOLD・SLIDEなどの数を「1曲に何個」で持つ | 30秒の曲では多すぎ、6分の曲では足りない | **1分あたり何個**で持つ |
| 曲をコードへ書く | 曲を足すのにコードを触る | 一覧ファイルと引数で足せるようにする |

### テンポの判定で外しやすいところ

自己相関の山だけで選ぶと、次の3つを取り違える。

- **半分のテンポ**（2拍を1拍と見る）… 173→86.5
- **3分の2のテンポ**（付点4分を1拍と見る）… 169→112.8
- **倍のテンポ**（細かい格子はいつでも当たりやすい）

決め手は「**そのテンポの16分格子に、実際の打点がどれだけ乗るか**」。
実測では 正 91% / 半分 77% / 3分の2 50% と、はっきり差が出る。
そのうえで「拍のところに音があるか（占有）」と「人が速いと感じる帯」で重みを付け、
最後に最小二乗で格子を当て直すと、2分半の曲でも数ミリ秒の精度になる。

**許容幅は刻みの幅に比例させること。** 固定にすると、細かい格子ほど窓が重なって
「どんな打点でも乗っている」ことになり、細かい格子がいつでも勝ってしまう。
ただし比例を強くしすぎると、今度は**遅いテンポのほうが窓が広くなる**ため、
速い曲を半分のテンポで読む。実曲30曲で確かめて決める（片側だけ見て決めない）。

### いちばん質の悪い壊れ方は「黙って外すこと」

テンポを外した譜面は、遊ぶ人には**ゲームが壊れている**ようにしか見えない。
しかも作った側は音を聴かない限り気づけない。だから道具は
「自信が無いときに、自信が無いと言う」ことまでを仕事に含める。

V3では解析のたびに次を測り、あやしければ `warnings[]` として書き出す。
重いもの（`critical`）が1つでもあると、パイプラインはランタイムへの反映を止める。

| 警告 | 何を見ているか | 重さ |
| --- | --- | --- |
| `tempo-unstable` | 曲を12秒ずつの窓に切り、**ずれている窓が全体の3割を超える** | 重い |
| `tempo-ambiguous` | 2位のテンポ候補と点が拮抗している | 軽い（実曲では当たっていても拮抗する） |
| `grid-loose` | 打点が16分格子に乗っていない | 重い |
| `few-onsets` | 打点が少なすぎて譜面にならない | 重い |
| `beat-weak` | 拍のところに音が無い拍が多い | 軽い |
| `short-audio` | 曲が短く、難易度の差が付きにくい | 軽い |
| `structure-flat` | 長い曲なのに区切りを見つけられない | 軽い |

人が耳で確かめた値（`rhythm-timing.js` の登録・`--bpm` 指定）を使っているときは、
自動判定のあやしさで止めない（軽い注意へ下げる）。止めるべきなのは
**自動判定だけで押し切るとき**だから。

テンポの揺れの測り方には、2つのつまずきがあった。

1. 窓ごとのBPMを**広く探す**と、打点の少ない窓が半分・1.5倍へ流れる
   （実測: 実曲30曲のうち20曲が誤って「揺れている」に）。±8%だけ探す
2. 「いちばんずれた窓」で決めると、生っぽい演奏の曲で1〜2窓だけ6〜8%ずれ、
   テンポが一定の曲まで止める（実測: 30曲中5曲）。
   本当にテンポが変わる曲は**まとまって**ずれるので、
   「ずれている窓が全体のどれだけを占めるか」で決める

### 正解が分かっている音を自分で作って試す

実曲は誰も正解を知らないので、実曲だけを見ていても「外していること」に気づけない。
`rhythm-audio-testtone.js` で、拍・拍子・跳ね・テンポ変化が分かっている音を作り、
毎回の検査で通す。ここで拾えたもの:

- 跳ね（シャッフル）の曲を「4分の3のテンポ」と読んでいた
- 200BPMの曲を150BPM（4分の3）と読んでいた
- 頭に長い無音がある曲で、静けさのぶんコントラストが跳ね上がって判定できなかった
- 途中でテンポが変わる曲を、**何も言わずに**一定のテンポとして通していた

## 8.6 外部の音ゲーから採った一般原則（2026-09-07）

公開されている譜面制作の基準・再現エンジンのソース・開発者の解説（osu! の Ranking criteria、
Quaver の基準、Beat Saber のコミュニティwiki、CHUNITHM／プロジェクトセカイ／Arcaea の判定の実装値、
maimai の無理配置の分類など。動画そのものは見ていない）から、**一般化できるもの**だけを採った。
よその譜面データは1つも使っていない。

| 採った原則 | この文書での置き場 |
| --- | --- |
| ノーツは聞こえる音の立ち上がりにだけ置く。全部の音を拾わない | 2章 |
| 同じ音は同じ重さ・同じ形（一貫性）。ただし機械的な反復は上位で退屈なので反転・発展で変化を付ける | 3.1.7 |
| 手の交互（パリティ）を基本にし、片手の連打は速度と長さを抑える | 3.3 / 手モデルの交互の好み |
| 速い連なりの中では種別・レーンの切り替えを減らす | `chunkFast`（16分は4個ずつの形） |
| 難所は曲の強度が最大の区間にだけ、直後に休みを置く | 5章（息継ぎ） |
| 同時押しは強い音にだけ・2個まで・速い連なりの中に入れない | 6章 |
| 離すのが遅いほうは罰しない（プロセカ・CHUNITHMは離す時刻を見ない、Quaverは離し忘れがGOOD） | `RHYTHM_MODE.md` 終端判定 |
| 判定は「動作が終わる方向」に広い（フリックの遅れ側・ホールドの早入り側） | 同上 |
| 物理的に不可能な配置（3点同時・同じ場所に200ms以内で重なる）は機械で検出して排除する | 1章・検査 |
| 表現用のノーツほど判定が緩い（Air・ExTap・フリック方向不問・スライド中間） | FLICK 方向不問・SLIDE 追従の猶予 |

## 10. 品質の6つの軸（`rhythm-chart-quality-report.js`・2026-09-07）

1つの点数にまとめない。0章の順そのままに、次の6つを別々に出す。

| 軸 | 見ているもの | ゲート |
| --- | --- | --- |
| Playability（押せる） | impossible／strained 率／忙しい連続の長さ／押さえている最中の空き手 | **impossible が1件でもあれば不合格** |
| Musicality（音） | 鳴っている音の上か／大事な音（大きな一発・拍の頭の重い音）の拾い率／同じフレーズが同じ形か／無音区間のノーツ | — |
| Readability（読める） | fallback の率／8分未満で3レーン以上跳ぶ率／同じ形の連続／8かたまい窓での偏り | — |
| Flow（流れ） | 16分での左右交互／1拍以上の休符の頻度／難所の長さ／難所の直後の休符 | — |
| Variety（飽きない） | 語彙の数／いちばん多い形の占有率／つなぎの種類（エントロピー）／左右反転率／区切りごとの密度差 | — |
| DifficultyFit（難易度なり） | 密度・忙しい率・跳びが難易度の帯に入っているか／使う種類／上位は複合要素（押さえながら叩く・連なり・スイープ・クロス）があるか | — |

帯（難易度ごとの狙い）は生成器の定数ではなくレポート側に書く。生成器が緩んだときに一緒に緩まないように。
パイプラインは自動修正のあとにこれを走らせ、`authoring/<曲>-v3-quality.json` へ残す。
`--baseline <dir>` で前回と比べられる（↑↓が付く）。
