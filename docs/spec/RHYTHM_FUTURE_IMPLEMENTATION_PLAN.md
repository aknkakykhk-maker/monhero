## 1. HOLD / SLIDE の途中追従判定強化 — **実装済み（暫定値）**

### 現行内容

- pointermove / touchmove と毎フレームの再評価による継続判定。
- HOLDは帯中心からの横ズレ、SLIDEは `slidePoints` 経路からの横ズレを確認する。
- 外れた瞬間ではなく、暫定120msを超えて戻らない場合にMISS確定。
- HOLD横ズレ許容は「帯の半分幅 + 0.15レーン（0.3サブレーン）」の暫定値。
- SLIDEは既存 `rhythmSlideTrackingTolerance` を利用する。
- 途中MISS後は復活せず、終端まで薄いグレーで流す。
- `1 authored note = 1最終判定` を維持する。

実機確認後、猶予とHOLD横ズレ許容は調整してよい。

## 2. ライフ / DOWN — **現行実装 + 将来の根性例外あり**

### 現行仕様

現行mainでは以下が実装済み。

| 項目 | 現行値 |
| --- | ---: |
| 最大ライフ | 1,000 |
| 開始時 | 1,000 |
| MARVELOUS | +2 |
| EXCELLENT | +2 |
| GREAT | +1 |
| GOOD | 0 |
| BAD | -20 |
| MISS | -50 |

- ライフ0でDOWN。
- DOWN後も曲とノーツ判定は最後まで継続する。
- DOWN後はライフ0固定、スコア加算停止。
- DOWN前までのスコアを保持し、リザルト・ランク・BESTもその固定スコアを使う。

### 確定・未実装の例外

将来のモンスターノーツ能力 **「根性」だけはDOWNから復帰できる唯一の例外** とする。

したがって将来実装後は、

- 通常判定による回復
- 「元気」による回復
- その他通常の回復処理

ではライフ0から復帰できない。

**根性だけが蘇生可能。**

DOWN中はスコアを固定し、根性で復活した後からスコア加算を再開する。DOWN中に発生した判定を遡ってスコアへ加算しない。

# 3. モンスターノーツ — **第1弾実装済み（2026-09-03 / PR #997）**

初期実装はTAP専用。譜面表現・専用ノーツ表示・能力4種（元気 / 無敵 / 我慢 / 根性）まで入っている。
検査は `node tools/mode/rhythm-monster-notes-check.js`。

## 3.1 目的

設定したマスモンを音ゲーのプレイ内容へ直接参加させ、

`マスモン設定 → モンスターノーツ → 能力発動 → 生存・攻略`

というMonster Hero本編との連携を作る。

単なる装飾ではなく、設定したモンスターによってプレイ中の生存能力が変わるシステムとする。

---

## 3.2 マスモン設定 — **実装済み（2026-09-03 / PR #995）**

- 音ゲー用モンスターは **マスモンから設定**する。
- **最大4体**まで設定可能。
- 1〜4枠目の並び順を保持し、その順番をモンスターノーツの登場順に使う。
- 4体設定を必須にはしない。1〜3体でもプレイ可能。

### 同一モンスターの重複禁止

同じベースモンスターは複数枠へ設定できない。

例:

- ミーア + ミーア → **不可**
- ミーア + パンドラ → **可**

実装上は同じ個体UUIDだけでなく、同じベースモンスター（同 `baseId`）を重複扱いにする方針。

別モンスターであれば、同じ血統・同じ能力でも同時設定できる。

例:

- ピクシー系能力の別モンスター同士 → 可
- ハム + ザン（どちらも根性） → 可

保存を追加する場合は既存 `mh_*` を壊さず後方互換を持たせる。具体的な保存キーは実装時に現行保存構造を確認して決める。

### 実装（2026-09-03）

保存キーは既存の `mh_rhythm_settings_v1` / `mh_rhythm_best_v1` へ混ぜず、
**`mh_rhythm_monsters_v1`** へ分けた。持つのはマスモンの個体IDの並び（文字列の配列・最大4件）だけで、
名前・染色・能力はマスモン本体から毎回引き直す。

実装は `monster-hero/data/rhythm-mode.js` に置き、役割を2つに分けた。

| 関数 | 役割 |
| --- | --- |
| `sanitizeRhythmMonsterSlotIds(saved)` | 保存値の**形**だけを整える（配列でなければ空／重複ID除去／4件で打ち切り）。所持確認はしない |
| `resolveRhythmMonsterSlots(saved, masuMons)` | **使うとき**に手元のマスモンへ解決する。手放した個体と同一 `baseId` の重複はここで落とす |

分けたのは保存を壊さないため。マスモン一覧を読む前に存在確認まで行うと、設定が空として
保存し直されてプレイヤーの設定が消える（CLAUDE.md ⑦）。落とすのは表示・使用のときだけで、
保存値そのものは書き換えない。

設定の可否は `rhythmMonsterSlotAddIssue()` が理由（`missing` / `full` / `duplicate-id` /
`duplicate-base`）で返し、UIはその日本語文（`RHYTHM_MONSTER_SLOT_ISSUE_TEXT`）をそのまま出す。
追加・削除・並べ替えは `addRhythmMonsterSlot` / `removeRhythmMonsterSlot` / `moveRhythmMonsterSlot`。

UIは音ゲーデバッグ画面の「⚙️ 設定・記録」タブに置いた（`data-rhythm-monster-slots`）。
4枠を常に並べて空き枠を見せ、一覧から選んで設定する。設定できない相手は押せないようにし、
理由を横に出す。マスモンの絵は既存の `DyedMonsterImage` + `getMasuColors` をそのまま使い、
base64で複製しない（§3.5の方針どおり）。

検査は `node tools/mode/rhythm-monster-slots-check.js`。

## 3.3 1曲あたりの出現回数

**設定した1体につき1回、最大4回。**

配置目安の割合は `RHYTHM_MONSTER_NOTE_BASE_RATIOS`（`[.2,.4,.6,.8]`）と
`rhythmMonsterNoteBaseRatios(count)` として実装済み。ここにあるのは**目安の割合だけ**で、
譜面への実配置（下記の配置ルール）は譜面データ側の仕事。

| 設定数 | 出現回数 | 基本位置 |
| ---: | ---: | --- |
| 1体 | 1回 | 約20% |
| 2体 | 2回 | 約20% / 40% |
| 3体 | 3回 | 約20% / 40% / 60% |
| 4体 | 4回 | 約20% / 40% / 60% / 80% |

1枠目 → 1個目、2枠目 → 2個目、3枠目 → 3個目、4枠目 → 4個目と対応する。

### 配置ルール

20 / 40 / 60 / 80%は機械的な固定秒数ではなく**配置目安**。

実際の時刻は譜面ごとに、

- イントロ明け
- Aメロ / Bメロ / サビ等のフレーズ境界
- 曲の特徴的な拍
- プレイヤーが狙って取れる場所

へ前後調整する。

以下は避ける。

- 曲開始直後
- 曲終了直前
- HOLD / SLIDE等が極端に忙しく、能力ノーツを意図的に取りづらくする場所
- 完全ランダム配置

**毎回同じ譜面では同じ位置に出す。** ランキング条件をランごとに変えないため、プレイごとのランダム出現にはしない。

難易度ごとは別譜面なので、EASY〜MASTERですべて同じ秒数に揃える必要はない。各譜面のフレーズ・密度に合わせる。

4体目は終盤の復帰チャンスを残すため、基本的に**80〜85%付近**を候補とする。

## 3.4 判定と能力発動条件 — **実装済み（2026-09-03）**

モンスターノーツにも通常のタイミング判定を使う。

**能力発動は GREAT 以上。**

| 判定 | 能力 |
| --- | --- |
| MARVELOUS | 発動 |
| EXCELLENT | 発動 |
| GREAT | 発動 |
| GOOD | 不発 |
| BAD | 不発 |
| MISS | 不発 |

判定窓そのものはモンスターノーツ専用に甘くしない。

通常の判定・コンボ・スコア処理を維持し、能力発動条件だけをGREAT以上にする方針。

### 譜面での書き方（2026-09-03 実装）

**通常のTAPノーツへ1行足すだけ** にした。専用の配列は作らない。

```js
{ type:'TAP', timeMs:8000, lane:2, subLane:4, subLaneWidth:2, monsterSlot:1 }
```

`monsterSlot` はマスモン設定の何枠目かを指す。判定・描画・幅の計算は通常ノーツの経路を
そのまま通るので、モンスターノーツのために判定や描画を2系統に分けていない。

書き間違い（同じ枠を2回、時刻の順と枠の順のずれ、TAP以外への付与、範囲外）は
`rhythmChartMonsterNoteIssues()` が拾い、検査ツールから通す。

### 決定（2026-09-03 / ユーザー判断）

長らく未確定としていた3点がすべて決まった。

**1. 初期実装は TAP型専用。**

まずTAPだけにモンスターノーツ属性を持たせる。判定・スコア・コンボの扱いが単純で、
能力発動そのものの検証がしやすいため。HOLD / FLICK / SLIDEは、
「始点はGREATだが途中でMISSした」ときに能力をどう扱うか（発動タイミングが始点か終端か、
途中失敗で取り消すか）を別途決める必要があるので、後回しにする。

**2. DOWN中の蘇生ノーツ自身のスコアは加算せず、次のノーツから再開する。**

蘇生ノーツ自身はDOWN中の判定なのでスコアへ加算しない。
「ライフが0になった判定終了時点のスコアから増えない」という §2 のDOWN仕様をそのまま保てるため、
リザルト・BEST・ランキングの計算経路へ例外を入れずに済む。

**3. 譜面には通常のTAPノーツへ `monsterSlot:1〜4` を1行足すだけで書く。**

専用の配列は作らない。判定・描画・幅の計算が通常ノーツの経路をそのまま通るので、
既存の譜面データ形式・判定経路を壊す範囲が最も小さい。書き方は上の
「譜面での書き方」のとおり。

## 3.5 見た目 — **第1弾実装済み（2026-09-03）**

通常ノーツと一目で区別できる**専用ノーツ**にする。

確定している方向性:

- ノーツ中央に、設定したマスモンのモンスター画像を表示する。
- ベース画像だけではなく、**設定したマスモン個体の現在の染色状態を反映**する。
- モンスターノーツ上のマスモンは、枠・背景・アイコン風の囲いを付けず、染色済みの透過画像だけをノーツ中央へ表示する。
- 能力成功時は短時間、モンスター名を付けず能力名だけを表示する。

例:

- `元気！`
- `根性！`

無敵 / 我慢のような時間効果は、発動中であることや残り時間をプレイヤーが把握できるUIを用意する方向。

### 染色表示の実装方針

染色はプレイ中に毎フレーム生成しない。

- 曲開始前またはプレイ開始時に、設定最大4体の染色済み表示を一度生成する。
- 生成済み結果をキャッシュし、モンスターノーツと能力表示で再利用する。
- 同じマスモンはノーツと発動表示で同じ見た目を使う。
- 既存の染色ロジック・マスク・個体の染色情報を再利用する。
- 既存画像を不用意にbase64複製しない。
- 縦横比を変更しない。

これによりモンスターノーツ最大4個のために毎フレーム染色処理を増やさない。

### 未確定

- 専用ノーツの枠色・形
- 能力ごとのアイコン
- 発動アニメーションの最終デザイン
- 残り時間UIの位置

見た目は軽量モードで非必須グロー・演出を抑制できるようにする。

# 4. モンスター能力 — **実装済み（2026-09-03 / PR #997）**

能力は `monster-hero/data/rhythm-mode.js` の `RHYTHM_MONSTER_ABILITIES` と
`RHYTHM_MONSTER_ABILITY_BY_LINEAGE` に置き、主血統から引く。状態
（無敵・我慢の残り時間、根性ストック）は run が持ち、毎フレーム作り直さない。

## 4.1 元気 — **回復量500へ変更・実装済み（2026-09-03）**

**ライフ +500**（旧値は +200。2026-09-03のユーザー判断で変更し実装済み）。

- 変更したのは回復量だけ。能力発動条件・対象主血統は変更していない。
- 最大ライフを超えない。
- 生存中のみ通常回復として働く。
- ライフ0のDOWN状態からは復帰できない。
- DOWNから復帰できるのは根性だけ。

### 対象主血統

- ピクシー
- ウンディーネ
- プラント
- スエゾー
- ライガー

---

## 4.2 無敵

**効果: 6秒間、ライフダメージ0**

- 発動中のBAD / MISS等による負のライフ変化を0にする。
- 判定、コンボ、スコアそのものを自動成功にはしない。
- MISSはMISSのまま。守るのはライフだけ。

### 対象主血統

- モノリス
- アーク

---

## 4.3 我慢

**効果時間: 15秒**

発動中、受けるライフダメージを軽減する。

### 現在の暫定軽減率

**50%軽減**を作業基準とする。

例:

- MISS -50 → -25
- BAD -20 → -10

ただし、**軽減率は今後のライフバランス確認で要検討**。50%を永久固定値とは扱わない。

### 対象主血統

- ゴーレム
- モッチー

### 未確定

- 最終軽減率
- 将来奇数ダメージが入った場合の端数処理

---

## 4.4 根性

**蘇生能力。復活ライフは50。**

### 根性ストック

- ストック上限は **1回分**。
- 生存中かつストックなしで根性発動 → 根性1回分をストック。
- 根性ストック中にライフ0 → ストックを消費し、自動でライフ50へ復活。
- ストック消費後、後の根性ノーツで再び取得することは可能。

### DOWN中の取得

DOWN中でもノーツ判定は続いているため、後から流れてきた根性モンスターノーツをGREAT以上で取れば、**その場でライフ50へ復活**する。

復活後はスコア加算を再開する。DOWN中に止まっていた分を遡って加算しない。

### すでにストックを持っている場合

根性ストックが1個ある状態で、さらに根性モンスターノーツを成功した場合は、ストックを2個へ増やさず、**ライフ +50**へ変換する。

最大ライフは超えない。

### 対象主血統

- ハム
- ザン

---

## 4.5 派生種の能力決定

能力は**主血統**を基準に決定する。

例:

- ミーア / パンドラ → 主血統ピクシー → 元気
- イヴリース → 主血統アーク → 無敵
- オボロ → 主血統プラント → 元気
- エイキ → 主血統ザン → 根性

副血統による能力変更は現時点では行わない。

## 4.7 同能力を複数設定した場合

**別モンスターであれば同じ能力を複数設定してよい。**

例:

- 元気 + 元気
- 無敵 + 無敵
- 根性 + 根性

を禁止しない。

時間効果の重なり方は下記のとおり。

### 時間効果の重なり — **確定（2026-09-03 / ユーザー判断）**

**無敵と我慢は効果時間が違う（6秒 / 15秒）ので、別の能力としてそれぞれの残り時間で
独立して走らせる。** 片方を取ってももう片方の残り時間は消えない。

両方が有効なあいだは**強いほう（無敵）が勝つ**。無敵が切れたら、そこから我慢の軽減へ変わる。
逆に我慢が先に切れた場合は、無敵が残っているあいだダメージ0のまま。

例（t=0で無敵と我慢の両方を取った場合）:

| 時刻 | 効いているもの | MISS のライフ変化 |
| --- | --- | ---: |
| 0〜6秒 | 無敵（我慢も走っている） | 0 |
| 6〜15秒 | 我慢 | -25 |
| 15秒〜 | なし | -50 |

同じ能力を続けて取った場合は、**終わりが遅いほう（＝いま取ったぶん）まで効く**。
軽減率を足したり、残り時間へ足したりはしない。

そもそもモンスターノーツは曲の 20 / 40 / 60 / 80% 付近へ置くため（§3.3）、
通常の曲尺では同じ能力の効果時間どうしが重なることはほとんどない。

根性は「ストック最大1、ストック中の再取得は+50」で確定（§4.4）。

UI表示は `data-rhythm-ability-badge` に「無敵 4.2s / 我慢 11.8s / 根性 ストック」の形で
並べて出す。無敵と我慢が同時に有効なときも両方の残り時間が見える。

# 5. ランキングとモンスターノーツ — **方針確定（2026-09-03 / ユーザー判断）・実装は未着手**

モンスターノーツ能力はスコア倍率を直接上げないが、生存時間を伸ばしDOWN後のスコア停止を避けたり、根性でスコア加算を再開できるため、**最終スコアへ間接的に影響する**。

## 決定

**マスモン能力込みのプレイを、正式な攻略要素としてランキングへそのまま許可する。**

能力はスコアに直接倍率をかけず、生存継続・DOWN回避・根性復活という間接効果に留まる。
通常のTAP/HOLD/SLIDE/FLICKの技量と同じ「プレイのうまさ」の一部として扱い、
モンスターノーツ専用の除外ランキングや使用有無での部門分けは作らない。

設定無しのプレイヤーは、単にその恩恵（DOWN回避・復活チャンス）が無いだけで、
参加資格そのものは制限しない。

**マスモン設定を途中で変えても、BEST / ランキング記録には何も残さない。**
現在のBESTは「その時点でのそのスコア」だけを持つ構造（`mh_rhythm_best_v1`）で、
ノーツ速度やサイズ設定と同じように、どの設定で取ったかは記録しない。
保存形式を増やさず、この方針のために新しい保存キー・メタデータは追加しない。

能力バランス（我慢の軽減率など、§4.3で暫定としている値を含む）は、
正式ランキング実装前に実機でのバランス確認を経てから確定させる。
バランスが今後変わっても、既存のBEST記録・保存形式には影響しない
（スコアの再計算や過去記録の書き換えを行わない）。

決める前にランキングDBや保存形式を先行実装しない、という方針自体は変わらない。
今回決めたのは**扱い方の方針**であり、Supabase実装等はまだ着手しない。

# 6. 縦画面 / 横画面の両対応 — **回転基盤・横画面HUDまで実装済み（2026-09-03）**

音ゲーは将来的に**縦画面・横画面の両方へ対応**する。

現在の主対象は引き続きスマートフォン縦画面だが、横画面も正式対応対象とする。

## 6.1 共通にするもの

縦横で以下を分けない。

- 譜面データ
- noteTime
- BPM / beatZero
- 判定窓
- スコア式
- コンボ
- 5メインレーン / 10サブレーンの論理座標
- 入力・判定ロジック

**縦用譜面 / 横用譜面を別々に作らない。**

同じ authored lane / subLane / width / timeMs を、現在のプレイエリア寸法へprojectionして描画する。

## 6.2 画面方向ごとに最適化するもの

- プレイエリア寸法
- projectionの表示用パラメータ
- HUD配置
- 曲名 / SCORE / COMBO / LIFE / ポーズ等の収まり
- Safe Area
- 必要に応じたノーツ・文字の見え方

横画面を縦画面の単純な横引き伸ばしにはしない。

## 6.3 回転時

目標仕様:

- 端末回転 / resizeを検知する。
- プレイ中でもaudio clock、run、スコア、コンボ、判定状態をリセットしない。
- geometryだけ再計測・再配置する。
- HOLD / SLIDE操作中も可能な限り現在のrunを維持する。

ブラウザ制約でプレイ中の無停止回転が安定しない場合は、その時点で実機結果を提示して仕様を再確認する。推測で曲を強制再スタートする仕様へ変えない。

### 実装済み（2026-09-03） — geometry再計測の基盤

- `installRhythmPerspectiveNoteVisuals` が `resize` / `orientationchange` /
  `visualViewport` の `resize` を購読し、**プレイエリアの大きさが実際に変わったときだけ**
  `rhythmLayoutPlayArea()` をやり直す。
  以前は「プレイエリアの要素が入れ替わったときだけ」だったため、回転してもレーン番号の位置や
  判定ラインの左右が古い縦横比のまま残っていた。
- **回転の再配置でrAFを増やさない。** ノーツの配置は本体の1本のrAFが持つという原則を守るため、
  イベントを時間でまとめるのではなく「大きさが変わっていなければ何もしない」で無駄働きを防ぐ。
  回転中に `resize` が連続で飛んできても、組み直しは1回。
- 触るのは見た目のstyleだけで、**audio clock / run / スコア / コンボ / 判定状態には関与しない**（§6.3の要件）。
- 入力側の rect キャッシュも同じイベントで捨てる（§7 の候補2対応で入れた仕組み）。
- ノーツの座標は本体のrAFが毎フレーム `measureTravel()` で測り直すので、回転後も自動で追従する。

検査は `node tools/mode/rhythm-orientation-check.js`。擬似DOM上で縦→横→縦と回して、
組み直しの回数と、run・スコア・判定に触っていないことを確かめる。

### 横画面の現状（2026-09-03 実測）

現行の縦画面向けHUDのまま横画面（844×390 / 926×428相当）にした場合:

- **レーンとHUDは重ならない**（横に広いぶんウェッジが広く、余裕がある）
- **Safe Areaの計算も正しい**（プレイエリア＝画面 − 上下Safe − 下余白8px）
- ただし**HUD本文がプレイエリアの縦の約39%を占める**（縦画面では約12〜20%）。
  横画面はプレイエリアが低いため、縦画面向けの積み上げ配置のままでは上部を大きく使ってしまう。

→ §6.2「横画面を縦画面の単純な横引き伸ばしにはしない」のとおり、横画面専用のHUD配置が必要
だったため、下記のとおり「案A: サイドウェッジ集約」を実装した。

### 横画面HUD配置「案A: サイドウェッジ集約」— 実装済み（2026-09-03 / ユーザー判断）

3案（サイドウェッジ集約 / トップシングルバー / コーナーミニマル）を比較用モックアップで
提示し、ユーザーが案Aを選択した。縦画面と同じ「左右ウェッジへ置く」考え方のまま、
各行を横並びへ畳んで縦の積み上げを減らす方針。

実装は Tailwind の `landscape:` バリアント（`@media (orientation: landscape)` そのもの）
だけで行い、縦画面のクラス・DOM構造は一切変更していない。

- 左ウェッジ: 「ランク＋SCORE＋BEST」を1行、「難易度バッジ＋曲名」をもう1行にまとめる。
  横画面では文字数を減らすため、SCOREの見出しラベルとHOLD TEST/TAP TESTの表記を隠す
  （難易度バッジと数値だけで用は足りるため）。曲名は3行→1行折り返しにする
  （JS側の`isLandscape`判定でWebkitLineClampの値だけを切り替える。判定・スコア・run等
  ゲームロジックには一切触れていない）
- 右ウェッジ: 「ポーズ＋LIFE」を1行、「COMBO」をもう1行にまとめる。無敵/我慢/根性の
  残り時間バッジは、発動中だけ独立した行として現れる
- 横画面では左右にノッチ（Dynamic Island等のセンサーハウジング）が来るため、
  プレイ画面自身が `landscape:pl-[env(safe-area-inset-left)]` /
  `landscape:pr-[env(safe-area-inset-right)]` で確保する。bodyは上下しか確保していないため、
  二重掛けにはならない
- ポーズボタンは横画面でもタップ精度を落とさないよう44px未満に縮めていない

実測（`node tools/mode/rhythm-landscape-hud-check.js`、844×390 / 926×428 / 667×375）:

- HUD本文がプレイエリアの縦の約**20.6〜23.7%**（縦画面のまま流用した場合の約39%から
  大きく削減。完全に縦画面と同じ12〜20%までは詰め切れていないが、台形が浅い上端付近へ
  2行分の文字を収める都合上の限界に近い）
- 台形の頂点（最上部中心）はHUDに覆われない
- HUD本文の実際のインク範囲は、それが描かれる高さの台形の外側（左右ウェッジ）に収まる

### HUDの見た目を丸バッジ・アイコン付きバーへ変更 — 実装済み（2026-09-03 / ユーザー提示の参考画像）

ユーザーが参考にしたい他アプリのスクリーンショットを提示し、それに合わせてHUDの見た目を
変更した。この時点では配置(左ウェッジ・右ウェッジ、絶対配置)・収束率(`.18`)・幅の制約は
変えていない（その後の再構成は次項参照）。

- SCORE: ランクの文字だけの表示 → 丸いバッジ(ランクの色でリング表示)＋その横に次のランクまでの
  進捗バー(`rhythmRankProgress`、`monster-hero/data/rhythm-mode.js`)。スコアそのものの数字・
  ランクしきい値・BESTの扱いは変更していない
- LIFE: 「LIFE」の見出し文字＋バー → ハートのアイコン＋バー(数値は維持)

### 横画面での見た目の飛行時間補正 — 実装したが取り消し（2026-09-03 / 実機フィードバック）

HUD配置を実装したうえで実機プレイしたところ「奥行きが短すぎて難易度が大幅アップした」という
指摘があり、一度は`rhythmTravelMsHeightRatio`（プレイエリアの実測高さに応じてノーツの見た目の
飛行時間`travelMs`を伸ばす）を実装した。しかし、その後の実機フィードバックで「落下速度が
遅くなるのはおかしい、縦画面と同じにしてほしい」と明確に指摘され、この対応は取り消した。

**`travelMs`は画面の向きに関係なく常に`rhythmTravelMsForSpeed(settings.noteSpeed)`のみを
使う。**

### HUDを薄い帯へ再構成し、収束率を .18→.55 へ引き上げ — 実装済み（2026-09-03 / ユーザー判断）

丸バッジ化しても「上部が見えるようになっていない」と指摘され、実際に収束率を上げてみたところ
（`.18`→`.19`程度が限界）、常時表示していたHUD本文(ランク・SCORE・BEST・難易度・曲名を
左ウェッジへ、LIFE・ポーズ・COMBOを右ウェッジへ、いずれも複数行で積み上げる形)の量が多く、
ウェッジ自体が絶対配置・左右ウェッジ方式のままでは収束率をほとんど上げられないことが分かった
（収束率を上げるとレーンの余白は画面のどの高さでも均等に狭くなるため、HUD本文がある深さの
余白も一緒に狭くなる。BEST=1,000,000や長い曲名が収まる`.18`が実質の上限だった）。

ユーザーに「HUDを薄い帯に戻して先に進む」か「現状維持」かを確認し、薄い帯を選んだため、
HUD(`<header data-rhythm-hud>`)を**プレイエリアへ重ねる絶対配置から、実領域を持つ薄い帯**
（`position:relative`、通常のflowで高さを取る）へ変更した。以前(§6.3冒頭)一度この方式を
試して「奥行きが変わった/改悪」と指摘され取り消した経緯があるが、その失敗は帯の中身が多く
(丸バッジ+進捗バー+スコア+BESTの行、難易度+曲名の行の2〜3行)帯自体の高さがかさんだことが
原因だった。今回は、

- 常時表示は1行だけ: 左＝丸いランクバッジ＋SCORE、右＝ハートアイコン＋LIFEバー＋数値＋
  COMBO＋ポーズボタン
- BEST・難易度バッジ＋TEST表記・曲名は2行目の細い行へ回す（横画面ではBEST・TEST表記を
  さらに`landscape:hidden`で省き、曲名を1行にする）
- ランクの進捗バーは廃止（丸バッジ＋ランク文字のみに戻した。帯の高さを増やす割に得られる
  情報が少なかったため）

という形に中身そのものを絞り、帯の実測高さを68.5〜81px（画面全体の8〜19%、横画面で
16〜19%）まで大きく削った。これにより、HUDが台形の幅に一切関与しなくなったため、
`RHYTHM_PROJECTION_TOP_SCALE`を`.18`→`.55`へ引き上げ、レーンを画面の上のほうまで広く
見せられるようになった。

検査は`node tools/mode/rhythm-hud-wedge-check.js` / `rhythm-landscape-hud-check.js`。
HUDがプレイエリアと重ならないこと・Safe Areaを二重消費しないこと・台形の頂点が覆われない
こと（回帰チェック）・帯の高さがmain全体の18%（横画面22%）以内に収まることを実測で固定する。

# 7. カクつき・描画負荷改善 — **現行課題 / 要計測**

ユーザー実機で音ゲープレイ中のカクつきを確認している。

現時点では**原因確定とは扱わない**。最新mainのコード上で負荷候補が見つかっているため、計測して切り分ける。

## 7.1 現在の主な負荷候補

1. HOLD / SLIDE途中追従の `RHYTHM_GESTURE_RUNTIME` が、プレイ本体とは別の `requestAnimationFrame` を持つ。
2. 途中追従側でプレイエリア検索と `getBoundingClientRect()` が繰り返される。
3. プレイ本体側でも毎フレームgeometry測定を行う箇所がある。
4. SLIDE帯はauthored点間を細分化し、多数のSVG polygonを毎フレーム計算・更新する。
5. Touch接触幅処理がtouchmoveごとにgeometry取得とサブレーン発光更新を行う。
6. デバッグ・gesture表示用のMutationObserverが複数存在し、DOM変化時の検索が重なる可能性がある。

これらは**候補**であり、計測前に「これが原因」と断定しない。

## 7.2 改善方針

可能な限り以下へ寄せる。

- プレイ中の主要フレーム処理は本体の1本のrAFへ統合する。
- 同じフレームで使う `songTimeMs` / playArea rect / geometryは共有する。
- `getBoundingClientRect()` を毎ノーツ・毎gestureで繰り返さない。
- playArea rectはプレイ開始時にキャッシュし、resize / orientation change / 実際のレイアウト変更時だけ再計測する。
- HOLD / SLIDE途中追従へ、取得済みgeometryと時刻を渡す。
- SLIDEは画面外部分の不要なpolygon更新を避け、可視区間だけを描画できるか検証する。
- 10分割等のsegment数を減らす場合は、レーンgeometryからのズレが再発しないことを実測する。
- Touch発光対象DOMをキャッシュし、変化したサブレーンだけ更新する。
- プレイ中不要なMutationObserverはdisconnectまたは早期returnし、全ノーツ再検索を避ける。
- 軽量モードでは非必須filter / shadow / transition / 演出をさらに抑える。

## 7.3 性能計測 — **実装済み（デバッグ限定）**

`RHYTHM_PERF`（`monster-hero/data/rhythm-mode.js`）として実装済み。音ゲーデバッグ画面の
「⚙️ 設定・記録」タブに「性能計測（デバッグ）」パネルがあり、ON/OFF・記録の表示・クリアができる。

- **既定はOFF。OFFのあいだは加算も配列追加も一切しない**（計測のために本体を重くしない）
- **計測のために `requestAnimationFrame` を増やさない。** 本体のrAFが受け取るタイムスタンプを使う
- ON/OFFの記憶は新しい保存キー `mh_rhythm_perf_v1` に分ける（既存の設定・BESTへは触らない）
- デバッグ専用なので、更新履歴・ヘルプには載せない（CLAUDE.md ⑤の但し書き）

記録している項目と、その計測箇所:

| 項目 | 計測箇所 |
| --- | --- |
| フレーム数 / 平均fps / 平均・最悪フレーム時間 | 本体rAF（`scheduleTick` の `tick`） |
| 16.7ms超 / 25ms超 / 33ms超フレーム数 | 同上 |
| 1フレームあたりのlayout read数 | `measureTravel`（area / 判定ライン / ノーツの3回）、`areaRect`、`rhythmLayoutNoteVisual`（フレーム共有rectが無い場合のみ） |
| 1フレームあたりのDOM検索数 | `areaRect`（`querySelector`）、`applyTouchSpanGlow`（`querySelectorAll`） |
| 1フレームあたりのSLIDE polygon更新数 | `rhythmSlideSegmentPolygons` の戻り値の数 |
| ジェスチャー側rAFのフレーム数 | `RHYTHM_GESTURE_RUNTIME` の `tick` |

一時停止やバックグラウンド復帰で数秒空いた間隔は、平均を壊さないよう数えない。

検査は `node tools/mode/rhythm-perf-check.js`。

### 静的に確認済みの負荷候補（2026-09-03）

計測前だが、コード上で実在を確認したもの:

- **候補1（別rAF）は実在。** `RHYTHM_GESTURE_RUNTIME` はHOLD/SLIDE/FLICK操作中、本体とは別の `requestAnimationFrame` を回す
- **候補2（rect反復）は実在。** `areaRect()` は呼ばれるたびに `querySelector` ＋ `getBoundingClientRect()`（＝強制レイアウト）を行い、
  これがジェスチャーの毎フレームと毎pointermoveで走る
- **候補5（発光の再検索）は実在。** `applyTouchSpanGlow()` はtouchmoveごとに `querySelectorAll('[data-rhythm-sublane-feedback]')` で10要素を引き直す

ただし**どれが実際のカクつきの主因かは、実機の計測値を見るまで断定しない。**

### 対応済み（2026-09-03）

主因の断定を待たずに済む、「同じ結果をより少ない仕事で出す」ものだけ先に直した。入力の意味・判定条件は一切変えていない。

- **候補2（rect反復）**: `areaRect()` を**同じフレームのあいだ共有**するようにした。
  以前は指の数ぶん・pointermoveの数ぶん `getBoundingClientRect()`（強制レイアウト）が走っていた。
  擬似DOMでの実測で、**12回の指移動あたり12回 → 1回**へ減った。
  キャッシュがズレると入力位置がずれるため、次のすべてで必ず捨てる。
  - 本体rAFの各フレーム先頭（`RHYTHM_GESTURE_RUNTIME.invalidateAreaRect()`）
  - ジェスチャー側rAFの各フレーム先頭
  - `resize` / `orientationchange` / `scroll`、および `visualViewport` の `resize` / `scroll`
- **候補5（発光の再検索）**: `applyTouchSpanGlow()` が要素を覚えて使い回し、
  **状態が変わったサブレーンだけ**書き換えるようにした（DOMが入れ替わったら引き直す）。

検査は `node tools/mode/rhythm-input-cost-check.js`。回数を数えるだけでなく、
**フレームが変わったら測り直す・画面が動いたら捨てる**という鮮度の条件を主目的として固定している。

- **候補6（MutationObserverの再検索）**: `installRhythmGestureVisuals` の `decorate()` は
  `area.querySelectorAll('[data-rhythm-note]')` で全ノーツを引き直すのに、
  `document.body` の `childList` 変化なら**何であっても**走っていた。
  ノーツ・プレイエリア・モード表記が増減したときだけ走るようフィルタを付けた（やることは変えない）。
  走った回数は計測パネルの「ノーツ再検索」で見える。

**候補1（別rAFの統合）は未対応。** 加えて、候補2で毎フレームの強制レイアウトを外した今、
rAFを1本にまとめて減るのは**コールバックの呼び出し回数だけ**で、中の仕事量は変わらない。
先に実機の計測値（ジェスチャー側rAFのフレーム数と、16.7ms超フレーム数の関係）を見て、
本当に効くかを確かめてから判断する。

**候補4（SLIDE帯の描画量）も未対応。** segment数を減らすとレーンgeometryからのズレが再発する恐れがあるため、
減らすなら「画面外の区間だけを省く」形にし、可視区間の分割数は変えないこと。

最低限確認したいもの:

- フレーム時間
- 16.7ms超フレーム数
- 25ms超フレーム数
- 33ms超フレーム数
- 1フレームあたりのlayout read回数
- 1フレームあたりのSLIDE polygon更新数
- HOLD / SLIDE有無での差

計測UIそのものを一般公開しない。

## 7.4 保護対象

性能改善で以下を変えない。

- BPM / beatZero
- noteTime
- 判定窓
- 入力座標の意味
- 10サブレーン / 可変幅
- HOLD / SLIDE追従判定条件
- スコア式
- BEST形式
- 譜面データ

「軽くするため」に判定や譜面を簡略化しない。

# 8. 近い将来の推奨実装順

現在の個別作業状況に応じて前後してよいが、依存関係としては以下を推奨する。

1. **現在進行中のプレイ画面 / レイアウト改善を安定させる**
2. **カクつきの性能計測・改善**
3. **縦 / 横のレスポンシブgeometry基盤**
4. **モンスターノーツ基盤 + 最大4体マスモン設定**
5. **元気 / 無敵 / 我慢 / 根性の能力実装**
6. **染色済みモンスター表示と能力発動UI**
7. **実機で能力・ライフ・速度・縦横・負荷をまとめて回帰確認**
8. その後、正式譜面・正式HOME・ランキング等の既存ロードマップへ戻る

理由:

- 描画負荷と画面geometryを先に安定させれば、モンスターノーツUIを縦画面専用で作り直す二度手間を減らせる。
- モンスターノーツは最大4個なので、それ自体の処理負荷は小さくできるが、既存のカクつきを残したまま演出を積み増さない。

ただしユーザーから別の優先指示があれば、その指示を最優先する。

# 9. モンスターノーツ実装時の最低回帰確認

実装時は少なくとも以下を確認する。

### 設定

- 0〜4体で正常動作する。
- 同じベースモンスターを2枠へ設定できない。
- 別モンスターで同能力は設定できる。
- 旧保存データ / 欠損データで起動できる。

### 配置

- 設定数とモンスターノーツ数が一致する。
- 1〜4枠目の順番と約20 / 40 / 60 / 80%の登場順が一致する。
- 同じ譜面では毎回同じ位置。

### 判定

- MARVELOUS / EXCELLENT / GREATで発動。
- GOOD / BAD / MISSでは不発。
- 判定窓自体は変わらない。

### 能力

- 元気は +500、最大値でクランプ。
- 元気ではDOWNから復活しない。
- 無敵6秒中は負のライフ変化0。
- 我慢15秒中は暫定50%軽減。
- 根性ストックは最大1。
- 根性ストック消費でライフ50へ自動復活。
- DOWN中の根性成功でライフ50へ復活。
- 根性ストック中の再取得は+50。
- 復活後にスコア加算が再開し、DOWN中のスコアは遡って増えない。

### 表示・性能

- 設定した個体の染色状態が反映される。
- 染色計算を毎フレーム行わない。
- ノーツ画像の縦横比を維持する。
- 軽量モードでも判別可能。
- 最大4個の追加でフレーム落ちを悪化させない。

# 10. まだ決めていない事項

### 決まった事項（2026-09-03）

- モンスターノーツの初期実装は **TAP専用**（§3.4）
- DOWN中に根性を取ったその蘇生ノーツ自身は **スコアへ加算せず、次のノーツから再開**（§3.4）
- 譜面は通常のTAPノーツへ `monsterSlot:1〜4` を1行足すだけで書く（§3.4）
- 無敵と我慢は **別の能力として独立して走り、片方が切れたらもう片方の効果へ変わる**（§4.7）
- 正式ランキングでマスモン能力込みのプレイをそのまま許可し、設定変更をBESTへ記録しない（§5）
- 元気の回復量を **200 → 500** に変更した（§4.1、実装済み）
- 横画面のノーツの見た目の飛行時間(travelMs)は、**縦画面と同じ値を使う**（プレイエリアの
  高さに応じて伸ばす対応は実機フィードバックで「落下速度が遅くなるのはおかしい」と指摘され
  取り消した。§6.3）
- HUD(`<header data-rhythm-hud>`)は**プレイエリアへ重ねる絶対配置から、実領域を持つ
  薄い帯へ変更した**（§6.3）。一度目の帯化(内容量が多く帯が高すぎた)は「奥行きが変わった」
  と指摘され取り消したが、常時表示を1行に絞った薄い帯(実測68.5〜81px)へ作り直し、
  ユーザーが「HUDを薄い帯に戻して先に進む」を選んだ
- 台形の上端の幅(`RHYTHM_PROJECTION_TOP_SCALE`)を **`.18` → `.55`** へ引き上げた
  （§6.3、portrait/landscape共通の1つの値、暫定値）。HUDが薄い帯になり台形の幅に
  一切関与しなくなったことで可能になった

### 未確定

以下は会話で未確定のため、実装時に勝手に決めない。

- 我慢の最終軽減率（現在50%は暫定）
- 能力発動中UIの最終デザイン
- `RHYTHM_PROJECTION_TOP_SCALE`（現状.55、portrait/landscape共通）の具体値。実機の見え方を
  見て、レーンの上端の広がり方をさらに調整するか
- HUDの帯の高さ（現状最大19%）をさらに詰めるか
- オプションへ「自動 / 縦優先 / 横優先」等の項目を追加するか
- 端末回転の細かな遷移演出
- ドラゴン / ジョーカー / ゲルの能力（プレイアブル代表が実装されるまで保留）

# 11. 既存の大ロードマップとの関係

`docs/spec/RHYTHM_MODE.md` にある正式譜面・HOME・ランキング・週間システム等の大ロードマップは引き続き有効。

- 縦横両対応

- マスモン生存能力

を、正式公開前に必要な基盤項目として追加する。
