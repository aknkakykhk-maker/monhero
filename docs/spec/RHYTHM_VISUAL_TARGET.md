# モンヒロビートの見た目の目標(参考動画の観察メモ)

2026-09-26、ユーザーが「モンビーをこのレベルまで仕上げたい」と、他社の音ゲー(バンドリ！アワーノーツ)の
プレイ動画を2本とスクリーンショットを送ってきた。この文書はそこから読み取ったことの控え。
**まねるのは完成度と手ごたえで、デザインをそのまま写すことではない**(色・形はモンスターヒーローらしく作る)。

- 動画1: iPad を机に置いて横向きで遊ぶ手元の録画(YouTubeの画面録画。640×360で細部は粗い)
- 動画2: スマホ横向きの画面録画(メニュー → 曲えらび → 読み込み → 開始演出 → 演奏)
- スクリーンショット3枚: モンヒロビート(横向き)とアワーノーツ2枚の並べ比べ

## 1. 読み取れたこと

### 道(レーン)

| 項目 | 参考動画 |
| --- | --- |
| 形 | 両端がまっすぐな三角形。画面の上の一点(画面のすぐ外)へ向かって細くなる |
| 判定ライン | ピンクの細い線が2本平行に走り、その間が判定の帯。画面の下から2割ほどの高さ。ラインの下にも道が続いて画面の下端から外へ抜ける |
| 道の色 | ほぼ黒の半透明。後ろの背景がうっすら透ける。境目の線は細く控えめ |
| レーン数 | 真ん中に境目の線がある(偶数)。6レーンに見える |
| 開始演出 | 始まる直前、レーンの線が光のレーザーのように奥へ走って道が組み上がる |

### ノーツ

| 種類 | 見た目 |
| --- | --- |
| TAP | 白〜水色の薄い板。奥では細く、手前で太く(遠近どおり) |
| HOLD | 明るい青白の太い帯。押している間はそのレーンが光り続ける |
| SLIDE | 太い帯が**S字にうねって**レーンをまたぐ。幅も途中で変わる |
| FLICK | 向きの付いた矢印。左右は `<<<`(緑)・`>>>>`(ピンク)の連なった山形、上は黄色の山形。**払う向きが一目でわかる** |
| 同時・連続 | 板が階段のように何段も積み重なって落ちてくる形がある |

### 叩いたときの演出

- 叩いたレーンから奥へ向かって**光の柱**が立つ(青〜水色、長押し中は緑)
- 判定ラインで**白い十字の光(レンズフレア)**と細かい粒がはじける
- 判定の文字は道の中央、判定ラインの少し上。PERFECT は虹〜緑、GREAT はピンク、GOOD は緑、BAD は白
- コンボ数は道の右外(空いた三角のすき間)に大きく。「COMBO」の上に数字
- 盛り上がる場面で、キャラクターの絵が画面の端から斜めに差し込まれる(カットイン)

### 画面のまわり

- 背景は演奏中ずっと動く舞台(3Dのライブ映像)。道の左右の三角のすき間に見える
- 左上に小さくスコアとランクの目盛り(進むほど埋まる)、右上に細いライフのゲージと一時停止
- 曲えらびは、左に曲の一覧(ジャケット・レベル)、右に大きなジャケットと難易度ごとのレベル。
  演奏前に「アシストモード」の説明が出る

## 3. まだの差(やる順)

ユーザーの指示で、**6レーン化(全曲の譜面の作り直し)はいちばん最後**に回す。

1. ~~道を黒寄りの半透明にして、後ろのライブ背景を透かすか~~ … **いまのまま(不透明に近い濃い青)に決定**(2026-09-26。
   ライブ背景「派手」で A いま / B 55% / C 35% の見本を見せ、ユーザーが A を選んだ。ライブ背景の既定は「シンプル」で、
   半透明にしても多くの人には道が黒っぽくなるだけという事情もある)
2. ~~カットイン~~ … 済み(#1784。重さを測って問題なし)
3. **6レーン化**(最後)。進め方は下の「5. 6レーン化」。サブレーンは6×2=12本になり、全曲の譜面を最新の版で作り直す(曲線のSLIDE・MASTERの横フリックもこのとき入る)。
   **過去の記録(自己ベストと全国ランキング)はそのまま残す**(2026-09-26 ユーザー判断「過去の記録はそのままでおっけー」)

**改修のたびに重さを測る**(ユーザー指示)。CPUを1/4に絞った実ブラウザで、叩かないとき
(`tools/mode/rhythm-live-frame-report.js --cpu 4 --runs 3`)と叩き続けたときの両方を、main と比べる。
GPU の仕事量(見た目の演出・WebGL・層の重なり)は `tools/mode/rhythm-gpu-load-report.js --compare origin/main` で main と比べる
(`--suite` でシンプル・派手・ライブ・全部ONの4つ)。この環境に GPU は無いので、実機の速さではなく「GPU にやらせている仕事の量」の比較。

### 実機が無くても GPU の重さを見積もる(2026-09-27)

`node tools/mode/rhythm-gpu-estimate.js`(1回5分ほど)。見た目の「おまかせ」4つそれぞれについて、
**「画面いっぱいを半透明で何回塗ったのと同じか」**(以下「画面◯回ぶん」)を出し、機種の帯ごとの GPU の時間と fps の目安に直す。

1. 較正: 同じ 390×844・dpr3 の画面で、画面いっぱいの半透明の四角を N=0/2/4/8 回塗り、ソフトの GPU(SwiftShader)の仕事の時間を
   `a + b×N` の直線に合わせる(b が「画面1回ぶん」)
2. 演奏画面を「おまかせ」ごとに WebGL で数秒動かし、同じ物差しで GPU の仕事を測って `(測った時間 − a) ÷ b` で「画面◯回ぶん」にする
3. 機種の帯(`tools/mode/gpu-device-profiles.json` の画素数と「1ms に塗れる画素の数」)で `回数 × 画素数 ÷ 塗る速さ` を出す

いまの値(2026-09-27): 軽さ優先 1.1 / 標準 2.2 / 華やか 5.5 / 全部のせ 15.0 回ぶん。
安いAndroid(Mali-G52 級)の目安は 標準 2.6ms・全部のせ 17.3ms(58fps)。

- `--check` … `tools/mode/gpu-budget.json` の上限(いまの値×1.25)を超えていないか。演出を足したら通す。
  わざと重くしたときは `--write-budget` で書き直す(理由をコミットに書く)
- `--only STANDARD` で1つだけ、`--runs 3` で3回の中央値
- どの演出が重いかは、`rhythm-gpu-load-report.js` の `measure()` に設定を1つずつ変えて渡して比べる。
  シェーダーの一部を消したら・書き換えたらどうなるかは、場面に `shaderPatch:[[探す文字,置き換える文字]]` を付けると
  本体を書き換えずに測れる(ブラウザの `shaderSource` で置き換える)
- **2026-09-27 の内訳**(「全部のせ」1440ms/フレームから1つずつ外したときの差・1回ずつ):
  背景「ライブ」→「派手」 −700ms(うちペンライト約430ms・レーザー約160ms) / にじむ光 −380ms /
  「派手」→「落ち着き」(サーチライトと光の粒) −240ms / 道・判定の文字・ノーツの動き・コンボの節目 それぞれ −140ms 前後(ぶれの範囲に近い)
- 見た目を変えずに軽くしたもの(同じ日):
  - にじむ光を画面へ重ねる最後の1回を「1回だけ読む」処理にし、光を描いた範囲+ぼかしの届く幅だけを塗る(「全部のせ」で −10%)。
    main と描き比べて、違いは最大1段・0.001% の画素
  - ペンライトの無い画面の上 16% は、拍の頭の色みだけの軽い処理で塗る(色は同じ)
  - レーザーは光の筋から、ペンライトは席から離れた画素で計算を打ち切る(明るさ 1/255 の1万分の1未満のところだけ)。
    **この環境の数字には出ない**(GPU のまね SwiftShader は分かれ道の両方を計算する)。実機の GPU では近くの画素がそろって
    飛ばせるので効く。色が変わらないことは `rhythm-stage-gl-check.js` が工夫を外した版と描き比べて見張る(最大1段・0.003% の画素)
- 試して効かなかったもの: ペンライトの乱数(sin)を軽くしても差は出なかった(重いのは指数関数と席の数)。
  DOM の層の合成(画面8〜11枚ぶん)は、演出量「最小」でも同じ枚数で GPU の仕事が145msなので、大きな重さではない
- **限界**: 数えているのは「塗る量」だけ。GPU ごとの得手不得手(ぼかし・大きい画像の読み込み・タイル型 GPU の癖)や発熱による
  速度の落ち込みは入らない。機種の帯の「塗る速さ」は公開されている理論値のおよそ1/3を置いた仮の値。
  実機の数字(デバッグの性能計測の「GPU(ノーツ)/(背景)」。Android の Chrome なら出る)が分かったら、その帯の値を直す

### レーンとノーツの演出を参考動画へ寄せた(2026-09-27)

ユーザー「モンビーは横向きが中心」「背景よりレーンやノーツ演出を重視」「音ゲーなんて背景なんて結局邪魔になるからレーンが重要」。
参考動画(スマホ横向きの録画・640×360・12fps)を1コマずつ追って読み取ったこと: 演出の主役は**叩いたあとの光**。
叩いたレーンが判定ラインの下から道の4割ほどまで青く光り、3〜4コマ(約0.3秒)で消える / 細かい青い粒が舞い上がる /
フリックは払った向きへオレンジの炎の筋が飛ぶ / ノーツは白〜水色の薄い板で光は控えめ / 道はほぼ黒の半透明で外のふちだけ白く光る。

| 項目 | やったこと | 場所 |
| --- | --- | --- |
| 道 | ほぼ黒の半透明(後ろが透ける)。境目は細く薄く、外のふちは白い線+水色のにじみ。**上の 3. の「濃い青のまま(A)」から変えた** | `data/rhythm-lane-svg.js` |
| ノーツ | 角の丸み 5→2、真ん中に白い芯の帯、光を少し強く(厚み・種類ごとの色は変えない) | `rhythm-mode.js` の `headOf` |
| 押したレーンの光 | 奥の半分は光らせず、判定ラインのまわりから手前を青く。離したあと 0.19→0.32秒で消える | `RHYTHM_LANE_PRESS_GRADIENT` / `[data-rhythm-sublane-feedback]` |
| 叩いた光の色 | 判定の文字の色と分けた(`RHYTHM_HIT_EFFECT_COLORS`)。MARVELOUS・EXCELLENT は水色〜青、GREAT は青紫。虹はジャストマーベラスだけ(以前どおり) | `rhythm-mode.js` |
| 光の柱 | 96px → 道の4割(96〜200px)。0.3秒の半ばまで明るさを保つ。上の角は14pxまで(半円のお椀に見えないように) | `HIT_KEYS.beam` / `mhRhythmHitBeam` |

| フリックの炎の筋 | 払った向き(上・左・右)へ、焼いた1枚を回して飛ばす | `hitStreakSprite` / `[data-rhythm-hit-effect]>em` |

| ホールド・スライドを押さえている所 | 焼いた白い十字の光を脈打たせて重ねる(標準以上)。細い縦の光の筋を 0.07秒ごとに場所を替えて3本(多め・最大) | `drawHoldSpark` / `holdBoltSprite` |
| 帯のふち | 帯の左右を明るい線(1.6px)でなぞる。SLIDE のふちも 1→1.6px・明るく | `drawBand` / `drawSlide` |
| 押し切ったとき | 光の柱を高く(120〜260px)・粒を遠くまで(1.6倍)・光を少し幅広に(1.3倍) | `rhythmSpawnHitEffect` の `finish` / `[data-hit-finish]` |

**押しやすさの戻し(同日・ユーザー「前より少し押しにくく感じる」「レーン幅が下部が広くなってる気がする」)**:
道の形(投影)は変えていない(判定ラインの高さで道は画面の約81%・1レーン約13.5%。参考動画は約68%・7レーンで1レーン約10%)。
押しにくく感じた原因は見た目で、道を暗くしたときに境目の線を細く薄くしすぎた(1.6→1px・.22→.16)ことと、押したレーンの光を手前だけにしたこと。
境目は色の段を付けた線(奥 .06 → 判定ライン付近 .42・1.4px)にし、押したレーンの光は奥も薄く光らせた。
下が広く見えたのは、外のふち(白い線+にじみ)が画面の下の角まで目立つようになったため。
ぴったりのMARVELOUSの虹色の柱は、柱を高くしたら大きな虹色の四角に見えたので、上へ行くほど透ける色にした。

**横画面の道の幅を選べるようにした(2026-09-28・ユーザー「横幅広くてスライド時に届きにくくなった」「オプションでパターン選べるにして」)**:
音ゲー設定「道の幅(横向き)」= `settings.roadWidth`(`WIDE` 1 / `STANDARD` .92 / `NARROW` .86)。判定ラインの高さで道は約81% / 75% / 70%。
縦画面では常に1(設定を無視)。

- 掛けるのは投影の**横の縮み**だけ(`rhythmProjectionScale` = `rhythmProjectionDepth(y) * RHYTHM_ROAD_WIDTH.factor`)。
  ノーツの厚み・明るさに使う奥行き(`scale:`)は `rhythmProjectionDepth` のままなので、幅以外は変わらない
- 指の位置→レーンの計算・ノーツ・レーンの SVG・ふちの帯・叩いた光・レーンカバーが全部同じ投影を通るので、見た目と判定がずれない
- 値は `RHYTHM_ROAD_WIDTH.set()` で描画の前に入れ、変わったら `rhythmLayoutPlayArea` と `rhythmLaneSvgRefresh` で作り直す。
  演奏画面を出るときに `reset()` で1へ戻す(ほかの画面の見本・検査に残さない)
- ふちの帯のキャッシュ(`roadEdgeCache`)とレーンの SVG(`data-road-factor`)は幅を鍵に含めている
- 道を CSS で狭くする案は、両脇に黒い帯が出るのでやめた

**押し続けている感じを強めた(2026-09-28・ユーザー「スライドとホールドはまだだいぶ参考動画に届いてない」「もうちょい押し続けてる感じにしたい」)**:

| 足したもの | 中身 | 場所 |
| --- | --- | --- |
| 左右の光の柱 | ノーツの左右のはしに、判定ラインから上へ立つ柱(白い芯+色のにじみ)。押さえているあいだ消えずに細かくゆらぐ | `holdPillarSprite` / `drawHoldSpark` |
| 立ちのぼる光 | 押さえているレーンの上へ、ノーツ幅の縦のグラデーション | `holdColumnSprite` |
| 吸い込まれる筋 | 帯(SLIDE も)の上を細い台形が3本、判定ラインへ流れる(0.45秒)。帯の形に沿うのではみ出さない | `drawPressFlow` |
| 溜め | 押さえ始めから0.7秒で柱と光が高く明るくなる(`opts.heldMs`)。押さえているあいだの音と一緒に効く | `drawHoldSpark` の `charge` |
| 押さえている間の音 | 高い「シャラシャラ」。周波数ごとの強さ(3.4〜5.4kHz と 8.5〜13.6kHz の2つの山・あいだは -12dB の谷・3kHz より下は無し)を決めて、でたらめな位相で逆FFTした約1.4秒の音を1回だけ作って繰り返す(つなぎ目無し)。作るのは prepare のとき。1本につき再生1つ+大きさ1つ。経緯: 「ウィーン」(のこぎり波が上がる)→「イメージと違う」で鈴の粒(2〜6kHz のドレミ・曲の和音とぶつかって浮いた)→ ユーザーが送ったバンドリ！アワーノーツの録画(曲を消した効果音だけ)を分析し、押さえ中だけ強くなる帯の形をまねた(どの帯も差 1.5dB 以内)。録画の音そのものは使っていない。参考動画(プレイ動画)には押さえ中の音は曲に埋もれて聞き取れなかった | `RHYTHM_NOTE_SE_RUNTIME.holdSync` |

★重さ: 押さえているノーツ1本につき drawImage 3枚+小さい台形3つが増え、バチバチの筋は3→2本に減らした(差し引き +3回)。塗る面積はノーツ幅×道の高さの4割ほど。
★音は本体が毎フレーム `holdSync(押さえているノーツ)` を呼び、並びから消えたら止める。呼ばれなくなったら0.25秒で見張りが全部止める(ポーズ・タブを隠した・画面を出た)。
検査は `tools/mode/rhythm-hold-charge-se-check.js`。

| CSS 版 | 同じ絵を画像にして器の CSS 変数へ(演奏の前に1回)。`em` を transform と opacity だけで動かす。明るさは同じ絵を2枚重ねて寄せる | `[data-rhythm-hit-effect]>em` |
| 手前の光 | 判定ラインから画面の下まで、レーンの形(手前ほど広い台形・投影で広げる)をノーツの色で | canvas: `drawPlume` / CSS: `>small` と `--rhythm-floor-clip` |

撮影ツールに `SEED`(撮るときだけ入れる保存データ。MASTER を開く・描き方を CSS 版にする)と `CSSANIM=1`(CSS のアニメーションも仮想の時間で進める)を足した。

参考動画では押さえている間もコンボが増える(ホールドの途中で数える)が、数え方の変更はコンボ・フルコンボ・スコアと
過去の記録・全国ランキングに響くので、入れていない(見た目の変更だけにした)。

★叩いた光は canvas 版(WebGL のとき・`drawOneHit`)と CSS 版(それ以外)の2つがある。**値は必ず両方そろえる**。
★重さ: 描く回数・層の数は増やしていない(炎の筋は焼いた1枚・粒の数は同じ)。塗る面積が増えるのは光の柱の高さのぶんだけ。

## 4. 気をつけること

- 発熱: 塗る画素の多さが原因(RHYTHM_ROADMAP 1-O)。ぼかし・影・filter を毎フレーム変えない。
  光は canvas に焼いた画像を重ねる形で足す
- **モンヒロビートは横向きが中心**(2026-09-27・ユーザー)。見た目を比べる・見本を撮るときは横向き(844×390 など)で撮る
- 縦向きのスマホ: 参考動画は横向き前提。縦で6レーンにすると1レーンが今の8割ほどの幅になる
- 見た目の方向を大きく変えるときは、撮影のときだけ差し替えた見本画像を先に見せて決める
  (今回のノーツ・道・奥行きはこのやり方で決めた)
- 演奏画面は `tools/mode/rhythm-play-smoke-check.js` で「見た目のおまかせ」4つの設定ごとに実際に開いて数秒動かす
  (render-error-check は演奏画面を開かない)。演奏画面の部品や演出の設定を触ったら通す
- 画面全体の CSS を外したときの重さは `rhythm-gpu-load-report.js --css '<CSS>'` で比べられる。
  演出量「最小」の `saturate` は外しても差が出なかった(2026-09-27)ので、そのまま
- 画質「自動」・演出の自動調整は、1フレームの間が 50ms 以上なら「重い」に数え、1秒未満の間だけを数える。
  以前は 250ms 以上の間を捨てていたので、3〜5fps の端末ではまったく働かなかった(2026-09-27)
  判断に要るフレーム数は3秒で5(`RHYTHM_AUTO_QUALITY_MIN_FRAMES`)。10のときは約3.3fpsを割ると判断しなかった(同日、約2fpsで0件だった)
- デバッグの「性能計測」を ON にして遊ぶと、「50ms以上のフレーム数」と「自動で下げた記録」(曲の何秒で・何を・そのときの重さ)が出る。
  実機で下がりすぎる・下がらないときは、この数字を見て線(8%・50ms・5フレーム)を合わせる
- HUD の検査(`rhythm-hud-wedge-check` / `rhythm-landscape-hud-check`)は、スコア・ライフの部品を
  `tools/mode/rhythm-hud-jsx.js` で展開してから測る。HUDへ部品を足したら、そこへ展開の仕方を1つ足す
