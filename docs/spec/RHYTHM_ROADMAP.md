## 1-B. 基盤固定ライン（自動検査で確認した断面）

正式譜面の制作へ入るにあたり、**譜面制作中に「なんとなく」で動かさない値・構造**をここに固定する。
下の項目を変えると遠近・落下速度・判定・入力位置のいずれかが必ず動く。変更したくなった場合は
譜面側の都合で触らず、先に理由をユーザーへ確認する。

| 固定する対象 | 現在の値・構造 | 置き場所 |
| --- | --- | --- |
| レーンの収束率 | `RHYTHM_PROJECTION_TOP_SCALE = .18` | `data/rhythm-mode.js` |
| 奥行きの曲線 | `TOP + (1-TOP) * pow(clamp01(y), 1.24)` | `data/rhythm-mode.js` |
| メインレーン / サブレーン | 5 / 10 | `data/rhythm-mode.js` |
| プレイ画面のHUD | プレイエリアへ重ねる絶対配置。レイアウトの高さを取らない | `src/game-system.jsx` |
| HUDの背景 | 背景色・背景画像・影・ぼかしを一切持たない（JSX側・`index.html` 側の両方） | `src/game-system.jsx` / `index.html` |
| プレイエリアの高さ | 画面の上端から下端まで。上端側の inset 影は置かない | `index.html` |
| ノーツの落下時間 | `rhythmTravelMsForSpeed(noteSpeed)` のみ。**画面の向きで分岐させない** | `src/game-system.jsx` |
| 判定窓 | モンスターノーツでも共通（能力用に甘くしない） | `data/rhythm-mode.js` |
| スコアの重み | 判定90% / コンボ10% | `data/rhythm-mode.js` |
| ライフ | 最大1000。元気 `+500` / 根性の復活 `50` | `data/rhythm-mode.js` |
| 保存キー | 音ゲーで増やすのはマスモンの枠のみ。既存 `mh_*` は触らない | — |

### 固定時点で通した自動検査

`tools/mode/rhythm-*.js` の全47件、`check-syntax` / `undefined-reference-check` /
`jsx-text-brace-check` / `render-error-check` / `build.js --check`、
ヘルプ・助手・起動系の各検査をすべて成功させた状態を基準断面とする。

- `rhythm-hud-wedge-check.js` / `rhythm-landscape-hud-check.js`
  … HUDが背景を持たず、プレイエリアが画面上端から始まることを実ブラウザで計測する

## 1-C. STEP 0: 現行HUD最終修正＋基盤固定準備（完了・2026-09-04）

STEP 1（iPhone実機での基盤固定）へ進む前に、公開直後にCodexレビューで指摘された
ランクゲージの表示不具合だけを先に直した。**レーンgeometry・projection曲線・判定窓・
入力座標・ノーツ落下時間には一切触れていない**（HUD/表示ロジックのみの変更）。

修正内容:

- `rhythmNextRankId(score, maxScore)` に第2引数`maxScore`（難易度ごとの満点、
  `RHYTHM_DIFFICULTIES`の`maxScore`）を追加。次ランクのしきい値が今の難易度の満点を
  超える場合は「次は無い(★MAX)」として扱うようにし、EASY(満点60万=A上限)なのに
  「→S」のような絶対に届かない次ランクを表示してしまう不具合を直した。
- ランク自体の判定・しきい値（`RHYTHM_RANKS`）、スコア計算、`rhythmRankForScore`、
  `rhythmRankProgress`は変更していない。

難易度ごとの満点における期待挙動（確認済み）:

| 難易度 | 満点 | 満点時のランク | 満点到達時の次ランク表示 |
| --- | --- | --- | --- |
| EASY | 600,000 | A | ★MAX |
| NORMAL | 700,000 | S | ★MAX |
| HARD | 800,000 | SS | ★MAX |
| EXPERT | 900,000 | M | ★MAX |
| MASTER | 1,000,000 | M | ★MAX |

※この表の「満点時のランク」はSTEP 0のこの修正を行った時点のもの。直後の「1-D」で
ランクのしきい値自体を1段ずつシフトしたため、現在の対応は1-Dを参照
（EASY→B / NORMAL→A / HARD→S / EXPERT→SS / MASTER→M）。

回帰確認（`tools/mode/rhythm-*.js`含む自動検査で確認、実機確認は別途iPhoneで実施）:

- ランクゲージ本体・目盛り表示
- 100コンボごとの演出が200 / 300 / 400 / 500以降も毎回出ること
- 500以降は最大段階(stage 5)を再利用すること
- FULL COMBO / ALL EXCELLENT / ALL MARVELOUSのcelebrate画面
- celebrate → result遷移
- 軽量モード / 演出量MINIMALでcelebrate・派手な演出をスキップすること

## 1-D. ランクしきい値を1段シフト（2026-09-04、STEP 0の続き）

ユーザー指示で `RHYTHM_RANKS` の各しきい値を1段ずつ上へずらした
（＝同じ点数で付くランクは1段ずつ下がる）。これもHUD/表示ロジックのみの変更で、
レーンgeometry・判定窓・入力座標・ノーツ落下時間・スコア計算式には触れていない。

理由: 旧しきい値ではEXPERTの満点(90万点)もMASTERの満点(100万点)と同じM評価に届いてしまい、
「MASTERの満点だけがMへ届く」という当初の設計意図と実際の挙動が食い違っていた。

| 難易度 | 満点 | 旧: 満点時のランク | 新: 満点時のランク |
| --- | --- | --- | --- |
| EASY | 600,000 | A | B |
| NORMAL | 700,000 | S | A |
| HARD | 800,000 | SS | S |
| EXPERT | 900,000 | M | SS |
| MASTER | 1,000,000 | M | M（ここだけ変わらず、唯一Mへ届く） |

`RHYTHM_RANKS`のG(0点)以外の9段のしきい値をすべて100,000ずつ引き上げた
（G→F→E→D→C→B→A→S→SS→Mの並び自体・段数・`rhythmRankForScore`/`rhythmRankProgress`/
`rhythmNextRankId`のロジックは変更していない。しきい値の定数だけを変えている）。
最新の値は本書ではなく`docs/spec/RHYTHM_MODE.md`「3.5. スコアランク」を正本とする。

## 1-E. 全国ランキング「モンビー」の先行実装（2026-09-04）

「10. 体験版後の正式版ロードマップ」のSTEP14（永続全国ランキング）は、本来STEP8の
体験版公開よりあとに予定していたが、ユーザーから「本実装で細かい実装はするが、
先行公開時にも全国ランキングがほしい」と明示の指示があり、Monster Hero 1曲分を
先行実装した。

要点（詳細設計は`docs/spec/RHYTHM_MODE.md`「9.5 全国ランキング『モンビー』」を正本とする）:

- 新テーブル・新列は増やさず、既存`rankings`テーブルの`difficulty`列へ
  `Rhythm-<songId>-<難易度id>`という専用キーを入れるだけで区別する
  （種族チャレンジの`Species-<血統>-<難易度>`と同じ考え方）
- EASY/NORMAL/HARDを1本にまとめた「難易度合算」方式。難易度が高いほど満点も高いため、
  高い難易度で挑むほど上位に近づく
- 自分のスコアは、これまでの中でいちばん高い1件だけが表示される
  （書き込みは1プレイ＝1行のまま、表示のときにユーザー名ごとの最高得点へ畳む）
- 各行に「詳細」ボタンを付け、判定内訳・最大コンボ・達成称号を確認できる
  （既存の`party`列へJSONで持たせる。新しい列は増やしていない）
- 体験版ホームから始めたプレイだけを送信し、デバッグ画面からのプレイは送信しない
- 送信に失敗したときだけ、新規キー`mh_rhythm_rank_pending_v1`(直近20件)へ退避する
  （既存のBEST記録`mh_rhythm_best_v1`には影響しない）
- 識別・不正対策は通常バトル等の既存ランキングと同じ水準
  （ブリーダー名ベース、クライアントからの送信をそのまま信頼）

STEP14で残っているのは、2曲目以降を追加したときの接続確認と、モンスターノーツ能力込みの
プレイを正式攻略要素として扱う方針の最終確認だけ（キー設計自体はsongIdを含むため、
曲を増やすだけで対応できる見込み）。

## 1-F. STEP1実機確認: タップ感度（隣接サブレーン重なり閾値）を調整（2026-09-04）

STEP1のiPhone実機確認中、ユーザーから「1つの指で3個（サブレーン）まで押すのが難しい」
という指摘があった。原因は`RHYTHM_TOUCH_MIN_SUBLANE_COVERAGE`（隣接サブレーンへどれだけ
重なったら接触扱いにするかの閾値）が25%と厳しめだったこと。

- `RHYTHM_TOUCH_MIN_SUBLANE_COVERAGE`を`.25`→`.20`へ緩和し、指腹の接触判定を少し広くした
- 判定窓・スコア計算・接触半径縮小(`RHYTHM_TOUCH_RADIUS_SCALE=.70`)・固定3上限なしの方針・
  異常値guardは変更していない（`docs/spec/RHYTHM_MODE.md`「入力: iPhone Touch接触幅」参照）
- 広すぎる誤爆（意図しない隣接サブレーンの誤検出）が起きていないか、引き続き実機で確認する

これはSTEP1の実機確認の中で見つかった調整であり、STEP1自体はこの後も続く。

## 1-K. STEP2: 「ノーツを押したときにカクつく」の原因を特定して修正（2026-09-04）

ユーザーから「区間というよりノーツを押したときにカクつくイメージ。感覚的なものではっきりとは
分からない」との追加報告があった。**「押したとき」という手がかりが決め手**で、描画側ではなく
入力〜判定の経路を読み直した結果、計測値を待たずに原因を特定できた。

**原因（いちばん大きいもの）**: ノーツを1つ判定するたびに `applyJudgment` が `setView` を呼び、
`RhythmTapTest` が再描画される。ところが譜面のノーツは `chart.notes.map(...)` として
**描画関数の中に直接書かれていた**ため、ノーツを1つ叩くたびに全ノーツ（最大300要素、
子要素を含めると1000要素以上）をReactが作り直し、`ref` も付け直していた。
つまり「タップ1回 = 譜面まるごと再構築」になっていた。JSX中のコメントには
「絵はプレイ開始時に一度だけ組み立て、そのまま使い回す」と書いてあり、意図とも食い違っていた。

修正:

- ノーツのDOMを `useMemo` で固定した（依存は譜面・マスモン・軽量モード・演出量のみ。
  遊んでいるあいだは変わらないので、判定のたびの再生成が完全になくなる）
- レーン枠・サブレーン境界・サブレーン発光の静的部分も同じく `useMemo` で固定した
- 入力のたびに呼んでいた `getBoundingClientRect()`（＝強制レイアウト）を、FLICK/SLIDE側が
  既に使っていた「1フレームに1回だけ測る」キャッシュへ寄せた（指の数ぶん・touchmoveの数ぶん
  レイアウトを確定させていたのをやめる）
- サブレーン発光は要素を覚えておき、状態が変わったサブレーンだけ書き換えるようにした
  （毎回 `querySelectorAll` で10要素を引き直し、押していない所まで書き込んでいた）

判定窓・スコア計算・ノーツの落下時間・保存形式は一切変更していない。回帰防止として
`tools/mode/rhythm-perf-check.js` へ4項目を追加した。

**この修正はコードの読み直しから導いた仮説であり、実機で軽くなったかの確認はまだ取れていない。**
次にiPhoneで触れるときに、ノーツを押したときの引っかかりが減ったかを見てもらう。
それでも残る場合は、DEBUG 60sの計測値（フレーム超過数・平均fps）を取ってから次を探す。

### 実機録画の解析（2026-09-04・39秒のHARDプレイ）

ユーザーから39秒の実機録画（720x1280 / 30fps / KineMasterで撮影）を受け取った。
タイトル画面の`VERSION`は`2026-09-04 12:10`＝**1-Kの修正を含むビルド**だと確認できた。
つまり**1-Kの修正を入れてもカクつきは残っている**。

録画は30fpsなので、アプリが33ms以内に新しい絵を出せなかった区間は録画に同じ絵が続く。
これを数えればカクつきを追える。ただし測り方を2回間違えたので、経緯ごと残す。

**失敗した測り方（採用しない）**: プレイエリア全体を90x160へ縮めてフレーム間の差を見た。
これだと「遠くにノーツが1つだけあって、1フレームの移動量がごく小さい」場面まで
「絵が止まった」と数えてしまい、**約10%が停止・最大167msの停止**という過大な結果が出た。
最初はこの数字を採用しかけたが、誤りだった。

**採用する測り方**: ノーツが大きく速く動く**判定ライン手前の帯だけ**を224x132で取り出し、
さらに「直前か直後のフレームはしっかり動いているのに、そのフレームだけ絵が変わらない」
ものだけをコマ落ちとして数える。これなら「動きが小さい」場面と取り違えない。

結果:

- コマ落ち: 判定ライン手前にノーツが映っている925フレーム中**20件（2.2%）**
- **すべて単発（約33ms）。2フレーム以上続いた停止は0件**＝長い固まりは起きていない
- 発生時刻は4.6/6.4/7.6/8.3/8.5/11.9/12.5/18.2/18.9/19.3/21.6/23.7/24.8/25.1/25.6/27.5/
  33.9/34.7/35.8/36.6秒と、曲全体へ散らばっている（おおよそ1.5秒に1回）

この解析の限界（重要）:

- 録画が30fpsのため、**16.7ms〜33msのフレーム（60fpsから30〜60fpsへ落ちた状態）は
  原理的に検出できない**。体感の「カクつき」の大半はこの範囲にある可能性が高く、
  録画からは見えない。ここを見るにはアプリ内蔵の性能計測（`16.7ms超`の件数）が要る
- 撮影に使われたKineMasterは画面録画中もCPUを使うため、録画そのものが
  コマ落ちを増やしている可能性がある（素の状態より不利な条件）

**次の一手**: 音ゲーデバッグ画面の設定タブにある「性能計測（デバッグ）」をONにして
プレイし、`平均fps` / `最悪フレーム` / `16.7ms超` / `25ms超` / `33ms超` を読む。
これはアプリの中で測るので録画アプリの影響を受けず、16.7ms〜33msの落ち込みも拾える。

### メモが親の再描画で無効化されないよう堅くした（同日）

1-Kのメモは依存に `monsterEntries` を使っていたが、この配列は親（App本体）が
描画のたびに `rhythmMonsterSlots.map(...)` で作り直すため、**親が再描画されると
配列の同一性が変わり、メモが無効化されてノーツが作り直されてしまう**。
プレイ中に親が再描画されなければ問題は出ないが、他の変更で再描画が入ると
静かに元の重さへ戻るため、ノーツの見た目に効く項目（baseId / imageUrl / 染色色）だけを
文字列にした `monsterSignature` を依存にし、中身が同じあいだはメモが保たれるようにした。

- **先頭**: 終わって非表示にし終えたノーツは二度と状態が変わらないので開始位置を進める

- **末尾**: 出番まで `travelMs*1.2` 以上あるノーツは判定も表示も要らないので打ち切る
  （自動MISSもHOLD終端も「すでに来ているノーツ」なので取りこぼさない）
- **初回フレームだけ**は全ノーツを一巡して初期の表示状態を作る
- 時刻の昇順でない譜面が来たときは、末尾の打ち切りを自動で止めて全ノーツを見る

あわせて、見えていないノーツにも `will-change: transform, opacity` が出しっぱなしで、
266要素すべてが合成レイヤーの対象になっていた点も直した（実測 266要素 → 5要素）。
iPhoneのようにGPUメモリが限られる端末では、この確保・解放が負担になる。

効果（`tools/mode/rhythm-note-scan-window-check.js`。曲全体を60fpsで最後まで回して
全走査と突き合わせる）:

| | 修正前 | 修正後 |
| --- | --- | --- |
| 1フレームの走査ノーツ数（平均） | 266.0 | **4.8（98.2%減）** |
| will-changeで合成レイヤーへ載る要素 | 266 | **5** |

`AudioContext.currentTime` ベースで単調増加しており異常が無かったため触っていない。
「軽くするために見た目を簡略化する」こともしていない。

デバッグの性能パネルへ「走査ノーツ/frame」「実描画ノーツ/frame」

差から言えるのは「**tickの外で起きている時間**」までで、その内訳（描画なのか、GCなのか、
他の処理なのか）は分からない。ここを取り違えると、JS側に原因が残っているのに

  逆に最悪frameのtick処理が数十msなら、原因はtickの中にある
- **走査の絞り込みが「無効」** → 譜面が昇順でないと判断されている。そこを直せば52.0は解消する

「tickの外」だと分かったら、そこから先（描画なのか他の処理なのか）は改めて測る。
計測はデバッグ限定・既定OFF・rAFを増やさない、という従来の条件をそのまま守っている。

### 1-N. カクつきはJSではなかった（実機で確定）（同日）

計測を足したビルドで、実機の値を取り直してもらった。

| 項目 | 値 |
| --- | --- |
| フレーム数 | 8565 |
| 平均fps | 56.1 |
| 平均フレーム | 17.8ms |
| 最悪フレーム | 107.0ms |
| 16.7ms超 | 5252（61.3%） |
| 25ms超 | 537（6.27%） |
| 33ms超 | 210（2.45%） |
| 走査ノーツ/frame | 21.2 |

1. **原因は「本体のrAFの中身（tick）」ではない。** 1フレーム17.8msのうち、tickは
   **0.25ms**しか使っていない。決定的なのは、**107msかかった最悪フレームで
   tick処理が0.0ms**だったこと。100ms以上がまるごとtickの外で起きており、
   これはvsync待ち（16.7ms）では説明できない大きさなので、
   **tickの中をどれだけ削っても直らない**と言い切れる。

   ⚠️ **ただしこれは「JS全体が無実」という意味ではない。** tickの計測が見ているのは
   このコールバックの中身だけで、**判定時の `setView` によるReactの再描画・GC・
   他のコールバック（ジェスチャー側のrAF・タッチイベント）はtickの外**で走る。
   これらもJSであり、まだ容疑者に残っている（Codexの指摘による訂正）。
   なお tick自身は `setView` を呼んでおらず、毎フレームのReact再描画は起きていない。
   `applyJudgment` 経由の再描画は判定のたびなので、16.7ms超が61%という
   常時の超過は説明できないが、107msのような単発の長いフレームは説明しうる
2. **走査の絞り込みは効くようになった。** 「走査の絞り込み＝有効」「先頭スキップ/frame＝116.9」で

3. ノーツ処理側の作業はここで打ち切る。実描画1.9ノーツ/frameまで減っており、これ以上削る意味がない

**tickの外の何が重いのかを、実ブラウザで切り分けた**（デスクトップChromium・266ノーツ・同時表示5・
毎フレームの書き込み直後に強制レイアウトを起こしてその時間を測る。**iPhoneではない**ので相対比較として読む）。

| 条件 | 毎フレームのstyle+layout | 現状比 |
| --- | --- | --- |
| いまの実装（そのまま） | 0.786ms | — |

| filter(brightness)ごと外す | 0.351ms | −55% |
| box-shadowだけ外す | 0.714ms | −9% |
| 横方向もtransformにする（left/widthを書かない） | 0.412ms | −48% |
| サブレーン発光の巨大box-shadowを外す | 0.730ms | −7% |
| transition除去 ＋ transform化 | 0.128ms | −84% |

**いちばん効いたのは `transition:filter 40ms linear` の除去だった。** `--rhythm-note-depth-brightness`
は落下中まいフレーム書き換えているため、40msのtransitionは**目標値が毎フレーム置き換わって補間が
ほぼ働かない**。それでいて「動いている遷移」を表示中の全ノーツぶん抱え続ける。
明るさは元から位置の関数として滑らかに変わるので、**見た目を変えずに外せる**。これは実施した。

**まだ手を付けていない候補**

- **横方向を `left`/`width` ではなく `transform` で表現する**（−48%）。ただしこれは
  ノーツの横位置の出し方そのものを変えることになり、「判定ライン位置・レーンgeometry・
  遠近projection・表示位置を変えない」という制約に触れる。やるなら位置が1pxも変わらないことを
  先に検証する必要がある
- サブレーン発光やノーツのbox-shadowは、効果が小さいうえ**見た目そのもの**なので触らない

**重要な限界**: 上の切り分けはstyle+layoutしか測れておらず、合計しても0.8ms程度にしかならない。
**17.8msや107msは説明できていない。** 残りはpaint/composite、あるいは上に書いた
「tickの外のJS」（React再描画・GC）など、この方法では見えない領域にある。

そこで **「フレームが始まってから実際にtickへ入るまでの遅れ」** も測るようにした
（rAFのタイムスタンプと、コールバックの中で読んだ `performance.now()` の差）。

- **遅れが大きいフレーム** → tickへ入る**前に**メインスレッドが塞がっていた。
  React再描画・GC・他のコールバックなど、**tickの外のJS**が犯人
- **遅れがほぼ0なのにフレームが長い** → 時間はtickの**後**（描画・合成）か、
  そもそもフレームが来ていない

**次の一手（コードを書かずに切り分けられる）**: 実機で **軽量モードON**（または演出量MINIMAL）で
1回プレイし、`平均フレーム` と `16.7ms超` を比べてもらう。

- 軽量モードで大きく改善する → 原因は装飾の描画（box-shadow・filter・グラデーション・
  transition）にある。**そのときも「見た目を簡略化する」のではなく、同じ絵を安く出す方法
  （ぼかし影を焼き込んだ画像に置き換える等）を探す**
- ほとんど変わらない → 装飾ではない。レイヤー構成や合成そのもの、tickの外のJS、
  あるいは端末側の要因を疑う

あわせて **「最悪frameの遅れ」** を読めば、tickの外のJSかどうかが直接分かる。

### 1-O. 端末を2台比べて原因が「塗る画素数」だと分かった（同日）

ユーザーが別の端末で試したところ**カクつかなかった**。しかもその端末のほうが**古い**。

| | 古い方 | いつもの |
| --- | --- | --- |
| 機種 | iPhone SE2 | iPhone 16e |
| チップ | A13 | A18 |
| 解像度 | 750×1334 | 1170×2532 |
| **画素数** | **1.00M** | **2.96M（約3倍）** |
| リフレッシュレート | 60Hz | **60Hz** |
| 体感 | **滑らか** | カクつく（しかも悪化していく） |

**16eもProMotionではなく60Hz**なので、リフレッシュレートの差ではない。決定的な差は
**塗らなければいけない画素数が約3倍**であること。60fpsなら毎秒 60M画素 対 178M画素になる。

**チップが速いのに新しい端末のほうが遅い**のは、ボトルネックが計算力ではなく
**塗り(fill rate)**だから、で説明がつく。

#### 数字の読み直し（重要な訂正）

超過時間がどこに集中しているかを分解したところ、**「16.7ms超が61%」はほぼ無意味な数字**だった。

| 帯域 | 本数 | 超過の合計 | 1本あたり |
| --- | --- | --- | --- |
| 33ms超 | 210本（2.45%） | **約5.95秒** | 大 |
| 25〜33ms | 327本（3.82%） | 約3.71秒 | 中 |
| 16.7〜25ms | 4715本（55.0%） | **0.05秒** | **0.011ms** |

16.7〜25msの4715本は超過がほぼゼロ＝**60fpsぴったりの正常フレームが閾値をわずかに跨いだだけ**。
**土台は60fps出ており、問題は33ms超の2.45%に集中している。**

そして、そこまでの修正はきちんと効いていた（平均フレームだけを見て「変わらず」と書いたのは誤り）。

| | 1回目 | 2回目 | 3回目 |
| --- | --- | --- | --- |
| 引っかかり(33ms超)の頻度 | 2.46回/秒 | 2.02回/秒 | **1.38回/秒** |
| 超過時間の合計 | 15.85秒 | 14.90秒 | **9.71秒** |

#### 実測: 重いのは「影とfilter」で、その重さは画素数に比例する

同じ描画内容を両端末と同じ画素数で回した（デスクトップChromium。絶対値は違うので相対比較）。

| 条件 | SE2相当(1.00M) | 16e相当(2.96M) |
| --- | --- | --- |
| いまの見た目のまま | 1.90ms | **2.70ms（+42%）** |
| 影とfilterを外す | 2.00ms | **1.70ms（差が消える）** |

**影とfilterを外すと画素数による差がきれいに消える。**

#### 対策: 見た目を変えずに「毎フレームの塗り直し」をやめる

`filter` の値が毎フレーム変わる要素は、GPUで動かすだけでは済まず**毎フレーム塗り直し**になる。
実装は見えているノーツへ毎フレーム `--rhythm-note-depth-scale`（`scaleY`）と
`--rhythm-note-depth-brightness`（`filter:brightness`）を書いていた。

0.01刻みへ丸め、**値が実際に変わったときだけ書く**ようにした。

- 明るさ … 0.72〜1.00を0.01刻み（1%刻み）。目では区別できない
- 拡大率 … 0.56〜1.00を0.01刻み。ノーツ高さ22pxなら1段0.22pxで画素より細かい

あわせて、HOLDの `filter:brightness(1.3)`（押している間だけ変わる値）と帯の長さも、
変わったときだけ書くようにした。

実測（Chromium・16e相当の画素数・同時表示4ノーツ）:

| | 書き込み/frame | フレーム中央値 | 上位5% |
| --- | --- | --- | --- |
| いまの実装 | 8.0回 | 1.90ms | 2.70ms |
| 0.01刻みで丸める | **1.4回** | **1.20ms（−37%）** | **1.80ms（−33%）** |

判定・当たり判定・ノーツの位置と大きさの決まり方は一切変えていない。

「変わったときだけ書く」を安全に成立させるため、`beginRun` が style を直接書き戻す箇所で
**覚えている値も一緒に捨てる**ようにした（控えだけ古いと、同じ値と誤判定して書き込みを飛ばし、
実際の見た目とズレたまま固まる）。

#### まだ確認できていないこと

実機での効果は未確認。次は16eで **33ms超の件数**（前回210件）を、次の条件で比べてもらう。

1. いまのまま（基準）
2. **軽量モードON / 演出量MINIMAL** … 影とfilterが消える。ここで激減すれば確定
3. **ノーツサイズ80%** … 塗る面積が減る
4. **冷えた状態**（10〜15分放置後） … 発熱ぶんの寄与

確定したら、**見た目を落とすのではなく同じ絵を安く出す**方向で進める
（ぼかし影を焼き込んだ画像へ置き換える、毎フレーム変わるfilterをやめて合成だけで同じ明るさを出す等）。

### 1-P. 実機A/Bで犯人が「装飾のラスタライズ」と確定（同日）

#### まずJSが全部シロだと確定した

計測項目を足したビルドで、決定的な数字が出た。

| 項目 | 値 |
| --- | --- |
| 最悪フレーム | 117.0ms |
| 最悪frameのtick処理 | **0.0ms** |
| **最悪frameの遅れ** | **1.0ms** |
| **遅れの最大** | **2.0ms** |

117msかかったフレームで、フレーム開始から本体のコールバックが動き出すまでの遅れが1.0ms。
全編でも遅れの最大が2.0msしかない。つまり**メインスレッドは一度も塞がっていない**。
これで tick / React再描画 / GC / ノーツ走査 のすべてが容疑者から外れ、
**時間はコールバックが終わったあと（描画・合成、またはフレーム配信）に消えている**と確定した。

なおJS側の削減は完全に効いている（走査ノーツ 21.2 → **1.8**、tick 0.21ms）。
それでも33ms超は減らなかったので、「原因はJSではない」の裏返しの証拠にもなっている。

#### 軽量モードA/Bで装飾が犯人だと確定した

記録をクリアせずに続けて計測されたため、累積から通常ぶんを引いて軽量モードだけを算出した。

| | 通常 | 軽量モードON＋演出量 最小 |
| --- | --- | --- |
| フレーム数 | 8651 | 8873 |
| 平均フレーム | 17.70ms | 17.11ms |
| 16.7ms超 | 60.6% | 63.9% |
| 25ms超 | 4.42% | 3.37% |
| **33ms超** | **2.72%（235件）** | **0.55%（49件）** |
| **引っかかり** | **1.53回/秒** | **0.32回/秒（−79%）** |

**平均はほとんど動かないのに、33ms超だけが79%減る。**
カクつきは「常時重い」問題ではなく「たまに大きく跳ねる」問題で、
その跳ねを作っているのは装飾のラスタライズだと確定した。

#### 見た目を落とさない解決が見つかった

どの装飾がいくら食っているかを、16e相当の画素数で個別に測った（5回ずつの中央値）。

| | 中央値 | 上位5% | 最大 |
| --- | --- | --- | --- |
| いまの見た目のまま | 1.30ms | **5.00ms** | 9.4ms |
| 装飾を全部外す（軽量モード相当・見た目が変わる） | 1.30ms | 3.30ms（−34%） | 5.2ms |
| **サブレーン発光を合成レイヤーへ載せる（見た目そのまま）** | 1.20ms | **2.00ms（−60%）** | **3.9ms** |

**装飾を全部消すより、レイヤーへ載せるほうが速い。** 理由は明快で、
サブレーン発光はプレイエリア全面サイズの要素が10枚あり、それぞれ42pxのぼかし影を持つ。
タップのたびに `opacity` が 0→1 になると、そのたびに**ぼかしを塗り直している**。
自前の合成レイヤーへ載せれば**ぼかしは一度だけ焼かれ**、以後はopacityの切り替え＝
GPUの合成だけで済む。絵は1ドットも変わらない。

実装したのは次の2つ。どちらも見た目・判定・表示位置を変えていない。

1. サブレーン発光へ `will-change: opacity`（軽量モードのときは付けない）
2. SLIDE帯SVGの**変わらない値**（幅・`--rhythm-slide-area-height`・`viewBox`）を毎フレーム
   書き直さない。プレイエリア全面サイズのSVGを毎フレーム作り直させていた

実ブラウザでの幾何実測（480通り）でノーツ頭のズレ最大0.01px、SLIDE帯・ENDバーとも従来どおり。

#### まだ確認できていないこと

実機での効果は未確認。トレードオフとして**合成レイヤーぶんのGPUメモリ**を10枚ぶん使う。
16e相当で概算80〜90MB。効果とメモリ圧のどちらが勝つかは実機の33ms超の件数で判断する。
悪化するようなら、レイヤー化をやめてぼかし影をグラデーションへ焼き替える案へ切り替える。

| 工程 | 内容 |
| --- | --- |
| **raster（塗り直し）** | サブレーン発光を合成レイヤーへ（ぼかしを一度だけ焼く）／ノーツの奥行き・明るさを0.01刻みで丸めて変化時のみ書く／HOLDのfilterと帯の長さをキャッシュ／SLIDE帯SVGの不変値をキャッシュ |
| **layout** | 横位置を `left` から独立 `translate` へ（ChatGPT側 PR #1044）／`_rhythmVisualBody` のnullキャッシュ |
| **JS** | 毎フレームの全ノーツ走査をやめて必要な範囲だけに（266→約5）／ノーツDOMの再生成停止／入力候補探索の削減（ChatGPT側） |

#### 学びとして残すこと

1. **「16.7ms超の割合」は指標にならない。** 60fpsぴったりのフレームが閾値をわずかに跨ぐだけで

2. **平均フレームも指標として弱い。** カクつきは「たまに大きく跳ねる」問題なので、
   平均はほとんど動かないのに体感だけ悪い、ということが起きる
3. **同じ端末でも熱で変わる。** 連続プレイや画面録画をしながらの計測は不利な条件になる
4. **画面の広い端末ほど不利。** 塗り直しの重さは画素数に比例するので、

   「新しい端末なのに遅い」はここで起きる
5. **装飾を消すより、レイヤーへ載せるほうが速いことがある。**
   ぼかしや影は「毎回描き直す」から重いのであって、「描くこと」自体が重いとは限らない

### 1-T. 終点フリック（HOLD / SLIDE の終わりでフリック）

ユーザー要望「ホールドとかスライドの最後でフリックを入れるパターンも追加してほしい」（2026-09-04）。

**ランタイム**は `HOLD` / `SLIDE` への属性 `endFlick: true` として実装した。新しいノーツ種別ではないので、
`endFlick` を書いていない既存ノーツの挙動・判定・見た目はいっさい変わらない
（`tools/mode/rhythm-end-flick-check.js` で機械的に固定。仕様は RHYTHM_MODE.md §2「終点フリック」）。

**自動生成**（V2 STEP3）は、全ノーツが出そろったあとに、終端の前後へ1拍以上の余裕がある
HOLD / SLIDE だけを選んで付ける。難易度ごとの上限は EASY 0 / NORMAL 3 / HARD 5 / EXPERT 7 / MASTER 9。

**STEP6**（プレイ可能性）へも `END_FLICK_RELEASE_MS`（80ms）を入れ、弾いた指の戻りを数えるようにした。
入れたあとも押せない件数は増えていない。検査では、同じ配置で `endFlick` の有無だけを変えて

## 3. 譜面制作ルールの追加方針

今後の正式譜面では、同時刻に横へ隣接し、見た目として1つに繋がるTAPを複数の別ノーツとして置かない。

例:

- 隣接する幅1 TAPが2個 → 幅2相当の1つの可変幅TAPとして制作
- 隣接する幅1 TAPが3個 → 幅3相当の1つの可変幅TAPとして制作
- 幅2 + 幅1が隙間なく連続する場合 → 可能なら連続範囲を1つの可変幅TAPとして制作

間に空白がある本当の同時押しは別ノーツのままにする。

この方針はruntimeで自動結合する仕様ではなく、**譜面を作るときの制作ルール**とする。
既存のデバッグ譜面を今すぐ一括修正する必要はなく、正式譜面の制作・調整時に適用する。

### EASY

- 初めて音ゲーへ触る人向け
- TAP中心
- HOLDは少なめ
- 激しい左右移動や複雑な同時押しを避ける

### NORMAL

- 標準的な遊び方を見せる
- TAP / HOLD / FLICK
- 可変幅ノーツを自然に使用
- EASYより密度・左右移動を増やす

### HARD

- 現在の音ゲーシステムの広さをある程度体験できる難易度
- TAP / HOLD / FLICK / SLIDE
- 0.5レーンや可変幅SLIDE、複合操作を必要な範囲で使用
- DEBUG譜面のような機能詰め込みではなく、曲として気持ちよく遊べることを優先する
