# モンヒロビートのタッチの診断と、消えたタッチの取り戻し（2026-09-30）

**ユーザー報告**「iPhoneで両手の高速連打のとき、押しても音も光も出ないことがある」。前からずっとある。Androidの人からは聞かない。
同じiPhoneでも、ほかの音ゲー（iPhone専用のアプリ）では起きない。親指2本で遊んでいる。ホーム画面のアイコンから開いている。

**ユーザー指示**「こっち側に委ねないで、調べる仕組みを作って、直せる仕組みも作って」。

## わかっていること（2026-09-30 時点）

- この環境（パソコン上の Chrome）で、本物のタッチ（CDP）で両手の連打を再現しても、道の上の取りこぼしは0件だった。
  版ごと（9/26〜）の入力の処理の重さ・メモリの増え方にも差が無かった
- 公開中の全130譜面は、同時に指を2本までしか要求しない（押さえ続けるノーツ＋叩くノーツを数えた）
- ゲームの入力は、ブラウザが渡す「いま触れている指の一覧」に毎回合わせ直しているので、ゲームの中で指が残って積み上がることは無い
- 同じiPhoneのほかの音ゲーでは起きないので、iPhone本体（画面・OS）は正常。**指はブラウザ（WebKit）を通る部分か、ゲームの作りのどこかで消えている**

## 仕組み

```
プレイヤーが公開中の曲を遊ぶ
  ↓ ゲームが1回のタッチを「ポインタ」と「タッチ」の2通りで受け取り、突き合わせる(data/rhythm-mode.js の RHYTHM_TOUCH_BRIDGE)
  ↓   ポインタだけ届いてタッチが来なかった指 → その場でポインタの経路で入力にする(取り戻し)
  ↓ 1曲ごとに数をまとめ、端末に直近20曲(mh_rhythm_touch_diag_v1)・サーバーへ1行(rhythm_touch_diagnostics)
サーバーに記録がたまる
  ↓ 週1回の定期実行: node tools/mode/rhythm-touch-diag.js --fetch --report --days 14
iPhone と Android を比べて、指がどの段階で消えているかを判定する
```

### 数えるもの（1曲ごと）

| 名前 | 意味 | 増えたら |
| --- | --- | --- |
| `pointerOnly` / `recovered` | ポインタだけ届いてタッチが来なかった指 / そのうち取り戻した数 | ブラウザがタッチを落としている。**取り戻しで直っている** |
| `touchOnly` | タッチだけ届いてポインタが来なかった指 | ポインタを出さない端末。害は無い（取り戻しが働かない端末の目印） |
| `matched` | ポインタとタッチが組になった数 | ふつう |
| `lateStart` | 自分の touchstart ではなく、別の指のイベントで初めて見えた指 | ブラウザが touchstart を出し損ねている |
| `lateDelivery` / `maxDelayMs` | 50ms以上遅れて届いたタッチ / いちばん遅れた長さ | 叩いた瞬間の処理が重い |
| `cancels` / `cancelledTouches` | 端末に指を取り消された回数 / 本数 | システムのジェスチャーに取られている |
| `maxTouches` | 同時に触れていた指の最大 | 5ならiPhoneの上限（6本目は届かない） |
| `noInputMisses` / `misses` | 叩いている最中なのに前後200msに入力が1つも無いMISS / MISSの数 | 指がポインタにもタッチにもならずに消えている（ふつうの見逃しも混ざるので、Androidとの差で見る） |
| `ignored` / `outside` / `gestures` | 道の外で無視した指 / 演奏エリアの外に触れた指 / 二本指ジェスチャー | 端の受け付け・持ち方 |

名前・ブリーダーID・セーブデータは送らない。端末ごとのでたらめなID（遊んだ記録と同じ `mh_rhythm_play_log_device_v1`）と数だけ。
デバッグ・練習・タイミング合わせは送らない。アシストモードは印を付けて送り、道具は比べる数に入れない。

### 取り戻し（`RHYTHM_TOUCH_BRIDGE`）

- ブラウザは1回のタッチを、ポインタ（pointerdown）→ タッチ（touchstart）の順に、同じ時刻・同じ位置で届ける（Chrome も iPhone の Safari も）
- ポインタが来てから45ms待ってもタッチが来なければ、ポインタの経路（演奏画面の pointer の入力）で入力にする。
  タイマーに加えて毎フレームの処理でも見るので、遅くても数コマで通る。**判定には指が触れた時刻を使う**（取り戻しの遅れで判定がずれない）
- **二重に数えない**: 取り戻したあとで同じ指のタッチが遅れて来たら無視する。タッチが先・ポインタがあとで来たときは取り戻さない。
  どちらも位置（28px以内）と時刻（600ms以内）で同じ指かを見る
- **ふつうの端末では一度も動かない**（ポインタとタッチが必ず組になるため）。検査 `rhythm-touch-bridge-check.js` の①

## 判定と、次にやること（`rhythm-touch-diag.js --report`）

iPhoneの記録が20曲そろってから判定する。

| 判定 | 次にやること |
| --- | --- |
| ブラウザがタッチを落としている（`pointerOnly`） | 取り戻しで直っている。`noInputMisses` がAndroid並みに下がったかを見る |
| 入力の無いMISSがAndroidの2倍以上 | 指がポインタにもタッチにもならずに消えている。`maxTouches`・`cancels` と合わせて見る。ブラウザの前の段階なので、ゲームの作りで減らせるのは「叩いた瞬間の処理」と「持ち方の案内」 |
| 同時に5本が5%以上の曲 | 手のひら・指のつけ根が画面に触れている。持ち方の案内・端の受け付けを考える |
| 取り消しがAndroidの2倍以上 | システムのジェスチャー（画面のふち・3本指など）。どのふちかを数える項目を足す |
| 50ms以上遅れて届いたタッチがAndroidの2倍以上 | 叩いた瞬間の処理（判定・光・音）を軽くする。性能計測の spikes を実機で見る |
| 道の外で無視した指が多い | 端の受け付け範囲（`RHYTHM_INPUT_EDGE_MARGIN_SUB_LANES`）を広げる |
| 差が無い | 報告の起きる条件（曲・難易度・場面）を記録から絞る項目を足す |

## サーバー（`docs/sql/rankings/RHYTHM_TOUCH_DIAG_*.sql`）

- 新しい表 `public.rhythm_touch_diagnostics` を作るだけ。既存の表・ビュー・関数・RLS・ポリシー・権限には触らない
- 誰でも追加・読み出しはできるが、書き換え・削除はできない。行の形と大きさは check 制約で縛る（stats は4KBまで）
- **表はユーザーが1回だけ作る**（`RHYTHM_TOUCH_DIAG_IPHONE_STEPS.md`）。アプリの公開とSQLの適用はどちらが先でもよい。
  表が無いあいだも、取り戻しはゲームの中で動いている
- 手元の PostgreSQL 16 で、予行演習・本番・2回目の本番・確認が通り、anon の立場で「追加できる・読める・書き換えと削除は拒まれる・形の違う行は拒まれる」を確かめた（`rhythm-touch-diag-check.js`）
