# モンヒロビートのタッチの診断と、消えたタッチの取り戻し（2026-09-30）

**ユーザー報告**「iPhoneで両手の高速連打のとき、押しても音も光も出ないことがある」。前からずっとある。Androidの人からは聞かない。
同じiPhoneでも、ほかの音ゲー（iPhone専用のアプリ）では起きない。親指2本で遊んでいる。ホーム画面のアイコンから開いている。

**ユーザー指示**「こっち側に委ねないで、調べる仕組みを作って、直せる仕組みも作って」。

## わかっていること（2026-09-30 時点）

- この環境（パソコン上の Chrome）で、本物のタッチ（CDP）で両手の連打を再現しても、道の上の取りこぼしは0件だった。
  版ごと（9/26〜）の入力の処理の重さ・メモリの増え方にも差が無かった
- 公開中の全130譜面は、同時に指を2本までしか要求しない（押さえ続けるノーツ＋叩くノーツを数えた）
- ゲームの入力は、ブラウザが渡す「いま触れている指の一覧」に毎回合わせ直しているので、ゲームの中で指が残って積み上がることは無い
- 同じiPhoneのほかの音ゲーでは起きないので、iPhone本体（画面・OS）は正常。**指はブラウザ（WebKit）を通る部分か、ゲームの作りのどこかで消えている**

## 仕組み

```
プレイヤーが公開中の曲を遊ぶ
  ↓ ゲームが1回のタッチを「ポインタ」と「タッチ」の2通りで受け取り、突き合わせる(data/rhythm-mode.js の RHYTHM_TOUCH_BRIDGE)
  ↓   ポインタだけ届いてタッチが来なかった指 → その場でポインタの経路で入力にする(取り戻し)
  ↓ 1曲ごとに数をまとめ、端末に直近20曲(mh_rhythm_touch_diag_v1)・サーバーへ1行(rhythm_touch_diagnostics)
サーバーに記録がたまる
  ↓ 日曜・水曜の音ゲー班(2026-10-07 に毎週月曜の定期実行からまとめた。tools/playbot/ROUTINE.md「音ゲー班だけの手順」):
    node tools/mode/rhythm-touch-diag.js --fetch --report --days 14 / node tools/mode/rhythm-device-regression.js
iPhone と Android を比べて、指がどの段階で消えているかを判定する
```

### 数えるもの（1曲ごと）

| 名前 | 意味 | 増えたら |
| --- | --- | --- |
| `pointerOnly` / `recovered` | ポインタだけ届いてタッチが来なかった指 / そのうち取り戻した数 | ブラウザがタッチを落としている。**取り戻しで直っている** |
| `touchOnly` | タッチだけ届いてポインタが来なかった指 | ポインタを出さない端末。害は無い（取り戻しが働かない端末の目印） |
| `matched` | ポインタとタッチが組になった数 | ふつう |
| `lateStart` | 自分の touchstart ではなく、別の指のイベントで初めて見えた指 | ブラウザが touchstart を出し損ねている |
| `lateDelivery` / `maxDelayMs` | 50ms以上遅れて届いたタッチ / いちばん遅れた長さ | 叩いた瞬間の処理が重い |
| `cancels` / `cancelledTouches` | 端末に指を取り消された回数 / 本数 | システムのジェスチャーに取られている |
| `maxTouches` | 同時に触れていた指の最大 | 5ならiPhoneの上限（6本目は届かない） |
| `noInputMisses` / `misses` | 叩いている最中なのに前後200msに入力が1つも無いMISS / MISSの数 | 指がポインタにもタッチにもならずに消えている（ふつうの見逃しも混ざるので、Androidとの差で見る） |
| `ignored` / `outside` / `gestures` | 道の外で無視した指 / 演奏エリアの外に触れた指 / 二本指ジェスチャー | 端の受け付け・持ち方 |

名前・ブリーダーID・セーブデータは送らない。端末ごとのでたらめなID（遊んだ記録と同じ `mh_rhythm_play_log_device_v1`）と数だけ。
デバッグ・練習・タイミング合わせは送らない。アシストモードは印を付けて送り、道具は比べる数に入れない。

### 取り戻し（`RHYTHM_TOUCH_BRIDGE`）

- ブラウザは1回のタッチを、ポインタ（pointerdown）→ タッチ（touchstart）の順に、同じ時刻・同じ位置で届ける（Chrome も iPhone の Safari も）
- ポインタが来てから45ms待ってもタッチが来なければ、ポインタの経路（演奏画面の pointer の入力）で入力にする。
  タイマーに加えて毎フレームの処理でも見るので、遅くても数コマで通る。**判定には指が触れた時刻を使う**（取り戻しの遅れで判定がずれない）
- **二重に数えない**: 取り戻したあとで同じ指のタッチが遅れて来たら無視する。タッチが先・ポインタがあとで来たときは取り戻さない。
  どちらも位置（28px以内）と時刻（600ms以内）で同じ指かを見る
- **ふつうの端末では一度も動かない**（ポインタとタッチが必ず組になるため）。検査 `rhythm-touch-bridge-check.js` の①

## 判定と、次にやること（`rhythm-touch-diag.js --report`）

iPhoneの記録が20曲そろってから判定する。

| 判定 | 次にやること |
| --- | --- |
| ブラウザがタッチを落としている（`pointerOnly`） | 取り戻しで直っている。`noInputMisses` がAndroid並みに下がったかを見る |
| 入力の無いMISSがAndroidの2倍以上 | 指がポインタにもタッチにもならずに消えている。`maxTouches`・`cancels` と合わせて見る。ブラウザの前の段階なので、ゲームの作りで減らせるのは「叩いた瞬間の処理」と「持ち方の案内」 |
| 同時に5本が5%以上の曲 | 手のひら・指のつけ根が画面に触れている。持ち方の案内・端の受け付けを考える |
| 取り消しがAndroidの2倍以上 | システムのジェスチャー（画面のふち・3本指など）。どのふちかを数える項目を足す |
| 50ms以上遅れて届いたタッチがAndroidの2倍以上 | 叩いた瞬間の処理（判定・光・音）を軽くする。性能計測の spikes を実機で見る |
| 道の外で無視した指が多い | 端の受け付け範囲（`RHYTHM_INPUT_EDGE_MARGIN_SUB_LANES`）を広げる |
| 差が無い | 報告の起きる条件（曲・難易度・場面）を記録から絞る項目を足す |

## リザルトの「押したのに反応しないことがあった」（2026-10-01）

**ユーザー指示**「(反応しなかったボタンを)よろしく」。数字だけでは「その曲で本当に抜けたのか」が分からないので、プレイヤーに印を付けてもらう。

- iPhone・Android の公開プレイのリザルトに出る（パソコン・練習・タイミング合わせ・デバッグには出ない）。1曲につき1回
- 診断の行には、1曲ごとのでたらめな番号 `stats.playId`（12文字）と、効いていた直し方 `stats.fixes` が入る
- 表は追加しかできないので、診断の行は直さず、**報告の行**（`stats` が `{kind:'report',playId}` だけ）を1行足す。
  端末の記録（`mh_rhythm_touch_diag_v1`）のその曲には `reported:true` を足す
- 道具は報告の行を数に入れず、`playId` で結ぶ。同じ iPhone の記録のなかで「報告あり」と「報告なし」を比べ、
  報告ありの曲だけ2倍以上多い数字を「指の消えている段階」として出す（報告ありが5曲そろってから）

## 用意してある直し方（`RHYTHM_TOUCH_FIXES`）

**ユーザー指示**「原因が分かったときの直し方を、先に用意しておいて」。外れた直し方を入れると別の不具合を生むので、
**入れるのは週の報告で原因が決まり、ユーザーが了承してから**。`data/rhythm-mode.js` の `RHYTHM_TOUCH_FIXES` を true にする。
効くのは iPhone だけ（`allPlatforms` は検査用）。入れたあとの診断の行には `stats.fixes` に名前が入るので、入れる前と比べられる。

| 名前 | 効く判定 | すること |
| --- | --- | --- |
| `lateInputEffectDown` | ⑤ 50ms以上遅れて届いたタッチ | 3秒の枠でタッチが3回以上遅れて届いたら、演出を一段下げる。「重いときは演出を自動で控えめに」と同じ道なので、その設定を切った人には効かない。**2026-10-05に入れた（iPhoneだけ）** |
| `wideEdge` | ⑥ 道の外で無視した指 | 道の外の受け付けを、サブレーン1本ぶんから2本ぶんへ広げる |

ほかの判定（入力が1つも来ないMISS・同時に5本・端末に取り消された）は、指がブラウザに届く前の話なので、
ゲームの作りだけでは直せない。報告ありの曲の比べで段階を絞ってから考える。

`rhythm-touch-diag.js --report` は判定の最後に「用意してある直し方」で、いまの判定に合うものの名前を出す。

### 2026-10-18 の週の判定と、`wideEdge` を入れた経緯

サーバーの記録が683回ぶん（タッチの診断は iPhone 345曲）たまり、「押したのに反応しないことがあった」の報告のある曲だけ、次の3つが出た。

- 「道の外で無視した指」が1000タッチに 9.59 回（報告の無い曲は 2.78 回・3.4倍）
- 「入力が1つも来ないMISS」が1000ノーツに 4.89 回（報告の無い曲は 0.97 回・5.1倍）
- 指が同時に5本触れていた曲が報告のある曲の 38%（報告の無い曲は 1%）

用意してあった `wideEdge`（道の外の受け付けをサブレーン1本ぶん→2本ぶん）が、1つ目に合う。ユーザーが了承して（2026-10-18）入れた。
効くのは iPhone だけ。入れたあとの記録は `stats.fixes` に `wideEdge` と入るので、入れる前と `--report` の「直し方を入れる前と後」で比べる
（5曲そろうと出る）。「道の外で無視した指」が半分以下に減り、入力の無いMISSが増えなければ効いている。悪さをしたら `wideEdge:false` へ戻す。
同時に5本の曲と入力の無いMISSは、指がブラウザに届く前の話なので、この直し方では変わらない。

### 2026-10-05 の週の判定と、`lateInputEffectDown` を入れた経緯

サーバーの記録が202行（iPhone 99曲・7台 / Android 192曲・5台）たまった。判定の出力は「差なし」だったが、数字を読むと iPhone だけに差があった。

| 1000タッチあたり | iPhone | Android |
| --- | --- | --- |
| ポインタだけ届いた（取り戻しの対象） | 0.00 | 0.00 |
| タッチだけ届いた | 8.12 | 0.00 |
| 自分の touchstart ではなく、あとで見えた指 | 7.91 | 0.00 |
| 50ms以上遅れて届いた | 18.05（最大931ms） | 0.02（最大99ms） |

- 99曲中92曲で、遅れて届いたタッチがあった。ブラウザがタッチを落としているのではなく（ポインタだけは0）、**届くのが遅れている**。
  遅れは最大931msで、判定の窓（185ms）をこえるので、そのタップは音も光も出ずに MISS になる
- 「あとで見えた指」と「タッチだけ届いた」は、端末ごとにほぼ同じ数で動く（タップが一度見えなくなり、次の操作で見つかっている形）
- 端末による差が大きい（1台で48曲分・遅れ515件、別の1台は11曲・遅れ57件で「あとで見えた指」は1件）
- 判定の基準（遅れた回数が1000タッチに20回以上かつ Android の2倍以上）に18.05で届かず、判定には出なかった。**基準のほうが厳しすぎた**
- 「押したのに反応しないことがあった」の報告は7件（iPhone 6曲）。報告ありの曲は「遅れて届いた」22.7、なしは17.7で、曲数が少なく2倍の基準には届かない

ユーザーが了承して（2026-10-05）`lateInputEffectDown` を入れた。遅れの原因が画面の描き直しの重さだというのは推測で、
入れたあとの記録（`stats.fixes` に名前が入る）と入れる前を、`--report` の「直し方を入れる前と後」で比べる。
半分以下に減れば効いている。減らなければ、原因は描き直しの重さではなく、別の段階（ブラウザ・OSのタッチの扱い）にある。

## 同期の総点検（2026-11-11）

社長の指示「モンビーの入力・描画・音声同期の総点検。今までの対策が本当に効いているか確認する。狙い: 突発的なズレや取りこぼしの根本改善」。
本番の記録（直近14日。iPhone 506曲・8台 / Android 597曲・4台）を `rhythm-touch-diag.js` で読んだ結果と、入れた直し。

### 分かったこと

| これまでの対策 | 本番の記録で見えたこと | どうしたか |
| --- | --- | --- |
| `smoothSongClock`（曲の時計をなめらかに・止まるコマが2%以上の端末で自動） | **入ったり切れたりをくり返していた**（iPhone 3〜4台・Android 1台）。入れている間は「止まったコマ」をなめらかにした後の時計で数えていたので必ず 0% になり、20曲たつと自分で切れる。切れている回は元の時計が 6〜12% のコマで止まっていた（ノーツが1コマ止まって次で跳ぶ。判定の時刻もその段の分だけ粗い） | **直した**。止まりは元の時計（`rawSongTimeMs`）で数える。画面の時計の止まりは `stallsShown` に別に数える |
| `inputAgeCap`（遅れの補正の上限を 80ms→300ms） | 10/07 夜から標準で切のまま。入れても「その間コマが止まっていた」ときしか使わない作りだが、iPhone では止まりが見えた遅れが 4回 / 見えなかった遅れが 約24,000回で、**条件が成り立たない** | 数字で決めるための診断を足した（下の `lateN` など）。判定はまだ変えていない |
| `lateInputEffectDown`（遅れが続いたら演出を下げる） | **効いていない**。50ms以上遅れて届くタッチは 10/05 の 18回/1000 → 33回/1000。iPhone の1コマの JS は平均 0.8ms・33ms超のコマは 0.6% で、遅れはコマ落ちと関係なく起きている | そのまま（害は無い）。遅れの出どころを決める診断を足した |

iPhone だけに残っていること（Android はどれもほぼ 0）:

- touchstart の 3.3% が 50ms 以上遅れて届く。入力（押す・動かす・離す）の 1.5% が 80ms、0.6% が 150ms、0.3% が 300ms を超えて遅れる。80ms を超えた分は戻さないので、その分だけ遅く判定される
- MASTER / HELL では 1000タッチに約23回、指が「自分の touchstart なしに、別の指の合図の指の一覧で初めて見える」（HARD / EXPERT は 5〜6回）。縦持ち・🔄横のどちらでも同じ

### 入れた直し

- **曲の時計の直しの入り切りのくり返し**（上の表）
- **一覧から消えて戻っただけの指を、新しく押した扱いにしない**（iPhone だけ）。自分の離しの合図（touchend / touchcancel の changedTouches）なしに指の一覧から消えた指が、
  1.5秒（`RHYTHM_TOUCH_BACK_MS`）のうちに同じ番号で、自分の touchstart なしに戻ったら、同じ接触が続いているだけなので入力にしない。
  iPhone は指の番号が1回きりなので、同じ番号は同じ接触。Android は番号を使い回すので数えるだけ。判定の窓・スコアの数え方は変えていない

### 足した数（どれも判定には使わない・古い行には無い）

| 名前 | 意味 | 決められること |
| --- | --- | --- |
| `timing.stallsShown` | 画面に出している時計が前のコマと同じ値だった数（`timing.stalls` は元の時計） | 時計の直しが効いているか |
| `timing.lateN` / `lateActMs` / `lateFullMs` / `lateExMs` | 上限（80ms）を超えて遅れた入力で取れた単押しの数 / いまの判定のずれの中央値 / 合図の時刻まで全部戻したときのずれの中央値 / 戻し切れなかった分の中央値。この単押しは `biasMs` に混ぜない | `lateFullMs` がふだんのずれ（`biasMs`）に近ければ、**合図の時刻は本当に指の触れた時刻**（コマが止まっていなくても戻してよい）。`lateActMs` が近ければ時刻だけ古い（今のままでよい） |
| `lateHist` | 遅れて届いた touchstart の遅れの分布（50〜80 / 〜150 / 〜300 / 300ms超） | 遅れの大きさ |
| `edgeAll` / `edgeLate` | touchstart の、画面のふちからの近さ（24px未満 / 60 / 120 / それより内）。全部と、遅れて届いたもの | 遅れが端末のふちのジェスチャー待ちかどうか（寄っていれば、叩く場所をふちから離す案が効く） |
| `multiAll` / `multiLate` | ほかの指が触れている最中の touchstart。全部と、遅れて届いたもの | 遅れが同時押し・交互連打のときだけか |
| `lsBack` / `lsBackGuard` | 自分の touchstart なしに見えた指のうち、消えていた指が戻っただけのもの / それを押した扱いにしなかった数 | 上の守りがどれだけ働いたか |
| `lsByStart` / `lsByMove` / `lsByEnd` | 初めて見えたのが、別の指の touchstart / touchmove / 離しの合図だった数（`lateStart` は今までどおり touchstart 以外の合計） | touchstart が抜けている形 |
| `lsFollow` / `lsFollowEarlier` / `lsFollowMaxMs` | そのあとで自分の touchstart が届いた数 / その時刻のほうが古かった数 / いちばん大きかった差 | 抜けたのではなく「あとから届く」のか |

`node tools/mode/rhythm-touch-diag.js --fetch --report --days 14` の最後の「同期の総点検の数」が、上をまとめて判定を出す。
見張りは `tools/mode/rhythm-timing-diag-check.js`（部品）と `tools/mode/rhythm-sync-audit-check.js`（実際に曲を流す）。

### 次に決めること（数日ぶんたまってから）

1. `lateFullMs` と `lateActMs` のどちらが `biasMs` に近いか → 近いのが `lateFullMs` なら、iPhone では「コマが止まっていた」の条件を外して合図の時刻まで戻す（判定の窓は変えない。遅く判定されていた分が正しい時刻になる）
2. `edgeLate` がふちに寄っているか → 寄っていれば、判定ラインの高さ・叩く場所の案内で減らせる
3. `lsBack` が多いか → 多ければ、今回の守りで空打ち・早取りが減っている。0 のままなら、見える指はすべて「touchstart が抜けた新しい指」

### 毎晩の判定の報告に足すとよい数字（案）

- iPhone の「50ms以上遅れて届いた touchstart」と「80ms を超えて遅れた入力」（1000あたり）。前の7日と比べて 1.5倍で知らせる
- 曲の時計の直しが入ったり切れたりしている端末の数（0 のはず）と、直しを入れた回の `stallsShown` の割合（0.5%未満のはず）
- `lsBackGuard`（守りが働いた数）と `lateStart`（1000タッチあたり）
- 端末ごとの `biasMs`（押したずれの中央値）が前の7日から 15ms 以上動いたら知らせる（版の入れ替えで時計・補正が狂ったときに最初に動く数字）

## 同期の総点検 2本目: 遅れて届いたタッチの戻し方（2026-11-14）

11/11 に足した数が iPhone 107曲・4台ぶんたまり、遅れて届くタッチの正体が決まった。社長が案A を選んだ（2026-11-14）。

### 分かったこと

| 数 | 結果 | 読み |
| --- | --- | --- |
| `multiAll` / `multiLate` | ほかの指が触れている最中のタッチは全体の 23.5%、遅れて届いたタッチでは 99.9% | 遅れは同時押し・交互連打のときだけ起きる |

### 入れた直し（`lateStampTypical`・iPhone だけ・標準で入）

- **ふだんの遅れ**（`rhythmInputAgeTypicalMs`）: 合図が起きてから処理されるまでの遅れのうち 80ms 以下のものの、直近64回の中央値。上限 50ms。8回たまるまでは 25ms
- **①80ms を超えて遅れ、その間コマは止まっていなかった入力**は、合図の時刻を使わず、ふだんの遅れだけ戻す（これまでは 80ms）
- **②別の指の合図の中で初めて見えた指**は、その合図の時刻が自分のものではないので、ふだんの遅れより古くは戻さない（`rhythmRevealedAgeMs`）。同じ合図に自分の touchstart の指が混ざるときだけ、分けて判定へ渡す（ふつうは今までどおり1まとめ）
- その間コマが本当に止まっていた遅れ・80ms 以下の遅れ・離しの合図・Android・パソコンは今までどおり。**判定の窓・スコア・ランキングの数え方・譜面は変えていない**
- 外れていたら `RHYTHM_TOUCH_FIXES.lateStampTypical` を false へ戻す（前の動きにそのまま戻る）。入れたあとの記録は `stats.fixes` に名前が入る

### 曲の時計の直しを、その曲の中で入れる（全端末）

端末の記録（前の20曲）から決めるだけだと、音の出し方が変わった直後（イヤホンの付け外しなど）の数曲は、元の時計が止まりやすいのに直しが入らないまま始まる。
その曲で元の時計を3秒ぶん（180コマ）読み、止まったコマが 2% 以上なら、その場で `smoothSongClock` を入れる（`rhythmSmoothClockLiveCheck`。曲の終わりまで入れたまま。入れた曲は `timing.smoothLive` に、入れた時のコマ数が残る）。

## タイミングの診断と、実機の直し方（2026-10-07）

**ユーザー指示**「実機で確認しないと直せないものは、直せる仕組みを作って」「**一人でやっているので、人の手で調整する前提の作りにしないで**」。
そのため、**ゲームが端末の記録から自分で入れ切りする**。人が数字を見て決めたり、パネルを触って試したりする前提は置かない（デバッグ用の上書きだけ、コンソールから使える）。
新しいSQL・表は要らない（`stats` は jsonb で4KBまで。`stats.timing` は約400バイト）。

### 数えるもの（`stats.timing`・`RHYTHM_TIMING_DIAG`）

| 名前 | 意味 |
| --- | --- |
| `ageHist` / `ageCapped` / `ageBacked` / `ageUnbacked` | 入力が届くまでの遅れの分布（〜25 / 50 / 80 / 150 / 300 / 300超 ms）/ 補正の上限（80ms）を超えた数 / うちコマ落ちが見えたもの / 見えなかったもの |
| `frames` / `stalls` / `maxStepMs` | 曲の時計を1コマごとに読んだ数 / 前のコマと同じ値だった数 / いちばん大きかった1コマの進み |
| `hidden` / `pen` | 演奏中にアプリを離れた回数 / ペンで直接押した回数 |
| `outLatMs` / `baseLatMs` / `hasTs` / `rate` / `headMs` | 端末の出力遅延・基準遅延・`getOutputTimestamp` の有無・サンプルレート・曲の頭の無音の長さ（mp3の先頭の遅れがブラウザで違わないかを比べる） |
| `tsLatMs` / `biasN` / `biasMs` | `tsLatMs` は端末が申告する「いま耳に届いている位置」(`getOutputTimestamp`)と `ctx.currentTime` の差(0.5秒おきに測った中央値・ms。測れない端末は null)。`biasMs` は単押しを取ったときのずれの中央値(正=遅い側)、`biasN` はその数。**どちらも判定には使わない**(診断だけ)。Safari の出力遅延の補正が足りているかは、`biasMs` が `outLatMs` と `tsLatMs` のどちらに近いかで見る。タップのずれから自動で補正すると、見た目を見て叩く人でずれが積み上がり続けるので、そうはしない(2026-10-07) |

### 直し方（`RHYTHM_TOUCH_FIXES`）と、ゲームが自分で決める入れ切り

> 2026-11-11 追記: `inputAgeCap` は 2026-10-07 21時（ユーザー報告「タップ抜けがひどくなった」）から**標準で切ってある**。下の表の「標準で入っている」は 10/07 昼の時点の話。いまの様子は上の「同期の総点検」を見る。

| 名前 | 効くこと | 入れ切り |
| --- | --- | --- |
| `inputAgeCap` | 遅れの補正の上限を80msから300msへ広げる。**使うのは、①時計の基準がそろっていて、②その間ゲームが本当に止まっていた（直前のコマが、入力の遅れの6割以上前だった）と見えたときだけ**。止まりが見えないのに古い時刻の入力は、80msで止める | **標準で入っている（iPhoneだけ）**。端末の記録で、止まりが見えない遅れた入力が、見えたものと同じかそれ以上に多い（合わせて5回以上）と分かった端末は、**自分で切る**（イベントの時刻が古いだけの疑い） |
| `smoothSongClock` | 曲の時計を、コマの間でなめらかに進める（段の値へゆっくり寄せ、離れすぎたら段の値に戻す） | 標準では切。端末の記録で、止まったコマが2%以上ある端末だけ、**自分で入れる**（全端末） |
| `autoPauseOnHidden` | 演奏中にアプリを離れたら、自動で一時停止する | **標準で入っている（全端末）** |

- 取りこぼしを見逃しMISSにするまでの待ち（`rhythmMissReclaimMs`）は、広げた上限（300ms）を足すのを、**直前にゲームが80ms以上止まったあとの600msのあいだだけ**にした。ふだんはこれまでどおり（MISSの出る時刻は変わらない）。
- 入れた名前は診断の行の `stats.fixes` に残る（入れる前と後を `rhythm-touch-diag.js` で比べられる）。
- デバッグ用の上書き（コンソールから `rhythmTouchFixSetOverride(name,true/false/null)`・新しい保存キー `mh_rhythm_fix_override_v1`）は残してあるが、画面のパネルは置かない。

### 報告ツール

`node tools/mode/rhythm-touch-diag.js --fetch --report` の「タイミングの診断」は、全端末の記録をまとめて、iPhone と Android の差・出力遅延・曲の頭の無音の差を出す（ゲームの入れ切りとは別に、全体の傾向を見る用）。
見張りは `tools/mode/rhythm-timing-diag-check.js`。

### 診断では決められないもの

- **出力遅延の既定値**: 診断で iPhone の `outLatMs` が小さいと分かっても、人ごとの耳の差があるので、全員へ決めた値は入れない。いまの「判定タイミング調整」（見た目と判定が同じ量だけ動く）で、その端末の定数は直せる。
- **mp3 の頭の遅れ**: `headMs` の差が見つかったら、音源を作り直す（曲を足すときの手順）。

## 手元のサーバーからは送らない

検査は本物の曲を最後まで流すので、そのまま送ると本番の表へ検査の行が混ざり、iPhone と Android の比べが狂う。
`localhost` などで開いたゲーム（`sbTelemetryLocal`）からは、タッチの診断も遊んだ記録も送らない。

## サーバー（`docs/sql/rankings/RHYTHM_TOUCH_DIAG_*.sql`）
