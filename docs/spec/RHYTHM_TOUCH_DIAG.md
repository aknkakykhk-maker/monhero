# モンヒロビートのタッチの診断と、消えたタッチの取り戻し（2026-09-30）

**ユーザー報告**「iPhoneで両手の高速連打のとき、押しても音も光も出ないことがある」。前からずっとある。Androidの人からは聞かない。
同じiPhoneでも、ほかの音ゲー（iPhone専用のアプリ）では起きない。親指2本で遊んでいる。ホーム画面のアイコンから開いている。

**ユーザー指示**「こっち側に委ねないで、調べる仕組みを作って、直せる仕組みも作って」。

## わかっていること（2026-09-30 時点）

- この環境（パソコン上の Chrome）で、本物のタッチ（CDP）で両手の連打を再現しても、道の上の取りこぼしは0件だった。
  版ごと（9/26〜）の入力の処理の重さ・メモリの増え方にも差が無かった
- 公開中の全130譜面は、同時に指を2本までしか要求しない（押さえ続けるノーツ＋叩くノーツを数えた）
- ゲームの入力は、ブラウザが渡す「いま触れている指の一覧」に毎回合わせ直しているので、ゲームの中で指が残って積み上がることは無い
- 同じiPhoneのほかの音ゲーでは起きないので、iPhone本体（画面・OS）は正常。**指はブラウザ（WebKit）を通る部分か、ゲームの作りのどこかで消えている**

## 仕組み

```
プレイヤーが公開中の曲を遊ぶ
  ↓ ゲームが1回のタッチを「ポインタ」と「タッチ」の2通りで受け取り、突き合わせる(data/rhythm-mode.js の RHYTHM_TOUCH_BRIDGE)
  ↓   ポインタだけ届いてタッチが来なかった指 → その場でポインタの経路で入力にする(取り戻し)
  ↓ 1曲ごとに数をまとめ、端末に直近20曲(mh_rhythm_touch_diag_v1)・サーバーへ1行(rhythm_touch_diagnostics)
サーバーに記録がたまる
  ↓ 週1回の定期実行: node tools/mode/rhythm-touch-diag.js --fetch --report --days 14
iPhone と Android を比べて、指がどの段階で消えているかを判定する
```

### 数えるもの（1曲ごと）

| 名前 | 意味 | 増えたら |
| --- | --- | --- |
| `pointerOnly` / `recovered` | ポインタだけ届いてタッチが来なかった指 / そのうち取り戻した数 | ブラウザがタッチを落としている。**取り戻しで直っている** |
| `touchOnly` | タッチだけ届いてポインタが来なかった指 | ポインタを出さない端末。害は無い（取り戻しが働かない端末の目印） |
| `matched` | ポインタとタッチが組になった数 | ふつう |
| `lateStart` | 自分の touchstart ではなく、別の指のイベントで初めて見えた指 | ブラウザが touchstart を出し損ねている |
| `lateDelivery` / `maxDelayMs` | 50ms以上遅れて届いたタッチ / いちばん遅れた長さ | 叩いた瞬間の処理が重い |
| `cancels` / `cancelledTouches` | 端末に指を取り消された回数 / 本数 | システムのジェスチャーに取られている |
| `maxTouches` | 同時に触れていた指の最大 | 5ならiPhoneの上限（6本目は届かない） |
| `noInputMisses` / `misses` | 叩いている最中なのに前後200msに入力が1つも無いMISS / MISSの数 | 指がポインタにもタッチにもならずに消えている（ふつうの見逃しも混ざるので、Androidとの差で見る） |
| `ignored` / `outside` / `gestures` | 道の外で無視した指 / 演奏エリアの外に触れた指 / 二本指ジェスチャー | 端の受け付け・持ち方 |

名前・ブリーダーID・セーブデータは送らない。端末ごとのでたらめなID（遊んだ記録と同じ `mh_rhythm_play_log_device_v1`）と数だけ。
デバッグ・練習・タイミング合わせは送らない。アシストモードは印を付けて送り、道具は比べる数に入れない。

### 取り戻し（`RHYTHM_TOUCH_BRIDGE`）

- ブラウザは1回のタッチを、ポインタ（pointerdown）→ タッチ（touchstart）の順に、同じ時刻・同じ位置で届ける（Chrome も iPhone の Safari も）
- ポインタが来てから45ms待ってもタッチが来なければ、ポインタの経路（演奏画面の pointer の入力）で入力にする。
  タイマーに加えて毎フレームの処理でも見るので、遅くても数コマで通る。**判定には指が触れた時刻を使う**（取り戻しの遅れで判定がずれない）
- **二重に数えない**: 取り戻したあとで同じ指のタッチが遅れて来たら無視する。タッチが先・ポインタがあとで来たときは取り戻さない。
  どちらも位置（28px以内）と時刻（600ms以内）で同じ指かを見る
- **ふつうの端末では一度も動かない**（ポインタとタッチが必ず組になるため）。検査 `rhythm-touch-bridge-check.js` の①

## 判定と、次にやること（`rhythm-touch-diag.js --report`）

iPhoneの記録が20曲そろってから判定する。

| 判定 | 次にやること |
| --- | --- |
| ブラウザがタッチを落としている（`pointerOnly`） | 取り戻しで直っている。`noInputMisses` がAndroid並みに下がったかを見る |
| 入力の無いMISSがAndroidの2倍以上 | 指がポインタにもタッチにもならずに消えている。`maxTouches`・`cancels` と合わせて見る。ブラウザの前の段階なので、ゲームの作りで減らせるのは「叩いた瞬間の処理」と「持ち方の案内」 |
| 同時に5本が5%以上の曲 | 手のひら・指のつけ根が画面に触れている。持ち方の案内・端の受け付けを考える |
| 取り消しがAndroidの2倍以上 | システムのジェスチャー（画面のふち・3本指など）。どのふちかを数える項目を足す |
| 50ms以上遅れて届いたタッチがAndroidの2倍以上 | 叩いた瞬間の処理（判定・光・音）を軽くする。性能計測の spikes を実機で見る |
| 道の外で無視した指が多い | 端の受け付け範囲（`RHYTHM_INPUT_EDGE_MARGIN_SUB_LANES`）を広げる |
| 差が無い | 報告の起きる条件（曲・難易度・場面）を記録から絞る項目を足す |

## リザルトの「押したのに反応しないことがあった」（2026-10-01）

**ユーザー指示**「(反応しなかったボタンを)よろしく」。数字だけでは「その曲で本当に抜けたのか」が分からないので、プレイヤーに印を付けてもらう。

- iPhone・Android の公開プレイのリザルトに出る（パソコン・練習・タイミング合わせ・デバッグには出ない）。1曲につき1回
- 診断の行には、1曲ごとのでたらめな番号 `stats.playId`（12文字）と、効いていた直し方 `stats.fixes` が入る
- 表は追加しかできないので、診断の行は直さず、**報告の行**（`stats` が `{kind:'report',playId}` だけ）を1行足す。
  端末の記録（`mh_rhythm_touch_diag_v1`）のその曲には `reported:true` を足す
- 道具は報告の行を数に入れず、`playId` で結ぶ。同じ iPhone の記録のなかで「報告あり」と「報告なし」を比べ、
  報告ありの曲だけ2倍以上多い数字を「指の消えている段階」として出す（報告ありが5曲そろってから）

## 用意してある直し方（`RHYTHM_TOUCH_FIXES`）

**ユーザー指示**「原因が分かったときの直し方を、先に用意しておいて」。外れた直し方を入れると別の不具合を生むので、
**入れるのは週の報告で原因が決まり、ユーザーが了承してから**。`data/rhythm-mode.js` の `RHYTHM_TOUCH_FIXES` を true にする。
効くのは iPhone だけ（`allPlatforms` は検査用）。入れたあとの診断の行には `stats.fixes` に名前が入るので、入れる前と比べられる。

| 名前 | 効く判定 | すること |
| --- | --- | --- |
| `lateInputEffectDown` | ⑤ 50ms以上遅れて届いたタッチ | 3秒の枠でタッチが3回以上遅れて届いたら、演出を一段下げる。「重いときは演出を自動で控えめに」と同じ道なので、その設定を切った人には効かない。**2026-10-05に入れた（iPhoneだけ）** |
| `wideEdge` | ⑥ 道の外で無視した指 | 道の外の受け付けを、サブレーン1本ぶんから2本ぶんへ広げる |

ほかの判定（入力が1つも来ないMISS・同時に5本・端末に取り消された）は、指がブラウザに届く前の話なので、
ゲームの作りだけでは直せない。報告ありの曲の比べで段階を絞ってから考える。

`rhythm-touch-diag.js --report` は判定の最後に「用意してある直し方」で、いまの判定に合うものの名前を出す。

### 2026-10-05 の週の判定と、`lateInputEffectDown` を入れた経緯

サーバーの記録が202行（iPhone 99曲・7台 / Android 192曲・5台）たまった。判定の出力は「差なし」だったが、数字を読むと iPhone だけに差があった。

| 1000タッチあたり | iPhone | Android |
| --- | --- | --- |
| ポインタだけ届いた（取り戻しの対象） | 0.00 | 0.00 |
| タッチだけ届いた | 8.12 | 0.00 |
| 自分の touchstart ではなく、あとで見えた指 | 7.91 | 0.00 |
| 50ms以上遅れて届いた | 18.05（最大931ms） | 0.02（最大99ms） |

- 99曲中92曲で、遅れて届いたタッチがあった。ブラウザがタッチを落としているのではなく（ポインタだけは0）、**届くのが遅れている**。
  遅れは最大931msで、判定の窓（185ms）をこえるので、そのタップは音も光も出ずに MISS になる
- 「あとで見えた指」と「タッチだけ届いた」は、端末ごとにほぼ同じ数で動く（タップが一度見えなくなり、次の操作で見つかっている形）
- 端末による差が大きい（1台で48曲分・遅れ515件、別の1台は11曲・遅れ57件で「あとで見えた指」は1件）
- 判定の基準（遅れた回数が1000タッチに20回以上かつ Android の2倍以上）に18.05で届かず、判定には出なかった。**基準のほうが厳しすぎた**
- 「押したのに反応しないことがあった」の報告は7件（iPhone 6曲）。報告ありの曲は「遅れて届いた」22.7、なしは17.7で、曲数が少なく2倍の基準には届かない

ユーザーが了承して（2026-10-05）`lateInputEffectDown` を入れた。遅れの原因が画面の描き直しの重さだというのは推測で、
入れたあとの記録（`stats.fixes` に名前が入る）と入れる前を、`--report` の「直し方を入れる前と後」で比べる。
半分以下に減れば効いている。減らなければ、原因は描き直しの重さではなく、別の段階（ブラウザ・OSのタッチの扱い）にある。

## タイミングの診断と、実機の直し方（2026-10-07）

**ユーザー指示**「実機で確認しないと直せないものは、直せる仕組みを作って」。点検（入力の経路・見た目と判定の位置・タイミング）で、実機でしか確かめられないものが残った。
どれも、**数える仕組み（診断）→ 直し方（既定は切ってある）→ この端末だけで試す → よければ全員へ**の順で進める。
新しいSQL・表は要らない（`stats` は jsonb で4KBまで。`stats.timing` は約400バイト）。判定・スコア・保存には関わらない。

### 数えるもの（`stats.timing`・`RHYTHM_TIMING_DIAG`）

| 名前 | 意味 | 何を決めるための数字か |
| --- | --- | --- |
| `ageHist` | 入力が届くまでの遅れ（イベントが起きてから処理されるまで）の分布。〜25 / 50 / 80 / 150 / 300 / 300超 ms の6つ | 遅れの補正の頭打ち（80ms）が足りているか |
| `ageCapped` | 補正の上限（80ms）を超えて遅れて届いた入力の数 | 同上。多い端末では、処理が詰まった回の空判定・隣のノーツ取りが起きている疑い |
| `frames` / `stalls` / `maxStepMs` | 曲の時計を1コマごとに読んだ数 / 前のコマと同じ値だった数 / いちばん大きかった1コマの進み | 曲の時計が階段状で、曲が止まって見えないか |
| `hidden` / `pen` | 演奏中にアプリを離れた回数 / ペンで直接押した回数 | 裏へ回ったあとの大量のMISS・ペンの二重入力の疑い |
| `outLatMs` / `baseLatMs` / `hasTs` / `rate` | その端末の出力遅延・基準遅延・`getOutputTimestamp` の有無・サンプルレート | Safari が出力遅延を申告せず、耳で合わせる人が遅れて判定される疑い |
| `headMs` | 曲の頭の無音の長さ（ms） | mp3 の先頭の遅れの扱いが、ブラウザで違わないか（同じ曲を iPhone と Android で比べる） |

### 用意した直し方（`RHYTHM_TOUCH_FIXES`・既定はすべて切ってある）

| 名前 | 効くこと | 入れる目安 |
| --- | --- | --- |
| `inputAgeCap` | 遅れの補正の上限を80msから300msへ広げる（時計の基準がそろっていると分かった端末だけ。取りこぼしの回収も同じだけ長くする） | `ageCapped` が1000入力に10回以上 |
| `smoothSongClock` | 曲の時計を、コマの間でなめらかに進める（段の値へゆっくり寄せ、離れすぎたら段の値に戻す） | `stalls` が2%以上 |
| `autoPauseOnHidden` | 演奏中にアプリを離れたら、自動で一時停止する | `hidden` が出た曲が5%以上 |

### この端末だけで試す（デバッグ画面）

デバッグ画面の「実機の直し方（この端末だけ・デバッグ）」で、上の3つをこの端末だけ入れる/切れる。保存先は新しいキー `mh_rhythm_fix_override_v1`（既存のキーは触らない）。
入れた名前は診断の行の `stats.fixes` に残るので、入れる前と後を `rhythm-touch-diag.js` で比べられる。パネルには直近1曲の数えも出る。

### 報告ツール

`node tools/mode/rhythm-touch-diag.js --fetch --report` の「タイミングの診断」で、端末の系統（iPhone / Android）ごとに上の数を集め、疑いと合う直し方の名前を出す。
**入れるのはユーザーが了承してから**（週の定期実行は報告するだけ）。見張りは `tools/mode/rhythm-timing-diag-check.js`。

### 診断では分からず、仕組みを用意していないもの

- **出力遅延の既定値**: 診断で iPhone の `outLatMs` が小さいと分かっても、人ごとの耳の差があるので、全員へ決めた値は入れない。いまの「判定タイミング調整」（見た目と判定が同じ量だけ動く）で、その端末の定数は直せる。
- **mp3 の頭の遅れ**: `headMs` の差が見つかったら、音源を作り直す（曲を足すときの手順）か、判定タイミング調整の目安を出す。端末ごとの補正は、全曲に同じ量が効くだけなので、診断が出てから決める。

## 手元のサーバーからは送らない

検査は本物の曲を最後まで流すので、そのまま送ると本番の表へ検査の行が混ざり、iPhone と Android の比べが狂う。
`localhost` などで開いたゲーム（`sbTelemetryLocal`）からは、タッチの診断も遊んだ記録も送らない。

## サーバー（`docs/sql/rankings/RHYTHM_TOUCH_DIAG_*.sql`）

- 新しい表 `public.rhythm_touch_diagnostics` を作るだけ。既存の表・ビュー・関数・RLS・ポリシー・権限には触らない
- 誰でも追加・読み出しはできるが、書き換え・削除はできない。行の形と大きさは check 制約で縛る（stats は4KBまで）
- **表はユーザーが1回だけ作る**（`RHYTHM_TOUCH_DIAG_IPHONE_STEPS.md`）。アプリの公開とSQLの適用はどちらが先でもよい。
  表が無いあいだも、取り戻しはゲームの中で動いている
- 手元の PostgreSQL 16 で、予行演習・本番・2回目の本番・確認が通り、anon の立場で「追加できる・読める・書き換えと削除は拒まれる・形の違う行は拒まれる」を確かめた（`rhythm-touch-diag-check.js`）
