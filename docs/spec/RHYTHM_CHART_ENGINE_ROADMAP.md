# MHB CHART ENGINE 強化の設計と進め方（2026-09-26）

譜面生成ツール（MHB CHART ENGINE）を「人が手直ししなくても、一般的な音ゲーの手作り譜面と
遜色ない」ところまで持っていくための、調査結果と段取り。**進み具合はこの文書の「進み具合」に書く。**
作業を再開するときは、まずこの文書と [`RHYTHM_CHART_DESIGN.md`](RHYTHM_CHART_DESIGN.md) を開く。

- 2026-09-26 に、ユーザーから別のAIの強化案を受け取り、実コードと照らして調べた（案は正解扱いしない）
- 同日、ユーザー判断「全部やってほしい」。段0から順に、**1段ごとに公開しながら**進める
- 関係する資料: [`RHYTHM_CHART_DESIGN.md`](RHYTHM_CHART_DESIGN.md)（原則と各リビジョンの実測）、
  [`RHYTHM_CHART_CORPUS.md`](RHYTHM_CHART_CORPUS.md)（人が確かめた譜面から統計を取る設計。段6とつながる）

## 守ること（どの段でも）

- **既存曲の譜面は変えない**（運用ルール ⑩-2）。譜面が変わる強化は新しいリビジョン（Rev.8〜）へ入れ、
  変更前のワークツリーと生成結果を突き合わせて、既存曲のノーツ数が一致することを確かめてからコミットする
- **既存の解析ファイル（`*-v3-audio.json`）は作り直さない**。解析を足すときは別のファイルに足し、
  新しく解析する曲だけに効かせる
- **手のモデルと「押せない譜面は出さない」関門は残す**。新しい仕組みは必ずこの関門の内側で動かす
- **毎回同じ結果になる**ことを崩さない（乱数を使わない。外部モデルを使うなら版と結果を固定して残す）
- 機能を増やすことが目的ではない。**遊んだときの体験が良くなるか**で判断する

## 1. いまできていること（2026-09-26・Rev.7 時点）

| 領域 | 実装済み |
| --- | --- |
| 解析 | 全部自前のJS（外部ライブラリなし）。16kHzモノラル・64msのSTFT・5帯域の立ち上がり。テンポ（自己相関＋倍・半分などの候補比較）・拍の頭・拍子（4/3/5）・刻み（2/3/4/6）・跳ね。打点の性格4種（FULL / PUNCH / BODY / LIGHT）。音高は中心600Hzの単声の線1本とベースの線1本。伸び（旋律・ベース）。構造（区切り・盛り上がり・同じ区切りの繰り返し。名前は付けない）。同じ入力なら毎回同じ結果 |
| 音を選ぶ | 優先度＝性格＋強さ＋拍の中の位置＋伸び＋音高（＋Rev.7の作法）。密度は1拍あたりの目標を毎秒の下限・上限で挟み、盛り上がりで小節へ配分。**下の難易度は上の難易度の部分集合** |
| 配置 | 形の語彙29種を点数で選ぶ（`rankShapes`）。直前3つの形を避ける。形の使用回数は曲全体で数える。区切りの役割4つ（intro / body / climax / outro）。フレーズの写し（Rev.2。2回目は左右反転、3回目は選び直し） |
| 種類 | HOLD・SLIDE は伸びる音から。SLIDE の曲線（Rev.3）・分岐・合流・同時スライド。フリックと同時押しは音の性格で置く（Rev.6）。横FLICK（Rev.4・MASTERだけ）。作法4件（Rev.7） |
| 手 | 親指2本・指の太さ1レーン・叩き直し105ms・移動は毎秒18レーン・押さえ中の拘束。先読み（ビーム幅8）で両手へ割り振る |
| 生成後 | 自動修正（レーンだけ動かす）→ 押せるかの検査 → 品質の6軸。複数候補を採点して選ぶ道具（`rhythm-chart-v3-candidates.js`。手で呼ぶ） |

## 2. 特に優れているところ（崩さない）

- **押せない譜面を出さない関門**。公開中の曲の押せない配置は0件
- **リビジョンで作り方を分け、毎回同じ結果になる**。どんな強化をしても既存曲を守れる
- **鳴っていない場所にノーツを置かない**。26曲×5難易度で、ノーツが音に乗る割合は 1.00
- **どんな曲でも作れる設計**（数を「1曲に何個」でなく「1分あたり」で持つ など）
- **物差しの誤りを直してきた経緯が資料に残っている**

## 3. 足りないところ（コードで確かめたもの）

### 3.1 物差しが満点近くに張り付いている（いちばんの壁）

全26曲の品質記録（`authoring/*-v3-quality.json`）の平均。公開中の23曲は同日に Rev.7 で作り直してある（残り3曲は公開していない Rev.1）。

| 難易度 | 押せる | 音 | 読める | 流れ | 飽きない | 難易度なり |
| --- | --- | --- | --- | --- | --- | --- |
| EASY | 100 | 92 | 100 | 99 | 94 | 100 |
| NORMAL | 100 | 91 | 100 | 99 | 97 | 99 |
| HARD | 100 | 91 | 99 | 94 | 95 | 100 |
| EXPERT | 100 | 90 | 98 | 89 | 94 | 97 |
| MASTER | 98 | 87 | 98 | 88 | 94 | 97 |

遊ぶと「似た配置が続く」「横FLICKの向きがバラバラ」と感じるのに、「読める」「飽きない」はほぼ満点。
物差しが体験との差を捉えていないので、生成器を直しても良くなったか機械で判定できず、
「批評して悪い区間を直す」も回らない。遊んだ感想（譜面メモ）も0件。

- 「飽きない」は**形の名前**を数えている。名前が違っても指の動きが同じなら同じに感じるが、それが見えない
- 見ているのは「直前3つ」と「曲全体の回数」だけ。4小節・8小節の窓が無い
- 気持ちよさ・予測しやすさ・見やすさの点数が無い
- 盛り上がりと密度の一致（`intensityDensityAgreement`）は計算しているが点数に入っていない
- 点数は曲全体・難易度ごとの1つだけで、**どの区間が悪いか**が出ない

### 3.2 音の理解

- 楽器・役割の区別が無い。「歌の語尾」の印も実際は「600Hz付近で音高が取れた打点」
- 旋律は単声の線1本。歌とギターが同時に鳴ると、どちらを追っているか分からない
- 16kHz 解析なので 8kHz より上（ハイハット・シンバルの芯）が見えない
- **テンポの自動判定が確定しきれない**。26曲中13曲で「テンポの候補が紛らわしい」警告。新しく足した3曲はすべて人が確かめ、
  FREEDOM DiVE↓ はテンポも拍子も誤判定（166.70 / 3拍子 → 正しくは 222.22 / 4拍子）。テンポは1曲に1つだけ

### 3.3 生成器

- **難易度で追う音を変えていない**（同じ優先順位の上から何個取るかだけ）
- **繰り返しの「発展」は選び直しだけ**。同時押し・フリック・区切りの一発は元のフレーズから写さないので、1番と2番でそろう保証が無い。ラスサビを見分けない
- **横FLICK（`applySideFlicks`）は後処理**。旋律の上下を最優先にし、次のノーツが逆側にあっても無視する。
  直前の動き・どちらの手か・SLIDEの向きを見ない。付けたあと手のシミュレートをやり直さない。
  ゲーム側は向きが合わないと成立しない判定なので、不自然さがそのまま体験に出る
- 終点フリックと HOLD の太さの形は、音を見ずに順番に回している
- **6レーンなのに中央を `2` と直書きしている**（`rhythm-chart-v3-generate.js` の `lastLane=2`・写しの補間 `lane>=2`・中央前提の形の費用 `Math.abs(base-2)`）。
  6レーンの中央は 2.5 なので、中央寄せと補間がわずかに左へ偏る。Rev.5 以降の譜面（公開中の23曲）に効いている
- **区間だけ作り直せない作り**。形の使用回数・1分あたりの予算を曲全体で順に積み上げている

## 4. 受け取った案の評価

| 案 | 評価 | 中身 |
| --- | --- | --- |
| 楽器の区別・音源分離 | 方向は賛成。音源分離から入るのは反対 | まず自前JSで「打楽器と音程楽器の分離（HPSS）」「キック・スネア・ハイハットの分類」「歌の有無」。音源分離（Demucs など）は、足りないと分かってから解析のときだけ使う補助にする |
| 主役の音を追う | 最も効果が大きい。新規 | 拍ごとに層の目立ち度を点数にし、切り替えにコストを付けて動的計画法でならす。切り替えは区切りの頭かフィルでだけ許す。いまの `layer_follow` は2択の簡易版 |
| 曲全体の物語 | 既存の強化 | 写しに同時押し・フリック・一発を含める／繰り返すたびの発展の操作を少数用意する／ラスサビ。EASY には発展を入れない |
| 横FLICK | 賛成。手の動きから決め直す | 親指は外向きがいちばん楽。①近くの次のノーツへ ②来た向きへ払い抜ける ③取る手の外向き ④旋律の上下は最後の決め手。同じフレーズは同じ向き。付けたら手のシミュレートをやり直す。語彙は「連なりの締め」「SLIDEの続き」「フィルの締め」程度に絞る |
| 単調さの見張り | 賛成。数える単位を変えるのが本題 | 形の名前でなく、レーンの動きとリズムの並びを4小節・8小節で数える。区切りごとの主役の種類を音から決める |
| 気持ちよさの評価 | 賛成。重みは感想で合わせてから | 手の折り返し・無駄な持ち替え・SLIDEの着地・FLICK後の次の動き・画面上の重なり・動きと旋律の向きの一致 |
| 自己批評と区間の手直し | 正しい。段階を踏む | 区間ごとの点数 → 複数候補から区間ごとに継ぎ合わせる（継ぎ目は手のシミュレートで確かめる）→ 区間だけの作り直し |
| 難易度ごとの別の遊び方 | 一部賛成 | 背骨（強拍・区切りの一発）は全難易度で共通、上乗せの層だけ難易度で変える。EASY を主旋律にするのは反対（歌のリズムは食い気味で読みにくい） |
| AI・機械学習 | 解析の段だけ | 音源分離・拍の推定の二つ目の意見・歌の有無。生成と保証はルールのまま。学習した採点役は感想が数百区間たまってから |

## 5. 人の手直しゼロに向けた壁（順に）

1. 拍の格子の自動確定（外れると全部崩れる。いまは半数の曲で人が確かめている）
2. 正解データが無い（譜面メモ0件）
3. 物差しが満点近くに張り付いている
4. 音の役割が分からない
5. 区間だけ作り直せない作り

難易度の決め方（`challengeFactor`）は運用ルールでユーザーが決める（⑥-3）。技術の壁ではなく決めごととして残る。

## 6. 進め方と進み具合

各段は1つ以上のPRで公開する。**段が終わったら、ここの印と「結果」を書き換える。**

### 段0 物差し（ツールだけ・譜面は変わらない）

- [x] 区間ごと（8秒。譜面メモと同じ区切り）の点数 → 品質の6軸とは別の道具 `tools/mode/rhythm-chart-feel-report.js` にした（重みが感想と合うまで6軸を動かさないため）
- [x] 単調さ: リズムが違うのに同じ動きの並び（ノーツ5個ぶん）が直前4小節・8小節に出る割合
- [x] 横FLICKの自然さ: 向きが ①次のノーツ ②来た向き ③外向き と合うか、もう片方の指へ向かって払っていないか
- [x] 手の流れ: 1本の指の急な切り返し・SLIDE の荒い着地（両手の交差は測れなかった。下の「分かったこと」）
- [x] 盛り上がりと密度の一致（`intensityDensityAgreement`）を表に出す（点数へ入れるのは感想と合わせてから）
- [ ] 判断の材料: ユーザーが遊んで気になった区間を3〜5か所もらい、新しい物差しがそこを高く出すかを見る → 重みを合わせる
- 結果（2026-09-26・公開中の曲の MASTER）:
  - **横FLICKの向きが自然なのは25〜71%（多くは30〜50%台）**。1曲あたり1〜11本は、もう片方の指へ向かって払っている。遊んだ感想「向きがバラバラ」と合う
  - 単調さ（8小節の窓）は曲で1〜18%と差が出た（多いのは dullahan・crossing_field・kaze_ga_soyogu）
  - 1本の指の急な切り返しは、どの曲もほぼ0。荒い着地は SLIDE の終わり0〜3件
  - **分かったこと: 手のシミュレートは親指の左右を区別しない。** 近いほうの指で取るので、指の番号で数えると EASY でも毎分40回「両手が交差」と出る。
    実際の親指は交差しにくいので、手のモデルに左右の区別（交差に費用）を入れるのを段1へ足した

- [x] フレーズの写しで FLICK・区切りの一発を揃える（同時押しは元の位置と同じ点で選ばれやすくするところまで）
- [x] 6レーンの中央（`2` の直書き3か所）を `CENTER_LANE=(LANES-1)/2` にする
- [x] （調べていて見つけた）手のモデルが SLIDE をゲーム本体と同じ座標で読む（Rev.8 の譜面だけ切り替える）
- [x] （調べていて見つけた）作り方の改良と学び直しの番号がぶつからないようにする（学び直しは作り方の最新＋1）
- [ ] 終点フリック・HOLD の太さの形を音で決める（効果が小さいので後回し）
- [ ] 手のシミュレートに親指の左右を持たせる（交差に費用）。いまの横フリックは「もう片方の指の位置」で外向きを決めている
- [ ] 公開のときの `rhythm-overlap-reach-fix.js` が TAP を動かしたあと、横フリックの向きを付け直す（Rev.8 で残るのは23曲で5組）
- 結果（2026-09-26・公開中の23曲を Rev.8 で作った実測。詳細は `RHYTHM_CHART_DESIGN.md` 3.1.22）:

  - SLIDE を押さえている指から1レーン未満の TAP は EXPERT 23 → 0組・MASTER 40 → 5組

  - Rev.7 以前の生成結果は全26曲で1バイトも変わらない
  - **公開中の曲は作り直していない**（⑩-2）。作り直すかはユーザーが決める。新しく足す曲から Rev.8 になる

### 段2 解析を足す（別ファイル・既存の解析は作り直さない）

- [x] 打楽器と音程楽器の分離（HPSS）と、16分ごとの層の強さ（音程楽器・打楽器・歌や主旋律の帯・高い打楽器）→ `tools/mode/rhythm-audio-layers-v3.js`
- [x] 8kHz より上を見る（層の解析は 32kHz で読む。既存の解析は 16kHz のまま）
- [x] キック・スネア・ハイハットの分類（検証音では正しい。**実際の曲では参考値**。下の「分かったこと」）
- [ ] 歌の有無（仕組みなしでは当てにならないので保留。段3で「歌や主旋律の帯の音程楽器」の強さで足りるかを先に見る）
- [ ] テンポの二つ目の意見（候補が紛らわしい曲を減らす）
- 結果（2026-09-26）:
  - 書き出しは `authoring/<曲>-v3-layers.json`（既存の `*-v3-audio.json` は読むだけ）。**まだどの曲も書き出していない**。
    段3で生成器が使うときに作る（全26曲で約3MB。使う前から持たない）
  - 打楽器の分類の作りで外したこと: 「直前との差」で測ると、ベースが鳴り続けている所のキックは差が小さく、無音から鳴るベースが大きく出た
    （検証音で裏拍のベース64件すべてをキックと呼んだ）。いまは「低域のうち打楽器成分の割合」でベースと分け、線は曲ごとに大津の方法で決める
  - **分かったこと: 実際の曲での分類はばらつく。** 2・4拍目にスネアが来る割合は kaze_ga_soyogu 78% と筋が通る一方、freedom_dive では
    キックの5%しか拍の頭に来ない。正解（耳で確かめた区間）が無いまま数字を合わせ込むと根拠の無い調整になるので、
    **分類は生成器に使わない**。使うのは物理量だけで決まる層の強さ（HPSS）から
  - **気になること（ユーザーに確認したい）: freedom_dive の拍の格子。** 低音の打点は16分の位置0（拍の頭）に集まるのに、
    大きな一発（`FULL`）75個は全部16分の裏（位置1と3）にある。曲の作りならそのままでよいが、拍の頭が16分1つぶんずれている可能性もある
  - 解析の読み込み（`rhythm-audio-decode.js`）が、Node 本体と同じ場所の全体用の Playwright も探すようにした。
    クラウドの作業環境で `rhythm-audio-analyze-v3-check` と `rhythm-held-pair-variety-check` が落ちていた原因

### 段3 Rev.9 主役の追跡と難易度ごとの層

- [x] 小節ごとの層の強さ（段2の `*-v3-layers.json`）から「ドラム / 歌・主旋律 / 混ざり」のどれを追うかを決める（`tools/mode/rhythm-chart-focus.js`。
      切り替えにコストを付けて動的計画法で並べる。フレーズの境目では安く切り替えられる）
- [x] 追っている層に合う打点を、拾う優先度で後押しする（難易度によらず同じ後押し＝下の難易度は上の部分集合のまま）。Rev.7 の作法 `layer_follow` は止める
- [x] パイプラインが Rev.9 以降の曲で、書き出すときに層の解析を作る
- [ ] 難易度ごとの上乗せの層（背骨は共通、上乗せだけ難易度で変える）。部分集合の決まりとぶつかるので、主役の追跡の感想を聞いてから決める
- 結果（2026-09-26・5曲を Rev.8 / Rev.9 で作った実測・自動修正後）:
  - ドラムを追う小節で打楽器寄りの打点（その曲の上位4割）は 46% → 50〜55%、メロディを追う小節で音程のある打点は 2〜4ポイント増
  - ノーツの置く位置が変わるのは 5〜13%（上の難易度ほど小さい。もともとほとんどの打点を拾うので選び直す余地が少ない）
  - 品質の6軸は MASTER の「流れ」88→93、ほかは ±1.5 以内。押せない配置は0のまま
  - 作りで外したこと: 打点の打楽器成分の割合をそのまま使い 0.5 を境にしたら、ほとんど効かなかった（割合の中央値は曲によって 0.08〜0.18）。
    その曲の打点の中の順位に直して効くようにした
  - 主役の並びは4〜8小節ほどのまとまりで移る。区切りの頭より1小節早く切り替わる所があり、構造解析の区切りのずれか、フィルを拾っているのかは遊んで確かめる
