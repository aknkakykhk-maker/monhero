# モンヒロビートのカクつき: 切り分けの記録(2026-09-12)

ユーザー報告「ノーツの落ちてくるときのカクカクが強くなった気がする。
今回の土台見直しの中で何か心当たりある？」

**結論: 土台見直し(`claude/execution-plan-next-step-*` の一連の作業)は原因ではない。**
ただし**どのコミットが原因かは、この環境の実測では特定できない**(下記「測定の限界」)。

> ## ⚠️ この文書の前の版は誤っていた
>
> 最初「#1328(ライフとコンボの強調)でフレームレートが12%落ちた」と書いたが、**撤回した**。
> 根拠にしたのは各コミット2回ずつのフレーム数(300/289 → 282/271 → 267/264)だったが、
> **同じコミットを5回測ると 244〜308 とばらつく**。差ではなく揺れを読んでいた。
> ユーザーからも「ライフ、コンボをいじる前からだから、そこは関係ない」と指摘された。
> **ばらつきの幅を確かめる前に、2回の測定で結論を出したのが誤り。**

## 土台見直しが原因でない根拠

### ① 演奏中の処理をほとんど触っていない

ノーツの描画と判定の実体は `monster-hero/data/rhythm-mode.js` と
`monster-hero/src/parts/30-rhythm-play.jsx`。この2つを触った直近15件のうち、
土台見直し由来は **`40a41e84` の1件だけ**で、残りはすべて音ゲー側の作業。

### ② その1件も、演奏中には走らない

`40a41e84` が `30-rhythm-play.jsx` へ入れたのは1行だけ。

```js
// 画面に対して極端に小さいプレイエリアは「まだ組み上がっていない」とみなす
if(viewportHeight>0&&areaRect.height<viewportHeight*0.25)return false;
```

これは `rhythmTravelLooksReady`(組み上がったかの判定)の中で、`measureTravel` から呼ばれる。
`measureTravel` は **`ready` のときだけ結果を覚える**ので、`ready` が false のあいだは
毎フレーム `getBoundingClientRect()` を3回呼ぶ(＝強制同期レイアウトが毎フレーム走る)。
条件を厳しくしたぶん、ここが false のままになると重くなる——という筋はあった。

**実測したら起きていなかった。** 演奏中の `getBoundingClientRect` は
**1フレームあたり 0.03回**(6秒で8回)。キャッシュが効いている。

### ③ Tailwind の静的化(#1326)も差が出ない

「いまの配信CSS(111KB・2820ルール)」と「その画面のクラスだけのCSS(11KB・1406ルール
＝以前のCDNのJIT相当)」を同じ条件(CPU 1/4)で比べた。

| | 配信CSS | CDN相当 |
| --- | --- | --- |
| フレーム間隔 中央 | 16.7ms | 16.7ms |
| フレーム間隔 p95 | 33.4ms | 33.4ms |
| スタイル再計算 | 214ms | 237ms |
| JS | 725ms | 753ms |

見た目も、演奏画面の骨格8要素・3695項目の computed style を突き合わせて、
違いは判定ラインの脈動アニメの位相(0.3px)だけだった。

理屈も合う。演奏中は canvas に描くだけでDOMがほとんど変わらないので、
スタイル再計算はスコア・コンボの更新ぶんしか走らない。ルールが増えても、
マッチしないものはブラウザ側のインデックスで弾かれる。
むしろ以前の Play CDN は MutationObserver でDOMを見張り続けていたので、
静的化でその負担は**無くなっている**。

## 測定の限界(いちばん大事なところ)

`node tools/mode/rhythm-live-frame-report.js --cpu 4` を**同じコミットで5回**:

```
300 / 298 / 292 / 288 / 251 フレーム   (6秒・CPU 1/4)
```

**幅17%。** 1フレームあたりのJS時間でも 2.25〜2.93ms と25%ぶれる。
つまり**この環境では、10〜20%程度の差は見分けられない**。

- **2回や3回の測定で「落ちた」と言わないこと。** 必ず `--runs 5` 以上で中央値を見る
- それでも埋もれる差はあるので、**実測でコミットを絞り込むのは筋が悪い**
- 代わりに「1フレームで何回呼ばれるか」を数える(環境に左右されない)

## 数えて分かっていること(環境に左右されない値)

1フレームあたり(`--draw` / 位置の測り直し):

```
drawImage 9.8〜11.7回 / fill 6.5〜7.7回 / stroke 3.3〜3.9回
グラデーション作成 4.9〜5.5回
getBoundingClientRect 0.03回   ← 測り直しは起きていない(正常)
```

**グラデーションを毎フレーム5回前後作り直している**(`data/rhythm-mode.js` の
14105 / 14142 / 14168 / 14193 / 14243 行)。#1327 が直した「スプライトの引数を
毎フレーム作り直さない」と同じ形の無駄が、グラデーション側に残っている。
座標が毎フレーム変わるので単純なキャッシュは効かないが、
`translate` してから固定座標で作れば使い回せる余地はある。

また、CPU 1/4 のとき**長いタスク(50ms以上)は0〜2回しか無いのにフレームは最大183ms飛ぶ**。
JSが詰まっているというより、描画側(ラスタライズ・合成)で待たされている形。
