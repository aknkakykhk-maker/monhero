# モンヒロビートのカクつき: 切り分けの記録(2026-09-12)

ユーザー報告。

> 「ノーツが落ちてくるのが今までより少しかくついて見える。ノーツ側に何かありそう」
> 「モンスターノーツ踏んだときは明らかに固まったり飛ぶ」「毎回じゃなくてたまに」

**まだ直していない。** 原因の性質までは確定したが、最後の一点(何の描画が重いか)は
実機でしか測れないので、総当たりできる逃げ道を用意したところ。

## 確定したこと

### ① JavaScript は無罪

実機(iPhone・4G・1曲163秒)で、33msを超えたフレーム40件をそのまま控えた結果:

```
2.3s 47ms tick 0ms 遅れ 0ms 走査2/描画2 モンスター後 —
4.0s 37ms tick 1ms 遅れ 0ms 走査3/描画3 モンスター後 —
   …40件すべて tick 0〜1ms・遅れ 0ms・走査1〜9個
```

**飛んだフレームでJSはほとんど何もしていない。** 原因は描画側(GPUの合成・
ラスタライズ)かブラウザの外。

### ② 正体は「1.3秒に1回、1フレームだけ落ちる」

飛びはすべて34〜47ms。ほぼ「2フレーム分」＝1フレーム落ち。数字も合う。

```
平均59.2fps        → 1秒あたり0.8フレーム落ち
33ms超 124回/163秒 → 0.76回/秒
```

ドカッと固まるのではなく、**描画が16.67msにほんのわずか間に合っていない**。
これが「ノーツが少しカクつく」の正体。

### ③ モンスターノーツは「踏んだ直後」に4回中2回

```
30.4s  36ms  モンスター後   37ms   ← 踏んで2フレーム後
65.1s  49ms  モンスター後   50ms   ← 踏んで3フレーム後
```

**軽量モードでも起きる**ので、光や画面全体のフラッシュではない。
判定処理そのものも 1.29〜3.00ms と軽い(setView による React の再描画は
次のフレームで起きるので、この数字には入っていない)。

### ④ canvas の解像度は主因ではない

軽量モード(dpr 3→2・画素数44%減)で測っても、ほぼ変わらない。

| | 通常 | 軽量 |
| --- | --- | --- |
| 33ms超 | 124 | 96 (-23%) |
| 25ms超 | 448 | 528 (+18%) |
| 平均fps | 59.2 | 59.1 |

## 外れた仮説(測って否定したもの)

1. **Tailwind の静的化(#1326)** … 配信CSSとCDN相当でフレーム間隔も computed style も一致
2. **#1328 ライフとコンボの強調** … 測定のばらつきを差と読み違えた。撤回済み
3. **曲の時刻の粗さ** … 実機で「進まないframe 0.0%」。完璧に滑らかだった
4. **モンスターノーツの判定処理** … 1.29〜3.00ms。ふつうのノーツより軽い回もある
5. **ヒットエフェクトの発動(will-change が無い)** … 本番の関数で12回出して
   12回とも16.6〜16.7ms。1フレームぶんの遅れも出ない
6. **canvas の解像度** … 上の④

## この環境では測れないもの

**プレイエリアの装飾の合成コストは、ここでは判定できない。**
ヘッドレスのLinuxはGPU合成が実機のiPhoneと別物で、

- CPUを1/4に絞る → 全条件で30fpsに飽和して差が出ない
- 絞らない → 全条件で60fps・33ms超0回で差が出ない

という結果になった(`blur` あり/なし、`drop-shadow` あり/なし、層そのものを消す、
の5条件で比較)。

**あわせて、このサンドボックスでは曲が一度も鳴らない**
(`AudioContext.currentTime` の読み出し0回・`playing:[]`)。
ここでの実測は「無音で演奏した場合」の数字でしかない。

## いま用意してあるもの(実機で総当たりする)

デバッグ画面の**赤いパネル「装飾を切って切り分ける」**で、次の演奏から個別に消せる。

| トグル | 何を消すか |
| --- | --- |
| 上の光（blur 12px） | `[data-rhythm-play-area]::after` |
| 奥行きの格子（drop-shadow） | 同 `::before` |
| 背景のグラデーション3層 | 同 `background` と `inset box-shadow` |
| レーンの影と縁 | `[data-rhythm-lane]` の `filter`/`box-shadow`/`::before` |

**ONにして1曲プレイ → 性能計測の「33ms超」を見る。減ったものが原因。**
まず4つ全部ONで、装飾が原因かどうか自体を確かめるのが早い。

保存は新しいキー `mh_rhythm_strip_v1`。既存の音ゲー設定・BESTには触らない。

## 道具

```
node tools/mode/rhythm-live-frame-report.js --cpu 4 --runs 5 --draw
```

本番の index.html を開いて実際に演奏させ、フレーム間隔・スタイル再計算・
canvasへの描き込み回数・位置の測り直しを測る(報告だけ)。
`--compare` はCSSの切り分け、`--inject-css` は静的CSS以前のコミットを測るため。

> ⚠️ **この環境のフレーム数は同じコミットでも244〜308とばらつく(幅17%)。**
> 2〜3回の測定で「落ちた」と言わないこと(実際にそれで誤った結論を出した)。
> `--runs 5` 以上で中央値を見るか、そもそも「1フレームで何回呼ばれるか」を数える。

## ついでに見つけたもの(主因ではない)

```
先頭スキップ/frame  299.7
```

毎フレーム、終わったノーツを約300個ぶん読み飛ばしている。曲が進むほど増える作り。
`tick処理/frame 0.39ms` と軽いので急がないが、素直に直せる無駄ではある。

## 実装上の注意

`RHYTHM_STRIP` は `RHYTHM_PERF` の**後ろ**へ置くこと。あいだに入れると
`rhythm-perf-check.js` の切り出し(`const RHYTHM_PERF_KEY=` から最初の `})();` まで)が
そこで止まり、「RHYTHM_PERF is not defined」で落ちる(実際に踏んだ)。

> ⚠️ 音ゲーの描画は別の会話でも触っている。**手を入れる前に担当を決めること。**

## 直したもの(2026-09-12 19:54)

**コンボ枠の脈動が、軽量モードでも演出量MINIMALでも止まっていなかった。**

`index.html` の演奏画面CSSには2026-09-07から

> 脈動は `opacity` だけ。`box-shadow` をキーフレームで変えると、モンスターノーツが
> 見えているあいだ毎フレームぼかしを描き直す

と書いてあるのに、**守れているかを見る検査が無かった**。唯一の違反が
`mhRhythmComboGlow`(ぼかし 2px→12px)と `mhRhythmComboGlowHot`(3px→14px→24px)で、
しかも HUD は `[data-rhythm-play-area]` の**外の兄弟**なので、
プレイエリア配下へ書いた軽量モードの打ち消しが1つも届いていなかった。

- 演奏画面の根(`<main data-rhythm-tap-test>`)へ `data-rhythm-lightweight` /
  `data-rhythm-effect` を出し、その目印で HUD 側も止めた。**通常モードの見た目は変えていない**
- 見張りを新設: `node tools/mode/rhythm-keyframe-blur-check.js`

> **これは主因ではない。** コンボ枠は 62.6×41.0px(canvas の1.7%)で、200コンボ以降しか
> 走らず MISS で 0 に戻る。「曲の序盤から1.3秒に1回、1フレームだけ落ちる」という症状と形が合わない。
> 直したのは「ルール違反」と「軽量モードの設定の抜け」の2つ。
