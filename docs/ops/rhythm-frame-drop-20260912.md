# モンヒロビートのカクつき: 切り分けの記録(2026-09-12)

ユーザー報告。

> 「ノーツが落ちてくるのが今までより少しかくついて見える。ノーツ側に何かありそう」
> 「モンスターノーツ踏んだときは明らかに固まったり飛ぶ」「毎回じゃなくてたまに」

**まだ直していない。** 原因の性質までは確定したが、最後の一点(何の描画が重いか)は
実機でしか測れないので、総当たりできる逃げ道を用意したところ。

## 確定したこと

### ① JavaScript は無罪

実機(iPhone・4G・1曲163秒)で、33msを超えたフレーム40件をそのまま控えた結果:

```
2.3s 47ms tick 0ms 遅れ 0ms 走査2/描画2 モンスター後 —
4.0s 37ms tick 1ms 遅れ 0ms 走査3/描画3 モンスター後 —
   …40件すべて tick 0〜1ms・遅れ 0ms・走査1〜9個
```

**飛んだフレームでJSはほとんど何もしていない。** 原因は描画側(GPUの合成・
ラスタライズ)かブラウザの外。

### ② 正体は「1.3秒に1回、1フレームだけ落ちる」

飛びはすべて34〜47ms。ほぼ「2フレーム分」＝1フレーム落ち。数字も合う。

```
平均59.2fps        → 1秒あたり0.8フレーム落ち
33ms超 124回/163秒 → 0.76回/秒
```

ドカッと固まるのではなく、**描画が16.67msにほんのわずか間に合っていない**。
これが「ノーツが少しカクつく」の正体。

### ③ モンスターノーツは「踏んだ直後」に4回中2回

```
30.4s  36ms  モンスター後   37ms   ← 踏んで2フレーム後
65.1s  49ms  モンスター後   50ms   ← 踏んで3フレーム後
```

**軽量モードでも起きる**ので、光や画面全体のフラッシュではない。
判定処理そのものも 1.29〜3.00ms と軽い(setView による React の再描画は
次のフレームで起きるので、この数字には入っていない)。

### ④ canvas の解像度は主因ではない

軽量モード(dpr 3→2・画素数44%減)で測っても、ほぼ変わらない。

| | 通常 | 軽量 |
| --- | --- | --- |
| 33ms超 | 124 | 96 (-23%) |
| 25ms超 | 448 | 528 (+18%) |
| 平均fps | 59.2 | 59.1 |

## 外れた仮説(測って否定したもの)

1. **Tailwind の静的化(#1326)** … 配信CSSとCDN相当でフレーム間隔も computed style も一致
2. **#1328 ライフとコンボの強調** … 測定のばらつきを差と読み違えた。撤回済み
3. **曲の時刻の粗さ** … 実機で「進まないframe 0.0%」。完璧に滑らかだった
4. **モンスターノーツの判定処理** … 1.29〜3.00ms。ふつうのノーツより軽い回もある
5. **ヒットエフェクトの発動(will-change が無い)** … 本番の関数で12回出して
   12回とも16.6〜16.7ms。1フレームぶんの遅れも出ない
6. **canvas の解像度** … 上の④

## この環境では測れないもの

**プレイエリアの装飾の合成コストは、ここでは判定できない。**
ヘッドレスのLinuxはGPU合成が実機のiPhoneと別物で、

- CPUを1/4に絞る → 全条件で30fpsに飽和して差が出ない
- 絞らない → 全条件で60fps・33ms超0回で差が出ない

という結果になった(`blur` あり/なし、`drop-shadow` あり/なし、層そのものを消す、
の5条件で比較)。

**あわせて、このサンドボックスでは曲が一度も鳴らない**
(`AudioContext.currentTime` の読み出し0回・`playing:[]`)。
ここでの実測は「無音で演奏した場合」の数字でしかない。

## いま用意してあるもの(実機で総当たりする)

デバッグ画面の**赤いパネル「装飾を切って切り分ける」**で、次の演奏から個別に消せる。

| トグル | 何を消すか |
| --- | --- |
| 上の光（blur 12px） | `[data-rhythm-play-area]::after` |
| 奥行きの格子（drop-shadow） | 同 `::before` |
| 背景のグラデーション3層 | 同 `background` と `inset box-shadow` |
| レーンの影と縁 | `[data-rhythm-lane]` の `filter`/`box-shadow`/`::before` |

**ONにして1曲プレイ → 性能計測の「33ms超」を見る。減ったものが原因。**
まず4つ全部ONで、装飾が原因かどうか自体を確かめるのが早い。

保存は新しいキー `mh_rhythm_strip_v1`。既存の音ゲー設定・BESTには触らない。

## 直したもの(2026-09-12 19:54)

**コンボ枠の脈動が、軽量モードでも演出量MINIMALでも止まっていなかった。**

`index.html` の演奏画面CSSには2026-09-07から

> 脈動は `opacity` だけ。`box-shadow` をキーフレームで変えると、モンスターノーツが
> 見えているあいだ毎フレームぼかしを描き直す

と書いてあるのに、**守れているかを見る検査が無かった**。唯一の違反が
`mhRhythmComboGlow`(ぼかし 2px→12px)と `mhRhythmComboGlowHot`(3px→14px→24px)で、
しかも HUD は `[data-rhythm-play-area]` の**外の兄弟**なので、
プレイエリア配下へ書いた軽量モードの打ち消しが1つも届いていなかった。

- 演奏画面の根(`<main data-rhythm-tap-test>`)へ `data-rhythm-lightweight` /
  `data-rhythm-effect` を出し、その目印で HUD 側も止めた。**通常モードの見た目は変えていない**
- 見張りを新設: `node tools/mode/rhythm-keyframe-blur-check.js`

> **これは主因ではない。** コンボ枠は 62.6×41.0px(canvas の1.7%)で、200コンボ以降しか
> 走らず MISS で 0 に戻る。「曲の序盤から1.3秒に1回、1フレームだけ落ちる」という症状と形が合わない。
> 直したのは「ルール違反」と「軽量モードの設定の抜け」の2つ。

## 原因が1つ見つかった(2026-09-12 20:55)— CSSを読むだけで分かった

ユーザー指摘。

> その4つだけでかくつきが起きるってのがそもそもピンとこないんだけど。大した演出じゃないよね？
> 演出の出し方に問題ある方を疑うんだけどそういう発想ある？
> ここまでおおがかりな調査が必要な案件とは思えない

**そのとおりだった。** 「装飾を切ったら半分になった」から言えるのは
「**その装飾が毎フレーム塗り直されている**」であって「装飾が重い」ではない。
あれは全部**静止している絵**で、本来は1度描けば使い回せる。
毎フレーム作り直されているなら、**出し方のほうがおかしい**。

読み直したらすぐ出てきた。

```css
[data-rhythm-lane]::after {
  filter: blur(4px);
  transition: opacity 60ms linear, filter 60ms linear;   /* ← ぼかし半径を補間している */
}
[data-rhythm-lane][data-pressed="true"]::after {
  filter: blur(1px);                                      /* ← 押すと 4px → 1px */
}
[data-rhythm-lane][data-pressed="true"] { filter:brightness(1.15) drop-shadow(1px 0 …); }
```

**ノーツを1回叩くたびに、そのレーンで filter のトランジションが2本、60msかけて走る。**
曲中は絶え間なく叩くので、**常にどこかのレーンでぼかしが作り直され続けている**。

これは `index.html` に自分で書いてある禁止事項そのものだった。

> 脈動は `opacity` だけ。`box-shadow` をキーフレームで変えると、毎フレームぼかしを描き直す

同じ日に作った `rhythm-keyframe-blur-check.js` が `@keyframes` しか見ておらず、
**`transition` で同じことをしている箇所を丸ごと見逃していた**。検査の穴。

### 直したもの(見た目は1画素も変わらない)

| 場所 | 前 | 後 |
| --- | --- | --- |
| `[data-rhythm-lane]::after` | `transition:opacity 60ms, filter 60ms` | **`transition:opacity 60ms`**(filter は切り替わる瞬間の1フレームだけ) |
| レーンの `transition`(JSX) | `background-color, box-shadow, filter, border-color` | **filter を外す** |
| サブレーンの光10枚 | `willChange:'opacity'` を常時 | **外す**(押していないあいだも10枚が居座っていた) |

`filter` そのものは残してある。**静止している filter は1度描けば使い回せる**ので、
問題なのは「変わること」のほう。だから `transition` から外すだけで足りる。
画素比較(`rhythm-decor-pixel-check.js`、押したレーンも含む)で**最大差0・平均差0**を確認済み。

### 検査を広げた

`rhythm-keyframe-blur-check.js` に2つ足した。

- ③ 演奏画面の `transition` に `filter` を入れていない(CSSとJSXの両方)
- ④ 演奏画面で `will-change` を条件なしに付けていない

どちらも**わざと元の書き方へ戻して落ちること**を確かめてある(空振りしていない)。
③はセレクタの拾い方を一度まちがえて「演奏画面の外」と誤って通したので、
コメントを長さごと空白へ潰してから拾う形に直した。

### まだ分かっていないこと

これで**どれだけ減るかは実機で測るまで分からない**。
装飾4つを切ったときの半減(25ms超 448→214)のうち、どれだけがこれだったのか。
残りが大きいなら、次に疑うのは同じ形のもの
(`::before` の `clip-path`＋`filter` の併用、背景の `box-shadow:inset 0 -42px 80px`)。
どれも「静止しているのにキャッシュされていない」という同じ話なので、
測る道具を増やすより**CSSを読んで直す**ほうが早い。

## 事前準備でどこまで消えるか（2026-09-12 21:39）

ユーザーの問い「演奏前に事前ダウンロードみたいな機能をいれて終わってから演奏開始とか意味ない？」
「そんぐらいならそもそもダウンロード時間もあってないようなもの？」への答え。

### ダウンロードは0バイト

| もの | いつ用意しているか |
| --- | --- |
| 曲の音源 | `startRhythmTrack(...,{autoStart:false})` を **await してから**開始 |
| 曲えらびのジャケット | 曲えらびを開いたときに読み終わっている |
| 譜面 | 起動時（`index.html` の `SIZES`） |
| ヒットエフェクトの器10個 | `beginRun` で先に作る（`rhythmEnsureHitEffects`） |
| タップ音 | 最初のタッチで `warm()` |

**読み込み画面を足しても出すものが無い。** 残っていたのは通信ではなく「描画の準備」だった。

### 残っていたのは光のスプライト

`glowSprite` / `auraSprite` / `arrowSprite` は id でキャッシュしており、
**その種類のノーツが曲の中で初めて出た瞬間**に作っていた。
モンスターノーツは3枚（glow + 外アウラ + 内アウラ）をまとめて作るのでいちばん重い。

`node tools/mode/rhythm-canvas-note-cost.js` で測った枚数（時間は機械の調子で揺れるので枚数で見る）。

| | 曲の中で作られる枚数 |
| --- | --- |
| 先焼きなし | **11枚** |
| 先焼きあり | **0枚** |

先焼きの11枚が、描くのに必要な11枚とぴったり一致する（検査が見張っている）。

### 直したもの

`RHYTHM_CANVAS_RENDERER.warmSprites(options)` を足し、`beginRun` で
`rhythmEnsureHitEffects` の隣から呼ぶ。**READY→3→2→1 のカウントダウンが3.2秒あるので、
そこへ黙って寄せればプレイヤーには見えない。画面もUIも増やしていない。**

⚠️ 渡す値は実際に描くときと同じでなければならない。スプライトのキャッシュのキーは
「種類と画素密度」だけなので、違う色・太さで焼くとそのまま曲の終わりまで使われる。
画素密度も `begin()` と同じやり方で決める（食い違うと最初の `begin()` が
`sprites.clear()` を呼び、焼いたぶんが丸ごと捨てられる）。

### これで消えるのは「初回だけ」

`③ モンスターノーツは「踏んだ直後」に4回中2回`（上の節）は、
**踏んで2〜3フレーム後**に落ちていて、判定処理そのものは 1.29〜3.00ms と軽い。
先焼きで消えるのは「その種類が初めて出たとき」の1回だけなので、
**毎回の落ちは別の原因**。次に疑うのは `setView` による React の再描画
（モンスターノーツだけ `view.ability` が増えて能力の帯がDOMへ挿し込まれる。
軽量モードでも帯自体は出る＝影だけ消えるので、「軽量モードでも起きる」と符合する）。
