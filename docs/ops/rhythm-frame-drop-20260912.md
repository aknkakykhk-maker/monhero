# モンヒロビートのカクつき: 切り分けの記録(2026-09-12)

ユーザー報告「ノーツの落ちてくるときのカクカクが強くなった気がする。
今回の土台見直しの中で何か心当たりある？」

**結論: Tailwind の静的化(#1326)は原因ではない。** そのあと main へ入った変更で
フレームレートが落ちている。いちばん効いているのは **#1328(ライフとコンボの強調)**。

測ったのは `node tools/mode/rhythm-live-frame-report.js`。
本番の `index.html` をそのまま開いて曲えらびから演奏まで進め、CPUを1/4に絞って6秒測る。
**ヘッドレスのChromiumなので絶対値は実機と違う。同じ条件で並べるための数字。**

## ① Tailwind の静的化は原因ではない

`--compare` で「いまの配信CSS(111KB・2820ルール)」と
「その画面に出ているクラスだけのCSS(11KB・1406ルール＝以前のCDNのJIT相当)」を
同じ手順で測った。CPU 1/4。

| | 配信CSS | CDN相当 |
| --- | --- | --- |
| フレーム間隔 中央 | 16.7ms | 16.7ms |
| フレーム間隔 p95 | 33.4ms | 33.4ms |
| スタイル再計算 | 214ms | 237ms |
| レイアウト | 35ms | 48ms |
| JS | 725ms | 753ms |

**差はゼロか、むしろ配信CSSのほうが速い。** 見た目も、演奏画面の骨格8要素・3695項目の
computed style を突き合わせて、違いは判定ラインの脈動アニメの位相(0.3px)だけだった。

理屈も合う。演奏中は canvas に描くだけでDOMはほとんど変わらないので、
スタイル再計算はスコア・コンボの更新ぶんしか走らない。ルールが増えても、
マッチしないものはブラウザ側のインデックスで弾かれるので1要素あたりの手間はほぼ増えない。
むしろ以前の Play CDN は MutationObserver でDOMを見張り続けていたので、
静的化でその負担は**無くなっている**。

## ② 落ちているのは、そのあと main へ入った変更

同じ条件(CPU 1/4・6秒)で、コミットを変えて測った。6秒で取れたフレーム数が指標。

| 時点 | フレーム数 | 33.3ms超 |
| --- | --- | --- |
| `8ff5a593` Tailwind静的化の直後 | 300 / 289 | 33回 / 41回 |
| `27d32c23` #1328 ライフとコンボの強調 | 282 / 271 | 46回 / 63回 |
| `0021f376` 最新main(#1329〜#1332まで) | 267 / 264 | 51回 / 58回 |

6秒で300フレーム≒50fps、264フレーム≒44fps。**約12%落ちている。**
各2回ずつだが、4測定とも同じ向きに出ている。

**#1328 で大きく落ち、そのあとさらに少し落ちている。**

#1328 が演奏画面へ足したもの:

- `lifeDownCount` / `lifeDownSlam` の `useState` と、それを見る `useEffect`(`setTimeout` 付き)
- 毎レンダリングで `rhythmLifeRatio` / `rhythmLifeState` / `rhythmComboTier` を計算
- HUD へ data 属性と `--mh-combo-scale` を書き込む
- コンボのキーフレームを `scale(calc(var(--mh-combo-scale,1)*1.34))` へ

ライフとコンボは**毎フレーム更新される**表示なので、ここへ state と属性の書き込みが増えると、
Reactの再レンダリングとスタイル再計算がそのぶん増える。

## ③ ほかに見えた手がかり

CPU 1/4 のとき、**長いタスク(50ms以上)は0〜2回しかないのにフレームは最大133〜183ms飛ぶ。**
JSが詰まっているというより、描画side(ラスタライズ・合成)で待たされている形。

1フレームあたりの canvas への描き込み(`--draw`):

```
drawImage 9.8〜11.7回 / fill 6.5〜7.7回 / stroke 3.3〜3.9回 / グラデーション作成 4.9〜5.5回
```

**グラデーションを毎フレーム5回前後作り直している**(`data/rhythm-mode.js` の
14105 / 14142 / 14168 / 14193 / 14243 行)。#1327 が直した「スプライトの引数を
毎フレーム作り直さない」と同じ形の無駄が、グラデーション側に残っている可能性がある。
座標が毎フレーム変わるので単純なキャッシュは効かないが、
`translate` してから固定座標で作れば使い回せる余地はある。

2. canvas のグラデーションを作り直さない形にできるか見る
