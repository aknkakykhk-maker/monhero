# タップ位置の確かめ(描かれた位置と判定が受け付ける位置)— 2026-10-12 深夜

社長「全曲エキスパート以上のノーツのタップ位置の確認作業をして。今まで押しづらいとかうまく反応しないのって判定位置のズレとかあるんじゃない？」
(予約 trig_01E2AjPwkuR8jzkQKmPRL8bB・ビート部テンポくん)

## 結論

- **見えている位置と判定の位置のずれは無かった。** 公開中の全曲の EXPERT・MASTER と HELL の試作2曲(82譜面・41,275ノーツ)を、
  8つの画面の条件で調べた。描かれたノーツの真ん中は、どの条件でも判定の真ん中とぴったり同じ位置(差 0 サブレーン)で、
  **描かれた真ん中を押して取れないノーツは 0**
- 描かれたノーツの左右の端の 10% 内側で取れないのは **2個だけ**(どちらも同じ時刻に2つのノーツが重なって置かれている所。下の「型」の C)
- 「押しづらい・反応しない」と感じる原因になりうるのは位置のずれではなく、次の **判定の決めごと** と **譜面の置き方**
  - A. 押さえている帯のすぐ隣のノーツは、帯の側の端の外(受付の広がり)を押すと「持ち替えの2本目」として控えに回る(2026-09-18 の決めごと)。
    判定ラインより少し下や上を押す人ほど起きやすい(各条件で 14〜17 個)
  - B. 間の短い同じ位置の連打で、間隔の 75% より遅れた叩きは次のノーツへ移る(2026-09-05 の決めごと・Grievous Lady 2分の件)
  - C. 同じ時刻に2つのノーツが重なって置かれている所は、重なった部分をどちらか一方が取る(譜面の置き方)

## 調べ方

1. 描く位置: ゲームの描く口 `RHYTHM_CANVAS_RENDERER.drawNote` に渡る座標(`rhythmNoteCanvasGeometry` の head の中心・幅)を使う。
   GPU で描くときも 2D で描くときも同じ口を通る
   - `tools/playbot/rhythm-tap-position-bot.js` … 曲を実際に流しながら毎コマ控え、判定ラインに来た瞬間に描かれた真ん中を叩く
   - `tools/playbot/rhythm-tap-position-static.js` … 曲を流さず、画面ごとに1回開いて同じ計算を全譜面へ当てる(82譜面で約40秒)。
     実際に流して控えた位置(Grievous Lady MASTER のタップ 527個)と**差 0.00px**
2. 受け付け: 描かれた位置(真ん中・左右の端の 10% 内側、判定ラインちょうど・20px 上・20px 下)を、ゲームの「押した位置→サブレーン」の計算
   (`rhythmSubLaneCoordinateAtPoint`・線より下は `rhythmSubLaneCoordinateAtLineIfBelow` も)に通し、判定の関数 `rhythmMatchInputBatch` が
   そのノーツを相手に選ぶかを見る(`tools/playbot/rhythm-tap-position-report.js`)。前のノーツは取り終え・続いている帯は別の指が押さえ・同じ時刻の和音はまだ、の状態で
3. 実際に流す確かめ: 1本だけで流した Grievous Lady MASTER(636ノーツ)は、描かれた真ん中を叩いて **MISS 0**(MARVELOUS 611・EXCELLENT 23・GREAT 2)。
   何本も並べて流すと叩く時刻が遅れる(コマ詰まり)ので、並べて流したときの MISS はすべて判定の窓(185ms)より遅れた叩きで、位置とは関係ない

## 型

### A. 押さえている帯のすぐ隣のノーツ(決めごと・直していない)
- 例: emerald_rush MASTER 10.91秒のタップ(サブ0〜1)。左手で押さえているホールドがその時刻にサブ1〜4へ太くなっていて、タップの右端の外(1.0〜)を
  押すと持ち替えの2本目として控えに回る。判定ラインの 20px 下を押すと、指の高さで測った位置が外へ 0.3 ずれるので、ここに入りやすい
- 端のレーン(サブ0〜1・10〜12)の幅1のタップに多い。全曲では「帯を押さえている最中のノーツ」2,844個のうち 1,548個がこの形(公開曲の全ノーツの 2.05%)
- 直すなら判定の決めごとの変更(Grievous Lady 2分の報告の案B)。社長の判断待ち

### B. 遅れた叩きが次のノーツへ移る(決めごと・直していない)
- Grievous Lady MASTER 1:58.17 など。位置ではなく時間の型。`docs/playbot/reports/2026-10-11/grievous-2min/`

### C. 同じ時刻にノーツが重なっている(譜面・確かめ済み・直さなくてよい)
公開曲の全譜面で、同じ時刻に横が重なるのは5か所(どれも重なりはサブレーン1本ぶん=半レーン)。
- kiki_issen MASTER 153.66秒: タップ(サブ3〜7)とスライドの押し始め(サブ6〜8)
- 4u_hitasura MASTER 70.55秒: スライド(サブ4〜6)とホールド(サブ5〜9)
- grievous_lady NORMAL 51.38秒・130.53秒、MASTER 55.17秒: タップどうし(サブ3本幅が1本ずつ重なる)

確かめたこと(10/12 テンポくん・`rhythmMatchInputBatch` を毎回作り直して当てた):
- **2本の指で同時に押すと、どの組も2つとも取れる。** 片方の指が重なりの部分に入っても、判定はもう片方の指と合わせて割り振り直す
  (例: 4u で 5.75 と 5 を同時に押す → スライド・ホールドの順に取れる)
- 1本だけで重なりの部分を押すと、相手のノーツ(和音のもう片方)が取る。相手が取れたあとなら、同じ場所を押せば残りが取れる
- 手の物理条件(`rhythm-hand-model.js` の `fingerPairFeasible`)でも、5か所とも「指2本で押せる」
- **4u の「食い違い」は道具の不具合ではなかった。** 集計(`rhythm-tap-position-report.js`)は「同じ時刻の和音はまだ押されていない」状態で1本ずつ当てるので、
  ホールドの左端の内側(5.75)はスライドが取る。前に「取れる」と出たのは、相手のスライドが先に取れた状態で当てたためと見られる(その状態で当てると 146 が取れることは確かめた)。
  使い回し・作り直しのどちらで当てても、同じ状態なら結果は同じ(戻し漏れ 0)
- 重なりが生まれた理由: 4u・kiki は譜面の作り方 Rev.1 のころの曲で、当時の物差しはスライドを半レーン左に見ていた
  (4u は当時の物差しではスライドがサブ3〜5でホールドとちょうど接するだけ。描く位置ではサブ4〜6)。
  生成器は「指2本が入るか」だけを見て、見た目の重なりは見ていない(Grievous Lady は手で置いた譜面)
- 結論: 遊んで取りこぼす形ではないので、公開中の譜面は直さない案。見た目の重なりを今後の生成で避けるかは、別の提案として残す

## 道具の直し(この作業で見つけたもの)
- 判定の関数 `rhythmMatchInputBatch` は、取れた HOLD/FLICK/SLIDE を指の動きを待つ形へ書き換える(FLICK は終わりを60秒先へ)。
  何度も当てて測る道具(`rhythm-note-reach-scan.js` ほか)では、当てるたびに元の形へ戻すようにした。直したあとも、全曲の「押しても取れないノーツ」は 0 のまま
- 前に窓口へ送った「案Bで変わるノーツ 1,970個」はこの書き換えが残って多めに出ていた。正しくは **1,548個(公開曲の全ノーツの 2.05%・EXPERT 783・MASTER 726)**
