# ホールド・スライドの線をコンボに組み込む見積もり(2026-10-17・作らずに調べただけ)

社長(#3152 の演出を見て)「いまいちだねー。やっぱコンボ数に組み込む？」→「まず見積もりだけ」。作: ビート部:部長テンポくん。
データベースは読むだけ(表の形と件数を1回だけ)。

## 0. 今の仕組み(調べた事実)

| もの | 今の作り | 置き場所 |
| --- | --- | --- |
| スコア | `判定の点(90%) + 最大コンボ ÷ ノーツ数(10%)` × 満点(MASTER まで 1,000,000・HELL 1,050,000)。`rhythmCalculateScore({judgments,maxCombo,totalNotes,maxScore})` | `13-bgm-and-rhythm-settings.jsx` / 重みは `RHYTHM_SCORE_WEIGHTS={judgment:.9,combo:.1}` |
| コンボ | 1ノーツにつき +1(GOOD 以上で続く・BAD/MISS で0)。ホールド・スライドは押し終わりの1回で +1 | `rhythmComboAfter`・`30-rhythm-play.jsx` の `run.combo` |
| 線(チェックポイント) | スライドだけにある。判定を下げるためのもの(通った割合で GREAT/GOOD/BAD/MISS)。**細かさは帯の曲がりの点の数で決まる**: 難易度の基準 125〜240ms ごと、ただし曲がりの点ごとに最低1本。HELL の曲がりの多い帯は約45ms ごとで、**1本に267本**ある帯もある | `rhythmSlideCheckpointTimes` |
| 称号 | フルコンボ = BAD と MISS が0 / ALL EXCELLENT / ALL MARVELOUS は判定の数だけで決まる(コンボの数は見ていない) | `rhythmResultAchievements` |
| 自己ベスト(端末) | `mh_rhythm_best_v1` の曲×難易度ごとに `bestScore`・`judgments`・`maxCombo`・称号の印。実績は `mh_rhythm_achievements_v1` | `mergeRhythmBestRecord` |
| ランキング(Supabase) | `rhythm_scores`(送った記録)・`rhythm_song_bests`(曲ごとのベスト)・`rhythm_total_rankings`(合計)・`rhythm_buddy_ranks`(難易度ごとのスコア)。**どれもスコアだけで、最大コンボは持っていない** | `docs/sql/rankings/` |
| ほかにスコアを比べる所 | マルチ(`77-screen-rhythm-multi.jsx`)・レイドジャック(`35-raid-jack.jsx`)・相棒ランク(`33-rhythm-buddy.jsx`)・判定の異変の報告(`rhythm_play_logs` の `note_count`) | |

**どの案でも先に決める必要があること**: 今の線の細かさ(帯の曲がりで決まる・HELL で1本267本)をそのままコンボに数えると、コンボがスライドだけで何千にもなり、曲ごと・難易度ごとの差がでたらめになる。
コンボ用には **別の「刻み」**(例: 4分音符か8分音符ごと、または難易度ごとに一定の間隔)を、譜面から必ず同じ数が出る形で決める必要がある。判定を下げるための今の線はそのまま残す。

## 1. 3つの案で何が起きるか

### 案①: 本格的に組み込む(他の音ゲーと同じ。ランキングは新しい物差し、古い記録は別枠)

| 項目 | 起きること |
| --- | --- |
| スコアの計算 | 刻みも1つの「ノーツ」として数える(押さえている=GOOD 以上、落とした=MISS)。`totalNotes` と `maxCombo` の意味が変わり、判定の点の割合も変わる → **同じ遊び方でもスコアが変わる**(長いスライドが多い曲ほど大きく) |
| 最大コンボ | ノーツ数+刻みの数まで伸びる(曲によって2〜5倍) |
| フルコンボ・称号 | 刻みを1つ落としただけで FC が消える(今より厳しい)。ALL MARVELOUS は刻みをどう判定するかで意味が変わる(刻みは MARVELOUS 扱いにするのが普通) |
| ランキング | 古いスコアと比べられないので、**新しい物差しの表(または `score_version` の列)を足す**。古い表は消さずに読むだけの別枠に。送信処理も新旧で分ける。古い版のままの端末が新しい表へ古い物差しで送らないよう、サーバー側で版を確かめる |
| 端末の自己ベスト | `mh_rhythm_best_v1` の意味を変えてはいけない(⑦)ので、**新しいキー `mh_rhythm_best_v2`** を足す。古いベストは残して「旧記録」として見せる。実績(FC など)も新旧で分けるか決める |
| 古い記録との比べ方 | 曲えらび・ランキングに「新」「旧(〜2026-10)」のタブ。旧は凍結(もう伸びない)。合計ランキング・相棒ランクも新旧2本 |
| ⑦で守れるか | 守れる(足すだけ)。ただし足す物が多い(表・関数・保存キー・画面) |

### 案②: スコアの満点はそのまま(コンボは刻みごとに増え、満点が変わらないよう正規化)

| 項目 | 起きること |
| --- | --- |
| スコアの計算 | 判定の点(90%)は今のまま(1ノーツ1判定)。コンボの点(10%)だけ `最大コンボ ÷ (ノーツ数 + 刻みの数)` に替える。**満点は同じ**。ノーツも刻みも1つも落とさずつないだ人は前も後も「コンボの点が満点」なので**スコアが1点も変わらない**。コンボが切れたプレイだけ、どこで切れたかで上下する(コンボの点は満点の10%=MASTER で10万点の枠。切れ方しだいで数千〜数万点) |
| 最大コンボ | ノーツ数+刻みの数まで伸びる。遊び中の表示と結果の表示は同じ数 |
| フルコンボ・称号 | 判定の数で決める今の決め方のままなら変わらない(ただし「刻みを落としてコンボが切れたのに FULL COMBO」という食い違いが出る)。「刻みを1つも落とさない」も条件に足すなら今より厳しくなる(取った称号は下がらないので、古い FC はそのまま) → **どちらにするか社長の判断が要る** |
| ランキング | **表も送信処理もそのまま**(スコアの満点・意味が同じ)。古い版の端末と新しい版の端末が同じ表に並んでも、全部つないだ上位のスコアは同じ。差が出るのはコンボが切れたプレイだけ(数千〜数万点) |
| 端末の自己ベスト | `bestScore` は同じ物差しなのでそのまま。`maxCombo` は意味が変わるので、**新しい項目(例 `maxComboTicks`)を足す**(既存の `maxCombo` は書き換えない) |
| 古い記録との比べ方 | スコアはそのまま比べられる。最大コンボだけ「刻み込み」と「旧」を分けて見せる(旧は小さく) |
| ⑦で守れるか | 守れる。足すのは自己ベストの1項目と、計算の分母だけ |

### 案③: 遊んでいる間の表示だけ増やす(記録は今の数え方)

| 項目 | 起きること |
| --- | --- |
| スコア・称号・ランキング・自己ベスト | **何も変わらない** |
| 食い違い | 遊び中は「1520 COMBO」なのに、結果の MAX COMBO は「640」。100コンボの節目の演出・フルコンボの演出とも数がずれる。結果に「刻み込みの最大 1520」を別に出せば和らぐが、説明が要る |
| ⑦で守れるか | 守れる(保存するものが無い) |

## 3. おすすめ

**案②**。理由:

- 社長の「他ゲーみたいにコンボが増えていく」がそのまま手に入る(遊び中も結果も同じ数で増える)
- **スコアの満点・ランキングの表・送信処理を変えずに済む**。ノーツも刻みも全部つないだスコアは1点も変わらないので、上位の記録は新旧そのまま比べられる
- ⑦(壊さない・足す)は、自己ベストに項目を1つ足すだけで守れる。データベースの変更が要らない
- 作業は①の半分以下

先に社長に決めてほしいこと:

1. **刻みの細かさ**(おすすめ: 8分音符ごと。テンポの速い曲ほど増える他ゲーと同じ感覚)。今の判定の線(曲がりで決まる・HELL で1本267本)はコンボには使わない
2. **フルコンボの決め方**: (a) 今のまま判定だけで決める(刻みを落としても FC は残るが、表示のコンボは切れる) / (b) 刻みを1つも落とさないことも条件にする(今より厳しい。取った FC は下がらない)
3. コンボが切れたプレイのスコアが数千〜数万点動くこと(古い記録との比べ・古い版の端末が混ざる間)を許すか

①は「スコアの物差しそのものを他ゲーに合わせたい」ときだけ。③は試しに入れて感触を見るだけなら1本で済むが、結果との食い違いが残る。
