# 空中を本物の3Dで描く・段階A(2026-10-16)

社長の判断「すぐ段階Aを始める」(見積もり: [`../floor3d-estimate.md`](../floor3d-estimate.md))。作: ビート部:部長テンポくん。
デバッグ専用(既定は今の見た目のまま)。**位置の式・判定・色・譜面・セーブデータは変えていない。**

## 見方(社長の iPhone)

デバッグ設定を開く → いちばん上の「🧪 確認待ちの試作」→「🎵 空中を本物の3Dで(段階A)」(NEW)の「入」→ 空中のノーツのある曲(HELL)を始める。
どれかの試作の「切」で今の見た目に戻る(試作1〜3と同じキー `mh_rhythm_floor3d_proto_v1`・値 `a3d`)。

## 何をしたか

| | 今 | 段階A |
| --- | --- | --- |
| 空中のタップ | 半透明の板 | **光の当たる立体の箱**(上の面が明るく・手前と側面が暗い・つや)。道の真ん中を向き、斜め上から見下ろした形 |
| 空中スライド | 半透明の帯 | **丸い断面の管**(上につやの線・ふちほど暗い) |
| 影 | 薄い板 | 箱の真下の床に、ふちのぼけた影。スライドの床の影も濃く |
| 地上・道 | — | 今のまま |

- 立体は、面ごとの向き(法線)から光の当たり方を計算して描く(`rhythmCreateGpuSky3d`)。置く場所は今の式が出した画面の位置そのままなので、判定・指の当たり判定は変わらない
- **WebGL の層は増やしていない**。ノーツの WebGL の層(GL2D)の中で、板の部品と同じやり方で描いている
- **描く準備(シェーダーの組み立て)は演奏前**(描き手をつなぐとき)に済ませる
- **WebGL で描いていないとき**(描画方式で Canvas を選んだ・WebGL が作れない・途中で取り上げられた)は、今の見た目で描く
- 空中スライドの帯は、段階Aのときは GPU の帯を使わず CPU で刻む(管の中心線を作るため)

## 重さ(前回と同じ物差し: CPU を4倍遅くした条件・Sheriruth HELL 70〜90秒・横持ち・ノーツを WebGL で描く)

| | 平均 | 95% | 最長 |
| --- | --- | --- | --- |
| 今の見た目 | 107.7 / 114.8ms | 150 / 167ms | 217 / 200ms |
| 段階A | 92.5 / 98.6ms | 150 / 150ms | 200 / 217ms |

関数ごと(1秒あたり ms): 箱 `drawSkyCube3d` 3.9・管 `drawSkyTube3d` 7.3。毎コマの処理 `tick` 230.8 → 243.8(ゆれの中)。
⚠️ 手元のブラウザには GPU が無く、WebGL を CPU で肩代わりしている(とても遅い)ので、数字はどちらも大きい。今と段階Aで悪くなっていないことだけを見ている。
iPhone の本物の GPU での重さはここでは測れない。実機で重く感じたら知らせてほしい。
