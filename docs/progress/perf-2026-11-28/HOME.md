# HOME の重さを測って減らした(2026-11-28・開発部 クラフトくん)

台帳 r1126-104 追記4・追跡表 r1128-072。ビート部の調べ(この README の「追記2」・案H)で、
HOME(裏クイックあり・CPU 4倍遅く)が 11/14 の 236ms/秒から今 517〜708ms/秒になっていた。社長の選択は「見た目を変えずに軽くする」。

## 測り方

`node tools/speed/home-weight-measure.js`(今回作った。リポジトリに入れた)。ビート部と同じ「メインスレッドが1秒のうち何ミリ秒ふさがっているか(TaskDuration)」を、
HOME に着いて6秒おいてから10秒、CPU 4倍遅く・390×844で数える。裏クイックは AUTO 設定の自動開始で HOME から回す(`--quick 0` で回さない)。

- `--anims 1` 動いている CSS の動きを数える / `--pause <名前>` その動きだけ止めて測る / `--css` 試しの CSS を差し込んで測る
- `--profile 1` CPU の記録の上位と、画面を測る呼び出し(elementsFromPoint など)の呼び出し元 / `--at` 時計をずらす / `--shot` 札の動きを同じ瞬間で止めて撮る
- タイマーの数を数える仕掛け自体が約8ms/秒かかる(前と後で同じ条件)

## わかったこと

1. **いちばん重いのは HOME の「開催中」「β版 開幕！」の札の光り方。** 裏クイックなしでも HOME は 464ms/秒あり、JS は 5ms/秒だけ。残りは毎コマの見た目の計算と描き直し
   - 札の脈は `box-shadow` を、光の帯は `left` を動かしていた。どちらも合成(GPU)では動かせず、札が出ているあいだ毎コマ見た目の計算・配置・描き直しが走る
   - HOME で動いている CSS の動き11本のうち、この札の4本を止めるだけで 464 → 97ms/秒(全部止めると 18)
   - 時計を 9:30 にずらした前の HOME でも同じ札が出ていて 678〜733ms/秒。**作り直し(#7958)そのものより、この札が出ている期間(花のイベント・モンヒロサクセス)に重くなった**
2. 裏クイックの分(約 +300ms/秒)は、周回の進みでゲーム全体(`MonsterHeroGame`)が毎秒約13回描き直されるため。HOME の中だけを描き直さない試し(上限)でも 45ms/秒しか減らず、HOME の外の作り。今回は触っていない
3. 小さい物: 成長の札の置き場所探し(`44-growth-fx.jsx` の `place`、elementsFromPoint)が出ているあいだ 10〜25ms/秒、ダイヤの数の書式(`compactCount` の toLocaleString)6ms/秒、曲の公開の判定(`rhythmDemoSongs`)約12ms/秒

## 直したこと(見た目は変えない)

- 札の脈: 大きさ(transform)はそのまま。光の輪は前の2つの形(ふだん・いちばん光る時)を `::before` / `::after` に1枚ずつ描き、透明度で入れ替える
- 札の光の帯: 札の中に空の部品(`.mh-home-event-badge-shine`)を1つ足して札の形に切り抜き、`left` のかわりに `transform` で同じ道のりを動かす
- 黒い縁取り・下の影はその部品へ移し、前と同じく光の輪より上に重ねる。動きを減らす設定の人は前と同じく止まる
- `compactCount`: 書式の部品を1つ作って使い回す(出る文字は同じ)
- 撮り比べ: 動きを 0・0.4・0.8・1.2 秒で止めて前と後を撮り、光の帯の位置・輪・大きさが同じことを目で確かめた

## 前と後(CPU 4倍遅く・390×844・10秒)

| | 直す前 | 直した後 |
| --- | --- | --- |
| 裏クイックなし | 464 / 469 ms/秒 | 146 / 169 ms/秒 |
| 裏クイックあり | 687 / 704 ms/秒(9:30 の前の HOME 678 / 733) | 445〜579 ms/秒(7回・中央 約 500) |

裏クイックありのぶれが大きいのは、裏の戦いの場面(WAVE の切れ目・成長の札が出るか)で変わるため。

## 残り(次の案)

- 裏クイックの進みで全体が描き直される分(約 300ms/秒)。周回の進みを `MonsterHeroGame` の状態から外し、帯だけが聞く形にするのが本筋。60-app と裏クイック(バトル部)にまたがる設計なので、窓口の判断を待つ
- 成長の札の置き場所探しを、帯の数字の書き換えでは走らせない(0.7秒ごとの見直しは残す)
- 曲の公開の判定を毎回の描き直しで全曲ぶん引かない(ビート部の案A・PR #8070 と重なる)
