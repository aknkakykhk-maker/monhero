# ゲームの重さの調べ(2026-11-28・ビート部 テンポくん)

台帳 r1126-104・追跡表 r1128-045。社長「ゲーム自体が重くなってるとかある？」「ゲーム内ダウンロード量も多くなってきたけど最適化できるものないのかな？」「ゲーム自体を軽くする(特にモンビー)方法はないの？」「裏クイック止めたらどうなるの？」→「まずはちゃんと調べて考えて」。

**この資料は調べて案を出すだけ。ゲームの部品は1つも変えていない。** 測った道具は作業用フォルダで動かした使い捨て(リポジトリには入れていない)。
ワルキューレのかくつき(演奏画面の描画のごみ)は別の会話が直しているので、演奏画面の描画には触れない。

## 測った環境と注意

- このコンテナの Chromium(ヘッドレス・Linux)。iPhone ではない。iPhone 相当の目安として CPU を4倍遅くした測りも並べた
- 数字は「メインスレッドが1秒のうち何ミリ秒ふさがっているか」(Chrome の TaskDuration)。1000ms/秒で張り付くと、押しても反応が遅れる・発熱する
- この環境では音が鳴らない・GPU は実機と別物(前の記録 `docs/ops/rhythm-frame-drop-20260912.md` と同じ制約)。演奏画面のコマ落ちそのものはここでは測っていない
- 1回ごとの数字は ±10% ほどぶれる。差が2倍以上あるものだけを「差がある」とした

## わかったこと(大きい順)

### 1. 裏クイックが回っていると、モンヒロビートの「曲の一覧」がずっと重い(いちばん大きい)

同じ画面に10秒いて測った。

| 画面 | 裏クイックあり | 裏クイックなし |
| --- | --- | --- |
| 曲の一覧(CPU そのまま) | 344〜405ms/秒(ほぼ全部 JS) | 8〜49ms/秒 |
| 曲の一覧(CPU 4倍遅く=iPhone の目安) | **938ms/秒(ほぼ張り付き)** | 49ms/秒 |
| モード選び(CPU そのまま) | 47ms/秒 | 42ms/秒 |
| HOME(CPU そのまま) | 108〜148ms/秒 | 81〜88ms/秒 |
| HOME(CPU 4倍遅く) | 708ms/秒 | 414ms/秒 |
| 演奏中(CPU そのまま) | 178〜211ms/秒 | 209〜225ms/秒(差なし) |

- 演奏のあとに曲の一覧へ戻ると、5秒ずつ8回測っても 388〜473ms/秒のまま下がらなかった。**一度きりの山ではなく、裏クイックが回っている間ずっと続く**
- 原因(CPU の記録で特定): 曲の一覧の画面(`29-rhythm-screens.jsx` の `versionsOf`・行の組み立て)が、描き直しのたびに「曲ごとに全曲を見て原曲とショートの組を探す」計算をやり直している。組を探す `rhythmSongVersionGroup`(`data/rhythm-mode.js`)は28組を毎回頭から探す作り。重さの上位2つがこの2つで、合わせて約 180ms/秒
- 裏クイックの進み(WAVE・周回数)はゲーム全体の状態(`MonsterHeroGame`)に持っているので、進むたびに曲の一覧まで丸ごと描き直される、と見られる(記録の上位に React の描き直しが並ぶ)。裏クイックが止まっていれば描き直しが起きないので軽い
- 社長の「モンビーが全体的に重くなってる？」(r1126-100 追記2)の答えの最有力。11/28 10:00 からクリスマスの「ビート5倍(クイックの∞周回を回しながら遊ぶと周回数5倍)」が始まり、裏クイックを回したまま曲の一覧にいる時間が増えた。iPhone では曲の一覧にいる間 CPU がほぼ埋まるので、押したときの反応が遅れ、端末が熱を持ち、そのあとの演奏のかくつきにもつながる(熱で CPU が絞られる)

### 2. 演奏中は、裏で動いている物はほとんど無い(作りのとおり)

演奏中の10秒に、呼び出し元ごとにタイマーと描画の呼び出しを数えた。

- 動いている setInterval は13〜14本。どれも軽い見張り(戻るボタンの見張り・遊んだ時間の記録・長押しの見張りなど)で、合わせて約8回/秒
- requestAnimationFrame は演奏の毎コマの処理(約60回/秒)と、指の動きの処理(約19回/秒)だけ
- **HOME の歩くモンスター・レイドの時計・HOME の札の送り・自動ダウンロード・裏クイックは、演奏中はどれも動いていなかった**。裏クイックは演奏に入ると止まり、曲を最後まで遊ぶと「曲の長さで何周ぶん」をまとめて配る(途中でやめたときだけ、止まっていた分を4倍の速さで追いつく)。作りのとおりだった(`60-app.jsx` の `beginCatchUp` の前後)
- 10:00 のイベント開幕の前(時計を 9:01 にずらした)と後(14:01)で、HOME・演奏中とも差は出なかった(HOME 81 と 88ms/秒・演奏中 225 と 209ms/秒)。**イベント開幕で演奏中の裏の仕事が増えた、ということは無い**

### 3. 起動のたびに読む物が3か月で4.5倍になった

`index.html` の BOOT_SIZES(起動が終わるまでに必ず読む物)の合計。

- 2026-08-28: 6.2MB
- 2026-09-28: 8.8MB
- 2026-10-28: 15.4MB
- 2026-11-14: 23.3MB
- いま(11-28): **27.8MB**(送るときは gzip で約 7.3MB)

いまの内訳(大きい順): 本体 `game-system.compiled.js` 13.2MB(gzip 3.0MB)/ `data/rhythm-mode.js` 7.2MB(gzip 2.0MB)/ `data/assistants.js` 2.3MB / `data/changelog.js` 2.1MB / `data/help.js` 0.9MB / タイトル画像 0.4MB / 見た目の CSS 0.3MB / タイトル曲 0.3MB / ほか。

- 起動の JS の解釈と実行は、CPU そのままで約 0.4 秒、CPU 4倍遅くで約 1.2 秒。**起動の重さの主役は JS の処理より、送る量(gzip で約 7.3MB)**
- 本体は直近7日で246回(1日に約35回)、更新履歴は158回、ヘルプは84回変わっている。ファイルごとに中身の印(`?v=`)が付くので、変わったファイルは事前ダウンロードをしていても取り直しになる。**遊ぶ人は、ほぼ開くたびに本体の約 3MB を取り直している**
- `data/rhythm-mode.js` の約 88%(6.1MB)は全曲・全難易度の譜面。演奏するのは1曲なのに、起動のたびに全部を読み、ずっと持っている。ブラウザで測ると、このファイルを読むだけで JS ヒープが **約 22MB** 増える(起動直後のヒープ約 92MB の4分の1)
- 同じ測りで、助手のデータ +3.6MB・更新履歴 +3.4MB・ヘルプ +1.7MB

### 4. 遊んでいる間のメモリ(漏れ)

`tools/memory-soak.js` の演奏の周回は、曲のあとにページを読み直して HOME へ戻るため、漏れが隠れる(1回目の計測はこれで無効にした)。読み直さずに「結果 → モード選びへ戻る → 戻る → HOME」と戻る写しで測った。ボットが2曲目のあと曲の一覧で止まったため、**きちんと測れたのは1周だけ**。

- 起動直後の HOME: JS ヒープ 42.5MB・画面の部品 450個・イベントの受け口 392個・持っている曲の音 2本・ブラウザの描画のプロセス 741MB
- 1曲遊んで HOME に戻ったあと: JS ヒープ 48.3MB(+5.8)・部品 823個(+373)・受け口 389個(±0)・持っている曲の音 **4本**・描画のプロセス 1,122MB(+381)
- 曲の一覧にいる間は、ジャケットなどの絵 200枚(解いたあとで約 398MB)を出している。HOME に戻ると 32MB に戻るので、これは漏れではなく一覧の画面の山
- 受け口の数は元に戻っているので、画面を作っては捨てる所の漏れは見えない。ヒープの +5.8MB は2周目以降も増え続けるかまでは確かめられていない(**未確定**)
- 増えた分の大半は音。演奏した曲・聞いた曲の音を、HOME に戻っても解いたまま4本まで持っている(数えた限り4本で止まり、それ以上は増えない)。ただし8分より長い曲(ワルキューレの原曲)は、11/23 から約20秒ずつ広げて鳴らし、持つのは3区切りまでなので、丸ごとは持たない(下の5)

### 5. 音はデコードすると大きい(参考)

曲は AudioBuffer に解いて(デコードして)鳴らしている。解いたあとの大きさは「長さ × 48000 × 2ch × 4バイト」。

- Dear Santa(ホームの曲・3分39秒)約 80MB / タイトル曲の別アレンジ(2分35秒)約 57MB。HOME にいるだけでこの2本(約 137MB)を持っている
- ワルキューレの原曲(11分32秒)は、丸ごと解けば約 253MB になる。**ただし 11/23(#7319・#7343)から、8分より長い曲は約20秒ずつ広げて鳴らし、持つのは3区切りまで**(`14-audio.jsx` の `LONG_SONG_SEC`・`tools/audio/long-song-chunk-check.js`)。なので丸ごと持ち続けることは無い(2026-11-28 追記で訂正。はじめは丸ごと持つと書いていた)。演奏中も約20秒ごとに次の区切りを広げる仕事が入るので、ワルキューレの原曲だけのかくつきの候補として、ワルキューレの会話へ渡す(この環境は音が鳴らないので測れない)

### 6. まとめてダウンロード(事前ダウンロード)の中身

`asset-manifest.json` の合計 **1,184MB・3,091件**(まとまりの「全部」)。ビート 332MB・バトル 815MB・カード 38MB・本体とデータ 27MB。

形式の内訳: PNG 1,679件 728MB / MP3 134件 381MB / JPG 1,216件 73MB / JS 24件 27MB / WebP 62件 3MB。

置き場所の上位: 助手の全身画 `images/assistant/fullbody` 206枚 379MB / サンタ服の助手 `images/assistant/santa` 144枚 116MB / サンタ服の立ち絵 56枚 46MB / ふだんの立ち絵 56枚 35MB / カードの絵(大)515枚 27MB / ハロウィンの立ち絵 24枚 23MB。

**画質・音質を下げない決めごと(r1115-143)を守ったまま軽くできるか**を試した。

- PNG を「画素を1つも変えずに」無劣化 WebP にすると、全身画は 66%・サンタ服 71%・立ち絵 65〜69% になった。見本の全部で、元の画素と1つ残らず一致することを確かめた(縮めない・色を減らさない・透明の部分の色もそのまま)。PNG を圧縮し直すだけでは 100%(もう詰まっていて縮まない)
  - PNG 728MB 全体に当てはめると、**約 240MB 減る見込み**(1,184MB → 約 940MB)
- JPG(カードの絵など)は無劣化 WebP にしても縮まない(100%)。手を付けない
- MP3 は元の音源のまま入れる決まりなので、作り直すと音が変わる。手を付けない。なお 320kbps の曲が5本、256kbps の曲が6本ある。Battle #5 のショート版(320kbps)は原曲(192kbps)より1秒あたりが大きいので、次に作り直す機会があれば、原曲と同じ形で切り出す方が小さくなる(音を良くする効果は無い)。今は直さない
- 名前がどのコードにも出てこない絵・音は、全身画(名前を組み立てて呼ぶので見かけだけ)を除くと約 9MB。使われていない物はほぼ無い

## 裏クイックを止めたらどうなるか(社長の問い)

- **軽くなる所**: 曲の一覧(iPhone の目安で 938 → 49ms/秒)と HOME(708 → 414ms/秒)。演奏中は、もともと止まっているので変わらない
- **失う物**: 曲を最後まで遊んだときの「曲の長さで何周ぶん」の周回と報酬。クリスマスの期間は周回数5倍・ビートP5倍もここに乗っている。**止めるのは遊ぶ人の損が大きい**
- なので「裏クイックを止める」ではなく、**裏クイックが回っていても曲の一覧を描き直さない・組を探す計算を一度だけにする**(下の案A)のがよい。これなら報酬は今のまま、重さだけが消える

## 軽くする案(効きの大きい順)

### 案A 曲の一覧を、裏クイックの更新で描き直さない・組を探す計算を一度だけにする(おすすめ・最優先)

- 効き: 大。裏クイックありの曲の一覧が、iPhone の目安で 938ms/秒 → 50ms/秒前後(なしと同じ)まで下がる見込み。HOME の差(+300ms/秒)も同じ形なら一緒に減る
- 中身: ① 組を探すのを「曲 → 組」の表を一度作って引く形にする(28組を毎回頭から探さない) ② 曲の一覧の行の組み立てを、曲・絞り込み・並べ替えが変わったときだけ作り直す(React の useMemo) ③ 裏クイックの WAVE の数字は帯の中だけで更新し、曲の一覧の画面全体を描き直さない
- 手間: 小〜中(①②は 29-rhythm-screens.jsx と rhythm-mode.js の数か所。③は 60-app.jsx の状態の持ち方に触るので中)
- 壊す危なさ: 低(見え方は変えない。並び順・選んでいる曲・組のまとめ方の検査を通す)
- 保存データ・ランキング: 触れない

### 案B 譜面を曲ごとのファイルに分け、遊ぶ曲だけ読む

- 効き: 中〜大。起動の読み込みが約 6MB(gzip 約 1.7MB)減り、JS ヒープが約 20MB 減る見込み。譜面を直すたびに全曲ぶんを取り直さなくてよくなる
- 手間: 大(曲えらびのレベル表示・ノーツ数・マルチ・ランキングの点検・事前ダウンロードの一覧・譜面生成ツールの書き出し先がすべて譜面を見ている)
- 壊す危なさ: 中(読み込みが間に合わないと演奏が始まらない。マルチで相手と譜面がずれない作りが要る)
- 保存データ: 触れない。ランキング: 送る中身は変えないが、譜面の印で点検している所があれば合わせる必要あり(要確認)

### 案C 全身画・立ち絵の PNG を無劣化 WebP にする

- 効き: 中。まとめてダウンロードが約 240MB 減る(1,184MB → 約 940MB)。画素は元と完全に同じなので見た目は1画素も変わらない。ふだんの読み込み(画面を開いたときの取り寄せ)も3分の2になる。表示に使うメモリ(解いたあとの画素)は変わらない
- 手間: 中(絵の置き場所の名前が `.png` から変わるので、`assistants.js` の道の組み立て・画像の検査・事前ダウンロードの一覧・切り出しの道具を合わせる。元の PNG は `tools/art-sources` 側に残す)
- 壊す危なさ: 低〜中(古い iPhone(iOS 13 以前)は WebP を出せない。いまの遊ぶ人の端末を確かめてから)
- 保存データ・ランキング: 触れない(着せ替えの持ち物は名前で持っていて、絵の道は持っていないことを確かめてから)

### 案D 更新履歴・ヘルプを、開いたときに読む

- 効き: 小〜中。起動の読み込みが 3.0MB(gzip 約 0.76MB)減り、JS ヒープが約 5MB 減る。この2つは1日に数十回変わるので、取り直しの回数も減る
- 手間: 中(起動時に「新しい」の印・助手のお知らせ・ヘルプの NEW を出すのに中身を見ている所があるはず。印に要る分だけを小さなファイルに分ける)
- 壊す危なさ: 低〜中(印が出なくなる・開いた直後に一瞬空になる、を検査で止める)
- 保存データ: 既読の印のキーは変えない

### 案E 本体を「よく変わる所」と「めったに変わらない所」に分ける

- 効き: 中。1日に約35回の取り直し(約 3MB ずつ)のうち、変わっていない側を取り直さなくてよくなる
- 手間: 大(部品の連結とビルドの作りを変える)。壊す危なさ: 中。保存データ・ランキング: 触れない
- 本体の名前の短縮(minify)でどこまで縮むかは、この環境に道具を入れられず**未測定**

### 案F′ 演奏を終えたら、その曲の解いた音を HOME まで持ち越さない

- 効き: 中(メモリ)。HOME に戻ったあとに持っている音が4本 → 2本になり、1曲あたり 50〜250MB 減る。iPhone でページが落ちる・重くなるのを減らす
- 手間: 小〜中(音の持ち方の上限・捨てる時機を変える。14-audio.jsx)。もう一度同じ曲を遊ぶときは解き直しの待ちが少し増える
- 壊す危なさ: 低〜中(曲えらびの試聴・続けて同じ曲を遊ぶときの待ちを確かめる)。保存データ・ランキング: 触れない

### 案F 長い曲の鳴らし方を見直す(参考・ワルキューレの会話へ)

- 長い曲は 11/23 からすでに区切って鳴らしている(上の5)。残るのは「演奏中に約20秒ごとに次の区切りを広げる」仕事がかくつきになっていないかで、実機でしか測れない。ワルキューレの会話の結果を見てから

## 追記(2026-11-28 夕方): 演奏中のかくつきを、過去の版と比べた(台帳 r1126-104 追記2 ②)

社長「今のモンビーはへんにカクつくんだけど今までと違う何かがあるんじゃない？」。演奏画面の重さが、過去の版と比べて変わったかを測った。

- 比べた版: 11/14・11/21・11/25・11/27・11/28 朝7時半・今の main(ワルキューレの会話の描画の直しはまだ入っていない)
- 条件: 同じ曲(Rebellion の HARD。2週間前からある曲)・CPU 6倍遅く(4倍では詰まりが出なかった)・曲の一覧に8秒いてから演奏・カウントダウンのあと20秒・各2回
- 結果: **版による差は出なかった。** 33ms を超えたコマは、どの版も20秒で16〜50回、メインスレッドの仕事は 670〜805ms/秒で、同じ版の1回目と2回目のぶれ(最大2倍)の中に収まった。11/14 の版も今の main も同じ幅
- このため二分探索で絞れるコミットは無かった。**この環境で測れる範囲(画面の描き方・JS の仕事)では、2週間前から演奏画面は重くなっていない**
- 測れていない所(=前と違う原因が残っているとすればここ)
  - 音: この環境では曲が鳴らない。11/23 から、8分より長い曲(ワルキューレの原曲)だけ、演奏中に約20秒ごとに次の区切りを広げて鳴らしている(#7319・#7343)。かくつきがワルキューレの原曲に強く出るなら、まずここを疑う。実機で「約20秒ごとに詰まるか」を見れば切り分けられる
  - 熱: 裏クイックが回ったまま曲の一覧にいると CPU が埋まっていた(わかったこと 1)。端末が熱を持つと CPU が絞られ、そのあとの演奏が詰まりやすくなる。案A(PR #8070)でこの山は約7割減る
  - GPU・合成: ヘッドレスの Chromium は実機の GPU と別物(前の記録と同じ制約)
- 次に打つ手の案: 実機でデバッグ画面の性能の計測(33ms 超えの回数)を、①ワルキューレの原曲と ②ショート版(区切らない)で比べる。①だけ多ければ音の区切りが原因、両方同じなら熱か GPU
