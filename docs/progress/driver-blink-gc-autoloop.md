# オート∞で「画面の部品の置き場(blink_gc)」が増える件の結論(2026-10-27・開発部ドライバーくん・PR #3111 #3125 の続き)

## 結論
**ゲーム側に「捨てたつもりの部品をつかみ続けている」漏れは無い。直すものは無い。** 増えているのは、作っては捨てる部品の跡地を Chromium が返さずに持っている分。

## 根拠(Chromium・AUTO∞・tools/memory-soak.js)
- 写しの比較(10分→40分・`tools/heap-snapshot-diff.js`): 生きている部品は 37.1 → 38.2MB(+1.1MB・ほぼ作られたコード)。画面から外れて残る部品(Detached)の増えは無し
- blink_gc の中身(20分・`--infra-every`): 実際に使っている部品は 5 → 9MB でほぼ平ら。「確保しているだけ」が 13 → 100MB で、伸びは 5分ごとに +46 → +18 → +12 → +11 → 0 と止まりかけ
- 入れ替わり(`--churn`・30秒ごと): 作る部品 約6,000〜9,000個・捨てる部品もほぼ同じ数。多い順に
  1. バトル画面の土台(`div[data-battle-speed]` の塊)… WAVE・戦いの切り替えのたびに画面ごと作り直す(30秒に 1,600〜3,000個分)
  2. 攻撃のエフェクト(`span.thm-atk`・`span.thm-atk[data-skill-fx]`)… 30秒に 800〜1,100個
  3. フェーズの帯(`div.mh-phase`)… 30秒に 460〜900個
  どれも出ては消える一時の部品で、置き場の跡地はこの入れ替わりの量で決まり、上限に近づくと止まる

## ゲーム側で減らせるとしたら(どれも作っていない・選ぶのは部長と社長)
| 案 | 中身 | 手間 | 危うさ |
| --- | --- | --- | --- |
| A | WAVE・戦いの切り替えでバトル画面を作り直さず、同じ画面を使い回す | 大(画面の状態の持ち方を変える) | 中〜大(前の戦いの表示が残る不具合が出やすい) |
| B | 攻撃のエフェクトとフェーズの帯を、毎回作らず決まった数の部品を使い回す | 中(2〜3時間) | 小〜中(見た目は変えない前提) |
| C | 何もしない(跡地は上限で止まるため) | なし | なし |

おすすめは **C**。iPhone のメモリには、展開した画像の置き場(約 +240MB・ストックくんの案B)と音(約 +170MB・「場面のBGMを軽く持つ」)の方が大きく効く。
