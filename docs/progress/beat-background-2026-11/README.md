## 続き: 12.0秒目・17.9秒目の重さの原因(r1119-082・2026-11-22 しらべ)

社長の選択「裏はそのまま・手がかりを直す」を受けて、手がかりの原因を調べた。**まだ直していない(下の理由で窓口へ返した)。**

### 分かったこと

1. 重いのは指の見回りの計算ではなく、その中で演奏エリアの位置を読む所(`rhythm-mode.js` の `areaRect` → `getBoundingClientRect`)。
   指の見回りは**ホールド・スライドを押さえている間だけ**毎コマ動き、毎コマ位置の覚えを捨てて読み直す(`invalidateAreaRect`。「ずれると入力位置がずれる」ための作り)。
   直前に画面の部品が変わっていると、ここでブラウザがその場でレイアウトを計算する(強制レイアウト)
2. 12.0秒目・17.9秒目は、crossing field HARD のホールドの押さえ始め(11.6秒目・17.4秒目)の約0.2秒後。判定の文字が「HOLD」「SLOW」⇔「—」へ入れ替わった直後のコマ
3. 重さの元はレイアウトそのもの。判定の文字が入れ替わるたびに**文書全体のレイアウト**が起き(20秒で約100回・合計約700ms・1回の上位17〜39ms・CPU 4倍遅く)、
   変わった部品は12個ほどなのに重い。指の見回りは、それをホールド中にその場で払っているだけ。同じコマの後の自然なレイアウトは 1.8ms と軽い
4. つまり**位置の読み直しを減らしても、レイアウトは後の描き出しで同じだけ起きる**見込みで、止まりは減らない

### 試して効かなかったこと(測るページの中だけ・本体は変えていない)

- フォントを1つに決める(Linux のフォント探しのせいかを確かめた) → レイアウトの重さは変わらない(合計 788ms)
- 判定の文字の入れ物を CSS の `contain: layout style` で囲う → 起点は文書全体のまま、変わらない(合計 676ms)

### 直すなら(判断が要る)

- A 判定の文字の表示を、文書全体のレイアウトを起こさない作りにする(文字を入れ替えずに重ねて置き、見える物だけ切り替えるなど)。
  見た目は同じにできる見込みだが、表示の作りの設計の変更になる
- B 指の見回りの位置の読み直しを、毎コマではなく画面の大きさ・向き・スクロールが変わったときだけにする。
  入力の位置がずれる恐れ(判定に関わる)があり、レイアウト自体は減らないので、効き目は小さい見込み
- C レイアウトが文書全体になる理由(演奏エリアの `:has()` の当たり・SVG のレーンなど)をさらに切り分けてから決める

## 続き2: 判定の文字の入れ替えが重い理由の切り分け(社長の選択「C もっと調べる」・2026-11-22 しらべ)

**本体のコードは変えていない。測るページの中だけで試した。** 台本は `survey.js.txt` の `--bisect` / `--bisect-lite` / `--has-keep` / `--add-css`。

### 結論

**重さの元は CSS の1行、`monster-hero/index.html` 2520 行目の `.mh-app:has([data-rhythm-counting="1"]) [data-rhythm-pause] { opacity: .35; }`**(曲が始まる前のカウントダウン中に一時停止ボタンを薄くするルール・2026-10-07)。
このルールがほかの `:has()` のルールと一緒にあると、`.mh-app` の中で文字が1つ変わるたびに、ブラウザが `.mh-app` の中全体のスタイルを計算し直す。
判定の文字(HOLD・SLOW など)は1秒に何度も変わるので、そのたびに払っている。

### 切り分けの順番(CPU 4倍遅く・判定の文字を何十回も入れ替えた真ん中の値)

| 試し | 文字の入れ替え1回 | わかったこと |
|---|---|---|
| 判定の文字を入れ替える / 色だけ変える | 約12〜21ms / 0.1〜0.7ms | 文字の入れ替えだけが重い |
| 部品を1つずつ隠す・演奏エリア・main・`.mh-app` に `contain` を付ける・フォントを変える | 11〜24ms(変わらない) | 並べ直しの伝わりや字の形のせいではない |
| 同じ見た目の文字を `.mh-app` の外に置く / 中に置く | 0.2〜0.9ms / 13〜16ms | `.mh-app` の中に当たる CSS が原因 |
| スタイルの計算とレイアウトを分けて測る | スタイル約15ms・レイアウト0ms | 重いのはスタイルの計算 |
| `:has()` のルール36個を全部抜いて開き直す | 約1ms | `:has()` が原因 |
| まとめ11個を1つずつ残して開き直す | どれも単独なら0.6〜1.8ms | 組み合わせで重くなる |
| `.mh-app:has(…)` + `section:has(…)` / + `[data-mh-screen]:has(…)` | 約12ms | `.mh-app:has(…)` がほかの `:has()` と重なると重い |
| **`.mh-app:has(…)` の1行だけ抜く(ほかの35個は残す)** | **約2ms** | **この1行が原因** |

(`:has()` は、ブラウザが部品に付ける印がルールを抜いても残るため、1つずつの切り分けはルールを抜いた状態でページを開き直して測った)

### 直し方の候補

| 候補 | やること | 見た目 | 判定 | 効き目の見込み |
