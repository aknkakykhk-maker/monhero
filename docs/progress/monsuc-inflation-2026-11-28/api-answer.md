# モンサク インフレ点検

## 1. インフレの大きさ

**結論: 育てた子を次の編成に入れる連鎖に天井がなく、本番では1人が3日で試算の「12代目」の水準に届いています。**

| 見る所 | 数字 |
|---|---|
| 試算(1代30回・12代) | いちばん高い能力の中央 1,239 → 11,087。総合力の中央 20,916 → 58,036 |
| 本番 heavy1(12回・3日) | 総合力 16,021 → 90,100。いちばん高い能力 816 → 11,355 |
| 本番・1回だけの66人 | 最高総合力の中央 5,337。いちばん高い能力の中央 421 |
| 本番・全93件 | いちばん高い能力が999超えは22件、5,000超えは4件、10,000超えは1件 |

- 試算は「1代=30回」で組んでいますが、本番の heavy1 は**1回ごとに1代進めている**ように見えます(推測)。12回目のいちばん高い能力 11,355 は、試算の12代目の中央 11,087 とほぼ同じです。つまり伸びは試算の想定よりずっと速いです。
- 伸び幅は代を重ねるほど大きくなり、頭打ちしません(試算 §3-1、heavy1 の推移も同じ形)。
- 対戦サーバ・アシストポイント・強さの段は999で切られており、影響はありません。壊れるのはモンサクの中とモンサクのランキングです。

## 2. 原因(重い順)

1. **② 補正が999を超えた分も数える(L752)**
   能力 ÷ 40 % の上乗せに天井がありません。案A(②③を999まで)だけで、12代目の上限が 17,444 → 4,332、いちばん高い能力の中央が 11,087 → 1,915 に下がります。いちばん効いている所です。
2. **① 上限に天井がない(L777〜780)**
   6体×20%で、上限は編成の子より速く上がります。①だけを止める案Cでも、12代目の上限は 2,193 に収まります。
3. **⑤ 貸し出しで999超えの子がそのまま効く**
   自分で回数を重ねなくても、借りるだけで伸びます。能力15,000の子を1体借りると、総合力の中央は 10,021 → 27,041 になります(§3-2)。
4. **③ はじめの能力に、いちばん高い能力 ÷ 25 を足す**
   上限(①)に従うので単独では弱いですが、②と重なって伸びを早めます。
5. **④ 総合力で999超えを1点3.5に数える**
   インフレの原因ではありませんが、ランキング上の差を大きく見せています。1つの能力に寄せるほど有利になります(推測)。

## 3. どこで遊びが壊れるか

- **ランキング**
  - 総合力の上位8件のうち7件が heavy1 です(90,100・81,320・76,694・62,743・52,598・49,355・45,354)。
  - 1回だけの66人(最高の中央 5,337)とは約17倍の差があり、新しい人が競える場ではなくなっています。
  - 1人の育成が何件も上位に並ぶ形です(並びが1回ごとのため)。
- **大会**
  - 相手は固定(頂点の基準で合計 2,050、星で ×0.75〜1.25)です。12代目の6能力合計の中央 15,125 に対して、大会が勝負所になりません。
  - ただし試算の勝率は 81.6% → 91.5% までしか上がっていません。何を数えた勝率かは §6 で確認が要ります。
- **育て方が一つに寄る**
  - heavy1 の12回目は、命中 11,355・ちから 5,659 に対して、かしこさ 840・丈夫さ 958 です。1つの能力に寄せるのが得になる形です(推測)。
- **貸し出しで新しい人にも広がる**
  - 今は小さいです。14日で5回しか使われておらず、3,000〜9,999の帯は0回です。
  - ただし貸し出し中の子の最大は 7,543 で、借り手が増えれば一気に広がります(推測)。
- **ほかのモードとの段差**
  - 11,355 の子でも対戦では999に切られます。「育てたのに対戦では同じ」という不満につながる恐れがあります(推測)。
- **サーバの見張り**
  - 1能力 99,999・総合力 2,500,000 を超えると送信が断られます。今の伸び方でいつ届くかの試算はありません。届けば、正しく育てた記録が送れなくなります。

## 4. 直す方針の案

どの案も保存データとランキングの記録は書き換えません。変えるのは「編成で数えるときの数え方」と「競う枠」だけです。

### 案1(推し): ①②③を 5,000 までで数える(試算の案D)+ ランキングを新しい枠にする

- **良い所**
  - 「999を超えて育つ」楽しさを残したまま、上限が 6,999 で止まります(16代目も 6,999)。
  - 12代目の総合力の中央は 33,299 で、1代目の 20,916 からは伸びます。つなぐ意味が残ります。
  - 2026-11-15 の判断(天井なし・999超えも数える)からの変更幅がいちばん小さい案です。
- **困る所**
  - 天井が 5,000 でよいかは未確定です(試した値はこれだけ)。
  - heavy1 の 90,100 には新しい育成では届きにくくなります。なので枠を分ける必要があります。
- **既存の子への影響**
  - 能力が5,000を超える子は、超えた分が編成で効かなくなります(本番で該当は4件、すべて heavy1)。それ以外は変わりません。
  - ランキングはエンジン番号で枠を分けます。今の枠(by_engine 9)は読むだけの記録として残します。

### 案2: ②③だけ999までで数える(案A。上限①は天井なしのまま)

- **良い所**: 「上限は天井なし」という判断は残せます。主な原因②は止まります。
- **困る所**
  - 12代目の総合力の中央が 19,062 で、1代目の 20,916 より低くなります。つなぐ旨味がほぼ消えます。
  - 上限は 4,332 までまだ伸びます。16代の数字はありません。
- **既存の子への影響**: 999を超えた子(本番22件)の補正とはじめの能力が下がります。

### 案3: ①②③を全部999までで数える(案B)

- **良い所**: いちばん固く、12代目の上限は 2,193 で止まります。
- **困る所**: 総合力の中央が 19,774 で、1代目より低くなります。11-15の判断をほぼ取り消す形です。
- **既存の子への影響**: 案2と同じく、22件の子の効きが下がります。

### 案4: 数え方は変えず、ランキングと大会の枠だけ分ける

- **良い所**: 芯に触れず、11-15の判断もそのままです。
- **困る所**
  - インフレ自体は止まりません。貸し出しで新しい人にも広がります。
  - サーバの見張りに届く問題は残ります。
- **既存の子への影響**: ありません。

推しを案1にする理由: 案2・案3は、試算で「つないでも1代目より弱くなる」ため、育成の目当てが消えます。案4は止まりません。案1だけが、伸びてから止まる形になっています。

## 5. 入れる順の段取り

1. **方針を決めて記録する**
   - 11-15の判断を見直す必要があります。社長に決めてもらいます。
   - 判断材料: 当時の試算は4代まで、今は12代+本番の数字があること。
2. **足りない試算を足す(芯は触らない)**
   - 「1回=1代」の条件で回す。
   - 案1の天井を変えて回す(5,000以外)。
   - 5,000の子を借りたときの新しい人の伸び。
   - 案2の16代目。
3. **見張りを続ける**
   - query.sql を日ごとに流し、次の2つを見ます。
     - いちばん高い能力が5,000超え・10,000超えの件数
     - 貸し出しの3,000以上の帯の使用回数
4. **芯の変更**
   - 案1の数え方を `capOfTeam`・`memberOf`・`startAdd` で同時に入れます。
   - 貸し出しの子も同じ数え方にそろえます(`56-...-lend.jsx`)。
5. **エンジン番号を上げてランキングの枠を分ける**
   - 新しい枠で競い、今の枠は読むだけで残します。
6. **お知らせ**
   - 「育てた子の能力の表示は変わらない」「編成で効く分の数え方が変わる」「今までのランキングは記録として残る」の3点を伝えます。
7. **入れた後の見張り**
   - 新しい枠の上位が、1人の何件にも占められていないか確認します。
   - ランキングを人ごとに1件だけ並べる案も、ここで判断します。

## 6. 渡された資料の読み違い・足りない数字

- **「代」と「回」がずれている**
  - 試算は1代30回で、本番の path は「何回目」です。
  - 本番は1回で1代進んでいる可能性が高いです(推測)。試算の「12代=360回」で考えると、速さを大きく見誤ります。
- **試算の勝率が本当に大会の勝率か分からない**
  - 6代 90.4% → 8代 89.2% → 10代 88.1% と下がる所があります。
  - 6能力合計 15,125 で 2,050 の相手に91.5%しか勝てないのは不自然です。試合側で999に切っているのか、何を数えているのか確認が要ります。
- **`top100_owners` の合計が合わない**
  - 12+7+4+61 = 84 で、件数93にも人数71にも合いません。
- **ラベルのない数字の列がある**
  - `pct_all`(power・top_stat は4つ、cap_max・stat_sum は3つ)と `lend.top_stat` が何の分位か書かれていません。中央・9割・最大と読むと数が合いません。
- **同じ値が並んでいる**
  - 1回だけの66人の最高総合力は、中央も9割も 5,337 です。
  - 11-20(31件)の中央と9割も 5,337 です。
  - 試しの送信や、決まった編成の重なりが混ざっている可能性があります(推測)。新しい人の実態としては使いにくい数字です。
- **`by_beta` の意味が書かれていない**
  - 1が12件で、heavy1 の12回と同じ数です。偶然かどうか分かりません。
- **試算の前提と本番の差**
  - 試算の1代目(real-S)は、いちばん高い能力の中央が 1,239 です。本番の1回だけの人は 421 です。
  - 3-2の「借りない新しい人」の総合力の中央 10,021 も、本番の 5,337 より高いです。新しい人への影響は、もっと大きく見える恐れがあります。
- **当時の試算の「4代で中央 1,739」が何の値か分からない**
  - 上限か能力か書かれていないので、今の4代目(上限 5,065・能力 3,720)と比べられません。
- **足りない数字**
  - 端末にだけある保存枠の子の分布(ランキングに送っていない子の強さ)
  - 案1で5,000の子を借りたときの伸び
  - サーバの見張りに届くまでの回数
  - 1回だけの66人のうち、続けなかった理由に関わる数字
