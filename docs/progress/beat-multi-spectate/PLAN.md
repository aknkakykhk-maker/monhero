# モンヒロビートのマルチ「観戦」設計(案)

担当: ショウタイ(ビート部)/ 2026-11-11 社長「モンビーマルチも観戦できるようにってできる？ 更に誘われて演奏中のときは待機になるけどその間見れたりとかも」「ステータスの変化も見えるように」
状態: **設計の案(コードはまだ書いていない)**。止め絵: `spectate-portrait.png`(縦) / `spectate-landscape.png`(横)

## 1. 見せるもの
- 曲が流れる(観戦する人の端末で、同じ曲を鳴らす)
- 画面の上: 曲の進み(バー)・全員の順位/スコア/コンボ(いまの「演奏中の札」と同じ並び)
- 1人を選ぶ(札をタップ)と、その人の**譜面(ノーツが流れる)と判定(PERFECT など)**が流れる
- 「ステータスの変化」= 選んだ人の **スコア・コンボ・判定の内訳(PERFECT/GREAT/…/MISS の数)・順位の入れ替わり**。順位が入れ替わった瞬間は札が光る。※ここは社長の言う「ステータス」をこう読んだ。ほかに見たいものがあれば窓口から確認

## 2. 見られる人(3つの入口)
| 入口 | 動き |
| --- | --- |
| A 誘われて入ったら演奏中だった人 | いまは待合いで待つだけ。待っているあいだ、**自動で観戦画面**(そのまま部屋のメンバー。次の曲から参加) |
| B フレンドの部屋を外から | フレンド一覧/「いまモンヒロビートにいる人」の帯に、演奏中の部屋なら「👁 観戦」。参加はせず見るだけ |
| C 公開している部屋を一覧から | フリーマッチの部屋の一覧に「演奏中」の部屋も出し、「👁 観戦」で入る |
- 部屋の人は「観戦を許す」を切れる(部屋の上の帯。既定は入。プライベートの部屋はフレンドにだけ見せる)。保存は新キー `mh_rhythm_multi_spectate_v1`(設定 `mh_rhythm_settings_v1` は触らない)
- 観戦の人は部屋の**メンバーではない**: 5人の枠に数えない・結果/報酬/ビートP/ランキング/実績/周回に一切入らない・演奏の人からは「👁 2」の小さい数だけ見える(名前は出さない)

## 3. 通信(Supabase の Broadcast だけ・SQL なし)
いまの `pg`(3秒ごと・スコアとコンボ)は部屋のメンバーだけが聞く前提。観戦用に**知らせを足すだけ**で、既存の知らせは変えない。
| t | 送る人 | 中身 | いつ |
| --- | --- | --- | --- |
| `wt` | 観戦する人 | 観戦したい(+見たい人の id `f`) | 入ったとき1回 + 10秒ごと(15秒聞こえなければ観戦なし) |
| `wi` | ホスト | 回の id・曲・難易度・開始時刻・参加者の名簿 | `wt` を聞いたとき(観戦1人につき1回) |
| `pg` | 演奏中の人 | 今までと同じ。観戦がいるあいだだけ**1秒ごと**に縮める。曲の位置 `p`(ms)を足す | 観戦がいるとき |
| `jd` | **見られている1人だけ** | 判定の束 `[[ノーツ番号, 判定コード], …]` | 見られている間だけ・1秒に1回まとめて |
- 古い版の端末は知らない `t` を捨てる(`rhythmMultiCleanMessage`)ので壊れない。応えが無ければ「この部屋は観戦に対応していない版です」と出す
- 受ける側(観戦)の `jd` / `pg` は `RHYTHM_MULTI.onLive` と同じく、部屋の `emit` を呼ばずその場で札へ渡す

## 4. 演奏している人の端末を重くしない(測ってから決める)
- 観戦が**いないとき**の追加の仕事は **ゼロ**(判定の側で「見られているか」のフラグ1つを読むだけ)
- いるとき: 判定が出るたびに配列へ1件 push(O(1)・1行)だけが演奏のループの中。送るのは**ループの外の `setInterval`(1秒)**で束にして1通。見られている1人だけが送る(ほかの人は `pg` だけ)
- 量の見積り: HELL で1人 1秒に約15判定 × 約8バイト ≒ 120B/秒。観戦が何人いても送る側は1通(Broadcast が配る)。受け取る観戦側は5人ぶんの `pg` + 1人ぶんの `jd` で約 1KB/秒以下
- 観戦する側の描画は、いまの演奏画面の部品(ノーツの絵)を**判定を入力にせず、時刻だけで流す**。曲の位置は `pg.p` で合わせ、ずれは次の `pg` で直す
- **測る**: `docs/progress/beat-multi-live-score/` と同じやり方(実ブラウザの縦/横・5人)で、観戦なし/あり(jd 送信)のフレーム時間を比べる。許容は「札を出しただけの今」から +0.3ms 以内(案)
- **重くなったときの代案(B)**: 譜面は出さず、スコア・コンボ・順位・判定の内訳の**数字だけ**(`jd` を送らない。`pg` の1秒ごとだけ)。送る側の追加は `pg` の間隔が縮むだけ。段階は設定でなく端末が決める(測った結果が悪い端末では自動で B)

## 5. 画面
- 縦: 上に曲名・進みバー・順位の札(横スクロールなし・5行まで)、中央に選んだ人の道(4レーンの簡略)と判定の文字、下に判定の内訳とボタン「観戦をやめる」(Aでは「次の曲まで待つ」の文)
- 横: 左に順位の札、右に道。判定の内訳は道の右下
- A(待合い): 上の帯に「次の曲から参加できます」
- 止め絵: `spectate-portrait.png` / `spectate-landscape.png`

## 6. 守ること・ぶつからないこと
- 演奏中の札 `pg`(担当はナラビ。#5243)・スタンプ(`beat/multi-stamp`)とは**知らせの種類を分ける**。`pg` の形は変えず、`p` を足すだけ(古い版は無視)
- 保存は新キーだけ。既存の `mh_*` は触らない(CLAUDE.md ⑦)
- 公開前: ミハリ確認(新機能・新しい保存キー)。更新履歴・ヘルプはそのとき案を出す

## 7. 決めてほしいこと(窓口へ)
1. 「ステータスの変化」は **スコア・コンボ・判定の内訳・順位の入れ替わり**でよいか(ライフ/ゲージ等は音ゲー側に無いので入れない)
2. 入口は **A → B → C の順に作る**でよいか(Aは待合いの画面を変えるだけで小さい。C は公開の一覧に「演奏中」を足す)
3. 観戦の人数の上限(案: 1部屋に最大10人。それ以上は「満員」)
4. 重さの測定がだめなら **B(数字だけ)** で公開してよいか

## 8. いまの作りとの突き合わせ(ナラビの確認・2026-11-11。案のままだと動かない所と、その直し)
いまの `77-screen-rhythm-multi.jsx`(`liveSend` / `liveReceive` / `onMessage` の先頭)が理由。`pg` に `p` を足しても、古い版・いまの版とも壊れない(読むのは `r`・`id`・`s`・`c` だけ。#5243 より前は溜めて捨てる)。
| 問題 | 直し |
| --- | --- |
| A 演奏中の人は `pg` 以外の知らせを全部溜めるので、`wt` を聞けず、ホストが演奏中なら `wi` も返せない | `wt` も `pg` と同じく `onMessage` の先頭で受け、印を1つ立てるだけ(`emit` なし)。`wi` は演奏していない人が返す。演奏中のホストでも返せる軽い道(`start` で配った曲・開始時刻を、`wt` に答えて1通返すだけ)を作る |
| B `liveReceive` は「その回の参加者」だけ受ける(`s.live` は参加者のときだけ作る)ので、観戦・待機の人は `pg` を捨てる | 観戦用の受け口を別に作る(`s.watch`。`s.live` とは分ける) |
| C `liveSend` はスコアとコンボが前と同じなら送らない → `p` だけ変わっても届かない区間ができる。受ける側も同じ値なら何もしない | 観戦がいるあいだは、値が同じでも1秒ごとに `p` を送る(観戦がいないときの条件は今のまま)。受ける観戦側は `p` だけでも更新する |
| D 送るタイマーは人の参加者が2人以上のときだけ動く → 人が1人(+マスモン)の部屋を観戦すると `pg` が1通も出ない | 観戦がいるあいだは、1人の部屋でもタイマーを動かす |
| E 終わりの1通は `reportResult` の中で、タイマーが動いているときだけ | 観戦がいるあいだは、終わりの1通も送る |
- 量: 観戦がいるときも**札は3秒のまま、見られている1人だけ1秒**にして、増え方を小さくする(全員1秒にしない)。5人が1秒ごとに送ると送信5通/秒・配る先は5人+観戦ぶんになり、仕様書 5 の Realtime の量の心配に当たる。#5243 より前の版は溜める上限が300件で、1秒ごと×4人×2分半≒600件になるとチャットや `bye` が古い版で捨てられる(結果は `res` と `hb` に載るので欠けない)
- 測り直し: 本物の作りでの測定は3秒間隔まで。**1秒間隔・観戦あり**を縦・横・5人で測り直す
- 触る場所: `77-screen-rhythm-multi.jsx` の `liveSend` / `liveReceive` / `onMessage` の先頭 / `reportResult`。`tools/mode/rhythm-multi-live-board-check.js`(「値が変わらないあいだは送らない」を見ている)も合わせて直す。札の重さの決まり(行を作り直さない・`will-change` を付けない・箱は `contain: strict`・`emit` を呼ばない)は `docs/spec/RHYTHM_MULTI.md`「演奏中の札」

## 実装の結果と、本物で測った重さ(2026-11-11・実装後に追記)

**実装は設計の案から1つ変えた**: 社長の答えの「譜面(ノーツ)が流れる」は入れていない。演奏画面の hud が元々持っている判定の数 `counts`・`life`・曲の位置 `timeMs` を読んで `pg` に足すだけにして、演奏のループには1行も触らない(案の `jd` は作っていない)。譜面を流す版は、重さが増えるので別の段階。
実装は `docs/spec/RHYTHM_MULTI.md`「観戦」。検査: `node tools/mode/rhythm-multi-spectate-check.js`(重さの表は `MH_MEASURE=1`)。

札(`beat-multi-live-score/PLAN.md`「本物で測った重さ」)と同じ測り方: 4つのページ(あかね・いぶき が演奏、うみ が外から観戦、えま は待機)。**あかね のページだけ CPU 1/4**、観戦なし(見られているのは いぶき)と観戦あり(見られているのは あかね。1秒ごとに pg を送る)を交互に3回ずつ。1回9秒(曲の長さに収まる回数。札の測定の15秒×4回だと曲が終わって測れなかった)。

| | 33.3ms を超えたフレーム | 1フレームの JS | スタイル再計算 | レイアウト |
| --- | --- | --- | --- | --- |
| 観戦なし(3回) | 1〜3 | 1.20〜1.57ms | 0.38〜0.53ms | 0.03〜0.04ms |
| 観戦あり(3回・1秒ごと) | 2〜6 | 1.21〜1.46ms | 0.39〜0.55ms | 0.03〜0.05ms |

- 幅が重なる。JS・スタイル・レイアウトに差は見えない(札のときと同じ)。「33.3ms を超えたフレーム」だけ観戦ありが1回 6 と高いが、同じ条件の観戦なしにも 3 があり、次の回は 2。CPU 1/4 では1回ごとにばらつく
- 等倍のフレーム間隔(8秒・480枚): 観戦なし 平均 16.61ms・95% 16.8ms、観戦あり 平均 16.74ms・95% 16.8ms
- 送る量: 見られている人は6秒で6通(1秒ごと)。ほかの人は今までの3秒ごとのまま。観戦がいないときは今までと同じ(札の検査 `rhythm-multi-live-board-check.js` は全部通る)
- 未測定: 本物の Supabase Realtime(偽の通信路での測定)・iPhone の実機
