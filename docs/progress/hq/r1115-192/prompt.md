Monster Hero — サクセスAI検証・バランス研究基盤の実装

目的

対象リポジトリ：aknkakykhk-maker/monhero

最新mainを正本として、モンヒロサクセスの育成バランスを定量的に評価できる、最大100,000回規模の自動シミュレーション・Claude API分析・比較レポート生成システムを実装してください。

今回は検証基盤の開発であり、ゲームバランスの変更は許可していません。

最終的には、Claude APIの余剰クレジットを活用して、今後のサクセス調整時に繰り返し利用できる仕組みにします。

1. 作業開始

1. 最新mainを取得し、基準コミットSHAを記録。
2. node tools/ctx.js brief を実行。
3. AGENTS.md、CLAUDE.md、DEVELOPMENT.md、tools/README.md およびサクセス関連の適用ルールを確認。
4. node tools/ctx.js decisions masmon などを使い、最新の確定仕様・数値・禁止事項を確認。
5. 既存の tools/success/ を調査し、再利用可能なコードを特定。

大容量ファイルの無条件全文読み込みは禁止。必要な関数と仕様だけ抽出してください。

現時点で確認済みの主な資産

* monster-hero/data/monhero-success-assist.js

最新mainで変更されている場合は、最新実装を優先してください。

2. 基本方針

* ゲームの実際の育成計算を使用する。
* 簡略化した独自の育成計算式を作らない。
* 同じ条件・同じ乱数IDで結果を再現できるようにする。
* 100,000回の試行をNode.js側で処理する。
* Claude APIは統計結果と異常ケースの分析に限定する。
* APIを呼び出さなくても全ての基本統計を出せるようにする。
* 既存の検証ツールは改造より再利用を優先する。
* ゲーム本体・保存形式・ランキング・経済・育成数値を変更しない。
* Supabaseの本番データを検証に使用・書き込みしない。

3. シミュレーション対象

A. 育成戦略

最低限、次の戦略を比較してください。

* トレーニング重視
* 修行重視
* バランス型
* 友情タッグ重視
* 体力管理重視
* 大会勝利重視
* 各ターンの期待値を優先する戦略

現行仕様で不可能な行動は選ばないこと。

修行チケットの取得・消費、修行可能条件、体力、イベント、強制大会などの制約を厳密に反映してください。

各戦略は同じ乱数ID群を使って比較し、偶然の差を可能な限り排除してください。

B. 編成

以下を検証してください。

* 低育成編成
* 中程度の育成編成
* 高育成編成
* 特定能力に特化した編成
* 6体の得意トレーニングを分散させた編成
* 友情タッグを重視した編成
* アシスト能力の組み合わせ
* 助手ごとの育成結果

実際の保存枠データやプレイヤー情報は使わず、現行仕様に適合する匿名の検証用編成を作成してください。

極端な編成だけでなく、一般的なプレイヤーを想定した編成を必ず含めてください。

C. 育成結果

各試行について、少なくとも以下を記録してください。

* 育成終了時の6能力
* 総合力と評価ランク
* 育成終了ターン
* トレーニング回数と成功率
* 修行回数と技習得結果
* 休養・遊び・通院などの回数
* 友情タッグの発生回数
* イベントによる能力変動
* 大会の勝敗と敗退理由
* 育成終了時の体力・忠誠度など
* 使用した助手・編成・戦略・乱数ID

実装上取得できない項目は捏造せず、理由を記録してください。

4. 100,000回試行

段階的に実行できるようにしてください。

* 100回：スモークテスト
* 1,000回：検証環境の正常性確認
* 10,000回：初期バランス分析
* 100,000回：本格分析

100,000回は全条件合計の試行数とし、戦略・助手・編成・血統などの組み合わせごとの割り当てをレポートに明記してください。

組み合わせが多すぎる場合は、全条件の総当たりではなく、代表条件を使った層化抽出・ペア比較を優先してください。

条件ごとのサンプル不足も検出してください。

性能・安定性

* 進捗表示
* 処理時間の計測
* メモリ使用量の計測
* 途中失敗時の安全な再開
* 結果の再現性確認
* 不正値・NaN・無限ループの検出
* 失敗した乱数IDの記録
* 結果の分割保存・集計

100,000回を実行する前に小規模試行で性能を測定し、必要なら実行方式を最適化してください。

APIを100,000回呼び出す構成は禁止です。

5. 大会とバトルの再現

大会勝率は、可能な限り実際の対戦計算を使用してください。

サクセスの育成計算と大会バトルは別の仕組みなので、既存の助手マスモン対戦エンジンとの接続を確認してください。

実対戦を再現できない場合、仮の勝率や固定勝敗を実測結果として扱わないこと。

次の2種類を区別してください。

* 育成計算のみの検証：大会勝敗は外部入力または固定シナリオ。
* 大会を含む統合検証：現行の対戦計算で実際に勝敗を決定。

統合検証が実現できない場合は、その制限をレポートに明記し、育成計算のみの結果と混同しないでください。

6. バランス分析

次の問題を自動検出してください。

1. 特定戦略が他の戦略を極端に上回る。
2. 修行特化とトレーニング特化の最終能力差が大きい。
3. 特定助手・編成が突出して強い。
4. 特定能力だけが伸びすぎる、または伸びにくい。
5. 育成結果が運に左右されすぎる。
6. 特定の大会で敗退率が急増する。
7. 強力な編成ほど育成格差が拡大し続ける。
8. アシスト能力の重複で想定外の倍率が発生する。
9. 上限突破・覚醒・超覚醒などの条件で極端な差が生じる。
10. 特定の行動選択が常に最適となり、選択の意味が薄れる。

ただし、差が大きいこと自体を自動的に不具合と判定しないでください。

意図された強さの差と、意図しないバランス崩壊を区別してください。

7. 調整案の比較

ゲーム本体を変更せず、検証環境内だけで調整候補を比較できる仕組みを作ってください。

最低限、以下の比較を想定します。

* 現行仕様（Baseline）
* 修行効果を調整した案
* アシスト効果を調整した案
* トレーニング成長量を調整した案

数値は勝手に確定しないこと。

仮の調整案は「検証用シナリオ」として明示し、現行値と混同しないでください。

実際の計算式に対して安全にパラメータを差し替えられない場合は、別計算による疑似結果を作らず、まず比較基盤の実装可否と必要な変更を報告してください。

比較では同一乱数IDを使い、変更した項目以外の条件を固定してください。

8. Claude API連携

Claude APIは以下に使用してください。

* 集計結果の解釈
* 異常な育成結果の原因分析
* 戦略間の優劣の説明
* バランス調整候補の提案
* 修正案の副作用の洗い出し
* 日本語レポートの生成

コスト削減

* シミュレーション本体でAPIを呼ばない。
* ローカル集計で異常候補を絞る。
* Claudeへ送るのは集計値、重要な差分、代表ケースのみ。
* 巨大なログやゲーム本体の全文を毎回送らない。
* 可能ならプロンプトキャッシュを利用する。
* 同じ入力の再分析はキャッシュを再利用する。
* 軽量な分析は低コストモデルを優先し、難しい判断のみ上位モデルを利用する。
* API利用料金の上限を設定できるようにする。
* API利用量・推定料金・実際に確認できた料金を区別して記録する。
* APIキーは環境変数またはSecretsから取得する。
* APIキーをリポジトリやレポートに書き込まない。

APIなしでも動作

APIキーが設定されていない場合でも、シミュレーションと統計レポートは完成するようにしてください。

API連携を実行できなかった場合は、実行済みと偽らず、未実行と明記してください。

9. 出力レポート

人間が読みやすい日本語Markdownを基本とし、必要に応じてCSV・JSONも生成してください。

最低限、次の内容を含めてください。

全体サマリー

* 基準コミットSHA
* 使用したゲーム計算のバージョン
* 試行回数と条件別内訳
* 所要時間
* エラー数
* API使用量・費用

育成バランス

* 戦略別平均総合力
* 中央値・標準偏差・分位点
* 評価ランク分布
* 能力別の成長傾向
* 大会勝率・敗退率
* 修行とトレーニングの実効効率

問題点

* 重要度
* 発生条件
* 発生頻度
* 再現用乱数ID
* 原因と根拠
* 仕様上の問題か、実装上の不具合か、未判定か

調整案

* 現行仕様との比較
* 改善する指標
* 悪化する指標
* 想定される副作用
* 推奨度
* 追加検証が必要な項目

最後に必ず以下を明記してください。

「本レポートはゲーム計算の自動シミュレーション結果であり、実機での操作感・画面表示・体感バランスまで確認したものではありません。」

10. 検証と完了条件

以下を満たしてください。

* 既存のサクセス検査が成功する。
* 100回、1,000回、10,000回の段階的試行が成功する。
* 100,000回の本試行を実行し、完了数を記録する。
* 同一条件・同一乱数IDの結果が一致する。
* 統計結果と生データの集計が一致する。
* 失敗試行を成功試行に含めない。
* APIなしで日本語レポートを生成できる。
* APIありの場合は実際の呼び出し結果と費用を記録する。
* APIを利用できない場合は、その部分だけ未検証として残す。
* ゲーム本体のバランス数値に変更がない。
* セーブデータ、ランキング、Supabaseに変更がない。
* node tools/run-checks.js --changed など、現行ルールで必要な検査が成功する。

100,000回の実行が環境制約で不可能な場合は、成功した最大規模・原因・推定所要時間を報告してください。未実行分を成功扱いしないこと。

11. 実装・公開

新規ツールは原則 tools/success/ 配下に整理してください。

既存のツールを活用し、不要な依存関係やGitHub Actionsの新規ワークフローは追加しないでください。

通常プレイに現れない開発用ツールとして実装し、ゲーム画面に新しいボタンやメニューを追加しないでください。

リポジトリの現行ルールに従い、実装、必要な検査、コミット、PR、CI、マージまで進めてください。

ゲームバランスの修正は、検証結果が良好でも絶対に自動適用しないでください。

12. 最終報告

日本語で次の順に報告してください。

1. 実装した検証基盤
2. 再利用した既存ツール
3. 実際に実行できた試行回数
4. サクセスの現行バランスで見つかった問題点
5. 最も効果が見込める調整案3〜5件
6. 調整案ごとの改善・悪化指標
7. API利用状況と費用
8. テスト・CI結果
9. PR・マージ・公開状態
10. 未確認事項

調整案は必ず「提案」で止め、採用する数値はユーザーの判断に委ねてください。

最重要：これはサクセスのバランスを勝手に直す作業ではなく、今後のバランス調整を正確に判断するための研究基盤を完成させる作業です。

最新mainの実装状況を確認し、利用できるものを活用してください。

2. 全画面・全状態の検証

少なくとも以下を確認してください。

* サクセス開始画面
* 育成モンスター選択
* 編成画面
* 助手選択
* 持ち込みアイテム選択
* 育成メイン画面
* 6種類のトレーニング

通常のプレイ経路だけでなく、長いモンスター名、能力上限付近、技やアイテムが多い状態、選択肢が多いイベントなど、表示が崩れやすい条件も再現してください。

3. スマートフォンを最優先

以下の画面幅で確認してください。

* 320px：狭いスマートフォン
* 375px：標準的なスマートフォン
* 390px：iPhone想定
* 430px：大きめのスマートフォン
* 844px：横画面
* PC幅：参考確認

特に390px縦画面を重点的に確認してください。

Safe Area、Dynamic Island、ホームインジケーター、スクロール、固定ボタンの位置を確認してください。

PlaywrightのiPhone相当設定と実機iPhone Safariは別物です。実機未確認の場合は必ずその旨を明記してください。

4. 見た目と表示バランス

各画面について、次の問題を探してください。

* 文字と画像が重なっている
* ボタンが小さすぎる
* ボタン同士が近すぎる
* 重要な情報が目立たない
* 逆に重要度の低い情報が大きすぎる
* 余白が不自然
* 画面内の情報密度が高すぎる
* カードの高さ・幅が不揃い
* アイコンの位置がずれている
* テキストが途中で切れている
* 画面外にはみ出している
* 色の組み合わせで文字が読みにくい
* 画面ごとにデザインの統一感がない
* スクロールしてもボタンが押せない
* モーダルが画面外へはみ出す
* 画面遷移時にレイアウトが跳ねる

自動的な要素位置検査に加え、スクリーンショットを実際に確認し、視覚的な違和感も評価してください。

単に「要素がはみ出していない」だけで合格にしないでください。

5. 文字の徹底検証

特に重点的に調査してください。

* 誤字脱字
* 文字化け
* 不自然な日本語
* 文字の途中切れ
* 不自然な改行
* 表記揺れ
* 古い仕様の説明が残っている
* 実際の能力上昇と説明文が一致しない
* ボタン名と実行内容が一致しない
* 助手ごとの口調が混ざっている
* イベント選択肢と結果が一致しない
* 未置換の変数やテンプレート文字列が表示されている
* 数字・単位・倍率・確率の表示がおかしい

DOMから表示テキストを抽出して検査するとともに、スクリーンショットで実際の表示も確認してください。

文字の問題は「表示されている原文」「問題点」「修正案」をセットで記録してください。

6. 実際の操作フローを検証

可能な限り、サクセスを開始から育成終了まで複数回プレイしてください。

最低限、以下の操作を確認してください。

* 育成開始
* 編成変更
* トレーニング選択
* 修行
* イベント選択
* 大会進行
* 育成終了
* 保存
* 中断と再開

操作の途中で画面が固まる、ボタンが反応しない、二重押しが起きる、表示が更新されないなどの問題も確認してください。

テスト用の高速進行やデバッグ機能を使う場合は、通常操作で確認した範囲と区別してください。

7. 問題点の整理

発見した問題を次の4段階に分類してください。

* 重大：操作不能、画面崩壊、進行不能、誤った数値表示
* 高：文字が読めない、重要ボタンが押しにくい、説明が誤っている
* 中：表示バランスが悪い、不自然な余白、レイアウトの不統一
* 低：細かな位置ずれ、装飾や表記の改善余地

各問題に以下を記録してください。

1. 対象画面
2. 発生条件
3. 端末・画面幅
4. 問題の具体的な内容
5. スクリーンショット
6. 再現手順
7. 原因候補
8. 推奨修正案
9. 他画面への影響

可能な限り、問題箇所が分かるスクリーンショットを残してください。

8. 自動検証の仕組み

今回だけの目視点検で終わらせず、今後のサクセス開発でも繰り返し使えるようにしてください。

* 主要画面のスクリーンショット自動取得
* 横方向のはみ出し検出
* 要素同士の重なり検出
* 文字切れの検出
* コンソールエラー検出
* 主要ボタンの操作テスト
* 画面遷移テスト
* 変更前後のスクリーンショット比較
* 日本語の検証レポート生成

自動検出だけで確定できない問題は「目視確認が必要」と分類してください。
