# トークン節約の仕組み(リセット後に取りかかる)

> **2026-11-11 済み。** 社長が案A〜Fを全部採用し、道具・フック・検査にした。いまの決まりは CLAUDE.md ⑪ と
> `docs/rules/`(MODEL_ROUTING・SESSION_HANDOFF・REVIEW_GATE・EDGE_REDEPLOY)、部の手引きは `docs/depts/`。下は元の案(経緯)。

2026-11-10 社長「トークン消費を抑える仕組みをリセットされたらとりかかりたい」「開発品質は落としたくない」「新しいモデルを有効活用したい」。
いまは使用量が残っていないので**まだやらない**。リセット後に、社長にどれを採るか選んでもらってから始める。

## 消費が膨らんでいる所(窓口の見立て)
- 会話が長いまま続く(窓口は数日分。毎回それを読み直す)。部の会話も公開を重ねて長い
- どの仕事も同じ高いモデル(Opus)。文言の直しも難しい不具合も同じ
- 同じ確認を何段も(部の検査 → ミハリ → 窓口)。小さな直しにも
- assistant-chat の配り直しで index.ts(約10KB)を毎回送る
- 全員が共通の CLAUDE.md(約16KB)を毎回読む。部に関係の無い決まりも乗る。部ごとの「読む場所の一覧」が無いので毎回 grep で探す

## 案(どれを採るかは社長が選ぶ)
- **A 区切りで会話を作り直す**: 公開が何件か済んだら引き継ぎメモ1枚 → 新しい会話。窓口も同じ
- **B モデルの使い分け**(新しく作る会話から効く): 小さい仕事・検査は Sonnet 5.5(Opus 5.5 の半額)/ 設計・原因不明の不具合は Opus 5.5 / 定期の見張りは Haiku 5.5
- **C 要所だけ Fable 5.2**(最新・最も賢い。Opus 5.5 の2倍の値段): 新機能の公開前の最終確認と、2回直しても直らない不具合だけ
- **D 確認の段数**: ミハリの確認は新機能・保存データ・ランキングに関わる変更だけ。小さな直しは部の検査で公開
- **E 配り直しを軽く**: assistant-chat の index.ts も GitHub(raw)から読む形にして、送る量を約1/100に
- **F 部署別の手引き**: `docs/depts/<部>.md` に、受け持つファイル・入口の関数・回す検査・関係する決まりを1枚。新しい部の会話はそれから読む。CLAUDE.md の部ごとの話を手引きへ移して共通部分を軽く
  (チェックアウト自体を部ごとに絞るのは、ビルドと検査が全ファイルを要るのでしない)

品質は `run-checks.js --changed` と、新機能・保存データでのミハリ確認を残すことで守る。

## 新しいモデル(Fable 5.2)の使い方(2026-11-10 社長と相談)
仕組みを**作るときの1回だけ**使い、できた仕組みは普段のモデルで回す(譜面ツールの強化と同じ考え方)。
- F の部署別の手引き: 全体を通して読ませ、部ごとに1枚へ絞らせる
- CLAUDE.md を削る: 古い書き方・重なり・部ごとの話を見つけ、意味を変えずに短くした案を出させる(`rules-index-check.js` が要の言葉の消え漏れを見張る)
- B・C の使い分けの決まり: これまでの頼みを振り返らせ、仕事の種類ごとのモデルを実例つきで決めさせる
- E のような繰り返しの作業をスクリプトにさせる
- 1トークンあたり高いので、1回の会話で上の4つに範囲を絞る。終わったらいつもの検査を通す
