# 文脈とトークンの使い方（詳細）

> ルート [`CLAUDE.md`](../../CLAUDE.md) ⑨ の詳細。**守ることの本文は CLAUDE.md が正本**で、
> ここには経緯・道具の使い方・数字を置いている。

2026-09-08にユーザーが指摘した（「他の作業をさせるとトークン量がかなりえぐい」)。
このリポジトリには**1ファイルで数MBのものが複数ある**。1回でも全文を開くと、その後の
やりとり全部にその中身が乗り続け、作業が途中で頭打ちになる。**依頼の大小に関係なく**作法を守る。

2026-09-17に「もっと減らす仕組みを、精度は落とさずに」と言われて道具を足した。
考え方は3つだけ。

1. **恒久コストを下げる** … 毎回必ず読み込まれるもの（`CLAUDE.md`）を小さく保つ。
   詳細は `docs/rules/` へ置き、必要なときだけ引く
2. **往復を減らす** … 「探す → 範囲を当てる → 外して読み直す」の読み直しを無くす。
   終わりの行を機械に決めさせる
3. **考える手間を機械に移す** … 「どの検査を通すか」を毎回考えない。変更内容から選ばせる

## 絶対に全文を開かないファイル

| ファイル | 大きさ | 代わりにすること |
| --- | --- | --- |
| `monster-hero/src/game-system.jsx` | 2.7MB | 自動生成物。**読む必要がない**。直すのは `src/parts/*.jsx` |
| `monster-hero/game-system.compiled.js` | 3.0MB | 同上。`node tools/build.js` が作る |
| `monster-hero/src/parts/60-app.jsx` | 1.5MB | `node tools/ctx.js read 60-app.jsx <名前>` で定義だけ切り出す |
| `monster-hero/data/rhythm-mode.js` | 0.9MB | 譜面データ。曲IDで `node tools/ctx.js text <曲ID>` |
| `monster-hero/data/changelog.js` | 0.5MB | 新しい項目は**先頭に足す**規則なので `head -80` で足りる |
| `docs/spec/RHYTHM_MODE.md` | 0.5MB | `node tools/ctx.js toc` で見出し → `doc` で節だけ |
| `tools/mode/authoring/*.json` | 0.4MB〜 | 中身を読まず、ツール経由で扱う |

## 打ってはいけないコマンド

- 素の `git diff` / `git show` / `git diff --cached`
  → 生成物2本で数MB流れ込む。`.gitattributes` で `-diff` にしてあるので通常は畳まれるが、
    それでも **`node tools/ctx.js diff` を使う**（生成物を外し、上限で切る）
- 除外なしの `grep -r`（生成物にヒットして巨大な行がそのまま出る）
  → `node tools/ctx.js text <語>`（生成物は最初から対象外）
- `cat` で丸ごと開く。大きさが分からないときは先に `wc -l` / `ls -lh`

## 道具

### `node tools/ctx.js` — 開かずに済ませる入口

```
node tools/ctx.js brief                  いまの状態（ブランチ・変更・次に打つもの）
node tools/ctx.js find <語>              定義を探す
node tools/ctx.js text <語>              本文を探す
node tools/ctx.js read <名前>            その定義の本体だけ（置き場所も自分で探す）
node tools/ctx.js read <ファイル> <名前>  ファイルが分かっているとき
node tools/ctx.js read <ファイル> <行>    その行の前後だけ（-C で幅）
node tools/ctx.js refs <名前>            その名前を使っている場所の全体像
node tools/ctx.js toc <ファイル>          見出し／骨格の一覧（.md も .js も .json も）
node tools/ctx.js doc <語>               資料を横断して見出しを探す
node tools/ctx.js doc <ファイル> <見出し> その節だけ
node tools/ctx.js rules [語]             ルールの該当節だけ
node tools/ctx.js checks [語]            検査を「名前＋何を見るか」で引く
node tools/ctx.js diff [パス…]           生成物を除いた差分
```

`read` は**名前だけでも通る**。どのファイルにあるかを先に調べる往復が消える
（定義が3件を超えたときだけ候補を並べて聞き返す）。

`refs` は「直し忘れ」を防ぐためのもの。たとえば新曲の名前は songId / 音源の一覧のid /
BGMのtrack id / 譜面のマーカー名 / ファイル名の**5か所で綴りが違う**（⑥-3）。
1か所忘れても画面はふつうに動いてしまうので、先にファイルごとの件数で全体像を見る。

`checks` はスクリプト自身の先頭コメント（**かたまり全体**）を読んで検査を探す。
`tools/README.md` は手で書いているので520本のうち187本が載っておらず、
READMEを読むより取りこぼしが少ない。`tools/` 直下の36本だけは
`rules-index-check.js` が掲載と説明コメントの有無を見張っている。

`read` の終わりの行は、文字列・コメント・テンプレート文字列・正規表現を飛ばしながら
括弧を数えて決める。JSX の自己終了タグ（`…}/>`）を正規表現と取り違えると、その先の
`)` `}` を食べて数が合わなくなるので、そこは明示的に外してある。
`monster-hero/src/parts/*.jsx` のトップレベル定義 1437 件すべてで終わりの行が取れることを
確かめてある。

長すぎる定義（`MonsterHeroGame` のように 15000 行あるもの）は上限で切ったうえで、
**その中にある定義の地図**を出す。当て推量で `sed` を打ち直さずに、次の1手で目的の場所へ行ける。

`--max <行数>` で上限を変えられるが、全文を出さないための道具なので、大きくするのは
本当に必要なときだけにする。

### `node tools/where.js` — 場所だけを知る

`60-app.jsx` は15000行あまりが**丸ごと1つの関数**（`MonsterHeroGame`）なので、ファイルを分割して
小さくすることができない。かわりに「開かずに場所だけ知る」道具を置いてある。

```
node tools/where.js --screens                 # 画面(gameState)73件と、その場所
node tools/where.js マーケット                 # 名前から定義の行を探す
node tools/where.js --text <語>               # 本文をふつうに検索する
node tools/where.js --outline <ファイル>       # そのファイルの骨格(定義の一覧)
```

生成物は最初から対象外で、出力は40件・1行110字に切ってある。全文を出さないための道具なので、
`--limit` を大きくするのは本当に必要なときだけにする。

`ctx.js find` / `ctx.js text` / `ctx.js toc` がこれを内部で呼んでいるので、ふつうは `ctx.js` で足りる。
画面（`gameState`）の一覧だけは `node tools/where.js --screens` にある。

### `node tools/run-checks.js --changed` — 変更から検査を選ぶ

```
node tools/run-checks.js --changed --plan    選んだ検査と、選んだ理由を出す（実行しない）
node tools/run-checks.js --changed           そのまま回す
```

変更したファイル名から語を取り出し、その語を名前に含む検査だけを拾う。
ゲーム本体（`src/parts/` `data/` `index.html` `images/`）を触っていれば、
CLAUDE.md ⑥ の必須検査14本は無条件で入る。

- 語が当たる検査が多いほど、その語は大まかだということなので、**当たりの少ない語から順に**並べる
- 既定の上限は40本。**切ったぶんは必ず本数を出す**（黙って減らすと「全部通した」と読めてしまう）
- 広げるなら `--limit N` か `--wide`（当たった領域を丸ごと）。`--base <ref>` でそのrefとの差も見る
- **検査スクリプト自身を直したときは、その検査を回す。** ファイル名から語を取る仕組みでは
  拾えず、直した本人だけが素通りしていた
- 落ちたときは**失敗をじかに言っている行**（`NG` / `Error` / `不一致` など）を拾って出す。
  末尾8行だと、原因が途中に出て最後は集計だけ、という検査で肝心の行が消えていた。
  失敗が6本以上あるときは5本まで（残りは本数だけ出す）

これは打鍵と出力を減らすためだけのものではない。**選び漏れが無くなるので精度が上がる**。
これまでは「どの検査を通すか」を毎回その場で考えていたので、打ち漏らす（精度が落ちる）か、
念のため全部回す（時間を食う）のどちらかになっていた。

### `node tools/rules-index-check.js` — ルールが痩せすぎていないか見張る

`CLAUDE.md` を小さくするのは、**中身を削ることではなく置き場所を変えること**でしか
やってはいけない。この検査が次を見る。

- `CLAUDE.md` の大きさが上限以内か（また膨らんでいないか）
- `CLAUDE.md` の各節から詳細ページへの参照があり、リンク先が実在するか
- `docs/rules/` に、どこからも参照されていない置き去りのページが無いか
- **要のことばが `CLAUDE.md` 本体から消えていないか**（一覧はこの検査の中にある）

4つめが本体。「短くする」作業で守るべき一文が落ちるのを機械で止める。

## 作業の進め方

- 変更箇所は「探してから読む」。`node tools/ctx.js find` → `node tools/ctx.js read` の順を徹底する
- 検査は `node tools/run-checks.js --changed`。個別に打つときは出力の最後だけ見る（`2>&1 | tail -20`）
- 長い作業（土台の見直しなど）は、区切りで `docs/` に進捗メモを1枚残して**会話を切る**。
  中断したまま別の依頼を重ねない
- 一度取得した情報を理由なく何度も読み直さない。「念のため全文を読む」は避ける
