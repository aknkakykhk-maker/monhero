# 更新履歴・ヘルプ・助手の告知（詳細）

> ルート [`CLAUDE.md`](../../CLAUDE.md) から切り出した詳細。**守ることの本文は CLAUDE.md が正本**で、
> ここには経緯・失敗例・具体的な手順を置いている。CLAUDE.md は毎回すべて読み込まれるため、
> 読まなくても困らない部分をここへ寄せている（CLAUDE.md ⑨ / [`CONTEXT_BUDGET.md`](CONTEXT_BUDGET.md)）。
>
> 探すときは `node tools/ctx.js rules <語>` を使うと、必要な節だけが出る。

### ⑤ 機能を追加・変更したら、必ずヘルプも更新する

手順はスキルにしてある。**`changelog-help-update` スキルを開いてから始める**
(`.claude/skills/changelog-help-update/SKILL.md`)。エントリの書き方・告知の種別・
`{t:'data'}` の使えるid・検査の読み方が1枚にまとまっている。以下はその要点。

**更新履歴の日時は「いま書いている実時刻(JST)」を書く。時刻まで実際に合わせる**
(2026-09-07・ユーザー指摘「更新履歴の時間とか並ぶ順番がおかしい」「更新情報の時間がおかしい /
さっき直したんじゃないの？ / ちゃんとリアルタイムで合わせて」)。

    TZ=Asia/Tokyo date '+%Y-%m-%d %H:%M'   # ← これをそのまま書く

`21:00` `20:40` `20:10` のような**きりのいい連番を自分で決めない**。実際にあった失敗は2段階で、
1回目は日付が2日先(`2026-09-08` が12件。コミットは `2026-09-06`)、
2回目は**日付は合っているのに時刻だけ未来**(いま17時なのに 23:30 / 21:00 / 20:40 …が8件)。
1回目の検査が日付だけを見ていたので、2回目を見逃した。**日時で比べること。**
**足す場所は配列の先頭**(いちばん新しいものが上)。
`node tools/boot/changelog-order-check.js` が、未来の日時・書式・並びの逆転に加えて、
**gitのコミット時刻と1時間以上ずれていないか**まで見張る。

**前に書いたお知らせも古くなる**(2026-09-08・ユーザー指摘「お知らせの詳細が前のままだからなおしといてね」)。
譜面を作り直したり数字が変わったときは、新しい項目を足すだけでなく
**前に書いた項目の数字も直す**。更新履歴の `items` は
**そのまま助手(みゅあ)の告知の本文になる**(`assistantUpdateNoticeFromChangelog`)ので、
放っておくと助手が古い数字を読み上げる。
`node tools/changelog/song-numbers-check.js` が、お知らせに書いた曲のレベルとノーツ数を
実データと突き合わせる(「Lv.11→9」のように変化を書いている行は対象外)。

> なお、画面に出る並び順は `CHANGELOG_ENTRIES` が日付の降順に並べ替えて決めている。
> `data/rhythm-step3-release.js` が起動時に `CHANGELOG.unshift` で古い項目を先頭へ
> 差し込むため、書いてある順に頼ると先頭が古いままになるので、そこは触らないこと。

ゲームに何か追加・変更したら、**更新履歴(`monster-hero/data/changelog.js`)だけでなく、
ヘルプ(`monster-hero/data/help.js`)にも必ず反映する**。ヘルプはプレイヤーが仕様を確認する唯一の場所なので、
「更新履歴には書いたがヘルプには載っていない」という状態を作らない。

具体的には、機能の追加・変更のたびに次を行う。

1. 該当する項目(トピック)の本文を書き直す。項目が無ければ新しく作る
2. 画面(`gameState`)を増やした場合は `HELP_SCREEN_COVERAGE` にも対応するヘルプ項目を追加する
3. 難易度・アイテム・ログインボーナス・ミッション・ブリーダーの教えのような**一覧になるものは
   ヘルプへ手で書き写さず、`{ t:'data', id:'...' }` を使って実データから表を作る**
   (一部しか載っていない、値が古い、といった状態を構造的に防ぐため)
4. 新しいトピックには助手のひとこと(`assistant`)を必ず付ける。
   助手(みゅあ)の名前・画像・場面ごとのセリフは `monster-hero/data/assistants.js` にまとめてあるので、
   ヘルプ以外の画面へ案内を出すときも、そこへ場面を1つ足して `<AssistantBubble scene="..."/>` を置く
5. `node tools/help-coverage-check.js` と `node tools/help-guide-check.js`、
   `node tools/help-render-check.js`、`node tools/assistant-check.js`、
   `node tools/assistant-bond-check.js` を通す。
   助手の表情画像を差し替えたら `node tools/make-assistant-faces.js` で顔アイコンを作り直し、
   `node tools/assistant-face-check.js` で顔が中央に切れているかも確かめる

助手(みゅあ)のセリフを足すときは、`ASSISTANT_SCENES` を直接書き換えるのではなく
`addAssistantLinePack({ id, lines })` で束にして足す。イベント・季節限定のセリフも
同じ形で足せる(`when` を書くとその条件のときだけ合流する)。
セリフには親密度の条件(`bond`)と出やすさ(`w`)を付けられ、本文の `{name}` は
そのときの呼び方(さん付け・呼び捨て・ちん付け)に置き換わる。

これらのチェックは「ヘルプの更新漏れ」を検出するためのものなので、
落ちた場合はチェック側を緩めるのではなく、ヘルプを更新して直す。

**マーケットに商品を足したら、助手からの告知も必ず付ける。**
更新履歴のエントリへ `assistantNotice: { id:'update_notice_◯◯_v1', type:'market' }` を書くと、
助手が一度だけ「新しく入ったよ」と知らせて「マーケットを見る」ボタンを出す
(`data/assistants.js` の `assistantUpdateNoticeFromChangelog`)。この1行は書き忘れても
画面はふつうに動いてしまい、「並んでいるのに誰も教えてくれない」状態に気づけないため、
`node tools/boot/market-notice-check.js` を通して確かめる。
`type` は マーケット=`market` / バトルの新モード・新難易度=`mode` / 新しい遊び(新曲・新しい助手・新しい育成システム・キャンペーンなど)=`content` の3つだけ。
**告知は大きい追加のときだけ付ける**(2026年9月にユーザーがそう指示した)。見た目の改善・並び替え・絵の追加・小さな機能・不具合修正には
付けない(更新履歴には書く)。以前の `feature` は廃止した。`node tools/assistant/assistant-update-notice-check.js` が種別と例を見張る。

**画面に出す名前は正式名称を使う**(2026年9月にユーザーがそう指示した)。
略称を使ってよいのは、そうする理由があるときだけ。

- 例: 音ゲーは「モンヒロビート」。見出し・説明文・ボタン・助手の案内・ヘルプ・更新履歴はすべてこの名前
- 略称「モンビー」を使ってよいのは、**キャラクターが愛称として呼ぶ会話**
  (ももすけの登場イベントで「モンビーって呼んでる」と紹介する場面など)。
  そこでは先に正式名称を出してから略称へ移る
- ボタンのように幅が足りない場所は、字を小さくするか折り返して**正式名称のまま入れる**。
  入らないからという理由だけで略称にしない
- ソースのコメントは開発者向けなので、読みやすさを優先して略称のままでよい

**大きい追加は、公開のときに「画面のなかでの使い方案内」もセットで用意する**(2026年9月にユーザーがそう指示した)。
ヘルプと更新履歴は**探しに行った人しか読まない**。遊んでいるだけでは気づけない仕組み
(別の画面へ移る・裏で動き続ける・ある条件のときだけ止まる、など)を足したときは、
公開と同時に**画面のなかでも**伝える。段取りを組むときは、実装の手順の中へこの1ステップを必ず入れる。

- 助手(みゅあ)の吹き出しで出す。`ASSISTANT_SCENES` へ場面を1つ足して `<AssistantBubble scene="..."/>` を置く
  (セリフは `addAssistantLinePack({ id, lines })` で束にして足す)
- 一度きりの案内には**新しい** `mh_◯◯_seen_v1` を作る。既存の保存キーは触らない(⑦)
- 公開フラグ(`RELEASE_FLAGS`)を持つ機能なら、案内も**同じフラグ**で出し入れする。
  そうしておけば「機能は出ているのに説明がどこにもない」も「説明だけ先に出る」も起きない
- 対象は助手の告知と同じ基準で、**大きい追加のときだけ**。見た目の改善・小さな機能・不具合修正には付けない

> ⚠️ **デバッグ専用の変更(`DEBUG_SETTINGS` 配下の確認ボタン・デバッグ画面など、
> プレイヤーの通常プレイに一切現れないもの)は、更新履歴(`monster-hero/data/changelog.js`)
> に載せない**(2026年8月にユーザーがそう指示した)。更新履歴はプレイヤー向けの案内であり、
> 開発者しか触らない機能はそこに書く対象ではない。ヘルプへの反映も同様に不要
> (ヘルプもプレイヤー向けのため)。この指示より前に載せてしまった既存の記載はそのまま残してよく、
> 遡って削除する必要はない。


## 更新履歴はプレイヤーの言葉で書く

2026-09-18にユーザーが指摘した(「助手の更新情報の文言がおかしい / あーいう形の更新情報ってどうなの？」)。
そのとき出してしまった実物がこれ。

> **助手のセリフを400本以上追加しました**
> ・みゅあ・きき・ももすけのセリフを増やしました。全部で1,691本から2,095本になります。
> ・とくに、きき と ももすけ はほとんどの画面で5〜6本しか用意がなく…全60場面へ3本ずつ足しています。
> ・ドラのセリフは今回そのままです。
>
> **ドラのセリフも増やしました**（31分後）
> ・さきほど見送っていたドラのセリフも増やしました。301本から481本になります。

**更新履歴は作業報告ではない。** 遊ぶ人が読んで「自分にとって何が変わるか」が分かる文章にする。

**書かないもの**

- **内部の数え方**。「◯◯本」「全60場面」「3本ずつ」「束」「◯◯を選んでいると〜へ落ちる」。
  プレイヤーは「場面」も「本数」も知らない。作り手の作業量は伝えるものではない
- **作業の都合**。「今回はここまで」「◯◯はそのままです」「さきほど見送っていた」。
  読む側には関係がなく、しかも上の例では**31分後に嘘になった**
- **数を誇るタイトル**。「400本以上追加しました」は、何が良くなったかを言っていない

**やること**

- **タイトルは「何が良くなったか」**。「助手が同じことを言う回数を減らしました」のように、
  遊んでいて気づく変化で書く
- **同じ日の同じ出来事は1件にまとめる。** 作業を2回に分けたのは作り手の都合。
  遊ぶ側から見れば1つの変更
- **不具合の修正は `type:'fix'` で分ける。** 「増やしました」の中に
  「出ていなかったものが出るようになりました」を混ぜない。タブが違う
- 数字を書くのは、**プレイヤーが判断に使う数字のときだけ**
  (報酬の個数・必要ポイント・難易度の倍率・曲のレベルとノーツ数など)

迷ったら、書いた本文を読み返して「これは誰に向けた文か」を見る。
作り手にしか意味のない語が1つでも入っていたら、それは作業報告になっている。
