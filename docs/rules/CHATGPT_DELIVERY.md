# ChatGPT 開発・検証・公開の標準フロー

この文書は ChatGPT（通常チャット・Work）によるモンヒロ開発の運用標準。共通ルールは `AGENTS.md`、ビルド・品質手順は `DEVELOPMENT.md` を優先し、Claude 固有の運用は `CLAUDE.md` を尊重する。

## 基本方針

ユーザーから「調査・実装から公開まで」の依頼と権限が与えられている場合、確認のためだけに push、PR、merge の各工程で停止せず、同じ作業の中で完走を目指す。明示的に PR 止め、main 禁止、確認待ち等を指示された場合はそちらを優先する。完走できなければ、実際に完了した工程と障害を区別して報告する。

## 1. 着手

- 最新 main と `AGENTS.md`、`DEVELOPMENT.md`、`docs/PROJECT_CONTEXT.md`、対象の仕様・検査を読む。
- 既存の担当者（Claude・Muse・Work）のブランチやPR、作業範囲を確認する。他者のブランチを上書きしない。
- 新規作業は `chatgpt/<task>` ブランチを使用。再開時は既存ブランチを使い、重複PRを作らない。
- 実行環境の有無を最初に検証する。GitHubコネクタの書込権限と、ローカルNode実行権限は別物であり、片方の成功を他方の成功とみなさない。

## 2. 実装・検証

- 編集元は `monster-hero/src/parts/*.jsx` 等。配信用生成物を手で書き換えず、正規の `node tools/build.js` で同期する。
- `node tools/build.js --check` と対象テスト・必要な全体検査を行う。実機確認、ブラウザ確認、静的検査を区別する。
- Node実行環境がない場合は GitHub連携だけでビルド済みと主張しない。既存の `build-and-check.yml` の正規手順を使用できる場合に限り利用する。
- 既存のCI失敗はベースmainでも再現するか切り分ける。テストを弱めたりワークフローを増やして見かけ上成功させない。

## 3. GitHubへの反映

- GitHubコネクタによるファイル作成・更新・PR作成・マージが利用可能なら、ターミナル `git push` の認証失敗を理由に直ちに断念しない。
- push/commit後、対象PRの head SHA、変更ファイル、baseとの差分を確認する。関連しない変更を混入させない。
- 既存の `.github/workflows/compiled-check.yml` のCI結果を確認し、失敗時はログの失敗ステップと個別検査を特定して修正する。
- CI成功、必要なビルド・検査成功、変更範囲の安全性、最新mainとの整合性を確認した場合に限り、ユーザーから許可された範囲でマージする。マージ時は可能なら expected head SHA を指定する。
- 競合やCI失敗が発生した場合、同一作業中に解決を試みる。ただしセーブデータ破壊、他者変更の巻き戻し、仕様判断が必要な場合は無断マージしない。
- マージ後にmainとPages公開を確認する。CI成功とPages公開成功は別々に検証する。

## 4. 監視と継続の限界

- 通常チャットが閉じられた後も自律的にコード修正・マージし続けることは保証しない。
- ChatGPTの定期タスクは状態監視・通知用であり、実装・修正・マージを行うときは、そのタスクに明示された権限と利用可能な実行環境が必要。
- CI待ちを最小化するため、可能な限り同じ実行セッション内で結果確認から次の処理まで進める。未完了なら、再開に必要なPR・ブランチ・SHA・CI URL・失敗原因をGitHubに残す。

## 5. 完了報告

- 変更内容、実際のビルド・テスト結果、PR、マージSHA、Pages確認結果、未確認事項を日本語で報告する。
- 「コミット成功」「CI起動」「CI成功」「マージ成功」「公開成功」を混同しない。
- ゲーム本体の改修を伴わない文書・診断変更で、無関係なゲーム側の既存CI不具合を勝手に修正しない。
