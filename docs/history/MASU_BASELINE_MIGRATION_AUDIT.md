# マスモン基礎値追従方式への移行調査（第1段階）

## 1. 目的と調査範囲

将来、種族の基礎値を常に最新の `ALL_PLAYER_MONSTERS` から解決し、`mh_masu_mons` には個体差と育成差分だけを
保持する方式へ移行するための現状調査である。本書は 2026-08-14 時点の作業ブランチ（調査開始時の先頭は
`33ace5e`）の実コードを正本としている。今回はコード、ゲーム挙動、保存キー、保存形式、既存セーブを変更しない。

確認対象は `AGENTS.md`、`README.md`、`docs/PROJECT_CONTEXT.md`、`DEVELOPMENT.md`、`docs/KNOWN_ISSUES.md`、
`docs/spec/MONSTER_SYSTEM.md`、`docs/spec/SAVE_DATA.md`、`tools/README.md`、
`monster-hero/src/game-system.jsx`、`monster-hero/data/ally-monsters.js` およびランキング関連コードである。

用語は次のように区別する。

- **最新参照**: 個体を使う時点で `baseId` から現在の `ALL_PLAYER_MONSTERS` を引く。
- **完成値保存**: 現在値や技定義全体を保存し、基礎値変更だけでは値が動かない。
- **差分保存**: 基礎値へ加算する育成量・回数・レベルだけを保存する。
- **追従**: 種定義を変更しただけで、既存個体の解決結果にも変更が現れる。

## 3. 重点確認

### 3.1 距離適性は旧ベース値が残る

通常登録、旧絆データからの移行、再生はいずれも、その時点の `base.distAptitude` を `distApt` へ配列コピーする。
解決時は `masu.distApt || base.distAptitude` なので、通常の有効な保存個体は常に保存配列が勝つ。したがって、
ベースモンの距離適性だけを後から変更しても、変更前から存在するマスモン（未強化を含む）には旧適性が残る。

例外的に、`distApt` が欠損した旧・破損データ、転生後、または絆ポイントリセット後は、その操作時点の最新ベース配列を
使う。しかしこれは自動追従ではなく、操作した個体だけが再同期される挙動である。さらにリセットは旧完成配列と新ベースの
差を「使用済み段階」とみなすため、ベース調整後に実行すると返却ポイントが実際の投入数と一致しない可能性がある。

### 3.2 再生個体は差分ではなく完成値を保存する

`buildRegeneratedMasu` は各基礎能力を 90%～110% の範囲で乱数化・四捨五入し、結果を
`individualStats.{hp,atk,def,guts}` へ保存する。解決時は null 合体演算子で `individualStats` をベースより優先する。

したがって、旧ベースが `600 / 120 / 120 / 100` で、生成結果が `610 / 117 / 123 / 97` なら、現保存値は
`610 / 117 / 123 / 97` であり、`+10 / -3 / +3 / -3` ではない。後日ベースを調整しても生成済み個体は新基礎値へ
追従しない。通常の `statPoints` は、この保存済み完成値へさらに加算される。一方、供モン用 `plusStats` は
`individualStats` を参照せず、最新種定義の `plusStats` と `statPoints` から解決される。

### 3.3 継承固有技は最新定義を使い、保存スナップショットへfallbackする

合体時の `inheritedUniques` は、副種の固有技をその時点のLvへ展開し、技オブジェクト全体をコピーしたものへ
`monId`、`lineageId`、`sourceMasuName` を付けて保存する。この旧技スナップショットは削除せず保持するが、ゲーム内で
使う技定義は `resolveInheritedUniqueDefinition` を通す。`savedUnique.monId` から
`ALL_PLAYER_MONSTERS[monId].unique` を解決できる場合、その現行定義が正本となり、倍率、消費G、効果、名称等の変更も
既存の継承技へ反映される。

`monId` がない記録、または現在の `ALL_PLAYER_MONSTERS` で元種・`unique` を解決できない旧記録では、保存済み
`inheritedUniques` のスナップショットを互換fallbackとしてそのまま使用する。技を削除・無効化はしない。

技定義の解決方法と個体の育成成果は分離する。各技に `inheritedUniqueId` を付け、恒久Lvは
`uniqueSkillLevels['inhId:<inheritedUniqueId>']` を正本にする。旧個体は現在配列と `inh:N` を厳密に対応させて一度だけ
コピーし、旧キー自体は互換用に残す。安定キーがある技は並び替え後に旧位置を参照しない。`lineageId` は血統情報であり、
恒久Lvの本人確認には流用しない。現時点では削除UI・実際の削除・ポイント返却は実装していない。

総合力は引き続き継承技の「所持数」と「恒久Lv」で計算する。最新定義へ追従して倍率、消費G、名称等が変わっても、
その変更自体を別の点数として計算しない。ランキング詳細も継承元 `monId` とLvを送り、閲覧端末の最新定義から再構築する。

## 4. 分類別の結論

### 4.1 現在安全に最新ベースへ追従している項目

- 通常個体（非再生）の4基礎能力。`statPoints` は最新基礎値へ加える差分である。
- 自前固有技と、`monId` から元種を解決できる継承固有技の定義（Lvは個体保存）、`plusStats`、勇者特性。
- 通常表示の総合力そのものは非保存の派生値。ただし入力に旧完成値があれば、その旧値を正しく反映してしまう。
- 限界突破・転生の回数、上限、確定獲得ポイントは基礎値のコピーではなく個体育成成果として独立している。

### 4.2 古い値が残る項目

- 全通常生成経路の完成 `distApt`。
- 再生個体の完成 `individualStats`。
- 元種を解決できない旧記録で互換fallbackとして使う、`inheritedUniques` の保存スナップショット。
- ランキングの `detail.power` と `detail.distApt` は記録時点スナップショットとして意図的に残る。

### 4.3 マイグレーションが必要な項目

1. `distApt` 完成配列から、生成時ベースに対する距離別投入段階への変換。
2. `individualStats` 完成値から、生成時ベースに対する個体差への変換。
3. **将来改善**として、`uniqueSkillLevels['inh:N']` の位置対応から、安定した `lineageId` 対応への変換。

ただし 1 と 2 は「生成時点のベース」が保存されていない。現在の最新ベースとの差をそのまま個体差とみなすと、過去の
バランス変更分まで個体育成成果として固定してしまう。正確な移行には、リリース履歴別の旧ベース定義または、移行時に
保全すべき現在完成値を基準とした明示的な変換方針が必要である。

### 4.4 既存セーブ互換で特に危険な部分

- **距離適性の投入数推定**: 完成値しかなく、どの旧ベースから何段階上げたかを一意に復元できない。リセットの返却数、
  未使用P、総合力を同時に照合しなければポイントを増減させる。
- **再生個体差の基準欠落**: 完成値はあるが生成時ベース版がない。単純に最新ベースとの差へ置換しては将来追従の目的を
  達成できず、逆に旧バランスを差分として永久固定する。
- **継承技の同一性**: `monId/lineageId` はあるものの、Lvは配列位置キーである。重複整理済みデータ、古い欠損データ、
  名称変更を含め、技とLvを誤結合しない必要がある。
- **再実行と中断**: `mh_masu_mons` 全体を書き換える移行は、pending保存→本体保存→専用完了フラグの順で冪等にし、
  途中終了と二重適用の双方を防ぐ必要がある。既存キーは改名・削除しない。
- **操作依存の状態差**: 転生・絆ポイントリセット済み個体は既に最新適性へ再同期され得る。全個体へ同じ推定を盲目的に
  適用してはならない。

## 5. 第2段階で最初に変更すべき最小範囲

最初は**新規生成データの追加記録と、読み取り解決関数のテスト可能な整理だけ**に限定することを推奨する。

1. `mergeMasuIntoMon` を唯一の能力・適性・技解決入口として維持し、現行形式を入力した時の結果を固定する回帰テストを追加する。
2. 既存フィールドを消さず、新規の再生だけに「個体差」と「その差分形式の版」を追加する。ただし旧
   `individualStats` も併記し、読み取り優先順位はまだ変えない。
3. 新規の通常登録・再生だけに距離別の投入段階を0として併記する。現行 `distApt` は引き続き書いて挙動を変えない。
4. 継承技は保存済み技コピーを互換fallbackとして保持し、`monId` から解決できる場合は最新元種の定義を使う。恒久Lvは現行の位置キーのまま維持する。
5. 新旧表現から得た解決結果（4能力、4適性、技、総合力）が完全一致する診断を蓄積してから、読み取り正本を差分側へ切り替える。

この段階では既存個体の一括変換を行わない。生成時ベースを復元できる履歴表、破損値の正規化、pendingを含む一度きりの
移行設計、バックアップ往復テストが揃った後にのみ、旧個体の移行を別段階として実施する。

## 7. 第2段階の実装状況（2026-08-14）

`mergeMasuIntoMon` の共通経路へ、`individualStatOffsets` と `distAptBoosts` の解決を追加した。優先順位はそれぞれ
「新形式 → 旧 `individualStats` / `distApt` → 最新ベース」であり、能力、適性、総合力、各表示は同じ解決結果を使う。
専用回帰検査は `node tools/masu/masu-baseline-resolution-check.js`。

これは新旧両形式を安全に読み取る**受け皿**のみである。既存データは未移行で、起動時一括書換え、新規生成の本番切替、
旧フィールド削除はいまだ未実施であり、基礎値追従方式への移行完了ではない。継承固有技の定義は
`monId` から最新元種を参照し、恒久Lvは別途 `inheritedUniqueId` の安定キーで解決する。

## 8. 第3段階の実装状況（2026-08-14）

新規通常マスモンは従来の `distApt` に加えて `distAptBoosts:[0,0,0,0]`、新規再生マスモンはさらに従来の
`individualStats` と、同じ抽選結果から生成時ベースを引いた `individualStatOffsets` を保存する。生成時には旧表現と
新表現の4能力・4距離適性・総合力が一致しない個体を保存しない。強化は両適性表現を同期し、リセット・転生はboostを
0へ戻すと同時に完成適性を最新ベースへ戻す。

この段階でも既存 `mh_masu_mons` の一括変換、起動時マイグレーション、新フィールドの自動追加は行わない。既存個体は
未移行で、旧フィールドも維持しているため、基礎値追従化の完了ではない。第4段階以降には、生成時ベースを復元できない
既存個体の安全な移行方針と、継承固有技Lvの安定した `lineageId` キー化を将来改善として残す。

## 9. 第4段階の実装状況（2026-08-14）

`diagnoseMasuBaselineMigration` と `diagnoseMasuBaselineMigrationList` により、既存個体を変更せず `SAFE` / `ESTIMATED` /
`BLOCKED` に分類し、候補、4能力・4距離適性・総合力・ポイント保全の検査結果と全個体集計を得られる。

- `SAFE`: 第3段階以降の新形式で、旧完成値と新しい差分表現、総合力、ポイント項目が一致する個体。
- `ESTIMATED`: 最新ベースとの差から候補を作って現在の完成値は維持できるが、生成時ベースが無く、個体差や使用済み適性ポイントを一意に復元できない旧個体。
- `BLOCKED`: ベース不明、配列欠損・不正等級、最新ベースより低い適性、非有限な能力、不正ポイント、または新旧表現不一致があり、自動変換すべきでない個体。

**第4段階：既存個体の移行可否をドライラン診断可能。実データは未移行。** 診断関数は `localStorage` と
`mh_masu_mons` を参照・更新せず、起動時移行、フィールド自動追加、完了フラグ、UI、保存処理には接続していない。
旧個体を `SAFE` にするには、生成時ベース履歴と、絆Lv・転生等から獲得総量を一意に照合できる根拠が第5段階以降で必要になる。

## 10. 第6B-3段階の実装状況（2026-08-14）

`diagnoseLegacyMasuBaselineMigration` は、第6B-1の能力診断と第6B-2の距離適性診断を個体単位で統合し、
`individualStats` と `aptitude` を独立分類する。能力側は確定した生成時ベースから個体差を求め、現行ベースと既存 `statPoints` へ適用する。能力変化量が新旧ベース差と合い、総合力を新能力から再計算できる場合に `SAFE_EXACT` の材料にする。能力と総合力の移行前後一致は要求しない。

- 両方が安全候補なら `SAFE_EXACT`、片方だけ安全で他方が曖昧なら `PARTIAL`。
- どちらかが不正または不整合なら `BLOCKED`。両方曖昧なら `AMBIGUOUS`。
- 新形式の新旧表現が一致する個体は `ALREADY_MODERN`。通常個体は能力完成値を持たないため能力移行不要として扱う。
- 旧ゴーレムの距離適性は生成時ベースを断定できず、引き続き `AMBIGUOUS` とする。

## 11. 第6C段階の実装状況（2026-08-14）

起動時に `diagnoseLegacyMasuBaselineMigration` が個体全体を `SAFE_EXACT` と確定した場合だけ、候補の
`individualStatOffsets` / `distAptBoosts` を追加する。旧 `individualStats` / `distApt` とその他の既存フィールド、
`statPoints` / `distAptPoints` は変更も削除もしない。`PARTIAL` / `AMBIGUOUS` / `BLOCKED` と旧ゴーレムは未変更である。

保存直前検証では能力の移行前後一致を要求しない。能力側が `SAFE_EXACT` なら、各能力が
「現行ベース + 確定した個体差 + statPoints」であることと、移行前からの変化量が
「現行ベース - 確定した生成時ベース」であることを検証する。
距離適性は4距離すべてを維持し、総合力は移行後の能力・距離適性・固有技Lv等を `monsterPowerParts` /
`monsterPowerOf` の現行式へ渡して再計算する。最後に候補を再診断して `ALREADY_MODERN` になる場合だけ保存する。

専用キーは `mh_masu_baseline_relative_migrated_v1`。trueでも一覧を再診断するため、以前の第6Cで保存直前検証により
保留された `SAFE_EXACT` 個体も修正版で再び安全判定される。処理は冪等であり、移行済み個体は変更しない。
