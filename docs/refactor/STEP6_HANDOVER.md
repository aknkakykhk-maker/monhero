## この日に分かった「型」

切り出しは同じ手順の繰り返しになる。**この4つを守れば速い。**

### 1. props は手で数えない

props を空にした仮のコンポーネントへ JSX を移し、`node tools/undefined-reference-check.js` を通す。
足りない参照が全部一覧で出るので、それをそのまま props にする(`PROFILE` の38個はこれで決めた)。

### 2. 移してはいけないものが3つある

- **画面をまたいで保たれる state**。図鑑の絞り込み・選択中・タブは、画面へ移すとアンマウントで消え、
  詳細から一覧へ戻ったときにリセットされて**挙動が変わる**。
  「画面の中だけの UI 一時 state」を移すのは、**その画面を出れば消えてよい値**に限る
- **タイマーを含む非同期の再生処理**。画面のライフサイクルで途中の `setTimeout` が止まると演出が固まる
- **`ref` そのもの**。ref は変わっても描き直しが起きないので、渡すなら**真偽値などの値**にする

> ref については、あとから分かったことがある。**描画のたびに読む値なら ref をそのまま渡してよい。**
> 切り出した画面はメモ化していないので本体と同じ描画の中で読まれ、読む時点が前と変わらないため。
> 実際 `fusionProcessingRef` / `extremeRunRef` / `allyCarouselRef` はそのまま渡してある
> (DOM を掴む ref は、そもそも値へ直せない)。真偽値へ直すのは、props の意味をはっきりさせたいときでよい。

### 2-2. 1つのブロックで2画面を出し分けているものがある

`PICK_HERO` と `PICK_ALLY` は元から1ブロックで、中で 21 箇所ぶん `gameState===` を見て出し分けている。
画面は `gameState` を知らない約束(`ui/screen-parts-check`)なので、**出し分けの綴りだけを
`pickMode`('hero' / 'ally')という props に置き換えた**。
このとき骨格の機械比較は素通しでは落ちるので、**比較の前に綴りを元へ戻す**ようにした
(`gameState==='PICK_HERO'` ⇔ `pickMode==='hero'`)。置き換えたのは条件の綴りだけで、
要素・文言・並びは1文字も変えていないことをそれで証明している。

### 3. 検査は「静かに」壊れる

`60-app.jsx` を直接 `readFileSync` している検査が12本以上ある。見ている画面が切り出されると
探し物を見失う。**落ちればまだよく、「探す文字列がそもそも無い」形だと何も言わずに対象外になる。**

→ `harness.js` の **`readAppSource()`**(本体＋切り出した画面をつないで返す)へ差し替える。
この日 `masu/soul-rank-step2-check`(画面の移動)と
`boot/mission-gift-badge-check` / `boot/market-item-quantity-purchase-check`(ハンドラの props 化)が実際に落ちた。
いずれも**見る対象を広げる方向**で直してあり、判定は緩めていない。

### 3-2. 画面の範囲を「次の gameState まで」で切る検査は、切り出しで必ず壊れる

`game.indexOf("gameState==='X'")` から次の `{gameState===` までを切り出して中身を調べる書き方が
あちこちにある。画面を別ファイルへ出すと、その範囲には呼び出し(`<XScreen …/>`)しか残らない。
さらに悪いことに、**部品ファイルの並びが変わると範囲が伸びて別の画面まで飲み込む**
(演奏画面の検査が、あいだに入った音ゲー画面部品を巻き込んで落ちた)。

→ `harness.js` の **`screenSource(gameState, componentName)`** を使う。
切り出し済みならコンポーネント本体を、まだ本体にあるなら従来の範囲を返す。
「1つの部品ファイルだけを見ればいい」検査(演奏画面など)は、そのファイルを直接読むほうが確実。

**モンヒロビートの5画面を切り出したときは、これで検査 10 本が落ちた。**
音ゲーは検査が122本と特に厚いので、切り出しの前に覚悟しておくこと。すべて
「見る対象を広げる / 正しい場所を見る」方向で直してあり、判定はひとつも緩めていない。

### 3-2b. 「窓で切り出す」検査は、通っていても信用しない

`layout-consistency-check` は `gameState==='X'` から **9000 文字の窓**を読んで
`overflow-y-auto` を探していた。窓が次の画面へはみ出すので、
**隣の画面のスクロール領域を拾って偶然通っていた**画面がある。
切り出して範囲が正確になった途端、`MONSTER_ATTACK_PREVIEW` に縦スクロールが無いことが見えた
(切り出しで壊したのではなく、元からそう。演出を見せる専用画面なので実害はない)。

**つまり「切り出したら落ちた」検査の中には、今まで見逃していた実態を暴いたものが混じる。**
落ちた原因を「切り出しのせい」と決めつけず、切り出し前のコードでも同じかを必ず確かめること。

### 3-3. 領域を絞って検査すると、壊れたことに気づけない

`PROFILE` を切り出した PR では `required` と `ci` しか回さず、`mode` 領域を回していなかったため、
`mode/species-challenge-profile-check` が落ちていたことに**次の本まで気づけなかった**。
画面を切り出したら、**その画面に関係する領域を必ず名指しで回す**
(プロフィール → `mode`、マーケット → `boot`、図鑑 → `battle`、音ゲー → `mode`)。

### 4. 骨格の機械比較を必ずやる

ハンドラだけを伏せて、要素・`className`・文言・並びを文字列比較する。
1文字でも違えば落ちるので、「見た目を変えていない」の証明になる。
比較の道具はこの日の作業ではその都度書き捨てた(`skel*.js`)。定着させるなら `tools/ui/` へ置くとよい。
