# 画面の描画コストを測った(2026-09-12)

`REFACTOR_MASTER_PLAN.md` STEP 7-2(一覧行の `React.memo`)に入る前の計測。

再現は `python3 tools/serve.py 8899` を上げてから
`node tools/browser/screen-render-cost-check.js`。

## 結論: いまは `React.memo` を入れなくてよい

| 画面 | 描画まで | 長いタスク |
| --- | ---: | ---: |
| バトルモード選択 | 59 ms | **0 ms** |
| ランキング50件(ブリーダーLv) | 21 ms | **0 ms** |
| 絆Lvランキング50件 | 45 ms | **0 ms** |
| M/B管理 | 21 ms | **0 ms** |

**50件の一覧を描いても、画面が固まる「長いタスク」(50ms以上)は1つも出ていない。**
`React.memo` は再描画をスキップする道具なので、そもそもの描画が軽いなら効果は小さい。

## なぜ入れないと決めたか

`TECH_DEBT_AUDIT.md` TD-22 は「`React.memo` が0個」を問題として挙げているが、
入れるには**そこそこの代償**がある。

- `memo` を `MonsterHeroGame` の中で定義すると、再描画のたびに関数が作り直されるので**効かない**。
  効かせるには共有層へ切り出して props で全部渡す形になり、STEP 6 の画面切り出しと同じ作業量になる
- props に毎回新しいオブジェクト(`entry`)や関数を渡していると、切り出しても効かない。
  渡し方まで直すことになる
- `memo` の比較が漏れると「更新されない行」が出る。これは見た目には出ず、
  プレイヤーが「反映されない」と気づくまで分からない

**効果が測れない状態でこれをやるのは割に合わない。** いまは測った結果が「速い」なので、
入れない。

## いつ入れるか

実機(iPhone)で「一覧を開くと引っかかる」と感じたときに、まずこの道具で測る。

> ⚠️ **この環境の数字を実機の目安にしない。** Tailwind の CDN へ出られないので
> レイアウト計算が減り、実機より軽く出る。**改修の前後で比べる**ために使う道具。

そのうえで長いタスクが出ているなら、原因を切り分けてから `memo` を検討する。
一覧の行より先に、染色(`getDyeRegionMasks`)やランキングの整形のような
**1回が重い処理**を疑うほうが当たりやすい
(ランキングは既に「一覧に絵を並べない」判断をしている。`60-app.jsx` のコメント参照)。

## この道具が見ているもの

- 画面の目印が出るまでの時間(遷移を始めてから)
- その間に出た「長いタスク」(`PerformanceObserver` の `longtask`)の合計

上限は 1画面 500ms / 長いタスク 200ms。実測(21〜62ms・0ms)に対して幅を持たせてあり、
「明らかに遅くなったら気づく」ためのもの。細かい増減を追う道具ではない。
