## 決めごと(ユーザーの指示)

- 名前は **モンヒロくん**
- **ランキングには載せない。** ゲームはふつうに送るつもりで動くが、ボットが通信を受け止めて本物へは届けない
  (`lib/fake-supabase.js`)。**この仕組みを外して動かさない**(CLAUDE.md ⑦)
- **明らかな不具合・バグは、直して公開(マージ)まで進めてから報告する**(2026-10-07 ユーザー指示「改良改善は報告提案、明らかなバグ不具合は直して報告」)。
  CLAUDE.md ③ のとおり最後まで進める。「明らか」とは、正しい動きがはっきりしていて(エラー・真っ白・数が合わない・二重に付く・
  ボタンが効かない・文字が切れる など)、直す範囲が小さく、直し方に迷いがないもの
- 次のものは**直さずに報告と提案へ回す**: 改良・改善(見た目・遊びやすさ・説明の足し引き)/ 仕様の判断が要るもの / 大きい直し /

## 手順

0. **前の日までの記録を読む**: 班の記録(上の表の `docs/playbot/history/<班id>.md`)と、全体の
   [`docs/playbot/HISTORY.md`](../../docs/playbot/HISTORY.md)(「ずっと守ること」)。このセッションは同じ会話でも、
   長くなると古いやりとりが要約されるので、**決まったこと・却下された提案・返事待ちの提案は記録を正とする**(同じ提案を繰り返さない)
1. 準備
   ```
   git fetch origin main && git checkout -B claude/playbot-<班id>-$(TZ=Asia/Tokyo date +%Y%m%d) origin/main
   (cd tools && npm install --no-audit --no-fund)
   ```
   ブランチは班と日ごとに分ける(ほかの班や前の日のPRとぶつからないように)。
2. 遊ぶ(受け持ちの班だけ。担当ごとに分かれて同時に動く)
   ```
   node tools/playbot/playbot.js --team <班id> 2>&1 | tail -40
   ```
   結果は `tools/out/playbot/<日時>/report.md`。担当の一覧は `--list`、担当の仕事は `README.md`。
3. 報告と画像を読む
   - まず先頭の「前回との比較」を見る。**新しく出たもの**と、前回は通ったのに今回つまずいた担当から調べる
     (前回は `tools/playbot/baseline.json`。前からあるものは、すでに報告済みか既知のことが多い)
   - 次に「担当ごとの結果」を担当の順に見る。❌ の担当は、どの段でつまずいたかを先に確かめる
   - `report.md` の「不具合候補」を1件ずつ、画像と「直前に押したもの」から確かめる。
     **ボットの勘違い**(押し方が悪い・待ち方が足りない)なら、ボットのほう(`tools/playbot/`)を直す
   - 「見た画面」の画像をひととおり見て、**人が遊んで引っかかりそうなところ**を拾う
     (文字が切れている・ボタンが押しにくい・何をすればいいか分からない・説明が足りない・待たされる)
   - 「改善のヒント」(小さいボタン・長い会話・反応しないボタンなど)は、本当に困るものだけ提案に回す
   - 意図どおりの挙動だと分かったものは、`lib/session.js` の `KNOWN` へ理由と根拠の場所を書いて足す
4. 不具合を直す(あれば)
   - ふつうの改修と同じく CLAUDE.md のとおりに直す(⑥の検査、⑤の更新履歴。プレイヤーに見えない修正なら書かない)
   - ボットで再現できるなら、直したあとに同じ種(`--seed`)と担当(`--only`)で回して消えたことを確かめる
   - PRを作る日は、直したあとに班で回し直して `--team <班id> --save-baseline` で基準を書き、そのPRに含める
     (基準は担当ごとのファイル `tools/playbot/baseline/<担当id>.json`。班は自分の担当のファイルしか触らないので、ほかの班とぶつからない)
   - コミット → プッシュ → PR → **マージまで進める**(CLAUDE.md ③。PR を作る直前に `git fetch origin main` して取り込む)。
     PRの本文に、ボットの報告のどれを直したかを書く
   - 「明らか」でないもの(上の「決めごと」)は、直さずに報告と提案へ回す
5. **報告する**(このセッションの返答として出す。日本語。ユーザーが朝に読む)
   - 前回との比較(新しく出たもの・出なくなったもの・数字の動き)
   - 担当ごとに見出しを1つ立て、中の部分を1行ずつ(担当は12人。2026-10-07 に22人から組み替えた。見る中身は変えていない):
     バトル係は手で・AUTO・タクティクスの到達WAVE(タクティクスは「危ないときに守った回数」も)/ イベント係はレイドの残り回数とダメージの記録 /
     音ゲー係はスコア・ランキングで見たこと・横画面で閉じられなかった画面と横向きの MISS / マルチ係は呼んだマスモンと演奏の結果・無料・券・朝5:00・経験値 /
     レイド音ゲー係は挑戦回数と「結果のダメージ = 送った記録」/ 新人係は手数 / 見回り係は案内と探検で見たこと / ストーリー係は流れた時刻と読めた回想 /
     見た目係は大きく変わった画面(並べた画像を見て、わざとか崩れかを書く)と小さい画面の起動の秒数・見えなかったもの・MISS /
     時間と保存係は久しぶりと時計で見たこと / 数字係と意地悪係は「数が合ったか・二重にならなかったか」と通信不良の控えと送り直し
   - 見つけた不具合と、**直して公開したもの**(PR のリンクと、本番で見る場所)/ 直さずに回したもの(理由)
   - ボットそのものを直したところ
6. **提案する(毎回必ず)**: 遊んで気づいた「もっとよくなるところ」を**1〜5個**出す。不具合が無い日も出す
   - 1つずつ「どの画面の・何を・どう変えると・なぜよいか(遊ぶ人にとって)・手間の大きさ(小/中/大)」を書く
   - 記録で却下されたものは出さない。前に出して返事待ちのものは「返事待ち」として短く並べ直す
   - 担当を増やす・遊び方を変えるなどボットの大きな作り直しは「作り手へ回したいこと」として分けて書く
7. **決めてほしいことを選択式で聞く**(`AskUserQuestion`。CLAUDE.md「返事待ちは質問形式にする」)
   - 直して公開した不具合は聞かない(報告だけ。戻してほしいときはユーザーが言う)
   - 提案は複数選べる形で「どれを実装するか」
   - そのあと PushNotification で1行だけ知らせる(「◯◯班: 不具合◯件・提案◯件。決めてほしいことがあります」)
8. **記録を残す**: 班の記録 `docs/playbot/history/<班id>.md` のいちばん上へ、その日のぶんを5〜10行で足す
   (結果のひとこと・不具合と PR の番号・出した提案・作り手へ回したいこと)。このファイルだけを変えたブランチ
   (`claude/playbot-history-<班id>-<日付>`)で PR を作り、**マージまで進める**(ゲームには何も起きない記録なので、聞かずに進めてよい)。
   PR を作る直前に `git fetch origin main` して取り込む
9. **ユーザーの答えが来たら**(朝や昼、このセッションで):
   - 「戻して」と言われた修正: 取り消しの PR を作ってマージする
   - 選ばれた提案: ふつうの改修として実装する(CLAUDE.md ⑤⑥を通し、③のとおり公開まで進める)
   - 選ばれなかった提案: 記録に「却下」と書く(次から出さない)。「あとで」と言われたものは「保留」と書く
   - 終わったら、何をしたかと本番で見る場所を報告し、記録(手順8と同じやり方)に決まったことを足す

## 音ゲー班だけの手順(実機の記録で「悪くなった」を見つけて直す)

2026-10-07 にユーザーが決めた(「昨日から色々直してかなりタップ抜けがひどくなった」のあと、「今後音ゲー班がこういうの見つけて直してくれる仕組みを」)。
モンヒロくんの演奏はパソコンの上なので、iPhone 実機でしか起きないこと(タッチの合図の抜け・届く遅れ)は再現できない。
そこはプレイヤーの端末から届いている**タッチの診断**(`rhythm_touch_diagnostics`)で見る。手順 2 の前に次を行う。

A. **記録を取り込む**(毎週月曜の「タッチの診断の週次判定」の仕事も、ここへまとめた)
   ```
   node tools/mode/rhythm-touch-diag.js --fetch --report --days 14 2>&1 | tail -40
   node tools/mode/rhythm-device-regression.js 2>&1 | tail -60
   ```
   - 1本目は、iPhone と Android の比べ・判定(● の行)・「直し方を入れる前と後」(◎ / ▲)を出す。読み方と次の手は
     [`docs/spec/RHYTHM_TOUCH_DIAG.md`](../../docs/spec/RHYTHM_TOUCH_DIAG.md)「判定と、次にやること」
   - 2本目は、**同じ端末・同じ曲・同じ難易度どうし**で直近4日をその前の10日と比べ、MISS が増えた・押したずれの中央値が動いた曲を ⚠ で出す。
     難しい曲を多く遊んだだけの日を「悪くなった」と取り違えないため、前に遊んでいない曲は比べない
   - 取り込んだ `tools/mode/authoring/touchdiag/rows.jsonl` は、手順 8 の記録の PR に含める(数だけで、名前・ブリーダーIDは入っていない)
   - 1本目から報告に必ず入れるもの(月曜の定期実行から引き継いだ決めごと): iPhone と Android の数字(50ms以上遅れた・あとで見えた指・
     タッチだけ・取り消し)を自分で見比べた差(判定の基準に届かない差も書く)/ 取り戻し(pointerOnly・recovered)が働いているか /
     入力の無いMISSが Android 並みに下がったか /「押したのに反応しないことがあった」の報告の件数と、報告のあった曲と無い曲の比べ /
     「直し方を入れる前と後」の行(◎=半分以下に減った / ▲=1.5倍以上に増えた。▲なら悪さをしていないか調べる)/
     まだ入れていない直し方(wideEdge など)が出たら、名前・何をするか・根拠の数字を書いて「入れてよいか」を選択式で聞く
   - サーバーへつながらないときは、何も書き換えずに、理由とユーザーがすること(環境のネットワーク設定の許可先への追加)を短く報告する
B. **⚠ が出たら、どの変更からかを絞り込む**
   - 2本目の最後に、その間に入った演奏まわりの変更(`git log`)が並ぶ。疑う順に読む
   - モンヒロくんで再現できるもの(判定・受付の広さ・ホールドの追い方など)は、変更の前の版を別の作業場所(`git worktree add`)に出し、
     **人の指のくせ**の演奏で前と今を遊び比べて、どの変更からかを確かめる
C. **直し方の決まり**
   - 原因がはっきりしていて直す範囲が小さいものは、直して公開まで進めてから報告する(上の「決めごと」と同じ)
   - **実機でしか確かめられないもの**(時刻の補正・タッチの合図の扱いなど)は、**まず悪くなる前の動きへ戻して公開し**、
     そのあと次の回の記録で、MISS とずれが戻ったかを確かめてから、原因を探して直す(2026-10-07 にこの順でやった。PR #2323)
   - `data/rhythm-mode.js` の `RHYTHM_TOUCH_FIXES` を **true にするのは、ユーザーが「入れて」と言ってから**。悪くなる前の値へ戻す(false にする)のは、上の決まりのとおり聞かずにしてよい
   - 報告には、⚠ の曲・前と今の数・疑った変更・したこと(直した / 戻した / 様子見)を書く

## 定期実行のしくみと引き継ぎ

- 定期実行は班ごとに1つ(「モンヒロくん<班の名前>のプレイ(日・水)」)。日曜・水曜の 2:51〜2:54 に**その班のセッション**を起こす(2026-10-07 ユーザー指示「毎日じゃなくて定期メンテと同じタイミングに」)
- 班のセッションにはリポジトリが付いているので、プッシュも PR も通る(定期実行そのものにはリポジトリを付けられなかったため、この形にした)
- 前の日のことは班の記録(`docs/playbot/history/<班id>.md`)が覚えている。セッションが長くなって要約されても、作り直しても続きから進める

### 班のセッションが長くなりすぎた・消えた・作り直したいとき

窓口(または、このリポジトリを付けた新しい会話)で「**モンヒロくん<班の名前>のセッションを作り直して**」と言う。受けた Claude は次を行う。

1. `create_session`(`source_url=https://github.com/aknkakykhk-maker/monhero`、`permission_mode=auto`、タイトル「モンヒロくん<班の名前>」、`model=claude-sonnet-5-5`、prompt なし)で立て直す(エフォート高はユーザーがセッションの画面で選ぶ)
2. `list_triggers` でその班の定期実行を探して `delete_trigger` で消し、`create_trigger`(`persistent_session_id` に新しいセッション、同じ時刻。例 `CRON_TZ=Asia/Tokyo 51 2 * * 0,3`)で
   作り直す。文面は下の「定期実行の文面」の <班> を入れ替えて使う
3. この手順書の上の表の「セッション(いま)」を書き換える(PR を作ってマージ)
